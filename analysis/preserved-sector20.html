촬영 준비와 보존 레코드 · 섹터 20·21

보존 섹터 20·21의 세 레코드: 적재, 정책 플래그 입력, 저장 준비

섹터 20과 21에는 같은 구조의 레코드가 주 사본과 백업 사본으로 한 벌씩 들어 있습니다. 부팅 때 어느 쪽이 RAM에 올라오는지, 올라온 내용이 촬영 정책의 플래그 하나와 저장 준비에 어떻게 쓰이는지 확인했습니다.

이 문서에서

  1. 배경: 주 사본과 백업 사본이 있는 보존 섹터
  2. 세 공급자가 128KiB를 나눠 맡고, 적재할 때 백업 사본의 마커를 봅니다
  3. RAM에 올라온 두 마커와 설정 바이트가 초기 플래그를 정합니다
  4. 저장 준비는 섹터를 통째로 복사한 뒤 세 구역을 덮습니다
  5. ID 0x63 레코드는 블록 32개로 나눠 읽고 씁니다
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 섹터 20·21은 공급자 세 개(ID 0x63·0x64·0x65)가 64·56·8KiB로 나눠 맡습니다. 섹터 20이 주 사본, 섹터 21이 백업 사본입니다.
  • 적재 함수는 공급자마다 백업 사본의 마커만 봅니다. 맞으면 백업을, 아니면 주 사본을 RAM에 복사합니다. 주 사본의 마커는 조건이 아닙니다. 여섯 가지 마커 조합에서 확인했습니다.
  • 픽셀 정책 함수가 맨 앞에서 정하는 플래그 하나는 RAM에 올라온 앞의 두 레코드 마커가 모두 맞고 설정 바이트가 0이 아닐 때만 1이 됩니다. 열두 가지 대조에서 확인했습니다.
  • 저장 준비는 대상 섹터를 통째로 준비 버퍼에 복사한 뒤 세 RAM 사본을 덮습니다. 패킷으로 고친 내용도 두 섹터의 준비 버퍼에 그대로 들어갔습니다. 여덟 번의 실행은 모두 섹터 쓰기 함수 직전에서 멈췄습니다.
  • 실제 플래시 기록과 레코드 내용의 물리적 의미는 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 세 공급자의 생성·등록과 RAM·플래시 주소·크기 함수
  • 적재 6건에서 고른 사본과 RAM 128KiB 전체
  • 초기 플래그 저장 12건, 저장 준비 버퍼 8건의 전체 바이트
  • ID 0x63 블록 32개의 읽기·쓰기, 패킷 3개

모델 시험 조건으로 정한 것

  • 두 섹터의 내용, 관리자·소유자 연결, 촬영 객체는 합성 값
  • 설정 바이트는 시험값 0 또는 7
  • 정책 구간과 저장 구간은 레지스터를 준비해 중간에서 진입

미확인 확인하지 않은 것

  • 섹터 쓰기 함수 본문, 저장 함수의 전처리와 반환, 물리 플래시 기록
  • 패킷의 상위 전달과 검증, 블록 번호 32의 실제 도달 가능성
  • 레코드에 든 값의 물리적 의미

배경: 주 사본과 백업 사본이 있는 보존 섹터

펌웨어 업데이트가 건너뛰는 보존 섹터 가운데 20과 21은 한 쌍입니다. 같은 구조의 레코드 세 개가 양쪽에 똑같은 배치로 들어 있습니다. 펌웨어는 이 레코드를 공급자 세 개로 나눠 다루고, 부팅 때 RAM에 사본을 만들어 놓고 씁니다. 공급자와 보존 관리자의 개념은 섹터 14 문서의 배경에 설명했습니다.

이 레코드가 관심을 끄는 이유는 픽셀 정책 함수가 촬영을 준비할 때 이 RAM 사본의 마커를 읽기 때문입니다. 이 문서는 “플래시 → RAM → 정책의 첫 플래그”와 “RAM → 저장 준비 버퍼”의 두 방향을 다룹니다.

읽는 법

섹터 번호는 플래시를 128KiB(0x20000바이트)씩 나눠 0부터 센 번호입니다. 함수와 명령의 주소는 복호화한 펌웨어 파일 안의 오프셋으로, 플래시·RAM 주소는 실행 주소(VA)로 적었습니다. ID는 16진수입니다. “유효”는 원본 코드가 첫 워드를 마커 0xA55A5AA5와 비교한 결과만 뜻합니다. 내용이 정확하다거나 실제 보정에 쓰인다는 뜻이 아닙니다.

세 공급자가 128KiB를 나눠 맡고, 적재할 때 백업 사본의 마커를 봅니다

공급자마다 백업 사본(섹터 21)의 첫 워드가 마커와 같으면 백업을, 아니면 주 사본(섹터 20)을 RAM에 복사합니다. 선택은 공급자별로 따로 이루어집니다.

RAM에 올라온 두 마커와 설정 바이트가 초기 플래그를 정합니다

픽셀 정책 함수는 앞부분에서 ID 0x63과 0x64의 RAM 마커를 읽습니다. 둘 다 맞고 설정 바이트가 0이 아닐 때만 촬영 컨텍스트 +0x4A에 1을 씁니다.

여섯 적재 조건마다 설정 객체의 +0xC 바이트를 0과 7로 바꿔 정책 함수의 해당 구간을 실행했습니다. RAM 마커는 다시 써 넣지 않고 앞의 적재가 만든 값을 그대로 두었습니다. 원본 코드가 실제로 읽은 주소와 값도 기록해, 앞에서 적재한 ID 0x63·0x64의 RAM 마커와 같은지 대조했습니다.

저장 준비는 섹터를 통째로 복사한 뒤 세 구역을 덮습니다

섹터 20용과 21용 저장 준비 구간은 같은 순서로 움직입니다. 대상 섹터 128KiB를 준비 버퍼에 복사하고, 등록된 공급자의 RAM 사본을 제자리에 덮은 뒤 섹터 쓰기를 요청합니다.

  1. 섹터 복사대상 섹터 128KiB를 준비 버퍼로
  2. 공급자 조회ID 0x63 → 0x64 → 0x65 순서
  3. RAM 사본 덮기섹터 안 위치 0 · 0x10000 · 0x1E000
  4. 요청 검사범위·섹터 검사, 길이는 16비트 값 0x10000개
  5. 섹터 쓰기 함수진입 직전에서 정지. 본문은 실행 안 함

함수 앞머리의 동기화와 CPU 전처리 구간은 건너뛰고, 관리자 레지스터를 준비해 그다음 명령에서 시작했습니다.

공급자의 플래시 주소 함수는 두 저장 경로 모두에서 백업 사본의 주소를 돌려줍니다. 그래도 덮어쓰기 함수는 그 주소가 섹터 안에서 몇 번째 바이트인지를 계산해 씁니다. 그래서 주 사본(섹터 20)을 저장할 때도 세 구역은 올바른 상대 위치에 들어갑니다.

저장 준비 시험 8건

마지막 적재가 만든 RAM 사본은 그대로 두고, 두 섹터의 내용만 다른 값으로 바꿨습니다. 이렇게 하면 준비 버퍼의 각 바이트가 “섹터에서 복사한 것”인지 “RAM에서 덮은 것”인지 구분됩니다. 네 가지 구성을 두 섹터에 각각 적용했습니다.

여덟 건 모두 준비 버퍼 128KiB 전체가 예상 바이트와 일치했습니다. 준비 버퍼 앞뒤의 대조값, 두 섹터의 원래 내용, RAM 사본은 바뀌지 않았습니다.

패킷으로 고친 내용이 두 섹터의 준비 버퍼에 들어갑니다

마지막 구성에서는 저장 준비 전에 원본 패킷 쓰기 함수를 한 번 실행했습니다. 이 함수는 같은 RAM 사본의 +0x4에 16비트 헤더를, +0x10부터 512워드 본문을 씁니다. 헤더 입력 0x12345678은 하위 16비트 0x5678만 저장됐습니다. 그 뒤 두 저장 준비 구간을 실행하니 고친 바이트가 섹터 20용·21용 준비 버퍼에 똑같이 들어 있었습니다. RAM을 다시 써 넣지 않았고, 첫 마커와 이웃 ID의 내용도 바뀌지 않았습니다.

주의

패킷 쓰기가 레코드를 “유효하게 만든다”고 해석하지 않습니다. 패킷이 어디서 오고 어떤 검사를 거치는지는 이 시험에 없습니다. 상위 경로는 보존 레코드의 상위 명령 경로에서 다룹니다.

ID 0x63 레코드는 블록 32개로 나눠 읽고 씁니다

64KiB 레코드는 앞 16바이트 헤더를 뺀 나머지를 512워드 블록으로 나눕니다. 마지막 블록(31번)만 508워드입니다. 블록 번호 32를 직접 넣으면 계산된 주소가 레코드 밖으로 나갑니다.

블록 읽기·쓰기 대조 확인 (합성 레코드를 따로 만들어 시험)
블록 번호본문 시작 / 크기읽기 함수의 반환값대조한 범위
0레코드 +0x10 / 512워드직접 읽기 512, 패킷 읽기 513패킷 읽기는 32비트로 넓힌 헤더 한 워드를 앞에 붙이고 본문을 내보냄
1…30+0x10 + 번호 × 0x800 / 512워드직접 읽기 512직접 읽기·쓰기는 모두, 패킷은 1번 블록을 확인
31+0xF810 / 508워드직접·패킷 모두 508끝 0x10000을 넘지 않음. 출력 버퍼의 나머지는 그대로
32 (앞부분만)첫 저장 예정 주소 0x80010010함수 반환까지 실행하지 않음첫 저장 명령 0x72E08C 직전에 정지

헤더 16바이트를 뺀 0x3FFC워드가 블록 대상입니다. 512워드 블록 31개 뒤에 508워드가 남으므로 마지막 블록이 짧습니다. 직접 쓰기 함수는 레코드 포인터를, 읽기 함수는 워드 수를 돌려줍니다. 패킷 형태의 쓰기·읽기 함수는 블록 번호 0·1·31에서 따로 확인했습니다. 0번 블록의 패킷 읽기는 헤더를 함께 내보내므로 반환값이 한 워드 큽니다.

블록 번호 32에 대해

블록 번호 32를 직접 넣은 시험에서는 반복 한계가 0xFFFFFFFC, 첫 저장 예정 주소가 0x80010010으로 계산됐습니다. 이 주소는 ID 0x63 구역을 지나 ID 0x64의 RAM 구역 안입니다. 실행은 첫 저장 명령 전에 멈췄고 레코드와 이웃 RAM은 그대로였습니다. 이 결과는 함수 안의 주소 계산만 보여 줍니다. 상위 패킷 입력이 이 값을 허용하는지, 실제 카메라에서 이 상태에 도달하는지는 확인하지 않았습니다.

블록 32개의 본문 해시와 패킷 3개의 응답 해시는 preserved-sector20.json의 id63_chunks에 있습니다. 이 크기 상수는 ID 0x63의 함수에서만 확인했습니다. ID 0x64가 같은 상수를 쓴다고 보지 않습니다.

한계와 남은 과제

원본 명령을 다른 코드로 바꿔 실행한 부분은 없습니다. 다만 시작 상태와 호출 경계를 준비해 제한된 구간만 실행한 결과입니다.

  • 전체 시작 코드 — 생성자와 등록 구간만 따로 실행했습니다. 그 사이의 초기화와 동기화는 포함하지 않았습니다.
  • 설정 바이트의 생산자 — 이 문서에서는 시험값입니다. 원본 생산자는 정책 플래그의 생산자에 있습니다.
  • 패킷의 전달과 검증 — 패킷 함수에 직접 인수를 주었습니다. 상위 명령 처리기는 보존 레코드의 상위 명령 경로에서 다룹니다.
  • 저장의 앞뒤 — 저장 함수의 전처리와 반환, 섹터 쓰기 함수 본문, 물리 플래시 기록은 실행하지 않았습니다.
  • 값의 의미 — 레코드 내용에 보정값·노출·온도 같은 물리적 의미를 붙일 근거가 아직 없습니다.
