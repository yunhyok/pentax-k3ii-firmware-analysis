픽셀 정책 입력의 생산

세 공급자가 적재한 같은 RAM 사본을 픽셀 정책의 초기 조건과 저장 준비에 연결했다. ID 0x63의 패킷 수정값도 두 섹터의 기록 요청 버퍼까지 추적했다. 실제 플래시 기록과 데이터의 물리적 의미는 확인하지 않았다.

픽셀 정책영역과 적재정책 초기값저장 준비블록·패킷재현 범위

함수·명령 주소는 해제 파일 오프셋, Flash·RAM 주소는 가상 주소다. ID는 16진수다. 여기서 “유효”는 원본 코드의 마커 비교 결과만 뜻하며 데이터 내용의 정확성이나 실물 보정을 보증하지 않는다.

1. 세 공급자가 128 KiB를 나누어 맡는다

원본 생성자와 가상 함수 표로 확인한 영역
ID / 크기주 사본 / 백업 사본RAM 시작원본 생성자
0x63 / 64 KiB0x02280000 / 0x022A00000x800000000x72E168
0x64 / 56 KiB0x02290000 / 0x022B00000x800100000x72DF50
0x65 / 8 KiB0x0229E000 / 0x022BE0000x8001E0000x599708

ID 0x64의 복사 길이는 0xE000바이트이며 크기 getter는 0x7000 halfword를 반환한다. 다음 ID 0x65의 0x2000바이트와 맞닿아 하나의 0x20000바이트 섹터를 채운다. 앞선 조사 메모의 중첩 추정은 이 크기를 잘못 읽은 결과였다. 원본 생성자 세 구간과 등록 구간 0x76B8E0…0x76B910을 실행해 실제 전역 객체를 관리자에 연결했고 세 공급자의 RAM·Flash·크기 getter도 대조했다. 공급자 주소·크기·등록 근거

원본 관리자 0x6E7EB0은 공급자마다 백업 첫 워드가 0xA55A5AA5인지 검사한다. 맞으면 백업, 아니면 주 사본을 복사한다. 주 사본의 마커까지 유효해야 복사하는 조건은 아니다. 서로 다른 비반복 내용을 두 사본에 넣고 여섯 조건에서 선택된 주소, 전체 RAM 128 KiB와 앞뒤 경계를 대조했다. 양쪽 마커가 모두 유효한 조건에서도 세 공급자 모두 백업을 선택했다. 적재 6건과 원본 복사 인수

2. 적재된 두 마커가 +0x4A의 초기값으로 이어진다

각 적재 조건에서 설정 객체 +0xC를 0 또는 7로 두고 원본 0x65EA90…0x65EAA4를 실행했다. 0x72E004와 0x72DDEC가 읽은 값은 앞서 적재한 ID 0x63·0x64의 RAM 마커와 같았다. 두 마커가 모두 맞고 설정 바이트가 비제로일 때만 이 지점의 +0x4A가 1이었다. 열두 대조는 초기 저장만 확인하며 뒤쪽 표 조회·디버그·작업 종류에 의한 최종 변경은 별도 분석이다. 실제 마커 읽기와 초기 플래그 저장

3. 저장할 섹터를 먼저 복사하고 등록 영역을 덮어 넣는다

두 저장 준비 구간의 명시적 경계
대상 섹터전체 함수 / 실행 시작실행한 요청 검사정지점
20 · 0x022800000x6E8C08 / 0x6E8C240x599D6C의 원본 범위·섹터 검사0x599914 진입 직전
요청 길이 0x10000 halfword
21 · 0x022A00000x6E8D7C / 0x6E8D98

원본 0x599D18은 대상 섹터 128 KiB를 0x40459204의 준비 버퍼로 복사한다. 이어 ID 0x63…0x65를 순서대로 조회하고 등록된 공급자의 RAM을 0x599E88로 덮어 넣는다. 공급자의 Flash getter는 두 저장 경로 모두 백업 주소를 반환하지만 덮어쓰기 함수는 그 주소가 속한 섹터 내부 오프셋을 계산한다. 따라서 주 사본 저장에서도 상대 위치 0, 0x10000, 0x1E000에 맞게 들어간다. 기본 복사·조회 순서·정확한 halfword 쓰기 범위

마지막 원본 적재가 만든 RAM 사본을 유지한 채 두 Flash 시험값만 다른 내용으로 바꾸어 기본 복사와 RAM 덮어쓰기를 구분했다. 공급자 전체, ID 0x64 생략, ID 0x65 생략의 세 구성을 두 섹터에 적용한 여섯 대조에서 전체 준비 버퍼가 예상 바이트와 일치했다. 빠진 공급자의 범위에는 대상 섹터의 기존 바이트가 남았다. 버퍼 경계, 원본 두 섹터와 RAM 사본도 보존됐다. 동기화·CPU 전처리 구간을 건너뛰어 시작했고 하위 쓰기 함수 본문은 실행하지 않았다. 선택적 덮어쓰기 6건

추가 두 대조에서는 원본 패킷 함수 0x72E0EC가 같은 RAM의 +0x4에 0x5678을, +0x10부터 512워드를 쓰게 했다. 헤더 입력 0x12345678은 하위 16비트만 저장됐다. 그 뒤 두 저장 준비 구간을 실행해 변경된 사본이 각 섹터의 준비 버퍼로 들어가는 것을 확인했다. RAM을 다시 주입하지 않았으며 첫 마커와 인접 ID의 내용도 바뀌지 않았다. 이 패킷 쓰기가 레코드를 유효하게 만든다고 해석하지 않는다. 패킷 수정 뒤 추가 저장 준비 2건

4. ID 0x63의 마지막 블록과 패킷 배치를 구분한다

별도 합성 레코드에서 원본 블록 읽기·쓰기 확인
인덱스본문 시작 / 크기읽기 반환대조 범위
0레코드 +0x10 / 512워드직접 512, 패킷 513패킷 출력은 확장된 halfword 한 워드 뒤에 본문

직접 쓰기 0x72E058와 읽기 0x72E09C를 인덱스 0…31에서 대조했다. 앞의 16바이트를 제외한 0x3FFC워드가 대상이므로 마지막 블록은 508워드다. 쓰기 함수는 입력 레코드 포인터를 반환하고 읽기 함수는 워드 수를 반환한다. 패킷 함수 0x72E0EC·0x72E130은 인덱스 0·1·31을 별도로 검사했다. 인덱스 0의 패킷 읽기는 halfword를 32비트로 확장한 헤더와 본문을 내보내므로 반환값이 한 워드 더 크다. 32개 직접 블록과 패킷 3개 대조

인덱스 32를 직접 준 별도 앞부분 대조에서는 반복 한계가 0xFFFFFFFC, 첫 저장 예정 주소가 0x80010010으로 계산됐다. 첫 저장 명령을 실행하기 전에 멈췄으며 레코드와 인접 RAM은 그대로였다. 이 결과는 해당 함수 안의 주소 계산만 보여 준다. 상위 패킷 입력이 이 값을 허용하는지, 실제 장치에서 도달하는지는 확인하지 않았다. 저장 전 정지점과 계산값

5. 실행 범위와 남은 과제

원본 명령을 다른 실행으로 바꾼 부분은 없다. 다만 시작 상태와 호출 경계를 준비한 제한적 재현이다. 전체 시작 코드, 설정 바이트의 상위 생산자, 패킷 전달·검증, 저장 함수의 전처리와 반환, 물리 Flash 기록은 남아 있다. 이 데이터에 보정값·노출·온도 같은 물리 의미를 부여할 근거도 아직 부족하다.
