보존 레코드 검증이
정책 플래그를 만든다

앞서 시험값으로 준비했던 설정 바이트 +0xC의 생산자를 원본 코드에서 확인했다. 두 레코드 그룹의 검사 결과가 +0xC와 +0xD에 따로 저장되며, 소비자가 두 RAM 마커를 다시 검사한 뒤 같은 객체의 +0xC로 촬영 정책의 초기 +0x4A를 정한다.

보존 섹터객체 연결검사와 생산갱신과 소비실행 범위

상위 호출자 후속: 명령 계획 → 작업자 목록 → 결과 setter와 갱신 호출을 원본 실행 구간별로 연결했다. 계산과 대기의 실제 완료는 미검증이다.

함수·명령 주소는 해제 파일 오프셋, RAM 주소는 가상 주소다. ID는 16진수다. “유효”는 합성 레코드에 대한 원본 검사 결과를 뜻한다. 실물 보정의 정확성이나 메뉴 활성화를 뜻하지 않는다.

2. 두 그룹을 검사해 +0xC와 +0xD를 각각 생산한다

원본 0x74EBF0은 설정 +0x10·+0x14에 두 RAM의 +0x10 헤더를 연결하고, +0x18부터 16바이트 간격으로 데이터 주소·용량·사용 길이·선언 개수를 배치한다. 어느 마커든 틀리면 주소와 용량만 구성한 뒤 반환한다. 이 경우 새 객체의 사용 길이·개수와 두 검사 바이트는 생성자가 넣은 0으로 남는다. 두 마커가 맞으면 0x74EA84가 헤더값을 가져와 두 그룹을 각각 검사한다. 원본 필드와 검사 순서

독립 생산자와 소비자
출력그룹 검사 / 공통 검사초기 저장 / 갱신 저장관찰한 소비자
설정 +0xC0x74EA34 → 0x74E8D00x74EBDC / 0x74EE3C0x74F9BC → 초기 CAP+0x4A
설정 +0xD0x74E9E4 → 0x74E8D00x74EBE8 / 0x74EE48별도 0x593740 → 0x74F9F8

시험 레코드는 상위 플래그 비트가 없는 halfword 하나와 0xB000 종결값으로 구성했다. 사용 길이는 4바이트이며 선언 개수 1은 통과하고 같은 본문의 개수 2는 실패했다. 인덱스 0의 개수만 바꾸면 +0xC만, 인덱스 7의 개수만 바꾸면 +0xD만 0이 됐다. 이는 해당 표현과 검사 결과의 대조이며 모든 레코드 형식이나 값의 물리적 의미를 해독한 결과는 아니다. 합성 레코드와 초기화 5건

3. 원본 갱신값이 같은 객체의 정책 소비자에 도달한다

원본 setter 0x74F974에 인덱스와 개수를 주고 0x74ED98을 호출했다. 이 함수는 바뀐 사용 길이·개수를 이미 적재된 RAM 헤더에 기록하고 두 바이트를 다시 계산했다. 한 그룹의 실패, 다른 그룹의 실패, 두 그룹의 복구를 순서대로 재현했으며 전체 64 KiB·56 KiB에서 예상한 개수 워드만 달라졌다. 원본 촬영 앞부분 0x65EA68…0x65EAA4와 별도 호출 구간 0x593740…0x59374C는 모두 같은 서비스 +0x3C를 거쳐 이 설정 객체를 얻었다. 두 소비자 0x74F9BC·0x74F9F8은 각각 0x72E004·0x72DDEC를 호출해 현재 RAM 마커 두 개를 다시 검사하므로, 설정 C/D가 1이어도 어느 마커든 틀리면 0을 낸다. 같은 RAM의 갱신 3건과 소비자 포인터

4. 검증 범위와 남은 연결

리터럴·포인터를 포함한 원본 워드 33개와 분기 37곳을 확인했고 실행 명령을 대체한 곳은 없다. 입력 레코드, 할당 결과, 관리자 연결과 초기화 가드는 준비했다. ID 0x62는 펌웨어의 기본 레코드를 원본 함수로 적재했으며 이번 실행은 버전 halfword가 0인 조정 없음 경로다. 다른 버전 분기, 전체 부팅·잠금·할당, 실제 촬영과 물리 기록은 실행하지 않았다. 원본 해시·명령·실행 검증기

원본 호출 지점 0x635568은 setter, 0x635F80·0x7B5130은 갱신 함수로 이어진다. 이 상위 호출자의 실제 이벤트 도달 조건은 다음 추적 대상이다. 인접 문자열의 “Change HW DPC Address”만으로 메뉴 항목이나 보정 절차를 확정할 수는 없다. 보조 스케일러 활성값이나 SuperResolution 메뉴와 이 바이트가 같다고 연결하지 않는다. 후속 픽셀 정책 · 보조 스케일러 조건 · SuperResolution 연결 근거
