정책 플래그를 만드는 곳: 보존 레코드의 두 그룹 검사

픽셀 정책 함수는 촬영을 준비할 때 설정 객체의 바이트 하나를 읽어 플래그를 정합니다. 그 바이트를 쓰는 코드를 거슬러 올라가 보니 보존 레코드의 내용을 검사한 결과였습니다.

핵심 요약

  • 촬영 서비스가 가진 설정 객체에는 검사 결과 바이트가 둘 있습니다. 보존 레코드 안의 데이터 묶음을 두 그룹으로 나눠 검사한 결과가 각각 저장됩니다.
  • 첫째 바이트는 픽셀 정책 함수 앞부분에서 초기 플래그가 됩니다. 둘째 바이트는 다른 호출자의 getter가 돌려줍니다. 두 소비자는 RAM 마커 둘을 다시 검사해 하나라도 틀리면 0을 냅니다.
  • 구간별 실험(초기화 5건, 갱신 3건)에서 한 그룹의 개수만 어긋나게 하면 그 그룹의 바이트만 0이 됐습니다. 초기 플래그와 getter 반환값도 그대로 따라 바뀌었습니다.
  • 연결 실험에서는 명령·작업자·갱신 구간을 같은 설정 객체로 이어 실행했습니다. 생산 6건과 마커 대조 30건에서 두 그룹의 독립 검사와 두 소비자의 마커 재검사를 모두 실행으로 확인했습니다.
  • 이 바이트를 메뉴 설정값이나 “실제 촬영에서 보정이 켜진다”는 뜻으로 확정하지 않았습니다. 레코드·계산 결과·대기값은 합성 값이고 촬영은 실행하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 서비스 생성자, 설정 객체의 생성·연결, 가상 함수 호출을 통한 초기화
  • 두 그룹 검사와 두 바이트의 저장 명령(초기화 5건)
  • 개수 변경 뒤의 재검사(갱신 3건)
  • 두 소비자가 같은 설정 객체를 받아 내는 값
  • 명령·작업자·갱신을 같은 객체로 이은 생산 6건과 두 소비자의 마커 대조 30건

모델 시험 조건으로 정한 것

  • 보존 레코드는 합성 값(4바이트짜리 데이터 묶음)
  • 할당 결과 포인터, 관리자 연결, 초기화 가드 세 개
  • 개수를 바꾸는 함수의 인수
  • 연결 실험의 작업자 연결, 계산 결과, 잠금 뒤 입력, 대기 반환값, RAM 마커 값

미확인 확인하지 않은 것

  • 실제 레코드 형식 전체와 값의 물리적 의미
  • 개수를 바꾸는 호출이 실제로 일어나는 조건
  • 전체 부팅·잠금·할당, 실제 촬영과 물리 기록
  • 메뉴 항목이나 보정 절차와의 관계

배경: 시험값으로 넣었던 바이트의 출처 찾기

섹터 20·21 문서는 픽셀 정책 함수의 초기 플래그가 세 가지로 정해진다는 것을 보였습니다. RAM에 올라온 레코드 마커 둘, 그리고 설정 객체의 바이트 하나입니다. 그 문서에서는 이 바이트에 시험값을 직접 넣었습니다. 이 문서는 원본 펌웨어에서 그 바이트를 쓰는 코드를 찾아, 무엇을 근거로 0이나 1을 넣는지 확인합니다.

읽는 데 필요한 이름은 다음과 같습니다.

촬영 컨텍스트(CAP)
촬영 작업 하나의 상태를 담는 객체입니다. 픽셀 정책 함수가 여기에 플래그를 씁니다. 이 문서의 대상은 +0x4A 바이트입니다.
설정 객체
촬영 서비스가 가진 객체입니다. 보존 레코드를 가리키는 포인터와 검사 결과 바이트 두 개(+0xC, +0xD)가 들어 있습니다. 설정 저장 문서에 나오는 메뉴 설정 객체와는 생성자와 필드 배치가 다른 별개의 객체입니다.
공급자 · RAM 레코드
보존 섹터 20·21의 레코드를 맡는 객체(ID 0x63, 0x64)와 그 RAM 사본입니다. 섹터 20·21 문서에서 다룹니다.
디스크립터
설정 객체가 레코드 안의 데이터 묶음 하나를 가리키는 16바이트 항목입니다. 데이터 주소, 용량, 사용 길이, 선언 개수를 담습니다. 인덱스 0~25로 구분합니다.
읽는 법

함수와 명령의 주소는 복호화한 펌웨어 파일 안의 오프셋으로, RAM 주소는 실행 주소(VA)로 적었습니다. ID는 16진수입니다. “유효”와 “통과”는 합성 레코드를 원본 코드가 검사한 결과만 뜻합니다. 실물 보정의 정확성이나 메뉴에서 기능이 켜졌다는 뜻이 아닙니다.

촬영 서비스의 설정 객체가 두 공급자를 가리킵니다

플래그를 읽는 쪽(촬영 서비스)과 레코드를 적재하는 쪽(보존 관리자)은 서로 다른 객체입니다. 둘은 설정 객체로 이어집니다. 설정 객체는 초기화 때 관리자에서 두 공급자를 찾아 자기 안에 적어 둡니다.

두 그룹을 따로 검사해 두 바이트를 만듭니다

설정 객체의 초기화 함수는 두 RAM 마커가 모두 맞을 때만 검사를 시작합니다. 그룹 1(인덱스 0~5)의 결과는 +0xC에, 그룹 2(인덱스 6~17, 24, 25)의 결과는 +0xD에 따로 저장합니다.

초기화 함수가 하는 일

  1. 헤더 연결 설정 객체의 +0x10과 +0x14에 두 RAM 레코드의 +0x10 위치(헤더 표)를 적습니다.
  2. 디스크립터 배치 +0x18부터 16바이트 간격으로 디스크립터를 만듭니다. 각 항목은 데이터 주소, 용량, 사용 길이, 선언 개수입니다.
  3. 마커 확인 두 RAM 마커 중 하나라도 틀리면 주소와 용량만 채우고 돌아갑니다. 이때 사용 길이·개수와 두 검사 바이트는 생성자가 넣은 0으로 남습니다.
  4. 그룹 검사 두 마커가 맞으면 헤더 표에서 사용 길이와 개수를 가져와 두 그룹을 각각 검사합니다. 그룹마다 첫 불일치에서 검사를 끝냅니다.

시험 조건

시험 레코드의 데이터 묶음은 상위 플래그 비트가 없는 16비트 값 하나와 종결값 0xB000으로 만들었습니다. 사용 길이는 4바이트입니다. 선언 개수를 1로 두면 검사를 통과했습니다. 같은 본문에 개수를 2로 적으면 실패했습니다. 인덱스 0의 개수만 바꾸면 +0xC만, 인덱스 7의 개수만 바꾸면 +0xD만 0이 됐습니다. 이는 이 표현 한 가지에서 검사 결과를 대조한 것입니다. 모든 레코드 형식이나 값의 물리적 의미를 해독한 결과가 아닙니다.

개수를 바꾸면 바이트가 다시 계산되어 소비자에게 전달됩니다

디스크립터의 개수를 바꾸는 함수와 갱신 함수를 차례로 부르면, 바뀐 값이 RAM 레코드에 기록되고 두 바이트가 다시 계산됩니다. 정책 앞부분과 다른 호출자는 같은 설정 객체에서 새 값을 읽었습니다.

  1. 개수 변경인덱스와 개수를 인수로 준비해 원본 setter 호출
  2. 갱신 함수RAM 헤더에 반영하고 두 그룹을 다시 검사
  3. 정책 앞부분+0xC → 초기 CAP+0x4A (저장 직후 정지)
  4. getter 반환값+0xD → R0 (호출자 중간에서 정지)

단계마다 호출 프레임을 따로 준비했습니다. 각 구간 안에서는 원본 명령을 바꾸지 않았습니다. 갱신 뒤 64KiB와 56KiB RAM 전체를 비교하니 예상한 개수 워드만 달라져 있었습니다.

갱신 3건은 “두 그룹 통과” 상태에서 이어서 실행했습니다. 여덟 건 모두에서 CAP+0x4A는 +0xC를, getter 반환값은 +0xD를 따랐습니다. 이 값은 호출자 0x59374C 직전에서 관찰한 0x74F9F8의 R0입니다. 바깥 함수 전체의 반환값과는 다릅니다.

두 소비자는 서비스의 +0x3C를 거쳐 같은 설정 객체를 얻습니다. 그리고 각자 RAM 마커 둘을 다시 읽습니다. 그래서 검사 바이트가 1이어도 마커 중 하나가 틀리면 0을 냅니다. +0xC 쪽의 이 동작은 섹터 20·21 문서의 열두 대조에서 직접 실행해 확인했습니다. +0xD 쪽은 이 구간별 실험만으로는 확인할 수 없었습니다. 마커가 틀린 사례에서는 +0xD도 이미 0이었기 때문입니다. 연결 실험은 두 바이트를 원본 검사 함수로 만든 뒤 마커만 바꿔 이 조건을 따로 실행했습니다.

해석의 한계

정책 앞부분은 CAP+0x4A에 처음 값을 저장한 직후 멈췄습니다. 그 뒤 정책이 값을 다시 바꾸는 조건은 픽셀 보정 활성값과 준비 분기에 있습니다. 이 바이트가 보조 스케일러의 활성 조건이나 SuperResolution 메뉴와 같은 값이라고 연결하지 않습니다.

명령에서 마커 소비까지 같은 설정 객체로 이어 실행했습니다

명령 계획, 작업자, 갱신, 두 소비자를 같은 VM의 같은 설정 객체로 이었습니다. 생산 사례 6건에 마커 조건 5개를 적용한 30개 대조에서 C/D가 1/1이어도 마커 하나가 틀리면 두 소비 결과는 모두 0이었습니다.

앞 절의 실험은 개수 setter와 갱신 함수에 인수를 직접 넣었습니다. 이 연결 실험은 상위 명령 경로의 원본 구간에서 출발합니다. 여기서 C와 D는 설정 객체의 +0xC·+0xD 바이트입니다. 이 바이트는 원본 검사 함수가 만들었고 재현기는 값을 쓰지 않았습니다. 재현기가 바꾼 것은 소비자를 부르기 전의 RAM 마커 두 개(0x80000000·0x80010000의 32비트 워드)뿐입니다. 정상값은 0xA55A5AA5, 오류값은 0입니다.

생산 사례 6건

selector 0은 첫 요청으로 인덱스 0/1을, selector 1은 6/7을 골랐습니다. 이 selector는 명령 경로의 입력입니다. 영상 처리 경로의 selector=6이나 촬영 메뉴 번호와는 연결하지 않았습니다. 결과 플래그가 0이면 작업자는 개수 setter를 건너뜁니다. 1이면 준비한 개수 둘을 저장합니다. 길이 setter는 두 경우 모두 4/4를 받았습니다.

같은 VM에서 차례로 실행한 생산 6건 확인 모델
사례selector / 인덱스준비한 결과 플래그준비한 개수원본이 만든 C/D준비한 대기값

갱신 구간은 대기값이 0일 때도 0x3FF일 때도 저장해 둔 같은 설정 객체로 갱신 함수를 불렀습니다. 128KiB RAM 전체를 대조하니 예상한 헤더 개수 워드만 달라져 있었습니다. C 오류에서는 인덱스 0에서, D 오류에서는 인덱스 6에서 그 그룹의 검사가 끝났습니다. 다른 그룹은 끝까지 검사했습니다. 명령 응답에는 0x19와 준비한 대기값이 기록됐습니다.

마커 대조 30건

생산 사례마다 적용한 마커 조건 5개와 두 소비자의 결과(CAP+0x4A / getter 반환값) 확인
마커 조건원본 C/D = 1/1원본 C/D = 0/1원본 C/D = 1/0C/D 바이트 읽기
둘 다 정상1/10/11/0읽음
첫째 마커 오류0/00/00/0건너뜀
둘째 마커 오류0/00/00/0읽음
두 마커 오류0/00/00/0건너뜀
둘 다 정상으로 복원1/10/11/0읽음

두 소비자는 오류 조건에서도 마커 둘을 모두 다시 읽었습니다. C/D 바이트 읽기를 건너뛴 것은 첫째 마커가 틀렸을 때뿐입니다. 마커를 복원하면 원래 C/D에 따른 결과로 돌아왔습니다. 소비하는 동안 설정 객체 548바이트와 RAM 128KiB는 바뀌지 않았습니다.

정책 앞부분은 +0x47=1, +0x48=1, +0x49=0, +0x4A=C 소비 결과의 네 번을 저장했습니다. 지켜본 128바이트에서 이 네 곳 말고는 바뀐 곳이 없었습니다. 둘째 관찰값은 0x59374C 직전에서 읽은 getter 0x74F9F8의 R0입니다. 이 실험에서도 촬영 컨텍스트 전체와 바깥 호출자의 반환은 실행하지 않았습니다.

한계와 남은 과제

실행 중 다른 코드로 바꾼 명령은 없습니다. 입력 레코드, 할당 결과, 관리자 연결, 초기화 가드는 준비한 값입니다.

  • 상위 호출자 개수 setter와 갱신 함수를 부르는 코드가 실제로 언제 실행되는지는 보존 레코드의 상위 명령 경로에서 이어서 다룹니다. 그 문서에서도 계산과 대기의 실제 완료는 확인하지 못했습니다.
  • 메뉴와의 관계 호출 지점 근처에 “Change HW DPC Address”라는 문자열이 있습니다. 이 문자열만으로 메뉴 항목이나 보정 절차를 확정할 수 없습니다.
  • 다른 버전 분기 ID 0x62 레코드는 버전 값이 0인 경로만 실행했습니다.
  • 레코드의 실제 형식 4바이트짜리 합성 표현 하나만 시험했습니다.
  • 전체 실행 전체 부팅, 잠금, 할당, 실제 촬영, 물리 기록은 실행하지 않았습니다.

재현 방법

검증기는 복호화한 펌웨어(펌웨어 파일 구조와 복호화)를 입력으로 받습니다. 원본 해시와 명령을 대조한 뒤 Unicorn 에뮬레이터의 Cortex-A9 모델에서 정해 둔 구간을 실행합니다.

Python 패키지

python verify_preserved_config.py .private/decoded/decoded.bin --compare analysis/preserved-config.json

연결 실험의 검증기도 같은 복호화 파일을 decoded.bin 자리에 지정합니다. 비교가 통과해야 결과를 출력합니다. --output은 새 파일만 만들고 기존 경로나 입력 파일의 별칭을 덮어쓰지 않습니다. 임시 파일을 완전히 쓴 뒤 같은 파일시스템의 하드 링크로 게시하므로 이 옵션에는 하드 링크를 지원하는 파일시스템이 필요합니다. 기존 파일을 바꾸지 않고 결과만 읽으려면 --output을 생략합니다.

python verify_preserved_markers.py decoded.bin --compare analysis/preserved-marker-checks.json --output marker-checks.json
python -O verify_preserved_markers.py decoded.bin --compare analysis/preserved-marker-checks.json

펌웨어 입력의 전체 길이·SHA-256을 실행 전에 확인하고 실행 뒤 다시 읽어 대조합니다. 이 CLI는 단일 스레드에서 사용하는 검사기입니다. 테스트는 합성 입력으로 파일 보호와 비교 동작을 확인하며 실제 펌웨어 재현은 별도로 실행했습니다.
