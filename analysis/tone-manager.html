48바이트 설정 레코드의 갱신자

직접 호출자 두 곳갱신 순서남은 경계근거와 재현

R1 원본 객체와 R2 통지 인자

6EAF70에 직접 진입하는 호출자 두 곳에서 입력 포인터와 통지 인자를 추적했습니다. 첫 호출 4BDB3C는 RAM 객체 40481A58을, 둘째 호출 4BF6C0은 RAM 객체 40481974를 R1에 전달합니다. 두 객체에서 복사하는 것은 픽셀 데이터가 아니라 48바이트 설정 payload입니다. 두 호출 모두 R2는 0입니다.

두 호출자는 관리자의 레코드를 임시 객체로 복사한 뒤 원본 setter로 일부 필드를 바꾸고 다시 관리자에 넘깁니다. 첫 호출은 selector 0x2B에 1을 공급하여 객체+0x2B의 bit6을 설정합니다. 둘째는 selector 0x1E에 word(R5)를 공급합니다. 이 selector는 일반 1바이트 경로가 아니라 객체+0x24와 +0x25에 상위·하위 바이트를 쓰는 분기입니다. 검사한 경로의 4BF580은 R5를 호출자 객체+0x6C80으로 계산합니다. 호출자 전체의 모든 진입 경로나 중간 함수의 별칭 쓰기를 검증한 것은 아닙니다.

6EAF70의 R200

관리자 포인터를 저장하는 조건부 초기화 경로는 두 곳 모두 70D180과 78591C를 호출합니다. 이 경로가 완료되면 전역 객체 4047B754의 +0x14에서 읽은 포인터를 캐시에 저장합니다. 첫 캐시는 RAM 4040BA28, 둘째는 RAM 4040B9F0입니다. 실제 실행에서 초기화 가드가 어느 분기를 택하는지와 기존 캐시의 내용은 확인하지 않았습니다.

근거: 원본 구간의 주소·해시의 4BDAC4..4BDACC·4BF194..4BF19C는 캐시 생산자, 4BDB10..4BDB3C·4BF694..4BF6C0은 읽기→setter→갱신 연결입니다. PC 상대 리터럴과 기술자 값은 정적 결과 JSON의 literals·descriptors에 있습니다. 두 객체의 생성자 호출은 같은 호출자 안의 4BDAF8·4BF1C8에 있지만, 그 분기의 런타임 실행은 확인하지 않았습니다.

selector1E는 6EB294..6EB2A0에서 별도 분기로 갑니다. 6EB2DC·6EB2E8이 두 바이트를 순서대로 씁니다. 기술자 maskFF만 보고 일반 1바이트 setter로 해석하면 틀립니다. 두 호출자의 임시 객체는 서로 다른 RAM 주소이며, 이 둘의 사용 시각이나 병행 실행 여부는 알 수 없습니다.

표시·복사·확정·후속 분기

갱신 함수는 먼저 새 인덱스를 1 & ~old_state로 계산하고 manager+0x18에 인덱스 | 0x8000을 씁니다. 선택한 객체에 48바이트 payload를 복사하는 함수가 반환한 뒤 같은 위치에 인덱스만 저장합니다. 그다음 manager+0x0C가 0이 아니면 6EF248을 호출하고 +0x0C를 0으로 만듭니다. 저장해 둔 진입 R2가 0일 때 함수가 반환하며, 0이 아닐 때만 마지막 통지 경로로 갑니다. 따라서 R2=0도 별도 +0x0C 경로의 호출을 막지는 않습니다.

719AE8은 수신 객체와 원본 객체를 보관하고, 52C0A8의 반환 뒤 길이 0x30과 양쪽 +4 주소를 7129D0에 전달합니다. 따라서 객체 첫 워드는 복사하지 않습니다. 6EAF9C의 상태 확정은 이 호출이 정상 반환한 뒤의 명령입니다. 복사가 성공하거나 동시 접근이 안전하다는 실기 증거는 아닙니다.

독자 6EAEBC는 상태 bit15가 1이면 1 & ~state를 계산합니다. 갱신자가 표시한 상태를 읽을 경우 새 index의 반대편을 선택하는 식입니다. bit15가 0이면 상태 워드 전체를 사용하므로 모든 임의 상태가 유효한 인덱스라는 뜻은 아닙니다. 아래 표는 이 정수식만 계산한 예시입니다.

두 직접 호출자의 앞선 읽기는 R2=1이며, reader는 보조 함수 6EF268이 반환한 뒤 manager+0x0C에 1을 씁니다. 뒤의 갱신자가 이 바이트를 읽어 6EF248을 호출하는 연결은 정적으로 확인됩니다. 다른 작업의 중간 쓰기나 서비스 실패는 검증하지 않았으므로 이를 실제 잠금 획득·해제 이력으로 이름 붙이지 않았습니다. 끝의 6992CC 경로는 진입 R2가 별도로 제어합니다.

메뉴와 촬영 작업에 대해 남은 경계

이 결과는 원본 코드 안의 데이터 전달과 명령 순서입니다. 스레드 사이의 실행 순서, 메모리 동기화, 실제 촬영에서의 버퍼 재사용을 관측한 기록은 아닙니다. 두 setter는 selector 5·6의 바이트인 객체+0x15·+0x16을 직접 쓰지 않습니다. 앞서 복사한 값이 payload에 포함되지만 그 값의 이전 생산자와 SuperResolution 메뉴 이벤트는 이번 한 단계 추적에서 확인하지 못했습니다.

정렬된 A32 B/BL 비트 패턴 검색은 27개 후보를 만들었습니다. 그중 주소순의 첫 두 BL 지점만 명령 문맥과 리터럴·호출 대상을 확인했습니다. 나머지 25개는 분석하지 않은 후보이며 실제 호출자 수로 세지 않습니다. Thumb·간접 호출을 포함한 전체 호출 그래프를 복원한 결과도 아닙니다.

후속 과제는 selector5·6을 직접 쓰는 생산자를 정해진 범위에서 찾는 일, manager 캐시의 실제 초기화와 동시성 계약을 확인하는 일, 메뉴 이벤트와 촬영 작업의 호출 순서를 잇는 일입니다. 이 문서는 두 호출자·한 단계의 분석으로 범위를 제한합니다. II31의 owner+21C와 앞선 owner+220을 같은 작업으로 결합하지 않았습니다.

공개 검증과 원본 정본의 구분

공개 검증기는 전체 decoded 입력의 크기와 SHA-256, 원본 19개 구간, 직접 분기 18개와 리터럴 12개를 대조합니다. 두 호출자와 갱신 순서에 대한 설명은 원본 명령을 보고 작성한 수동 정적 해석입니다. 주소·인자 값의 기계적 대조가 실제 메뉴 도달이나 작업 사이의 실행 순서를 자동으로 증명하지는 않습니다.

II33 정본의 필드를 모두 보존했습니다. 원본 스키마·구간·리터럴·호출자·정수식 예시·제한 문구·연구 코드 해시까지 전체 타입과 직렬화 해시를 먼저 확인한 뒤 공개용 정보를 붙입니다. 정수와 불리언을 바꾸거나 필드를 지우면 검증에 실패합니다. 정본 안의 reproduction_source_sha256은 원본 연구 코드의 해시이고, 새 검증기의 해시는 밖의 public_checker_sha256에 따로 기록합니다.

정본의 Capstone 5.0.7과 312개 해석 명령은 기존 연구의 출처 정보입니다. 기본 공개 검증은 표준 라이브러리만 사용하며 Capstone을 불러오지 않습니다. 고정한 ARM 구간의 312개 워드와 원본 바이트 해시를 대조합니다. --check-decoder를 선택하면 정확한 입력을 확인한 뒤 Capstone을 불러와 기존 목록의 해시를 메모리 안에서 다시 계산합니다. 원본 명령 목록이나 펌웨어 바이트는 파일로 내보내지 않습니다.

기본 모드의 일반·최적화 실행은 같은 공개 JSON을 만들었습니다. 선택 디코더 검사도 원본 목록 해시에 일치했습니다. 선택 모드 결과는 capstone_rechecked=true라는 공개 메타데이터만 다르며 정본 관측은 같습니다. CI용 검사는 펌웨어 없이 정본의 무결성과 입출력 경계만 확인합니다.

입력과 비교 파일은 일반 파일 여부를 경로와 열린 파일 핸들에서 각각 확인하고 제한된 길이만 읽습니다. 비교 파일 상한은 생성할 JSON 크기의 4배입니다. 기존 출력·하드링크·끊어진 심볼릭 링크를 덮어쓰지 않으며, 마지막 배타적 파일 생성에서도 다른 파일이 먼저 생기면 실패합니다. 비교가 틀리거나 파일 동기화에 실패하면 출력 결과를 게시하지 않습니다.

실행 방법

저장소 루트에서 별도로 준비한 decoded 파일을 지정합니다. 기본 검증과 CI용 검사에는 Capstone이 필요하지 않습니다. 출력은 새 경로여야 하며 부모 디렉터리는 미리 존재해야 합니다.

python -B verify_tone_manager.py /path/to/decoded.bin --output manager-new.json --compare analysis/tone-manager.json
python -B -O verify_tone_manager.py /path/to/decoded.bin --output manager-opt-new.json --compare analysis/tone-manager.json
python -B -m unittest discover -s tests -p test_tone_manager.py
python -B -O -m unittest discover -s tests -p test_tone_manager.py

선택 검사에는 Capstone 5.0.7이 필요합니다. 아래 명령은 펌웨어를 실행하지 않으며 별도 원본 목록을 배포하지 않습니다. 기본 모드와 메타데이터가 다르므로 기본 결과를 --compare에 넘기지 않습니다.

python -B verify_tone_manager.py /path/to/decoded.bin --output manager-decoder-new.json --check-decoder

정확한 입력과 모든 원본 구간이 같아도 실제 캐시 값, 메뉴 이벤트, 동시성 안전, 촬영 순서와 버퍼 재사용 이력을 입증한 것은 아닙니다. 내부 48바이트 설정 레코드와 픽셀 버퍼를 구분해야 합니다. 실물 카메라와 브라우저 렌더링은 확인하지 않았습니다.
