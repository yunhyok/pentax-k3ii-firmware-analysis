톤 설정 관리자의 두 호출자와 48바이트 설정 레코드

톤 입력 바이트는 관리자 객체가 보관하는 작은 설정 레코드에서 작업 객체로 복사됩니다. 그 레코드를 고쳐 쓰는 원본 코드 두 곳과, 관리자가 레코드를 바꾸는 명령 순서를 코드를 읽어 정리했습니다.

이 문서에서

  1. 배경: 관리자와 설정 레코드
  2. 두 호출자는 레코드를 읽고 한 필드를 바꿔 되돌려 줍니다
  3. 갱신 함수는 표시, 복사, 확정 순서로 칸을 바꿉니다
  4. 한계와 남은 과제
  5. 검증 방법
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 관리자의 갱신 함수에 직접 들어가는 호출자 두 곳을 확인했습니다. 둘 다 관리자의 레코드를 임시 객체로 읽고 원본 setter로 한 필드를 바꾼 뒤 다시 관리자에 넘깁니다.
  • 오가는 것은 48바이트 내부 설정 레코드이며 픽셀 데이터가 아닙니다. 두 호출자가 바꾸는 필드는 톤 selector 5·6의 바이트가 아닙니다.
  • 갱신 함수는 새 칸 번호에 표시를 남기고 48바이트를 복사한 다음 상태를 확정합니다. 이어서 보조 플래그와 진입 인자를 따로 검사합니다. 두 호출자는 마지막 통지 경로를 고르지 않는 값을 넘깁니다.
  • 모두 코드를 읽은 정적 분석입니다. 문법으로 찾은 호출 후보 27개 중 2개만 확인했습니다. 동시 실행 안전성·메뉴 이벤트·촬영 순서는 확인하지 않았습니다.

정적 분석 코드를 읽어 판단

  • 두 호출자의 읽기 → setter → 쓰기 연결과 인자
  • setter가 바꾸는 레코드 위치(기술자 두 개)
  • 갱신 함수 안의 저장과 분기 순서

확인 파일 바이트로 대조

  • 원본 19개 구간의 주소·해시
  • 직접 분기 18개, 리터럴 12개의 명령 워드

모델 계산 예시

  • 상태 워드 정수식에 가정한 이전 상태 다섯 개를 넣은 표. 펌웨어를 실행한 값이 아님

미확인 확인하지 않은 것

  • 캐시 초기화가 실제로 어느 분기를 타는지, 캐시의 내용
  • 나머지 호출 후보 25개, Thumb·간접 호출
  • 동시 실행 안전성, 메뉴 이벤트, 촬영 순서, 버퍼 재사용

배경: 관리자와 설정 레코드

톤 입력 R5 문서에서 본 것처럼, 톤 계산의 selector 5·6 바이트는 작업 객체에 내장된 작은 객체에 있습니다. 그 객체의 48바이트를 덮어쓰는 경로 하나가 관리자의 레코드를 복사하는 길입니다. 이 문서는 그 관리자 레코드를 누가 고치는지를 한 단계 거슬러 올라갑니다.

관리자
전역 객체 4047B754의 +0x14가 가리키는 객체입니다. 같은 모양의 레코드 두 칸이 있으며 상태 워드(+0x18)로 칸을 고릅니다.
레코드
첫 워드 4바이트 뒤에 48바이트 payload가 붙은 구조입니다. 복사는 payload만 합니다.
setter와 기술자
setter는 selector 번호로 ROM 기술자(오프셋·마스크·시프트)를 찾아 레코드의 해당 위치를 씁니다.
R1, R2
함수에 넘기는 둘째·셋째 인자 레지스터입니다(Arm AAPCS32). 갱신 함수에서 R1은 새 레코드를 담은 객체, R2는 통지 여부를 정하는 값입니다.
쉽게 말하면

관리자는 레코드 칸 두 개를 번갈아 씁니다. 쓰는 동안에는 상태 워드에 표시를 해 두고 그 사이에 읽는 쪽은 다른 칸을 고르게 됩니다. 이것은 명령 순서를 읽은 해석입니다. 실제 잠금이나 동시 접근 안전성을 확인한 결과는 아닙니다.

주소 표기

명령 주소는 16진수 파일 오프셋이고 실행 주소는 여기에 0x02000000을 더합니다. 4040BA28, 40481A58 같은 RAM 값은 VA입니다.

두 호출자는 레코드를 읽고 한 필드를 바꿔 되돌려 줍니다

두 호출자 모두 읽기(R2 = 1) → setter → 쓰기(R2 = 0) 순서이고 바꾸는 필드가 서로 다릅니다.

첫 호출자는 selector 0x2B에 1을 넣어 객체 +0x2B의 bit6을 켭니다. 둘째 호출자는 selector 0x1E에 word(R5)를 넣습니다. 이 selector는 일반 1바이트 경로를 타지 않고 객체 +0x24와 +0x25에 상위·하위 바이트를 씁니다. 확인한 경로에서는 4BF580이 R5를 호출자 객체 +0x6C80으로 계산합니다. 호출자 전체의 모든 진입 경로나 중간 함수의 별칭 쓰기까지 검증하지는 않았습니다.

레코드의 어느 칸이 바뀌는가

selector 0x1E의 기술자 마스크는 0xFF입니다. 마스크만 보고 일반 1바이트 setter로 해석하면 틀립니다. setter 안에서 이 번호는 별도 분기로 가서 두 바이트를 차례로 씁니다. 두 호출자의 임시 객체는 서로 다른 RAM 주소에 있습니다. 둘의 사용 시각이나 동시 실행 여부는 알 수 없습니다.

갱신 함수는 표시, 복사, 확정 순서로 칸을 바꿉니다

새 칸 번호에 busy 표시를 남기고 48바이트를 복사한 뒤 번호만 다시 씁니다. R2 = 0은 마지막 통지 경로만 막습니다.

  1. 인덱스 계산과 표시 새 인덱스를 1 & ~old_state로 구하고 manager+0x18에 인덱스 | 0x8000을 씁니다(6EAF8C).
  2. payload 복사 넘겨받은 객체의 +4부터 48바이트를 고른 칸의 +4로 복사합니다(6EAF98 → 719AE8 → 7129D0).
  3. 확정 복사 함수가 반환한 뒤 같은 자리에 인덱스만 씁니다(6EAF9C).
  4. 보조 플래그 검사 manager+0x0C가 0이 아니면 6EF248을 부르고 +0x0C를 0으로 만듭니다(6EAFB0).
  5. 진입 R2 검사 진입 때 저장한 R2가 0이면 반환합니다. 0이 아니면 70D180 → 73E08C → 6992CC(꼬리 호출)로 갑니다(6EAFBC). 두 호출자는 0을 넘기므로 이 경로를 고르지 않습니다.

4단계는 R2와 상관없이 실행됩니다. R2 = 0이어도 +0x0C 경로의 호출은 막지 않습니다. 두 호출자가 앞서 부르는 리더는 R2 = 1입니다. 리더는 보조 함수 6EF268이 반환한 뒤 manager+0x0C에 1을 씁니다. 뒤의 갱신 함수가 이 바이트를 읽어 6EF248을 부르는 연결은 정적으로 확인됩니다. 다른 작업의 중간 쓰기나 서비스 실패는 검증하지 않았으므로, 이것을 실제 잠금의 획득과 해제 이력이라고 부르지 않았습니다.

719AE8은 수신 객체와 원본 객체를 보관하고 52C0A8이 반환한 뒤 길이 0x30과 양쪽 +4 주소를 7129D0에 넘깁니다. 그래서 객체 첫 워드는 복사되지 않습니다. 3단계의 확정은 이 호출이 정상 반환한 뒤의 명령입니다. 복사가 성공하거나 동시 접근이 안전하다는 실기 증거는 아닙니다.

리더가 칸을 고르는 식

리더 6EAEBC는 상태 워드의 bit15가 1이면 1 & ~state를 계산합니다. 갱신 함수가 표시해 둔 상태를 읽으면 새 인덱스의 반대편 칸을 고르게 됩니다. bit15가 0이면 상태 워드 전체를 인덱스로 씁니다. 모든 임의 상태가 올바른 인덱스가 된다는 뜻은 아닙니다.

한계와 남은 과제

이 결과는 원본 코드 안의 데이터 전달과 명령 순서입니다. 스레드 사이의 실행 순서, 메모리 동기화, 실제 촬영의 버퍼 재사용을 관측한 기록은 아닙니다.

  • 호출자 범위: 정렬된 A32 B/BL 비트 패턴 검색은 후보 27개를 냈습니다. 주소순 첫 두 BL만 명령 문맥과 리터럴·호출 대상을 확인했습니다. 나머지 25개는 분석하지 않은 후보이며 호출자 수로 세지 않습니다. Thumb·간접 호출을 포함한 호출 그래프도 복원하지 않았습니다.
  • selector 5·6: 두 setter는 객체 +0x15·+0x16을 직접 쓰지 않습니다. 그 값은 복사되는 payload에 들어 있지만 이전 생산자와 SuperResolution 메뉴 이벤트는 이 분석에서 찾지 못했습니다. 두 바이트를 직접 쓰는 코드는 selector 5·6의 직접 생산 경로에서 다룹니다. 그 문서가 정적으로 연결한 4EBBFC의 갱신 호출(R2 = 1)은 이 문서의 두 호출자에 들어 있지 않습니다.
  • 캐시와 동시성: 관리자 캐시의 실제 초기화, 동시 접근 규칙, 메뉴 이벤트와 촬영 작업의 호출 순서는 남은 과제입니다.
  • 다른 경로와의 관계: 이 문서는 두 호출자와 한 단계만 다룹니다. R5 입력 분석의 owner+0x21C 경로와 다른 문서의 owner+0x220 경로를 같은 작업으로 합치지 않았습니다.
주의

입력과 모든 원본 구간이 같다는 결과만으로는 실제 캐시 값, 메뉴 이벤트, 동시성 안전, 촬영 순서와 버퍼 재사용 이력을 알 수 없습니다. 내부 48바이트 설정 레코드와 픽셀 버퍼는 구분해서 읽어야 합니다.

검증 방법

공개 검증기는 펌웨어를 실행하지 않습니다. 원본 구간의 해시와 분기·리터럴 워드를 파일 바이트로 대조합니다.

  • 복호화 입력 전체의 크기와 SHA-256, 원본 19개 구간, 직접 분기 18개, 리터럴 12개를 대조합니다. 두 호출자와 갱신 순서의 설명은 원본 명령을 보고 쓴 수동 정적 해석입니다. 주소·인자를 기계적으로 대조했다고 메뉴 도달이나 실행 순서가 증명되지는 않습니다.
  • 원래 기록(II33)의 필드를 모두 보존했습니다. 스키마·구간·리터럴·호출자·정수식 예시·제한 문구·연구 코드 해시까지 타입과 직렬화 해시를 먼저 확인한 뒤 공개 정보를 붙입니다. 정수와 불리언을 바꾸거나 필드를 지우면 실패합니다.
  • 기록 안의 reproduction_source_sha256은 원래 연구 코드의 해시입니다. 공개 검증기의 해시는 밖의 public_checker_sha256에 따로 적었습니다.
  • 기본 검증은 표준 라이브러리만 씁니다. 고정한 ARM 구간의 312개 워드와 원본 바이트 해시를 대조하며 Capstone을 불러오지 않습니다.
  • --check-decoder를 고르면 입력을 확인한 뒤 Capstone 5.0.7로 기존 명령 목록의 해시를 메모리 안에서 다시 계산합니다. 명령 목록이나 펌웨어 바이트는 파일로 내보내지 않습니다. 이 모드의 결과는 capstone_rechecked=true 메타데이터만 다르고 관측은 같습니다.
  • 기본 모드의 일반·최적화 실행은 같은 공개 JSON을 만들었습니다. CI용 검사는 펌웨어 없이 기록의 무결성과 입출력 경계만 확인합니다.
  • 입력과 비교 파일은 경로와 열린 파일 핸들에서 각각 일반 파일인지 확인하고 제한된 길이만 읽습니다. 비교 파일 상한은 생성할 JSON 크기의 4배입니다. 기존 출력·하드링크·끊어진 심볼릭 링크를 덮어쓰지 않습니다. 마지막 배타적 생성에서 다른 파일이 먼저 생겨도 실패합니다. 비교가 틀리거나 파일 동기화가 실패하면 결과를 쓰지 않습니다.

재현 방법
