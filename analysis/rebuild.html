재구축과 업데이트 · 1단계 포장과 검사

업데이트 파일을 다시 포장하고 원본 검사 코드로 확인하기

펌웨어를 고치려면 고친 내용을 카메라가 받는 파일 형식으로 되돌릴 수 있어야 합니다. 되돌리는 방법이 정확한지, 그리고 카메라의 업데이트 검사가 파일에서 무엇을 보는지 조사했습니다.

이 문서에서

  1. 배경: 업데이트 파일은 어떻게 카메라에 들어가는가
  2. 파일 구조: 주 이미지와 보조 이미지는 포장 방식이 다릅니다
  3. 원본 검사 코드가 확인하는 네 가지
  4. 체크섬 칸이 0xFFFFFFFF이면 합계 검사를 건너뜁니다
  5. 수정 후보 세 개를 넣어 본 결과
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 복호화한 이미지를 고치지 않고 다시 포장하면 배포 파일과 한 바이트도 다르지 않았습니다. 포장 방법을 정확히 알고 있습니다.
  • 펌웨어 안의 업데이트 검사 코드는 파일 길이, 모델값, 고정 표식, 덧셈 체크섬을 확인합니다. 조사한 검사 구간에는 암호 서명 연산이 없었습니다.
  • 메뉴 글자 하나를 바꾸고 체크섬을 다시 맞춘 후보는 원본 검사 코드를 통과했습니다. 일부러 망가뜨린 이미지도 체크섬만 맞추면 통과했습니다. 검사 통과가 정상 동작을 뜻하지는 않습니다.
  • 모든 실행은 PC의 에뮬레이터에서 했습니다. 카메라에 설치하거나 부팅해 보지 않았고 도구는 크기가 같은 바이트 교체만 다룹니다.

확인 파일 대조와 원본 코드 실행

  • 무수정 재포장 결과의 SHA-256이 배포 파일과 같음
  • 원본 복호화 함수를 파일 전체에 실행한 결과가 Python 도구와 같음
  • 원본 체크섬·헤더 검사, 합계 요청의 송신기와 수신기 실행(후보 3종)
  • 표식 자리 5곳과 체크섬 값 12건의 거부·수용

정적 분석 코드를 읽어 판단

  • 업데이트 함수가 길이 검사, 복호화, 헤더 검사를 부르는 순서
  • 합계 요청(명령 7)에 서명 연산이 없다는 판단

모델 시험 조건으로 정한 것

  • 에뮬레이터의 메모리 배치와 이미지 적재 주소
  • 송신기와 수신기를 한 CPU에서 차례로 실행(동시 실행·캐시는 재현하지 않음)
  • 연구자가 만든 수정 후보 3종과 손상 입력

미확인 확인하지 않은 것

  • 카메라가 수정 후보를 실제로 받아들이는지
  • 설치 뒤 부팅·촬영·저장
  • 전체 업데이트 경로나 내부 ROM에 다른 인증이 있는지

배경: 업데이트 파일은 어떻게 카메라에 들어가는가

리코가 배포하는 K-3 II 펌웨어 1.12는 fwdc230b.bin 파일 하나입니다. 공식 안내에 따르면 이 파일을 SD 카드 최상위 폴더에 넣고 MENU 버튼을 누른 채 전원을 켜면 업데이트가 시작됩니다. 같은 안내는 도중에 전원이 꺼지면 카메라가 동작하지 않게 된다고 경고합니다. 그래서 이 연구는 카메라를 쓰지 않고 PC에서만 진행했습니다.

배포 파일은 그대로는 읽을 수 없습니다. 내용이 XOR 난독화로 가려져 있기 때문입니다. 가린 것을 푸는 과정을 이 문서에서는 복호화라고 부릅니다. 복호화 방법 자체는 펌웨어 파일 구조와 복호화에서 다룹니다.

이 문서가 답하려는 질문은 두 가지입니다.

  • 복호화한 이미지를 다시 가려서 원래 파일과 똑같이 만들 수 있는가.
  • 카메라의 업데이트 코드는 파일을 받아들이기 전에 무엇을 검사하는가.

두 질문에 답하려고 아래 순서로 작업했습니다. 앞의 세 단계는 Python 도구가 하고 마지막 단계는 펌웨어에 들어 있는 원본 ARM 코드를 Unicorn CPU 에뮬레이터에서 실행합니다.

  1. 식별·복호화배포 파일의 SHA-256을 확인하고 주·보조 이미지를 풉니다
  2. 같은 크기로 수정바이트를 교체합니다. 삽입·삭제는 지원하지 않습니다
  3. 체크섬 보정·재포장합을 0으로 맞추고 XOR로 다시 가립니다. 풀어서 수정본과 같은지도 봅니다
  4. 원본 검사 실행펌웨어의 검사 코드에 후보를 넣어 실행합니다
주소 표기

이 문서의 코드 위치는 복호화한 파일의 오프셋입니다. 주 이미지 코드의 분석용 실행 주소는 오프셋에 0x02000000을 더한 값입니다. 0xC0001FD0처럼 0xC로 시작하는 값은 코드가 읽고 쓰는 공유 메모리 주소입니다. K-3 Mark III의 압축 컨테이너·주소·체크섬 규칙은 K-3 II에 적용하지 않았습니다.

파일 구조: 주 이미지와 보조 이미지는 포장 방식이 다릅니다

파일은 16 MiB짜리 주 이미지와 60 KiB짜리 보조 이미지로 이루어지고 두 이미지는 키의 재료와 체크섬 방식이 서로 다릅니다.

각 이미지의 평문 헤더 첫 16바이트가 키의 재료(IV)입니다. 주 이미지는 0x100, 보조 이미지는 0x1000000에서 IV를 읽습니다. IV로 만든 키를 128바이트 블록마다 XOR하므로, 같은 변환을 두 번 적용하면 원래 바이트로 돌아옵니다. 재포장 도구는 이 성질을 그대로 씁니다.

쉽게 말하면

체크섬은 “모두 더하면 0”이 되게 맞춰 둔 숫자입니다. 이미지를 32비트 값으로 잘라 전부 더한 뒤 아래 32비트만 남깁니다. 체크섬 칸을 0으로 두고 구한 합을 부호만 뒤집어(2의 보수) 그 칸에 적으면 전체 합이 0이 됩니다. 내용을 한 바이트라도 바꾸면 합이 달라지므로 체크섬 칸도 다시 계산해야 합니다.

이 포장 단계에는 K-3 Mark III와 같은 바깥쪽 압축 스트림이 없습니다. 다만 이미지 안에 든 리소스까지 모두 비압축이라는 뜻은 아닙니다.

  • 구현은 inspect_firmware.py(복호화)와 repack_firmware.py(체크섬·재포장)에 있습니다.

원본 검사 코드가 확인하는 네 가지

업데이트 코드는 길이, 모델값, 고정 표식, 합계를 봅니다. 주 이미지의 합계는 다른 실행 문맥에 계산을 맡기는데 그 계산은 단순한 덧셈이었습니다.

업데이트 함수 전체를 실행하지는 않았습니다. 위 함수들이 서로를 부르는 관계는 분기 명령의 바이트를 읽어 대조했고 각 함수는 따로 떼어 실행했습니다. SD 카드나 플래시 같은 장치 입출력은 실행하지 않았습니다.

주 이미지의 합계는 공유 메모리로 요청합니다

주 이미지를 검사할 때 헤더 검사 함수는 합을 직접 구하지 않습니다. 공유 메모리의 정해진 칸(슬롯)에 “명령 7”과 이미지 주소, 워드 수를 적어 두고 응답을 기다립니다. 같은 주 이미지 안에 있는 수신 코드가 이 요청을 읽어 합을 구한 뒤 응답 칸에 적습니다. 이런 주고받기를 이 문서에서는 메일박스라고 부릅니다.

수신기의 덧셈 루프는 넘겨받은 워드 수만큼 값을 읽어 32비트로 더하고 그 합을 돌려줍니다. 워드 수 0x400000에 4바이트를 곱하면 주 이미지 크기 16 MiB와 같습니다. 따라서 확인한 명령 7은 덧셈 검사이며 암호 서명 연산이 아닙니다.

시험 조건

송신기와 수신기는 에뮬레이터의 CPU 문맥 두 개에 나눠 담아 차례로 실행했고 두 문맥이 같은 메모리를 봅니다. 완료 표시와 합계는 원본 명령이 직접 적었으며 연구자가 대신 넣지 않았습니다. 수신 코드가 실제로 어느 CPU 코어에서 도는지, 두 코드가 동시에 돌 때의 타이밍과 캐시 일관성은 이 실행으로 알 수 없습니다.

보조 이미지의 합계는 함수 하나가 직접 구합니다

보조 이미지에서는 헤더 검사가 함수 0x84765C를 부릅니다. 이 함수는 워드의 바이트 순서를 뒤집어(빅엔디언으로) 더한 합이 0인지 봅니다. 검증기는 같은 함수를 주 이미지에도 직접 실행해 보았고 두 이미지 모두 수용했습니다.

체크섬 칸이 0xFFFFFFFF이면 합계 검사를 건너뜁니다

덧셈 체크섬 함수에는 예외가 하나 있습니다. 저장된 체크섬이 0xFFFFFFFF이면 합이 틀려도 수용합니다.

함수 0x84765C에 합이 맞지 않는 이미지를 넣고 체크섬 칸의 값만 여섯 가지로 바꿔 실행했습니다. 두 이미지 종류를 합쳐 12건 가운데 0xFFFFFFFF를 넣은 2건만 수용했습니다. 이 함수의 명령 구간에는 이 밖에 상수로 검사를 건너뛰는 분기가 없었습니다.

주의

이 결과는 함수 하나의 예외 분기를 확인한 것입니다. 업데이트 전체의 검사를 우회할 수 있다는 주장이 아닙니다. 주 이미지는 헤더 검사에서 명령 7로 합을 따로 확인하고 업데이트 경로의 다른 검사를 모두 조사하지도 않았습니다.

체크섬을 정상적으로 다시 계산한 값이 우연히 0xFFFFFFFF가 될 수도 있습니다. 이 경우 합은 0으로 맞지만 원본 코드는 검사 생략 쪽을 고릅니다. 그래서 재포장 도구는 계산 결과가 이 값이 되는 입력을 출력하기 전에 거부합니다. 두 바이트 순서 모두에서 거부되는 것을 단위 검사와 실제 펌웨어 입력으로 확인했습니다.

한계와 남은 과제

확인한 길이·모델값·표식·덧셈 검사는 암호 서명 검증이 아닙니다. 그렇다고 업데이트 경로 전체, 카메라 내부 ROM, 설치 뒤의 부팅 경로에 다른 인증이 없다고 입증한 것도 아닙니다.

  • 수정 범위: 도구는 같은 크기의 바이트 교체만 처리합니다. 코드나 구역을 추가·삭제하는 수정, 주소가 밀리는 수정, 함수 호출 방식이 바뀌는 수정은 지원하지 않습니다.
  • 실기 검증: 카메라 플래시 기록, 보조 이미지 쪽 갱신, 렌즈 EEPROM 쓰기를 하지 않았습니다.
  • 단계 구분: 원본으로의 왕복 일치, 수정 후보의 구조 검사, 실제 업데이트 수용, 부팅, 촬영·저장은 서로 다른 단계입니다. 뒤의 세 단계는 확인하지 않았습니다.

검사를 통과한 이미지가 그다음에 어떻게 전송되고 기록되는지는 업데이트 전송과 기록 오류에서 이어집니다. 함수 하나를 C로 다시 만들어 바꿔 끼우는 시험은 톤 보간 함수 C 재구현에 있습니다. 연구 목표별 상태는 hq-status.json에 정리되어 있습니다.
