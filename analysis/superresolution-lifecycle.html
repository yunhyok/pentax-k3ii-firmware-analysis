Pixel Shift 메뉴를 연결하고,
일반·마스크 버퍼의 수명을 구분했다

Pixel Shift Resolution의 On/Off 이벤트가 쓰는 설정과 SuperResolution 분기가 읽는 설정을 연결했다. 버퍼 분석에서는 일반 출력 평면이 별도 슬롯에서 먼저 만들어지고 JPEG 처리까지 유지되는 경로를 찾았다. 보조 스케일러 활성값은 공통 설정부터 큐 호출 지점까지 추적했지만, 확인한 실행은 모두 0을 기록했다.

초기 분석앞선 마스크 분석실제 메뉴SuperResolution 순서RAW 버퍼 수명보조 활성값검증·재현남은 범위

코드 위치는 해제 이미지의 파일 오프셋이며 코드 VA는 오프셋 + 0x02000000이다. 슬롯 번호·레시피 행·내부 작업 종류는 서로 다른 값이다. 원본 ARM과 원본 레시피를 합성 메모리에서 검증했으며 실제 촬영을 관찰한 결과는 아니다.

1. Pixel Shift Resolution 메뉴가 SuperResolution 선택에 연결된다

위젯 행 0x98EDC4는 ID 0x01306003과 문자열 리소스를 연결한다. 영어 리소스 0xE4C6D8을 복원하면 Pixel Shift Resolution이다. 선택 이벤트 0x01306005는 화면의 +0xE7에 1을, 0x01306006은 0을 쓴다. 별도 적용 함수 0x3C651C가 이 값을 설정 ID 0x98로 전달한다. 리소스·이벤트·설정 근거

화면의 가상 함수표 0xA70BFC는 선택·이벤트·적용 처리기를 각각 연결한다. 적용 처리의 내부 이벤트 0·1·0x10·0x11·6·0x1D는 설정 쓰기로 이어지며, 3·0xF는 같은 쓰기를 하지 않는다. 이 이벤트 숫자를 물리 버튼 이름으로 치환하지 않았다. 쓰기와 조회가 같은 활성 프로필의 값을 사용하는지 원본 명령으로 대조했다. 메뉴 적용·조회 검증

이 프로필 설정 0x98과 RAW 현상 객체의 태그 0x98은 저장소가 다르다. RAW 쪽은 MakerNote 0x0243의 원본 처리기 0x7496DC가 입력 첫 바이트를 1과 비교해 기록한다. 프로필 0·1과 RAW 입력 0·1·2를 교차한 6개 사례에서 RAW 가져오기는 작업 태그만 바꿨고, 촬영 작업 선택은 프로필 값을 따랐다. 같은 번호라는 이유로 RAW 파일의 설정을 현재 메뉴 상태와 동일시할 수 없다. 독립 저장소 교차 검증

제조사 설명서는 Pixel Shift Resolution을 촬영 메뉴 A1 또는 컨트롤 패널에서 켤 수 있다고 설명한다. 센서를 이동해 얻은 네 장을 합성하는 기능이라는 공식 설명도 펌웨어의 메뉴 식별을 뒷받침한다. 단, 사용 가능한 노출 모드와 기능 조합에 관한 공식 제한을 이번 합성 실행으로 검증한 것은 아니다. Ricoh K-3 II 설명서, 인쇄 60쪽 · 공식 Pixel Shift FAQ

2. SuperResolution 레시피에는 마스크용 슬롯 17이 없다

위 진단 분기는 레시피 0x09를 선택한 뒤 작업 종류 11을 준비 함수에 전달한다. 원본 레시피 생성자로 복원한 주요 순서는 아래와 같다. 행 번호는 0부터 시작하며 중간 작업은 표에서 생략했다. 레시피 생성·행 대조

앞선 보고서에서 확인한 모듈 20 완료는 마스크 0x40을 0x80으로 바꾼다. 이후 (mask & 0x44) == 0인 CPP 출력 선택은 일반 평면을 사용한다. 원본 출력 선택 구간을 별도로 실행해 마스크 4 → 8과 0x40 → 0x80 모두 일반 평면으로 바뀌고 job+0x7F가 0이 됨을 확인했다. 따라서 확인한 후속 경로는 일반 출력으로 설명된다. 보조 스케일러 출력과 JPEG 입력이 반드시 같은 주소여야 한다는 가정은 필요하지 않다. 모듈 20 완료·CPP 입력 근거 · 후속 출력 선택과 버퍼 상태

3. RAW 현상은 일반 버퍼와 마스크 버퍼를 따로 구성한다

슬롯 4의 원본 생성 경로 0x654218 → 0x6603AC는 일반 평면 필드 job+0x160…0x18C와 디스크립터 +0x2140/+0x21E8/+0x2204를 구성한다. 배치 구분값 job+0x20B2=1인 상태에서도 이 일반 평면이 만들어진다. 슬롯 17의 0x65473C → 0x6609AC는 같은 구분값에서 마스크 디스크립터 +0x2354/+0x238C/+0x23A8를 구성하고 일반 평면을 유지한다. 원본 슬롯 할당·레이아웃 검증

컨트롤러의 슬롯 4 할당은 풀의 사용 표식을 검사하고, 선택한 버퍼를 작업의 가상 할당 함수에 넘긴다. 슬롯 17은 기존 슬롯 포인터가 없을 때 별도 할당기를 호출한다. 따라서 두 슬롯은 할당 출처부터 다르다. 앞선 보고서의 “일반 레이아웃을 만든 뒤 같은 주소로 마스크 레이아웃을 만들면 일치한다”는 결과는 조건부 합성 사례로 남는다. 그것을 실제 RAW 작업의 필수 이력으로 채택하지 않았다.

해제 함수가 슬롯 포인터를 지워도 평면 디스크립터에 과거 주소가 남을 수 있다. 이번에는 주소 값의 잔존과 버퍼의 사용 기간을 함께 추적했다. 실제 촬영 프레임을 관찰하지 않았으므로 어느 물리 주소가 몇 번째 촬영에서 재사용되는지는 확인하지 않았다. 할당·반환·잔존 필드 검증

항목이 하나인 합성 풀에서 슬롯 4를 반환한 뒤 다시 요청하면 같은 풀 항목을 다시 받았다. 반면 슬롯 17을 해제 후 다른 주소로 재할당하면 마스크 평면만 새 주소로 구성됐다. 이미 연결된 슬롯을 다시 요청할 때는 기존 디스크립터를 재구성하지 않았다. 이 결과는 원본 할당·해제 코드의 재사용 규칙이며, 실제 카메라의 촬영별 주소 기록은 아니다.

후속 스케일러의 입력 디스크립터는 job+0x2140, 출력은 +0x21B0/+0x21CC다. 원본 JPEG 모듈 16 설정도 같은 두 출력 객체를 입력으로 사용한다. 이는 앞서 미확정이던 마스크 디스크립터의 직접 전달과 별개로, 일반 출력으로 돌아온 뒤의 연결을 보여 준다. 배치 구분값 2인 보조 작업은 슬롯 17만으로 일반 평면을 구성하므로, 구분값 1의 주 작업과 같은 배치로 해석하지 않았다. 작업별 평면 구성·스케일러/JPEG 객체 일치

작업 객체와 그 객체가 가리키는 메모리도 구분했다. 0x5A152C/0x5A1534는 작업 객체의 할당기와 생성자를 호출한다. 별도의 부속 버퍼 풀 0x5A1448/0x5A1400은 합성 항목에 대해 취득 성공→사용 중 재취득 실패→반환 후 재취득 성공을 보였고, 마지막에는 처음과 같은 네 포인터를 반환했다. 이 부속 풀은 컨트롤러의 슬롯 4 풀과 다른 구조다. 객체 생성 호출·부속 풀 재취득 근거

4. 공통 스케일러 설정에서 큐 호출까지 활성값은 0이다

앞선 검증은 생성자와 설정 함수 일부에서 payload+0x38=0을 확인했다. 이번에는 컨트롤러 0x6DC2D0부터 모듈 2의 설정 함수 전체, payload 조회, 메시지 조립, 큐 삽입 호출 지점까지 원본 코드를 실행했다. 출력·상태 플래그와 메시지 저장 위치를 바꾼 합성 사례 64개 모두, 0x71B090이 활성 바이트에 0을 한 번 기록했다. 큐 호출 지점에서 기록한 메시지도 같은 payload를 가리켰다. 64개 전체 설정·큐 호출 사례

다른 미리보기 호출 지점 0x528BD4/0x528BE0이 바꾸는 바이트는 +0x2A/+0x2B로, 조사 중인 +0x38과 다르다. 기존의 정렬된 A32 직접 호출·setter 주소·오프셋 검색 결과도 다시 대조했다. 확인한 공통 경로 안에는 비영 활성값의 생산자가 없지만 다른 코드의 계산된 포인터 쓰기·메모리 복사·동시 작업까지 배제한 것은 아니다. 검사 범위와 한계

6. 이번에 확인한 것과 남은 것

Pixel Shift 메뉴와 SuperResolution 설정 조회는 연결했다. 일반 출력 평면을 만드는 슬롯과 마스크 평면을 만드는 슬롯, JPEG 전후의 해제 순서도 구분했다. 보조 스케일러를 실제로 켜는 생산자는 아직 찾지 못했다. 확인한 레시피의 일반 출력 경로와, 활성 조건이 미확정인 보조 경로를 별개로 기록한다.

촬영 시 모든 기능 제한의 판정, 실제 할당 주소와 프레임별 재사용, 각 모듈의 픽셀 결과·JPEG 생성·SD 기록은 검증하지 않았다. 디스크립터 주소가 남아 있다는 사실만으로 버퍼가 유효하거나 데이터가 보존됐다고 볼 수 없다.
