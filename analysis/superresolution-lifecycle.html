Pixel Shift Resolution 메뉴에서 버퍼 할당과 해제까지

Pixel Shift Resolution은 센서를 조금씩 움직여 찍은 네 장을 합치는 K-3 II의 기능입니다. 메뉴에서 켠 값이 펌웨어의 어느 작업으로 이어지는지, 그 작업이 영상 버퍼를 언제 잡고 놓는지 따라갔습니다.

이 문서에서

  1. 배경: Pixel Shift Resolution이란
  2. Pixel Shift Resolution 메뉴 값이 SuperResolution 작업을 고릅니다
  3. SuperResolution 작업의 레시피는 마스크용 버퍼를 할당하지 않습니다
  4. 일반 버퍼와 마스크 버퍼는 따로 할당되고 수명이 다릅니다
  5. 스케일러 설정에서 큐 호출까지 보조 활성값은 0이었습니다
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 메뉴의 Pixel Shift Resolution On/Off는 활성 프로필의 설정 하나에 저장됩니다. 작업을 준비하는 코드가 같은 설정을 읽어, 켜져 있으면 내부 이름이 SuperResolution인 작업 종류를 고릅니다.
  • RAW 파일의 MakerNote에도 같은 번호의 태그가 있지만 저장소가 다릅니다. RAW를 가져와도 현재 메뉴 설정은 바뀌지 않았습니다.
  • 영상 평면은 번호가 붙은 버퍼 슬롯에서 만들어집니다. 일반 출력은 슬롯 4, 마스크 출력은 슬롯 17이고 둘은 할당하는 곳부터 다릅니다. 슬롯 4는 스케일러와 JPEG 단계가 끝난 뒤에 반환됩니다.
  • 슬롯을 해제해도 디스크립터에는 예전 주소 숫자가 남습니다. 숫자가 남아 있다고 그 버퍼가 유효한 것은 아닙니다.
  • 스케일러의 보조 활성값은 공통 설정부터 큐 호출 직전까지 실행한 64건에서 모두 0이었습니다. 0이 아닌 값을 쓰는 코드와 실제 촬영에서의 주소 이력은 확인하지 못했습니다.

확인 원본 코드 실행으로 확인

  • 메뉴 선택·적용·조회·작업 선택 10건, RAW 교차 6건
  • 원본 레시피 6개에서 지정한 행 44개
  • 슬롯 4·17·18의 할당, 해제, 재할당과 평면 주소
  • 스케일러 설정 전체와 큐 호출 지점 64건

  • 위젯 표, 가상 함수표, 분기 43개

모델 시험 조건으로 넣은 값

  • 합성 화면 객체, 프로필, 명령
  • 항목이 하나인 버퍼 풀, 할당기가 돌려주는 주소, 치수
  • 출력·상태 플래그 조합 64가지

미확인 확인하지 않은 것

  • 실제 버튼 조작, LCD 표시, 촬영
  • 촬영마다의 실제 버퍼 주소와 재사용
  • 0이 아닌 활성값을 쓰는 코드, 큐를 거친 전달

배경: Pixel Shift Resolution이란

보통의 이미지 센서는 화소마다 빨강(R), 초록(G), 파랑(B) 가운데 한 색의 필터만 얹혀 있습니다. 화소 하나는 한 색의 밝기만 기록하고, 나머지 두 색은 주변 화소에서 추정합니다. 리코의 설명대로라면 이런 센서에서 색별 해상도는 초록이 1/2, 빨강과 파랑이 1/4입니다.

Pixel Shift Resolution은 손떨림 보정(SR) 기구로 센서를 한 화소씩 옮기며 같은 장면을 네 번 찍고, 네 장을 한 장으로 합칩니다. 피사체의 같은 지점이 노출마다 다른 색 필터 아래에 놓이므로, 화소마다 세 색의 정보를 모두 얻습니다. 삼각대에 고정한 정지 피사체가 대상입니다.

리코의 공식 설명(“센서를 한 화소씩 옮겨 네 장을 찍어 합성”, “화소마다 모든 색 정보를 얻음”)을 그림으로 옮긴 것입니다. 펌웨어에서 확인한 내용이 아닙니다.

설명서에 따르면 이 기능은 촬영 메뉴 A1이나 컨트롤 패널에서 켭니다. 켜 두면 손떨림 보정은 꺼짐으로 고정되고 전자 셔터를 씁니다. 펌웨어 안에서는 이 기능과 이어지는 작업에 SuperResolution이라는 이름이 붙어 있습니다. 이 문서는 세 가지를 다룹니다.

  • 메뉴 값이 어떤 설정에 저장되고, 어떤 코드가 그 값을 읽어 작업을 고르는가
  • 그 작업의 레시피가 영상 버퍼를 언제 할당하고 해제하는가
  • 마스크 CPP 문서에서 0만 관측한 보조 스케일러 활성값이 스케일러 설정 전체를 실행해도 0인가
이 문서에 나오는 이름
이름뜻
활성 프로필카메라 설정은 여러 묶음으로 저장됩니다. 지금 쓰는 묶음이 활성 프로필입니다. 펌웨어에는 묶음이 여덟 개(인덱스 0~7) 있습니다. 이 묶음이 사용자 기능의 무엇에 해당하는지는 확인하지 않았습니다.
작업 종류작업을 준비할 때 넘기는 내부 번호입니다. 11이 SuperResolution, 5가 일반 현상입니다. 노출 모드 다이얼의 번호가 아닙니다.
레시피작업이 실행할 단계를 적은 표입니다. 행마다 연산 번호와 인수가 있습니다. 연산 2는 버퍼 슬롯 할당, 1은 해제, 5는 모듈 실행입니다.
버퍼 슬롯작업 객체가 버퍼를 붙잡는 자리입니다. 슬롯마다 번호가 있고, 번호에 따라 만들어지는 평면과 디스크립터가 다릅니다. 슬롯 번호, 레시피 행 번호, 작업 종류는 서로 다른 번호 체계입니다.
일반 평면, 마스크 평면CPP가 평소에 출력하는 평면과, 마스크 분기에서 출력하는 별도 평면입니다. 마스크 CPP 문서에 두 묶음의 위치가 있습니다.

모듈 번호와 디스크립터의 뜻은 백엔드 B와 두 번째 CPP 출력 문서의 이름 표에, 전체 흐름은 영상 처리 경로 안내에 있습니다. 코드 위치는 복호화한 이미지의 파일 오프셋이며, 실행 주소(VA)는 여기에 0x02000000을 더한 값입니다.

Pixel Shift Resolution 메뉴 값이 SuperResolution 작업을 고릅니다

메뉴에서 On을 고르고 적용하면 활성 프로필의 설정 0x98에 1이 저장됩니다. 작업을 준비하는 코드는 같은 설정을 읽어, 1이면 SuperResolution 분기로 가서 작업 종류 11을 넘깁니다. RAW 파일에서 가져온 같은 번호의 태그는 다른 곳에 저장되며 이 선택에 영향을 주지 않습니다.

메뉴 선택과 적용은 서로 다른 단계입니다. 선택만으로는 프로필이 바뀌지 않고, 적용 이벤트가 와야 기록됩니다. 화면 객체, 프로필 메모리, 명령은 시험용으로 만든 것이며 LCD 표시, 실제 버튼, 촬영은 실행하지 않았습니다.

메뉴 이름과 이벤트

위젯 행 0x98EDC4는 위젯 ID 0x01306003과 문자열 리소스를 잇습니다. 영어 리소스 0xE4C6D8을 복원하면 Pixel Shift Resolution입니다. 선택 이벤트 0x01306005(On)는 화면의 +0xE7에 1을, 0x01306006(Off)은 0을 씁니다. 적용 함수 0x3C651C가 이 값을 설정 ID 0x98로 넘깁니다.

화면의 가상 함수표 0xA70BFC가 선택, 이벤트, 적용 처리 함수를 잇습니다. 적용 처리에 들어오는 내부 이벤트 가운데 0, 1, 6, 0x10, 0x11, 0x1D는 설정 쓰기로 이어지고 3과 0xF는 쓰지 않습니다. 이 이벤트 숫자가 어떤 버튼에 해당하는지는 정하지 않았습니다.

RAW 파일의 태그는 다른 저장소입니다

RAW 파일의 MakerNote에는 태그 0x0243이 있습니다. ExifTool은 이 태그를 PixelShiftInfo로, 그 첫 바이트를 PixelShiftResolution(0 = Off, 1 = On)으로 풉니다. 펌웨어의 처리 함수 0x7496DC는 이 첫 바이트를 1과 비교해 RAW 작업의 태그 0x98에 기록합니다. 번호는 프로필 설정과 같지만 작업 객체 안의 다른 자리입니다.

SuperResolution 작업의 레시피는 마스크용 버퍼를 할당하지 않습니다

SuperResolution 분기는 레시피 0x09를 고릅니다. 이 레시피는 모듈 20을 먼저 실행한 뒤 일반 출력 버퍼인 슬롯 4를 할당하고, JPEG 단계가 지난 뒤에 해제합니다. 마스크 평면을 만드는 슬롯 17은 할당하지 않습니다.

행 번호는 0부터 세며, 원본 레시피 생성 함수 0x76E7AC를 실행해 얻었습니다. 그림에 없는 행은 추적하지 않은 단계입니다. 레시피의 순서와 할당·해제 코드, 완료 처리를 따로 실행해 이은 것이며, RTOS 스케줄러와 각 장치의 픽셀 연산을 이어서 실행하지는 않았습니다. 행 번호만으로 앞 단계가 성공했는지, 출력 데이터가 유효한지는 알 수 없습니다.

마스크 값이 바뀌어 일반 평면으로 돌아옵니다

작업 종류 11은 마스크 값 0x40으로 시작합니다. 이 값은 마스크 분기에 들어가는 값입니다. 그런데 모듈 20의 완료 처리가 0x40을 0x80으로 바꿉니다. CPP의 출력 선택 구간을 따로 실행해 보면, 마스크가 0x04나 0x40일 때는 마스크 평면을 고르고 job+0x7F에 1을 씁니다. 완료 뒤의 0x08이나 0x80에서는 mask & 0x44가 0이므로 일반 평면을 고르고 job+0x7F를 0으로 되돌립니다.

레시피 0x09에서는 모듈 20(행 2)이 CPP(행 5)보다 앞에 있습니다. 이 순서대로 실행한 시험에서 CPP의 출력은 슬롯 4의 일반 평면이었고 슬롯 17의 포인터는 0이었습니다. 따라서 이 경로는 일반 출력으로 설명됩니다. 보조 스케일러의 출력과 JPEG 입력이 같은 주소여야 한다는 가정은 필요하지 않습니다.

Normal 분기와의 차이

SuperResolution 분기는 준비 단계에 번호 9를 넘기고(0x7B56E8), Normal 분기는 같은 자리에 8을 넘깁니다. 레시피 0x08은 슬롯 4 할당(행 0), CPP(행 1), 스케일러(행 8), JPEG(행 10), 슬롯 4 해제(행 12)뿐입니다. 레시피 0x09는 여기에 슬롯 18·15와 모듈 20이 앞에 더해진 모양입니다.

일반 버퍼와 마스크 버퍼는 따로 할당되고 수명이 다릅니다

RAW 현상 레시피 0x15에서 일반 평면은 슬롯 4, 마스크 평면은 슬롯 17에서 만들어집니다. 슬롯 17은 스케일러보다 앞서 해제되고, 슬롯 4는 스케일러와 JPEG가 끝난 뒤 반환됩니다. 스케일러와 JPEG가 쓰는 것은 일반 쪽 디스크립터입니다.

할당기가 돌려주는 주소는 시험에서 넣어 준 값입니다. 두 슬롯의 주소가 같다는 가정은 넣지 않았습니다.

두 슬롯은 할당하는 곳부터 다릅니다

배치 구분값(job+0x20B2)이 2인 보조 작업은 사정이 다릅니다. 이 작업은 슬롯 4 없이 슬롯 17만으로 일반 디스크립터를 구성했고, 마스크 디스크립터는 0으로 남았습니다. 그래서 구분값 1인 주 작업과 같은 배치로 해석하지 않습니다.

남아 있는 숫자와 유효한 버퍼는 다릅니다

해제 함수가 슬롯 포인터를 지워도 디스크립터에는 예전 평면 주소가 남습니다. 이 숫자가 남아 있다는 사실만으로 버퍼가 유효하거나 데이터가 보존됐다고 볼 수 없습니다. 실제 촬영을 관찰하지 않았으므로, 어느 물리 주소가 몇 번째 촬영에서 다시 쓰이는지도 알 수 없습니다. 여기서 확인한 것은 원본 할당·해제 코드의 규칙입니다.

마스크 CPP 문서의 “일반 배치를 만든 뒤 같은 주소로 마스크 배치를 만들면 평면 주소가 일치한다”는 결과는 조건을 맞춘 합성 사례로 남습니다. 두 슬롯의 출처가 다르므로, 그 순서를 실제 RAW 작업이 반드시 거치는 이력으로 받아들이지 않았습니다.

일반 출력에서 스케일러를 거쳐 JPEG까지

  1. 슬롯 4의 일반 평면job+0x160부터의 주소. CPP가 디스크립터 job+0x2140을 이 주소로 다시 채움
  2. 스케일러 입력job+0x2140
  3. 스케일러 출력job+0x21B0, job+0x21CC
  4. JPEG 모듈 16 입력같은 두 출력 객체

슬롯 17을 해제한 뒤에 스케일러와 JPEG의 설정 코드를 실행해 이 연결을 확인했습니다. 마스크 디스크립터가 JPEG로 직접 넘어가는지와는 별개로, 일반 출력으로 돌아온 뒤의 연결을 보여 줍니다. 픽셀 연산은 실행하지 않았습니다.

배치 구분값을 쓰는 곳과 부속 버퍼 풀

  • 구분값을 쓰는 코드 — RAW 현상의 0x52A048부터의 코드가 네 작업에 1, 2, 3, 4를 씁니다. 촬영 쪽의 0x638D84부터의 코드도 소유 객체의 카운터를 작업의 구분값으로 씁니다. 카운터 3을 넣은 시험에서 구분값이 3이 됐고, 평면은 다시 만들어지지 않았습니다.
  • 작업 객체 — 0x5A152C와 0x5A1534가 작업 객체의 할당기와 생성자를 부릅니다. 작업 객체와 그 객체가 가리키는 버퍼는 따로 관리됩니다.
  • 부속 버퍼 풀 — 0x5A1448(취득)과 0x5A1400(반환)은 컨트롤러의 슬롯 4 풀과 다른 구조입니다. 합성 항목으로 실행하니 취득 성공, 사용 중 재취득 실패, 반환 뒤 재취득 성공 순서였고, 마지막에는 처음과 같은 네 포인터를 돌려주었습니다.

컨트롤러가 스케일러(모듈 2)를 설정하고 요청 메시지를 큐에 넣기 직전까지를 원본 코드로 실행했습니다. 조건을 바꾼 64건 모두에서 보조 스케일러의 활성 바이트에는 0이 한 번 기록됐고, 같은 설정 블록을 읽은 소비자는 보조 스케일러를 건너뛰었습니다.

이 결과의 범위

확인한 공통 경로 안에는 0이 아닌 활성값을 쓰는 코드가 없습니다. 다른 코드가 계산한 포인터로 쓰거나, 메모리를 복사하거나, 동시에 도는 작업이 값을 바꿀 가능성까지 배제한 것은 아닙니다. 64가지 플래그 조합이 실제 메뉴에서 모두 가능한지도 검증하지 않았습니다.

미리보기 쪽 호출 지점 0x528BD4와 0x528BE0이 바꾸는 바이트는 +0x2A와 +0x2B입니다. 조사 중인 +0x38과 다른 바이트입니다. 이미지 전체에서 직접 호출, 설정 함수 주소, 오프셋을 찾은 검색 결과도 다시 대조했고 같았습니다.

한계와 남은 과제

  • 메뉴 — 메뉴 이름, 설정 저장, 설정 조회, 작업 선택을 이었습니다. 실제 버튼과 LCD, 촬영은 실행하지 않았습니다. 촬영할 때 기능 제한을 판정하는 코드는 검증하지 않았습니다.
  • 버퍼 — 일반 평면과 마스크 평면을 만드는 슬롯, JPEG 앞뒤의 해제 순서를 구분했습니다. 실제 할당 주소와 촬영마다의 재사용, 모듈별 픽셀 결과는 확인하지 않았습니다.
  • 보조 스케일러 — 켜는 코드를 찾지 못했습니다. 확인한 레시피의 일반 출력 경로와, 활성 조건을 모르는 보조 경로를 따로 기록합니다.
  • 하드웨어 — JPEG 생성과 SD 기록은 실행하지 않았습니다.

재현 방법

분석 대상은 K-3 II 펌웨어 1.12입니다. 검증기는 복호화한 이미지 decoded.bin을 입력으로 받습니다. 만드는 방법은 펌웨어 파일 구조와 복호화에 있습니다. 원본 코드 실행에는 Unicorn 2.1.4를 썼습니다.
