톤 문맥과 곡선 생산자의 연결

어떤 객체의 값을 읽고, 어느 계산을 거쳐 곡선으로 만드는지 확인했습니다.

이 결과의 범위부터 읽어 주십시오

이 문서는 K-3 II 펌웨어의 톤 곡선 생산자, 그 입력을 계산하는 문맥 생산자, 같은 작업 객체의 포인터 연결, 조건부 문맥 복사를 한데 정리합니다. 원본 명령은 분리된 구간과 VM에서 재현했습니다. 실제 촬영을 처음부터 끝까지 실행하지는 않았습니다. 서비스·할당 호출과 실제 큐 순서를 생략한 곳은 각 단계에 표시했습니다. 생성자 값은 촬영 기본값으로 해석하지 않으며 EV 단위, Q 형식, 감마도 아직 확인하지 못했습니다.

연결도는 데이터 의존 관계입니다. 실촬영의 작업 순서·중간 덮어쓰기·캐시 이력·픽셀 처리·JPEG 출력은 검증하지 않았습니다. 생산자의 0x4000 제한은 전체 경로의 포화 처리나 센서 비트 깊이를 뜻하지 않습니다. 재현 코드와 JSON은 아래에서 연결하며, 명령 주소는 복호화 파일 오프셋입니다. VA는 0x02000000을 더합니다.

복사한 문맥에서 곡선까지: 연결과 경계

도식의 점선은 재현 사이의 관계를 설명하며 실제 함수 호출이나 완료 이벤트를 나타내지 않습니다. 특히 복사 시험의 0 포함 값들을 문맥 수식 시험에 그대로 이어 넣지 않았습니다. 후자는 모든 나눗셈 분모가 0이 아닌 별도 입력 범위에서 검증했습니다.

1. 포인터 생산자와 조건부 문맥 복사

같은 작업 객체에서 원본 저장 명령은 job+D828에 job+2730을 기록합니다. selector 4의 조건이 맞으면 이 포인터를 읽어 job+E608에 네 halfword와 104바이트를 복사합니다. 다른 재현에서는 job+E608이 생산자와 톤 처리자 양쪽에 전달되는 것을 확인했습니다. 두 결과에서 주소의 데이터 의존 관계를 확인했습니다. 실제 작업의 실행 순서와 중간 덮어쓰기는 입증되지 않았습니다. 참조 슬롯은 job+26C0이며 이전 job+225C 해석을 정정합니다.

6593B0의 원본 프롤로그를 실행하면 [SP+20]=job+2684이고 [SP+28]=job+2220입니다. 따라서 명령 내부 참조는 job+2684+8+34 = job+26C0입니다. selector 3의 719988이 job+C2F8을 기록한 경우 72D534는 receiver=job+C30C를 반환합니다. 585FE8 → 71A384는 같은 명령에서 source=job+2730을 계산하고 87BAB0가 receiver+151C, 즉 job+D828에 저장합니다. 호스트는 두 포인터 필드를 직접 쓰지 않습니다.

selector 4는 job+2080=0, job+20BB≠0, 참조≠0 조건에서 포인터를 읽습니다. 7F42E4의 52회 STRH가 목적 문맥+6100부터 104바이트를 복사하고, 719628/719638/719630/719620의 네 STRH가 +8/+A/+C/+E를 복사합니다. 별도 할당 객체의 +1794에 쓰는 7A21C4, job+1828에 쓰는 653F88은 같은 슬롯의 생산자로 합치지 않았습니다. 원본 구간 재현 코드

2. 생산자와 톤 처리자의 공유 주소

원본 생성자가 recipe=job+E0C4와 context=job+E608을 만듭니다. 653E94에서 계산한 R6를 유지해 7855A4가 생산자 명령 +14에, 785868이 톤 명령 +90에 같은 포인터를 씁니다. 원본 getter·vtable·thunk를 실행한 소비자는 이 값을 각각 다섯 번째 인자와 R3로 받았습니다. job=0x10100000과 0x10200000의 두 배치에서 재현했습니다. 공유 포인터 재현 코드

생산자 4E02F8 프레임의 [SP+250]은 다섯 번째 인자이고 [SP+224]는 저장한 진입 R2, 즉 recipe입니다. 후자를 R1로 해석하면 안 됩니다. 생산자 메시지는 0x00608001이며 selector 4의 job+A3FC를 사용합니다. 톤 소비 재현은 0x00600001 분기 안의 57C118에 따로 진입했습니다. generic selector 0의 메시지는 0x00600002이므로 그 가드까지 실행했다고 주장하지 않습니다. 바깥 객체 생성자는 vtable 설치 앞부분만 실행했습니다.

3. context+7A74의 원본 정수 계산

4DF834의 R1은 recipe, R2는 context입니다. 원본 저장 72D094가 결과를 context+7A74에 씁니다. 4FA83C getter를 통해 4DDAB8의 입력 +18에 같은 정수가 전달되는지 검사했습니다. 아래 u32/u16은 하위 32/16비트이며 udiv는 부호 없는 정수 나눗셈입니다. 네 halfword g에는 색 채널 이름을 붙이지 않았습니다. 원본 수치 재현 코드

c = recipe[+92] ? 0xFFBF : 0xFFFB
if recipe[+A4] == 0:
    d = u32(c - word(recipe+BC)) >> 2
    x = u16(word(recipe+9C))
else:

    x = prior_half(context+60DC)
m = min(256, g0, g1, g2, g3)

half(context+6010+2*i) = min(u16(u32(gi*k) >> 13), 0x7FF)

4. ROM 기반 곡선과 보간·확장

원본 문맥 계산은 context+7A74를 쓰고 톤 생산자는 그 정수를 입력으로 받습니다. 준비한 입력으로 계산한 8192와 4096을 각각 톤 생산자에 전달했습니다. 각 곡선의 256개 원소는 같은 값을 직접 공급했을 때의 곡선과 모두 일치했습니다. 보간 265개 좌표와 확장 1280개 halfword도 비교했습니다. 생산자의 0x4000 제한을 모든 단계의 포화 처리로 일반화할 수는 없습니다. 합성 FFFF 입력에서 보간 결과와 확장 꼬리는 65535였습니다. 공개 재현 자료에는 범위 해시, 생성된 곡선과 관측 수치를 담았습니다. ROM 바이트와 전체 명령 hex 배열은 제외했습니다.

원본 초기화 데이터 복사 [A84504,A9A3B4) → 404094B0를 먼저 실행한 뒤 기본 프로파일 getter와 곡선 생산자를 실행합니다. regular 생산자는 4DC980, selector=6 생산자는 4DD924입니다. Natural, Bright, Reversal Film이라는 이름은 기존 프로파일 대응에 따른 표기이며 이번 재현 자체가 UI 이벤트를 실행한 것은 아닙니다. 기존 Reversal Film 메뉴 분석과 Pixel Shift 메뉴·수명 분석은 별도 근거입니다. 이 문서의 selector=6을 SuperResolution의 작업 selector와 혼동하지 않습니다.

Bright의 control_c만 중립 값으로 바꾸면 Natural의 곡선과 같아지고 selector 0↔1 변경만으로 regular 생산자가 바뀌지는 않았습니다. Reversal Film의 special selector를 제거한 대조군도 같은 regular 곡선으로 돌아왔습니다. 원본 초기화 데이터 복사를 생략한 음성 대조는 4DCB68의 주소 4 읽기에서 예상대로 실패합니다. 곡선·보간·확장 재현 코드

재현 방법과 파일 보호

실행 검증 환경은 Python 3.12.3와 Unicorn 2.1.4입니다. Python 3.10 문법 검사는 별도로 통과했지만 해당 버전의 실행 검증을 뜻하지 않습니다. 사용자가 보유한 복호화 이미지가 필요하며 이미지나 ROM 바이트는 이 저장소에 포함하지 않습니다. 입력은 16,838,656바이트이고 SHA-256은 다음 값입니다.

1b87bf35b290e4b4e8910beb4055c34f97504b65e249ad65e5ccc0402bd14cfc

python -B verify_tone_provenance.py decoded.bin --output tone-result-new.json --compare analysis/tone-provenance.json
python -B -O verify_tone_provenance.py decoded.bin --output tone-result-optimized-new.json --compare analysis/tone-provenance.json
python -B -m unittest discover -s tests -p test_tone_provenance.py

CLI가 있는 디렉터리와 기존 helper가 있는 체크아웃이 다르면 --repository 경로를 지정합니다. inspect_firmware.py, verify_findings.py, verify_tone_path.py, verify_tone_numeric.py와 네 재현 모듈을 모두 바이트로 캡처하고 LF 줄바꿈으로 정규화한 SHA-256을 확인한 뒤 실행합니다. 프로젝트 모듈은 전역 import 캐시·pyc·검색 경로에서 가져오지 않으며, 캡처 후 파일이 바뀌어도 재읽지 않습니다. 표준 라이브러리와 설치된 Unicorn은 실행 환경 의존성입니다. 이 로더를 범용 보안 샌드박스로 주장하지 않습니다.

전체 입력 해시, RX 코드 매핑, 모든 실행 명령과 원본 바이트의 일치, 원본 출력 저장 PC와 범위를 확인합니다. 정상 종료한 사례는 실행 뒤 매핑된 코드 이미지 보존도 확인합니다. 네 단계의 전체 내부 결과는 수락된 canonical JSON 해시와 먼저 대조한 뒤 공개 관측값으로 투영합니다. JSON 비교는 bool·int·float를 구분합니다. require 검사가 -O에서도 동작하며 Python assert에 검증을 맡기지 않습니다.

출력은 새 경로만 허용합니다. 기존 파일·별칭·하드링크·심볼릭링크를 거부하고, 같은 디렉터리의 임시 파일을 기록·동기화한 뒤 배타적인 하드링크 생성으로 게시합니다. 게시 직전 다른 프로세스가 목적지를 만들어도 덮어쓰지 않습니다. 기록 실패 시 임시 파일을 정리하며 하드링크를 지원하지 않는 파일시스템에서는 성공으로 처리하지 않습니다. 입력·소스·비교 기준을 덮어쓰는 옵션은 없습니다.
