톤 문맥과 곡선 생산자의 연결

톤 곡선을 만드는 코드는 작업 객체 안의 문맥에서 정수 하나를 받아 곡선을 계산합니다. 그 문맥 주소와 정수를 어느 코드가 쓰는지 원본 코드를 나눠 실행하며 따라갔습니다.

핵심 요약

  • 톤 곡선 생산자가 받는 문맥 주소와 정수 입력의 출처를 원본 코드로 추적했습니다. 코드를 네 갈래로 나눠 에뮬레이터에서 실행했고 사례는 모두 24개입니다(곡선 8, 문맥 계산 8, 공유 주소 2, 복사 6).
  • 같은 작업 객체 안에서 문맥 포인터를 저장하는 코드와 조건이 맞을 때 문맥을 복사하는 코드를 찾았습니다. 같은 문맥 주소가 곡선 생산자와 톤 처리 코드 양쪽에 전달되는 것도 확인했습니다.
  • 문맥 계산 코드가 쓴 정수(8192, 4096)를 곡선 생산자에 넘기면 그 값을 직접 넣었을 때와 같은 곡선이 나왔습니다. 곡선 생산자는 출력을 16,384에서 자르므로 상류 값이 달라도 곡선이 같아지는 경우가 있습니다.
  • 네 갈래는 서로 다른 VM에서 따로 실행했고 입력 일부는 연구자가 정한 값입니다. 실제 촬영의 실행 순서, 픽셀·JPEG 결과, 값의 물리 단위(EV·고정소수점 형식·감마)는 확인하지 않았습니다. 카메라에서 실행한 것은 없습니다.

확인 원본 코드 실행으로 확인

  • 포인터 저장과 조건부 문맥 복사 6건(가드가 막힌 경우와 null 참조 포함)
  • 같은 문맥 주소가 생산자 명령과 톤 명령에 기록되고 소비 코드의 인자로 도착함(작업 주소 2개)
  • 문맥 정수 계산 8건과 getter를 거친 전달
  • 곡선 256개 원소, 보간 265개 좌표, 확장 1,280개 halfword의 일치

정적 분석 코드를 읽어 판단

  • 생산자·톤 명령의 메시지 경로와 큐 전달 코드의 위치
  • 같은 오프셋에 쓰는 다른 객체의 코드를 같은 생산자로 보지 않은 판단

모델 시험 조건으로 정한 것

  • recipe·문맥의 상류 입력값과 복사 시험의 원본 halfword
  • 생략하거나 대체한 서비스·메모리 할당 호출
  • 보간·확장 커널에 넣은 합성 FFFF 입력, Unicorn의 Cortex-A9 설정

미확인 확인하지 않은 것

  • 실제 촬영에서 같은 작업의 실행 순서, 중간 덮어쓰기, 값의 변화 이력
  • 생성자 값이 촬영 기본값인지, EV 단위·Q 형식·감마
  • 픽셀 처리, 하드웨어 출력, JPEG, SuperResolution 메뉴 도달

배경: 톤 곡선과 이 문서의 객체들

카메라는 센서 값을 사진으로 바꿀 때 밝기를 톤 곡선에 통과시킵니다. 곡선은 입력 밝기를 출력 밝기로 바꾸는 대응표이고 명암과 계조의 느낌을 정합니다. K-3 II는 값 256개짜리 곡선을 만들어 두고 그 사이를 보간해 씁니다. 공통 경로의 계산은 RAW 이후의 톤·WB·색 행렬에, 보간 함수는 톤 보간 C 재구현에 있습니다.

이 문서는 곡선 생산자 앞단을 봅니다. 생산자가 읽는 정수가 어디서 계산되고 어느 객체를 거쳐 오는지가 질문입니다. 아래 용어는 원본 분석 자료의 이름을 그대로 따랐습니다.

작업 객체(job)
사진 한 장의 처리를 담는 큰 객체입니다. 아래 객체들은 모두 job 안의 고정 오프셋에 있습니다.
recipe 객체
job+E0C4에 있는 톤 설정 객체입니다. 톤 선택값(+0x44)과 이 문서가 다루는 +92·+A4·+BC·+9C 필드가 있습니다. 용어집의 레시피(모듈 호출 순서를 적은 단계 목록)와는 다른 것입니다.
문맥(context)
job+E608에 있는 톤 계산용 작업 공간입니다. 곡선 생산자에 넘길 정수를 +7A74에 둡니다.
처리 단계 selector
작업 안의 처리 단계를 고르는 번호입니다(selector 3, 4). 톤 곡선을 고르는 톤 선택값(예: 6 = Reversal Film)과는 다른 번호입니다.
주소 표기

명령 주소는 복호화한 이미지의 16진수 파일 오프셋입니다. 실행 주소(VA)를 구하려면 여기에 0x02000000을 더합니다. job+D828처럼 쓴 것은 작업 객체 시작에서 잰 오프셋입니다.

같은 작업 객체에서 누가 어느 필드를 쓰는가

작업 객체의 여섯 자리를 원본 코드가 쓰고 읽는 관계를 확인했습니다. 다만 네 시험은 따로 실행했으므로 실제 처리 순서는 이 그림에서 알 수 없습니다.

복사 시험의 원본 halfword를 그대로 문맥 계산 시험에 넣지는 않았습니다. 원본 값에 0이 들어 있기 때문입니다. 문맥 계산은 모든 나눗셈 분모가 0이 아닌 별도 입력으로 검증했습니다.

포인터 생산자와 조건부 문맥 복사

원본 코드가 job+D828에 원본 문맥 주소를 저장합니다. selector 4는 조건이 맞을 때만 그 문맥을 job+E608로 복사합니다.

selector 3의 명령 안에서 원본 코드가 원본 문맥 주소 job+2730을 계산해 job+D828에 저장합니다. 호스트(시험 프로그램)는 두 포인터 필드를 직접 쓰지 않았습니다. selector 4는 세 조건이 모두 맞을 때 이 포인터를 읽어 목적 문맥에 halfword 4개와 104바이트를 복사합니다.

  • job+2080 바이트가 0
  • job+20BB 바이트가 0이 아님
  • 명령의 참조 슬롯 job+26C0이 0이 아님
정정

명령 내부의 참조 슬롯은 job+26C0입니다. 앞서 job+225C로 본 해석을 원본 프롤로그 실행 결과로 바로잡았습니다.

명령 주소와 생략한 부분
  • 6593B0의 원본 프롤로그를 실행하면 [SP+20]=job+2684, [SP+28]=job+2220입니다. 명령 내부 참조는 job+2684+8+34 = job+26C0입니다.
  • selector 3의 719988이 job+C2F8을 기록하면 72D534가 receiver job+C30C를 반환합니다.
  • 585FE8 → 71A384가 같은 명령에서 source job+2730을 계산합니다. 87BAB0은 이 값을 receiver+151C(job+D828)에 저장합니다.
  • 7F42E4의 STRH 52회는 목적 문맥+6100부터 104바이트를 옮깁니다. 719628, 719638, 719630, 719620의 STRH 4회가 +8, +A, +C, +E를 복사합니다.
  • 별도 할당 객체의 +1794에 쓰는 7A21C4와 job+1828에 쓰는 653F88은 같은 슬롯의 생산자로 합치지 않았습니다.
  • 생략: selector 3의 R8 경로 선택, 원본 처리 함수 중간의 서비스·차원 읽기·할당 호출. 명령의 원본 생성자와 writer 스택 프레임은 실행했습니다. D828의 초기 0은 새 RAM의 초기 상태입니다. 참조 객체 전체 생성자를 실행한 결과가 아닙니다.

생산자와 톤 처리 코드가 같은 문맥 주소를 받습니다

원본 코드가 같은 문맥 주소 job+E608을 생산자 명령과 톤 명령 양쪽에 기록합니다. 두 소비 코드는 그 값을 인자로 받았습니다.

원본 생성자가 recipe 객체(job+E0C4)와 문맥(job+E608)을 만듭니다. 653E94에서 계산한 R6를 유지한 채 7855A4가 생산자 명령의 +14에, 785868이 톤 명령의 +90에 같은 포인터를 씁니다. 원본 getter·vtable·thunk를 거친 소비 코드는 이 값을 각각 다섯째 인자와 R3로 받았습니다.

프레임 해석과 메시지 경로
  • 생산자 4E02F8 프레임의 [SP+250]은 다섯째 인자이고 [SP+224]는 저장한 진입 R2(recipe)입니다. 후자를 R1로 해석하면 안 됩니다.

문맥 +7A74의 정수 계산

원본 코드 4DF834가 recipe와 문맥의 값으로 정수 하나를 계산해 context+7A74에 씁니다. getter는 그 값을 곡선 생산자 쪽으로 넘깁니다.

4DF834는 R1로 recipe, R2로 문맥을 받습니다. 원본 저장 코드 72D094가 결과를 context+7A74에 씁니다. 이어서 4FA83C getter를 거쳐 4DDAB8의 입력 +18에 같은 정수가 도착하는지 검사했습니다. 아래 식은 원본 명령의 정수 연산 순서를 옮긴 것입니다. u32/u16은 하위 32/16비트, udiv는 부호 없는 정수 나눗셈입니다.

c = recipe[+92] ? 0xFFBF : 0xFFFB
if recipe[+A4] == 0:
    d = u32(c - word(recipe+BC)) >> 2
    x = u16(word(recipe+9C))
else:
    d = prior_word(context+7A68)
    x = prior_half(context+60DC)
m = min(256, g0, g1, g2, g3)
a = udiv(u32(c << 13), u32(d << 2))
k = udiv(u32(a << 8), m)
half(context+6010+2*i) = min(u16(u32(gi*k) >> 13), 0x7FF)
word(context+7A74) = udiv(u32(k << 13), x)

식의 g0~g3은 문맥 +8~+E의 halfword 4개입니다. 색 채널 이름은 붙이지 않았습니다. 대응이 확인되지 않았기 때문입니다.

주의

recipe 생성자가 쓰는 +9C=8192와 문맥 생성자가 쓰는 halfword 420, 256, 256, 320은 생성 시점의 정수입니다. 실제 촬영의 최종 설정이나 물리 단위를 뜻하지 않습니다.

ROM 기반 곡선과 보간·확장

문맥 계산이 만든 8192와 4096을 곡선 생산자에 넘기면, 같은 값을 직접 넣었을 때와 곡선 256개 원소가 모두 같았습니다.

곡선 생산자를 실행하기 전에 원본 초기화 데이터 복사를 먼저 실행했습니다. 그다음 기본 프로파일 getter와 곡선 생산자를 실행했습니다. 일반 생산자는 4DC980, 톤 선택값 6의 전용 생산자는 4DD924입니다. Natural, Bright, Reversal Film은 기존 프로파일 대응에 따른 커스텀 이미지 이름입니다. 메뉴 이벤트는 이 재현에서 실행하지 않았습니다.

  • Bright의 control_c만 중립 값으로 바꾸면 Natural과 같은 곡선이 나옵니다. 톤 선택값을 0↔1로 바꾸는 것만으로는 일반 생산자의 곡선이 바뀌지 않았습니다.
  • Reversal Film의 전용 선택을 뺀 대조도 같은 일반 곡선으로 돌아왔습니다.
  • 초기화 데이터 복사를 생략한 음성 대조는 4DCB68의 주소 4 읽기에서 예상대로 실패합니다.

Reversal Film 메뉴는 기존 Reversal Film 메뉴 분석, Pixel Shift 쪽은 Pixel Shift 메뉴·수명 분석이 별도 근거입니다. 이 문서의 톤 선택값 6을 SuperResolution의 작업 selector와 혼동하지 마십시오.

16,384 제한은 생산자에만 해당합니다

곡선 생산자는 출력을 16,384(0x4000)에서 자릅니다. 그러나 이것을 모든 단계의 포화 처리나 센서 비트 깊이로 일반화할 수 없습니다. 합성 FFFF 입력을 뒤 단계 커널에 넣으면 다음과 같았습니다.

초기화 구간과 곡선별 수치
  • 원본 초기화 데이터 복사: [A84504,A9A3B4) → 404094B0.
  • 16,384에 닿는 원소 수: Natural 36, Bright 40, Reversal Film 16, 문맥 4096 곡선 90. 네 곡선 모두 최솟값 0, 단조 증가.
  • 비교 범위: 곡선 256개, 보간 265개 좌표, 확장 1,280개 halfword.
  • 공개 자료에는 범위 해시, 생성된 곡선과 관측 수치를 담았습니다. ROM 바이트와 전체 명령 hex 배열은 넣지 않았습니다.

한계와 남은 과제

이 문서의 그림은 데이터가 어디서 어디로 가는지를 보여 줍니다. 실제 촬영에서의 작업 순서, 중간 덮어쓰기, 캐시 이력, 픽셀 처리, JPEG 출력은 검증하지 않았습니다.

  • 분리 실행: 네 시험은 서로 다른 VM에서 실행했습니다. 서비스·할당 호출과 실제 큐 순서는 생략했습니다. selector 3 → 4의 실행 순서도 증명하지 않았습니다.
  • 값의 뜻: 생성자 값을 촬영 기본값으로 해석하지 않습니다. EV 단위, Q 형식, 감마도 확인하지 못했습니다.
  • 다음 과제: 실제 촬영에서 같은 작업이 실행되는 순서와 원본 문맥 값이 바뀌는 이력입니다.

입력 쪽은 이어지는 문서에서 더 따라갑니다. 톤 입력의 원본 생산자는 recipe 필드를 쓰는 코드를 다룹니다. recipe+9C 정수 생산자와 내장 입력 복사에는 +9C 생산자의 산술·저장 20조건과 바이트 전달 3조건이 있습니다. 각 문서의 실행 범위는 따로 읽어야 합니다.

재현 방법

실행 검증 환경은 Python 3.12.3과 Unicorn 2.1.4입니다. Python 3.10 문법 검사는 따로 통과했지만 그 버전에서 실행 검증을 한 것은 아닙니다. 복호화 이미지는 사용자가 직접 준비해야 하며 이미지나 ROM 바이트는 저장소에 없습니다.

python -B verify_tone_provenance.py decoded.bin --output tone-result-new.json \
  --compare analysis/tone-provenance.json
python -B -O verify_tone_provenance.py decoded.bin --output tone-result-optimized-new.json \
  --compare analysis/tone-provenance.json
python -B -m unittest discover -s tests -p test_tone_provenance.py

줄 끝의 역슬래시는 줄을 잇는 표시입니다. CLI가 있는 디렉터리와 기존 helper가 있는 체크아웃이 다르면 --repository로 경로를 지정합니다.

검증기가 지키는 조건
  • 소스 고정: inspect_firmware.py, verify_findings.py, verify_tone_path.py, verify_tone_numeric.py와 재현 모듈 네 개를 바이트로 캡처합니다. LF 줄바꿈으로 정규화한 SHA-256을 확인한 뒤 실행합니다.
  • import 격리: 프로젝트 모듈은 전역 import 캐시·pyc·검색 경로에서 가져오지 않습니다. 캡처 뒤 파일이 바뀌어도 다시 읽지 않습니다. 표준 라이브러리와 설치된 Unicorn은 실행 환경 의존성입니다. 이 로더를 범용 보안 샌드박스로 주장하지 않습니다.
  • 실행 검사: 입력 전체 해시, RX 코드 매핑, 모든 실행 명령과 원본 바이트의 일치, 원본 출력 저장 PC와 범위를 확인합니다. 정상 종료한 사례는 실행 뒤 코드 이미지가 그대로인지도 봅니다.
  • 결과 대조: 네 단계의 전체 내부 결과를 수락된 canonical JSON 해시와 먼저 대조한 뒤 공개 관측값으로 줄입니다. JSON 비교는 bool·int·float를 구분합니다. require 검사는 -O에서도 동작하며 Python assert에 검증을 맡기지 않습니다.
  • 출력 보호: 새 경로만 허용하고 기존 파일·별칭·하드링크·심볼릭링크를 거부합니다. 같은 디렉터리의 임시 파일을 기록·동기화한 뒤 배타적 하드링크로 게시하므로, 직전에 다른 프로세스가 목적지를 만들어도 덮어쓰지 않습니다. 기록에 실패하면 임시 파일을 지웁니다. 하드링크를 지원하지 않는 파일시스템에서는 성공으로 처리하지 않습니다. 입력·소스·비교 기준을 덮어쓰는 옵션은 없습니다.
