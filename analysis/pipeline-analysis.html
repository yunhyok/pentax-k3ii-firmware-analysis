영상 처리와 저장 경로 · 색을 정하는 설정

RAW 작업이 톤·화이트 밸런스·색 행렬 설정에 닿는 경로

RAW 데이터가 JPEG가 되려면 밝기 곡선(톤), 화이트 밸런스, 색 행렬이 먼저 정해져야 합니다. 펌웨어가 이 값들을 어디서 읽어 영상 처리 회로의 어느 레지스터에 쓰는지 따라갔습니다.

이 문서에서

  1. 배경: 사진의 색을 정하는 세 가지 설정
  2. RAW 작업은 레시피를 따라 톤 설정 함수에 전달됩니다
  3. 톤 선택값 6은 Reversal Film입니다
  4. 화이트 밸런스 값은 채널 순서를 바꿔 레지스터에 기록됩니다
  5. 색 행렬 세 벌의 준비와 적용
  6. 계수 포화와 픽셀 클립 설정은 다른 것입니다
  7. 한계와 남은 과제
  8. 재현 방법
  9. 근거 파일과 참고 자료

핵심 요약

  • RAW 현상 작업은 작업 목록에 등록된 뒤, 레시피라는 명령 배열에 적힌 순서대로 모듈에 전달됩니다. 원본 레시피 생성 함수를 실행해 11종의 순서를 얻었고, 그중 3종에 RAW 입력·톤·스케일러·저장 단계가 모두 들어 있습니다.
  • 톤 곡선을 고르는 내부 선택값 6은 Custom Image의 Reversal Film입니다. 펌웨어가 이 값을 사진 메타데이터의 ImageTone 값 7로 바꿔 적는 것을 실행해 확인했고, 공개된 메타데이터 정의에서 7이 Reversal Film입니다.
  • 화이트 밸런스 값은 설정 레코드의 채널 순서(RR, GR, GB, BB)와 다른 순서(RR/BB, GR/GB)로 레지스터에 묶여 기록됩니다. 색 행렬은 세 벌이 있고, 그중 한 벌의 계수를 만드는 정수 계산식을 원본 명령 실행 결과와 맞췄습니다.
  • 확인한 범위는 CPU가 설정값을 계산해 레지스터에 쓰는 데까지입니다. 영상 처리 회로가 그 값으로 픽셀을 어떻게 처리하는지, 실제 JPEG의 색이 어떻게 나오는지는 관측하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 레시피 생성 함수로 레시피 11종을 만들고 배열 128개 항목을 판독
  • 톤 선택값 0~10이 ImageTone 태그 값으로 바뀌는 11건, 기본 프로필 42개 조회
  • 화이트 밸런스 8건, 색 행렬 준비·적용 10건, 톤 클립 1건에서 레지스터 영역 4,096바이트 전체 대조
  • 행렬곱 3건과 계수 포화 경계 9개의 출력 대조

정적 분석 코드를 읽어 판단

  • 작업 등록 → 작업자 → 명령 분배 → 색 처리 모듈 → 톤·색 행렬 적용 함수의 호출 관계
  • 톤 완료 메시지 뒤 컨트롤러가 작업을 다시 제출하는 경로
  • StoreImage 수신부, JPEG 코덱, Exif 작성기의 위치

모델 시험 조건으로 정한 것

  • 장치 레지스터 주소에 일반 RAM을 배치
  • 설정 레코드와 계수 값은 직접 만든 합성 값
  • 레시피 생성 시 메모리 할당 함수만 대체

미확인 확인하지 않은 것

  • 영상 처리 회로 안의 픽셀 처리 순서와 수식, 클립의 실제 동작
  • 화이트 밸런스 추정 알고리즘, 1배 게인의 표현
  • 기본 프로필 ID 41의 화면 이름
  • 실제 촬영 JPEG와의 색 대조

배경: 사진의 색을 정하는 세 가지 설정

센서가 기록한 RAW 데이터는 그대로 JPEG가 되지 않습니다. 카메라는 먼저 색과 밝기를 정하는 값을 계산해 영상 처리 회로(ISP)에 넣어 줍니다. 이 문서는 그 값 세 가지를 다룹니다.

이 문서가 따라간 세 가지 설정
설정사진에서 하는 일이 문서의 질문
톤 곡선밝기 값을 다른 밝기 값으로 바꾸는 표입니다. Custom Image(사진의 마무리 느낌)를 바꾸면 곡선이 달라집니다.RAW 작업이 톤 설정 함수까지 어떻게 전달되는가. 내부 선택값 6은 어떤 Custom Image인가.

읽기 전에 알아 둘 용어와 표기

  • 작업(job)과 레시피 — 펌웨어는 사진 한 장의 처리를 작업 객체 하나로 다룹니다. 작업마다 “어느 모듈을 어떤 순서로 부를지” 적은 명령 배열이 붙는데, 이 문서에서는 이를 레시피라고 부릅니다.
  • 모듈 — 레시피가 호출하는 처리 단위입니다. 번호로 구분합니다. 모듈 0은 톤과 색 행렬을 적용하는 색 처리 모듈이고, 같은 주제의 다른 문서에서는 CPP라고 부릅니다.
  • B2Y — 펌웨어의 진단 문자열(IO_B2Y)에 나오는 레지스터 묶음의 이름입니다. 화이트 밸런스, 색 행렬, 톤 레지스터가 여기에 모여 있습니다.
  • 주소 표기 — 코드 주소는 따로 적지 않으면 복호화한 펌웨어 이미지의 파일 오프셋입니다. 분석용 가상 주소는 여기에 0x02000000을 더한 값입니다. 0x2002…로 시작하는 주소는 코드가 값을 쓰는 장치 레지스터 주소입니다.
그림을 읽을 때 주의

이 문서의 화살표는 CPU가 함수를 부르고 값을 넘기는 관계입니다. 영상 처리 회로 안에서 픽셀이 지나가는 순서를 뜻하지 않습니다.

RAW 현상 함수 자체와 톤 곡선을 만드는 계산은 하드웨어 식별과 RAW 현상 개관에서 다룹니다. 이 문서는 그 뒤를 잇습니다.

RAW 작업은 레시피를 따라 톤 설정 함수에 전달됩니다

RAW 현상 함수가 만든 작업은 목록에 등록되고, 작업자가 레시피의 명령을 하나씩 꺼내 모듈로 보냅니다. 색 처리 모듈이 받은 명령은 톤과 색 행렬의 준비·적용 함수로 이어집니다.

작업은 세 단계의 상태를 거칩니다. 생성 함수가 목록에 넣으며 상태 1을 쓰고, 컨트롤러에 제출될 때 상태 2가 됩니다. 작업자는 상태 2인 작업을 골라 상태 3으로 바꾼 뒤 레시피를 처리합니다. 컨트롤러와 RAW 보조 객체가 같은 목록 객체를 가리킨다는 점은 두 객체의 생성 코드에서 확인했습니다.

색 처리 객체의 적용 함수는 상태 바이트에 따라 색 행렬 하위 객체와 톤 하위 객체를 각각 호출합니다. 두 설정을 한 객체가 함께 관리한다는 뜻입니다. 하드웨어 안에서 두 블록이 어떤 순서로 동작하는지, 같은 프레임에서 언제 끝나는지를 말해 주지는 않습니다.

레시피 11종의 단계 순서

번호 체계를 섞지 않기

레시피 ID는 다음 절의 톤 선택값과 다른 번호 체계입니다. 그리고 이 표는 배열에 적힌 순서일 뿐입니다. 실제 스레드와 장치가 모든 조건 분기를 지나 끝까지 실행되는 상황을 돌려 본 것은 아니며, 모든 RAW 작업이 같은 경로를 지난다고 일반화하지도 않습니다.

톤 처리가 끝나면 컨트롤러로 돌아옵니다

톤 수신부는 처리를 마치면 완료 메시지를 컨트롤러에 보냅니다. 컨트롤러는 해당 작업의 모듈 0 완료 상태를 기록하고, 조건이 맞으면 작업을 다시 제출해 레시피의 다음 명령으로 넘어갑니다. 톤 호출에서 끝나지 않고 컨트롤러로 되돌아오는 연결까지 확인했습니다.

JPEG 압축과 파일 출력 쪽에서 이 문서가 확인한 범위

레시피의 끝에는 저장 단계가 있습니다. 이 문서의 근거로는 저장 수신부, JPEG 코덱, Exif 작성기가 각각 어디에 있는지까지 확인했습니다. 세 지점 사이로 영상 버퍼가 넘어가는 연결은 다음 문서에서 다룹니다.

  1. StoreImage 수신부모듈 9가 저장 메시지를 받습니다. StoreImage 진단 문자열이 있는 처리부로 이어집니다.
  2. JPEG 코덱 (모듈 8)DC·AC 허프먼 표를 구성해 장치에 설정합니다. 레시피 11종에는 이 모듈을 직접 부르는 항목이 없습니다.
  3. Exif JPEG 작성기FF D8(SOI), FF E1(APP1), Exif\0\0를 준비하고 출력 객체를 호출합니다.
이어지는 문서

RAW 레시피가 실제로 쓰는 JPEG 모듈은 모듈 8이 아닌 모듈 16이었습니다. 색 처리 출력 → 스케일러 → 모듈 16 → StoreImage → Exif 작성기로 버퍼 주소와 길이가 넘어가는 경로는 JPEG 출력 버퍼와 Reversal Film 메뉴에 있습니다. 레시피에 모듈 8 호출이 없다는 사실은 JPEG 압축이 실행되지 않는다는 뜻이 아닙니다.

톤 선택값 6은 Reversal Film입니다

저장된 설정 레코드의 한 바이트가 톤 곡선 선택과 사진 메타데이터 기록 양쪽에 쓰입니다. 값 6은 톤 쪽에서 전용 곡선 생산자를 고르고, 메타데이터 쪽에서는 ImageTone 7로 바뀌어 기록됩니다.

이름을 메뉴에 나열된 순서에서 짐작하지 않았습니다. 근거는 두 가지입니다.

  1. 펌웨어 안의 값 변환 — 메타데이터 처리기가 태그 0x004F를 기록할 때 선택값 6을 7로 바꿉니다. 태그 분배 함수부터 16비트 값을 쓰는 명령까지 원본 코드로 실행했습니다.
  2. 공개된 태그 정의 — ExifTool의 Pentax 태그 정의에서 0x004F는 ImageTone이고 값 7은 Reversal Film입니다. 리코의 K-3 II 사양도 Custom Image 항목에 Reversal Film을 적고 있습니다.

이 결론은 뒤에 화면 쪽에서도 확인했습니다. 메뉴 이벤트 0x01205010이 설정값 6을 기록하는 경로와 펌웨어에 든 Reversal Film 문자열은 다음 문서의 메뉴 절에 있습니다.

기본 프로필이 돌려주는 선택값

기본 설정을 초기화하는 함수와 프로필 조회 함수를 실행해 프로필 ID 0~41의 기본 선택값을 읽었습니다. ID 0~10은 자기 번호와 같은 선택값을 돌려줍니다. ID 41도 선택값 6을 돌려주는데, 이 프로필이 화면에서 어떤 이름인지는 확인하지 못했습니다.

주의

이것은 초기값을 읽은 결과입니다. 사용자가 카메라에 저장해 둔 현재 설정값과는 다릅니다.

값 6일 때 달라지는 것과 그대로인 것

곡선을 다시 계산해야 할 때, 선택값 6은 일반 곡선 생산자 대신 전용 생산자를 씁니다. 그 뒤의 보간, 곡선 4개 구성, 표 확장, 장치 주소 쓰기는 다른 선택값과 같은 공통 경로입니다. 공통 경로의 계산은 RAW 현상 개관의 톤 절에 있습니다. 전용 생산자의 곡선과 상위 문맥의 정수 계산은 톤 문맥과 곡선 생산자의 연결에서 별도 원본 실행으로 확인했습니다. 실제 JPEG의 색과는 대조하지 않았습니다.

게인이 들어오는 두 경로

게인을 레지스터에 넣는 적용 함수는 하나지만, 값을 가져오는 호출 구간은 둘입니다.

  • 직접 경로 — 설정 레코드의 16비트 게인과 오프셋을 그대로 적용 함수에 넘깁니다.
  • 우측 이동 경로 — 부모 객체에 든 다른 레코드에서 게인 네 개를 읽고, 오른쪽으로 5비트 이동한 뒤 같은 게인 적용 함수에 넘깁니다.

두 경로를 각각 4건씩, 모두 8건 실행했습니다. 입력은 0과 필드 경계값, 필드 폭을 넘는 값, 5비트 이동의 경계값, 채널마다 다른 값입니다. 매번 장치 주소를 대신한 메모리 4,096바이트 전체를 기대값과 비교해, 쓰려던 필드 밖의 비트가 그대로인지도 확인했습니다.

해석의 한계

여기서 확인한 것은 CPU가 필드에 써넣는 값의 변환입니다. 회로가 게인을 곱할 때 소수점이 어디에 있는지, 1배 게인이 어떤 값인지, 광원을 추정하는 알고리즘은 정하지 못했습니다.

펌웨어는 CC0, CC1, YC라는 이름의 3×3 계수 세 벌을 서로 다른 출처에서 준비해 서로 다른 레지스터에 씁니다. CC0은 행렬을 여러 번 곱하고 게인으로 조정한 결과이고, CC1은 저장된 값을 그대로 복사합니다.

CC0, CC1, YC는 펌웨어의 진단 이름입니다. 어느 행렬이 어떤 색 공간 변환을 맡는지는 이 결과만으로 정하지 않았습니다.

CC0 계수를 만드는 계산

  1. 3×3 행렬곱 연속A×B를 구하고, 조건에 따라 ROM 행렬을 한 번 더 곱한 뒤, 셋째 입력 행렬을 곱합니다.
  2. 게인 조정각 계수 × factor ÷ 4,096. 나머지는 0 쪽으로 버립니다.
  3. 대각 성분 재계산대각 = 2 × factor − 같은 행의 나머지 두 계수
  4. 포화와 기록−2,048 이상 2,047 이하로 제한해 12비트 필드에 씁니다.
  • 행렬곱 한 번 — 부호 있는 16비트 값 세 쌍의 곱을 32비트로 더하고, 0x1000을 더한 뒤 오른쪽으로 13비트 밀어 하위 16비트를 남깁니다. 1.0을 8,192로 나타내는 Q13 고정소수점 곱셈에 반올림을 더한 형태입니다.
  • factor — factor = floor(gain × multiplier ÷ 256)입니다. 객체에 든 선택값 0~4가 multiplier 64, 91, 128, 181, 256에 대응하고, 그 밖의 값은 128을 씁니다.
  • 중간값의 폭 — 단계마다 하위 16비트만 남기고 부호 있는 값으로 다시 읽습니다. 이 절단과 부호 해석까지 넣어야 펌웨어 결과와 일치합니다.

대각 성분을 다시 계산하면 행의 합이 맞춰집니다. 그러나 뒤따르는 16비트 절단과 포화를 거친 뒤에도 행의 합이 늘 보존된다고 말할 수는 없습니다.

실행해 확인한 사례

  • 준비와 적용 10건 — multiplier 선택값, 게인, CC1 우회 여부를 바꿔 가며 레지스터 영역 전체를 대조했습니다. 게인이 0이면 CC0 계수가 모두 0이 되고, 게인이 크면 여러 계수가 포화 한계에 닿습니다.
  • 행렬곱 3건 — 반올림이 절반에 걸리는 값, 32비트 누산이 넘치는 값(양수·음수)을 넣었습니다.
  • 포화 경계 9개 — −32,768, −2,049, −2,048, −2,047, −1, 0, 2,047, 2,048, 32,767을 넣어 −2,048과 2,047에서 잘리는 것을 확인했습니다.
  • CC1 제어값 — CC1의 제어값이 0이 아니면 제어 비트만 기록하고 계수와 클립 설정을 건너뜁니다. 이 분기도 실행했습니다.

필드 폭이 알려 주지 않는 것

쓰기 명령에서 알 수 있는 것은 값이 들어가는 비트 위치와 폭입니다. 회로가 픽셀과 비교할 때 부호를 어떻게 다루는지, 두 값 중 어느 쪽이 상한이고 하한인지, 클립이 톤 처리보다 먼저 일어나는지는 알 수 없습니다.

펌웨어에는 TCYC와 CCYC_CLP라는 서로 다른 이름이 있습니다. 확인하지 못한 TCYC_CLP라는 이름을 새로 붙이지 않았습니다.

한계와 남은 과제

  • 회로 안의 동작 — 레지스터 주소에는 일반 RAM을 놓았습니다. 실행 결과는 CPU 명령이 값을 어떻게 바꿔 어디에 쓰는지를 보여 줄 뿐, 영상 처리 회로가 프레임을 처리하는 데 성공했다는 증거가 아닙니다.
  • 실제 사진과의 대조 — 최종 JPEG의 픽셀이 일치하는지, 회로 안에서 감마와 클립이 어떤 순서로 적용되는지 정하려면 같은 장면의 RAW·JPEG 쌍과 촬영 설정, 장치에서 관측한 완료 이벤트와 레지스터 값이 필요합니다.
  • 부품 식별 — 보드 사진이나 실제 칩 식별값이 없어 SoC와 보조 MCU의 정확한 부품 번호는 하드웨어 식별 절의 미확정 상태 그대로입니다.
  • 프로필 ID 41 — 기본 선택값 6을 돌려주지만 화면 이름을 모릅니다.

추적 방법은 K-3 Mark III 연구에서 쓴 것과 같습니다. 설정값을 따라가고, 수신 객체와 가상 함수표를 잇고, 정수 연산을 실행해 대조했습니다. 다만 모드 번호, 주소, 칩 구조는 K-3 II 이미지에서 따로 확인했습니다. K-3 Mark III의 UI 값 6이나 공통 모드 번호를 이 문서의 선택값 6에 대입하지 않았습니다(비교한 K-3 Mark III 모드 분석).
