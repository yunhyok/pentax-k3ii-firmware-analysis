재구축과 업데이트 · 2단계 전송과 기록

검사를 통과한 이미지가 전송·기록되는 절차와 오류 처리

업데이트 파일이 검사를 통과한 뒤에는 실제로 옮겨 적는 단계가 이어집니다. 이 단계가 어떤 순서로 진행되고, 도중에 문제가 생기면 코드가 어떻게 반응하는지 조사했습니다.

이 문서에서

  1. 배경: 검사 다음에 벌어지는 일
  2. 보조 이미지: 전송 오류는 즉시 실패, 내용 불일치만 다시 시도
  3. 주 이미지: RAM에 복사된 송신기가 기록 명령을 보냅니다
  4. 프로그램 오류 2는 응답에 남지 않고 다시 비교가 불일치를 잡습니다
  5. 실제 갱신 순서: 섹터 13~22는 건너뛰고 섹터 0은 마지막
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 보조 이미지는 64바이트씩 960번 전송한 뒤 전체를 다시 읽어 비교합니다. 전송이나 읽기가 실패하면 바로 포기하고 내용이 다를 때만 처음부터 다시 보냅니다(시도는 모두 3회까지).
  • 주 이미지는 128 KiB 섹터 단위로 “비교 → 지우기 → 프로그램 → 다시 비교” 순서로 기록합니다. 섹터 13~22는 건너뛰고 첫 섹터(섹터 0)를 맨 마지막에 처리합니다.
  • 프로그램 함수가 실패를 뜻하는 값 2를 돌려줘도 그 값은 요청한 쪽에 전달되지 않습니다. 대신 기록 뒤의 다시 비교 단계가 내용 불일치를 알려 줍니다.
  • 모두 PC 에뮬레이터의 합성 메모리에서 실행한 43건입니다. 직렬 통신과 플래시 상태는 연구자가 넣은 값이며 실제 장치에 기록하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 보조 이미지 제어 함수의 전송·읽기·비교·재시도 판단(7건)과 직렬 함수가 보내는 바이트 순서(4건)
  • 주 이미지 송신기·수신기·기록 명령 함수의 요청, 응답, 메모리 쓰기 순서(9건)
  • 기록 제어 함수의 판단: 일반 쓰기 7건, 갱신 진입 2건, 블록 5건, 섹터 순서 6건, 재시도 3건

정적 분석 코드를 읽어 판단

  • 함수들이 서로를 부르는 관계(분기 30개)
  • 직렬 읽기의 오류값 0x10004가 “오류 4, 단계 1”을 합친 값이라는 해석

모델 시험 조건으로 정한 것

  • 직렬 포트, 동기화, 핸드셰이크, GPIO 함수는 대체
  • 플래시 상태 함수는 연구자가 0 또는 1을 넣음. 플래시 영역은 평범한 RAM
  • 계층별 시험에서는 아래 계층의 반환값을 직접 공급
  • 두 CPU 문맥을 차례로 실행(동시 실행·캐시는 재현하지 않음)

미확인 확인하지 않은 것

  • 보조 이미지를 받는 쪽의 코드와 실제 기록 위치
  • 실제 플래시에서 기록 오류가 어떻게 나타나는지
  • 전원이 끊겼을 때의 복구, 설치 뒤 부팅
  • 섹터 13·22를 추가로 쓰는 분기에 도달하는 조건

배경: 검사 다음에 벌어지는 일

앞 문서에서 업데이트 코드가 파일의 길이·표식·합계를 확인한다는 것을 보았습니다. 검사를 통과하면 코드는 두 이미지를 서로 다른 방법으로 옮겨 적습니다.

  • 보조 이미지(60 KiB) — 직렬 통신으로 다른 쪽에 보냅니다. 받는 쪽이 무엇인지는 이 연구에서 추적하지 못했습니다. 이미지의 내용이 8비트 MCU용 코드로 보인다는 근거는 하드웨어 식별 문서에 있습니다.
  • 주 이미지(16 MiB) — 카메라의 NOR 플래시에 섹터 단위로 기록합니다. 기록 중에는 플래시에 있는 코드를 믿을 수 없으므로, 기록을 맡은 코드는 먼저 RAM으로 복사된 뒤 실행됩니다.
주소 표기

코드 위치는 복호화한 파일의 오프셋입니다. 실행·데이터 주소에는 VA를 붙였습니다. RAM에 복사되는 코드는 파일 0xB324부터가 VA 0x40304000부터에 놓이므로, 이 구간의 함수는 파일 오프셋으로 부르되 실제 실행은 RAM에서 했습니다.

보조 이미지: 전송 오류는 즉시 실패, 내용 불일치만 다시 시도

보조 이미지 제어 함수는 “전송이 안 됨”과 “보낸 것과 읽은 것이 다름”을 다르게 다룹니다. 앞의 경우는 한 번에 포기하고 뒤의 경우만 처음부터 다시 보냅니다.

이 경로는 검사 직후의 호출 0x5D663C에서 시작해 0x5D633C를 거쳐 제어 함수 0x5D5370으로 들어갑니다. 제어 함수가 보내는 것은 이미지 시작점에 0x1000000을 더한 위치, 곧 보조 이미지입니다. 주 이미지의 기록까지 이 경로로 설명하면 안 됩니다.

다시 읽은 내용은 배포 파일 바로 뒤의 버퍼(시작점 +0x100F000)에 놓입니다. 그래서 업데이트 코드는 처음부터 파일 크기에 수신 버퍼를 더한 0x101E000바이트를 요청합니다.

주 이미지: RAM에 복사된 송신기가 기록 명령을 보냅니다

주 이미지 기록은 메일박스 명령 세 개(비교 8, 지우기 9, 프로그램 0xA)로 이루어지고 명령을 받는 쪽의 기록 함수가 플래시에 명령 바이트를 써 넣습니다.

송신기는 처음부터 RAM에 있지 않습니다. 함수 0x73CFF4를 실행하면 파일 0xB324부터 0x62C바이트가 VA 0x40304000으로 복사됩니다. 복사 결과를 원본과 바이트 단위로 대조한 뒤, 실제 래퍼 함수에서 이 RAM 송신기로 들어갔습니다. 요청과 응답은 합계 명령 7에서 본 것과 같은 공유 슬롯을 씁니다.

이 바이트 순서는 AMD·Spansion 계열 NOR 플래시의 표준 명령 집합과 모양이 같습니다. 예를 들어 S29GL-N 데이터시트의 명령 정의 표와 U-Boot의 CFI 플래시 상수에 같은 값이 나옵니다. 그러나 이 명령 집합은 여러 제조사가 함께 쓰고 예로 든 S29GL-N은 한 번에 16워드까지만 버퍼에 쓰므로 여기서 본 128개와 다릅니다. 이 패턴만으로 제조사나 부품 번호를 정하지 않았습니다.

프로그램 오류 2는 응답에 남지 않고 다시 비교가 불일치를 잡습니다

비교와 지우기는 함수의 결과가 요청한 쪽에 그대로 전달됩니다. 프로그램만 다릅니다. 수신기가 프로그램 함수의 반환값을 응답 칸에 적지 않습니다.

상태 함수 0xD9CD0에 실패값 0을 주면 프로그램 함수 0xD9EB4는 첫 블록 뒤에 멈추고 2를 반환합니다. 그런데 수신기에서 이 함수를 부르는 0xDA2A8의 바로 다음 명령은 R0에 0xA를 넣는 명령입니다. 비교·지우기 분기와 달리 반환값을 결과 칸에 저장하는 명령이 없습니다. 수신기가 요청을 처리하기 전에 결과 칸을 0으로 지워 두었으므로, 송신기는 완료 표시 0xA와 결과 0을 받습니다. 성공 사례와 실패 사례 모두에서 같은 응답을 확인했습니다.

그렇다고 실패가 묻히는 것은 아닙니다. 기록을 지휘하는 두 제어 함수는 프로그램 응답이 0이면 내용을 다시 비교합니다. 이 비교가 3을 돌려주면 제어 함수도 3을 반환합니다.

비교 3, 프로그램 0, 재비교 3합 → 비교 → 지우기 → 프로그램 → 비교3
비교 3, 프로그램 0, 재비교 0합 → 비교 → 지우기 → 프로그램 → 비교0

준비 버퍼는 VA 0x40459204입니다. 이미 내용이 같으면 합 검사 결과와 상관없이 0을 반환하고 합 검사가 3이면서 내용이 다르면 지우지 않고 3을 반환합니다. “프로그램 2” 사례는 제어 함수의 판단만 본 것입니다. 실제 수신기는 위에서 본 대로 2를 전달하지 않습니다.

두 제어 함수는 진입점이 다른 별개의 함수입니다. 블록 제어 함수는 대상 VA에서 0x02000000을 빼고 최하위 비트를 지운 값에 이미지 포인터를 더해 원본 버퍼의 위치를 고릅니다.

주의

프로그램 오류와 내용 불일치가 실제 플래시에서 어떻게 나타나는지는 확인하지 않았습니다. 위 결과는 상태 함수에 0 또는 1을 넣었을 때 원본 코드가 내린 판단입니다.

  • 수신기의 해당 명령: 0xDA2A8(프로그램 함수 호출), 0xDA2AC(R0 ← 0xA), 0xDA2B0(분기). 비교는 0xDA278, 지우기는 0xDA28C에서 호출합니다.
  • 일반 섹터 쓰기 함수의 호출: 0x599930 → 0x63013C(합), 0x599944·0x5999A0 → 0x63015C(비교), 0x599970 → 0x630114(지우기), 0x599988 → 0x63011C(프로그램).
  • 블록 제어 함수의 호출: 0xC010·0xC078 → 0xB358(비교), 0xC02C → 0xB3E8(지우기), 0xC050 → 0xB468(프로그램).
  • 근거는 installation.json의 program_poll_success, program_poll_failure, primary_control, actual_updater입니다.

실제 갱신 순서: 섹터 13~22는 건너뛰고 섹터 0은 마지막

일반 업데이트는 주 이미지의 128개 섹터 가운데 118개만 다시 씁니다. 가운데 10개는 손대지 않고 맨 앞 섹터는 나머지가 모두 성공한 뒤에 씁니다.

보조 이미지 함수가 1을 돌려준 정상 경로에서는 래퍼 0x630174를 거쳐 RAM의 갱신 진입 함수 0xC278에 인수 (2, 0)이 전달됐습니다. 이 함수와 그 아래 함수도 RAM 코드입니다. 앞서 함수 0x73CF94가 파일 0xB950부터 0xEF6E까지를 VA 0x4030462C로 복사합니다.

  • 건너뛰는 섹터 — 섹터 13~22는 일반 업데이트가 덮어쓰지 않고 남겨 두는 영역입니다. 섹터 13과 22는 설정 저장 문서에서 설정 사본으로 확인했습니다. 섹터 14~21에서 읽는 레코드는 촬영 준비·보존 레코드 안내의 문서들이 다룹니다.
  • 오류 전파 — 섹터 하나가 실패하면 순회를 바로 끝내고 그 값을 반환합니다. 섹터 1에 실패를 넣으면 섹터 1만 처리하고 3을 반환했습니다.
  • 전체 재시도 — 갱신 진입 함수는 순회 전체를 최대 16회 시도합니다. 실패를 0회·1회·16회 넣었을 때 시도 횟수는 1·2·16이었습니다. 이 시험은 마지막 MMIO·전원 제어 루프에 들어가기 전에 멈췄습니다.

둘째 인수가 1인 별도 분기

둘째 인수가 1이면 기본 순회 뒤에 섹터 13과 22를 추가로 처리하고 나서 섹터 0으로 갑니다. 이때 섹터 13의 반환값은 검사하지 않고 섹터 22의 결과로 덮어씁니다. 섹터 13에만 실패를 넣은 사례에서도 섹터 22와 0까지 진행해 최종 0을 반환했습니다. 일반 업데이트는 인수 0을 쓰므로 이 분기와 구분해야 합니다. 사용자가 어떤 조작으로 이 분기에 도달하는지는 확인하지 않았습니다.

한계와 남은 과제

  • 전체 설치를 실행한 것이 아닙니다. 각 층의 판단을 따로 실행했고 층과 층 사이는 반환값을 공급해 이었습니다. 원본 코드가 내린 판단은 확인했지만 처음부터 끝까지 이어진 플래시 기록 모형은 아닙니다.
  • 플래시 상태 함수를 대체했습니다. 물리적으로 기록이 성공한다는 주장은 하지 않습니다.
  • 보조 이미지를 받는 쪽의 코드와 그쪽 플래시의 위치는 추적하지 못했습니다. 태그 0xF0은 보내는 쪽에서만 확인했습니다.
  • 보존 영역 가운데 설정 사본(섹터 13·22) 밖의 의미, 전원이 끊겼을 때의 복구, 설치 뒤의 부팅 경로는 이 문서의 범위 밖입니다.
  • 두 CPU 문맥을 차례로 실행했으므로 실제 동시 실행의 타이밍과 캐시 일관성은 재현하지 않았습니다.

이 결과는 재포장과 검사 다음 단계의 제어 흐름을 좁힌 것입니다. 카메라가 업데이트를 받아들이고 부팅해 촬영하는지는 별개의 과제로 남아 있습니다.
