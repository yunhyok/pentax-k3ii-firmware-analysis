색공간 메뉴 요청이
화면 할당에 도달하는 조건

앞선 색공간 메뉴 검증에서 남아 있던 알림 소비자를 연결했다. 원본 상태가 메뉴 필터에 복사되는 과정과 대기 레코드의 갱신 조건을 확인하고, 작업 루프의 일부 구간을 이어 실제 전환 함수가 화면 할당을 요청하는 지점까지 실행했다. 물리 버튼·RTOS 전달·화면 생성 완료는 이번 검증에 포함하지 않았다.

앞선 색공간 메뉴필터 값 생산알림 수신작업과 전환재현 범위연구 상태

주소는 해제 파일 오프셋이다. 객체 필드는 app+0x14B4처럼 표기했다. 키·이벤트·화면 ID는 K-3 II 펌웨어 내부 값이며 다른 모델에 그대로 적용하는 이식 규약이 아니다.

1. 공유 상태와 메뉴 필터 값은 서로 다른 시점에 바뀐다

상태 제공자의 원본 초기화는 두 뱅크의 13바이트 데이터 영역을 0으로 만든다. 서비스의 +0x54에서 가져온 같은 객체가 읽기 문맥의 +0x28과 쓰기 객체의 +0x18에 연결된다. 키 0x1D의 표 항목은 데이터 오프셋 6·마스크 0x04·시프트 2이며 4바이트 헤더를 포함한 객체 위치는 +0xA다. 상태 제공자 연결과 키 표

인수 1을 주는 원본 호출은 활성 데이터의 0xA3을 반대 뱅크의 0xA7로 바꿨다. 이웃 비트는 유지됐지만 app+0x14B4는 그대로였다. 초기화 구간 0x30A3A8…0x30A3D0을 실행한 뒤에야 필터 값이 1이 됐다. 반대로 상태를 0으로 지운 뒤에도 애플리케이션이 다시 복사하기 전까지 필터 값 1이 남았다. 원본 쓰기·뱅크 전환·필터 대조

이벤트 0x0112005E는 0x30AF2C를 거쳐 필터 값을 0으로 지우지만 공유 상태의 키는 바꾸지 않았다. 또한 app+0x59 = 1이고 요청 대상이 0xBE이면 필터 값 1보다 앞선 조건에서 거부했다. 따라서 이 바이트를 모든 메뉴의 허용 여부로 해석하지 않았다. 값이 0인 B4 거부 사례도 후속 상태 조건을 따로 준비한 경우의 결과다. 필터 경로별 실행 결과

실행 중 갱신 경로도 있다. 원본 가상 호출 0x3097E8은 0x2FE2F8로 이어지며 검사한 조건에서 키 0x1D = 1이고 별도 키 0x52를 signed 32비트로 읽은 값이 양수일 때 0x2FE498이 필터 값 1을 기록했다. 0·양수·0xFFFFFFFF를 포함한 다섯 조합을 대조했다. 이 경로는 현재 화면 ID 0에서 실행했고 이후 ID 0x42를 별도로 준비했으므로, 두 상태가 실기에서 함께 성립한다고 주장하지 않는다. 실행 중 설정 분기

2. 원본 알림 수신자는 app+0xB0에 요청을 보관한다

상위 화면 ID 0x42의 색공간 항목 0x0140B043은 논리 동작 0x1D에서 대상 0xB4를 요청한다. 화면의 +0xC4는 레지스트리의 원본 연결 코드가 app+0x4C로 설정한다. 이 보조 인터페이스의 실제 가상 함수 0x30BE40은 원래 app 포인터를 복원하고 0x2FB408 필터를 호출한 뒤 0x30B904로 넘겼다. 기존 메뉴 의미·위젯 검증 · 실제 가상 함수·연결 코드

같은 앱 상태에서 원본 이벤트로 필터 캐시만 지우면 상위 메뉴 동작은 큐 기록 전에 거부되고 깨움 0x2만 요청했다. 원본 스냅샷으로 캐시를 다시 채운 뒤에는 아래 경로가 실행됐다. 대기 레코드가 비어 있으면 대상·출발 화면·종류·동작과 부가 인수를 기록한다. 이미 요청이 있으면 종류 1이면서 동작 0x0B 또는 0x2E인 경우에만 바꾼다. 실제 색공간 동작 0x1D는 기존 요청을 덮어쓰지 않았다. 이 경우에도 수신자는 깨움 0x800을 요청했다. 가상 함수 앞에서 추가로 관찰한 깨움 비트는 0x2다. 빈 슬롯·점유 슬롯과 직접 갱신 조건 대조

3. 복사할 필드와 전환을 허용하는 조건이 따로 있다

0x32B710은 대상·출발 화면·종류·동작·1바이트 인수·두 워드 인수만 복사한다. 레코드 전체 24바이트를 복사하지 않으며 첫 4바이트와 패딩은 유지한다. 깨움 비트맵에 0을 주입한 대조에서는 대기 요청이 남고 처리 중 레코드가 초기화됐다. 뒤의 분기에서는 별도 레코드 app+0x98에 대상이 있으면 app+0x68보다 우선했다. 패딩 대조값·비트 분기·우선순위 검증

전환 함수 0x3099A0은 원본 사전 처리 0x2F8A84와 허용 판정 0x2F915C를 호출한다. 검사한 상태에서는 대상 B4와 출발 화면 42가 유지됐고 레지스트리 조회가 0x6D9E7C로 이어졌다. 할당 함수 0x712828 입구에서 크기 0xE8과 복귀 위치 0x6D9E84를 관찰했다. 이 복귀 위치의 다음 호출이 색공간 화면 생성자 0x4377A0다. 이번 실행은 생성자까지 완료하지 않았다. 같은 요청 레코드의 전환·할당 경계

허용 판정에는 app+0x56도 관여한다. 작업 루프의 원본 명령은 주입한 깨움 비트 0x8에서 이 바이트를 1로 쓰고 0x10에서는 0으로 썼다. 0인 대조는 전환 함수에서 거부됐다. 0x8 구간은 뒤의 가상 호출 전에, 0x10 구간은 직접 알림 호출 0x309E18 전에 각각 멈췄으며 해당 깨움 비트를 실제 장치 이벤트와 연결한 결과는 아니다. 사전 처리에 사용한 별도 상태 제공자·가드·0값 입력도 검증기에 명시했다. 허용 바이트의 원본 저장과 실행 한계

4. 메뉴 의미의 이식에 쓸 수 있는 범위

python verify_ui_dispatch.py decoded.bin --compare analysis/ui-dispatch.json

공개 검증기는 원본 해시·분기·가상 함수 표·키 표를 확인한 뒤 Unicorn에서 실행한다. 상태 제공자의 초기 할당, 상태 변경 뒤 알림, 깨움 요청과 레지스트리 잠금은 명시한 대체 경계다. 필터의 생산자와 메뉴 요청·처리 중 레코드는 같은 객체에서 연결해 검사하며 실행 중 설정의 별도 조건 실험은 구분해 기록했다. 검증기 · 실행 결과와 대체 함수 목록

다른 모델과 비교할 때는 메뉴 항목의 의미, 적용·취소 동작, 대기 레코드 정책, 상태를 복사하는 시점을 비교할 수 있다. K-3 III·Q7의 숫자 ID와 객체 배치는 각 펌웨어에서 다시 확인해야 한다. 이번 결과는 물리 입력, 전체 작업 루프, 생성자 이후 UI 초기화, LCD 렌더링과 실제 카메라에서의 동시 도달 조건을 검증한 이식 결과가 아니다. 목표별 진행 상태
