메뉴와 UI · 알림에서 화면 할당 요청까지

색공간 메뉴 요청이 화면 전환으로 이어지는 조건

메뉴 항목이 새 화면을 요청하면 펌웨어는 몇 가지 조건을 확인한 뒤에야 화면을 만듭니다. 색공간 항목의 요청이 걸러지고, 대기하고, 화면을 만들라는 요청으로 바뀌기까지를 추적했습니다.

이 문서에서

  1. 배경: 요청이 지나가는 길과 용어
  2. 필터가 보는 값은 공유 상태를 복사해 둔 값입니다
  3. 필터를 통과한 요청은 대기 레코드에 적힙니다
  4. 작업 구간이 레코드를 옮기고 전환 함수가 화면 할당을 요청합니다
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 색공간 메뉴 문서에서 비워 두었던 “알림을 받는 쪽”을 원본 코드로 이었습니다. 상위 메뉴의 요청은 필터 → 대기 레코드 → 처리 중 레코드 → 전환 함수를 거쳐, 색공간 화면에 쓸 메모리 232바이트를 요청하는 지점까지 갔습니다.
  • 필터는 앱 객체에 복사해 둔 1바이트를 봅니다. 원본인 공유 상태가 바뀌어도, 앱이 다시 복사하기 전에는 예전 값으로 판단합니다.
  • 요청은 대기 레코드에 적혔다가, 작업 루프가 깨움 신호를 확인하면 처리 중 레코드로 옮겨집니다. 대기 레코드가 이미 차 있으면 색공간 요청은 기존 요청을 덮어쓰지 않습니다.
  • 전환 함수는 허용 판정을 통과해야 화면 등록부를 부릅니다. 판정에 쓰이는 바이트 하나는 다른 깨움 신호가 1이나 0으로 바꿉니다.
  • 깨움 신호는 직접 넣었고, 작업 구간 사이의 스케줄링은 실행하지 않았습니다. 실제 버튼, RTOS의 전달, 화면 생성 완료는 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 알림 경로의 함수 다섯 개와 대기 레코드에 적힌 값
  • 필터 사례 9건, 실행 중 갱신 조건 5건
  • 대기 레코드에서 처리 중 레코드로의 필드 복사와 초기화
  • 전환 함수의 등록부 조회와 할당 함수 입구의 요청 크기

모델 시험 조건으로 정한 것

  • 상위 메뉴 동작을 함수 입구에 직접 전달
  • 깨움 값을 직접 넣고 작업 구간 사이의 코드는 건너뜀
  • 깨움 요청, 등록부 잠금, 초기 할당, 상태 변경 알림은 대체 코드
  • 앱 객체, 화면 등록부, 사전 처리용 상태는 준비한 메모리

미확인 확인하지 않은 것

  • 물리 버튼, RTOS가 작업을 깨우는 과정
  • 화면 생성자 이후의 초기화와 표시
  • 이 조건들이 실기에서 동시에 성립하는지
  • 다른 기종의 번호와 객체 배치

배경: 요청이 지나가는 길과 용어

색공간 메뉴 문서는 두 구간을 따로 확인했습니다. 상위 메뉴 항목이 화면 0xB4를 요청하는 알림을 내는 구간과, 화면 등록부가 색공간 화면 객체를 만드는 구간입니다. 그 사이에서 알림을 받아 등록부를 부르는 쪽은 검증용 코드로 대신했습니다. 이 문서는 그 사이를 원본 코드로 채웁니다.

앱 객체
메뉴 화면의 요청을 받아 화면 전환을 처리하는 펌웨어 객체입니다. 이 문서에서는 필드를 app+0x14B4처럼 적습니다.
화면 등록부
화면 ID마다 화면 객체의 주소를 보관하는 표입니다. 현재 화면의 ID도 여기에 있습니다.
공유 상태
여러 객체가 함께 읽는 13바이트짜리 상태 묶음입니다. “키” 번호로 그 안의 비트나 바이트를 가리킵니다. 이 문서의 주인공은 키 0x1D입니다.
레코드
화면 전환 요청 하나를 적는 24바이트 기록입니다. 대상 화면, 출발 화면, 종류, 동작, 인수가 들어갑니다.
깨움 값
작업 루프에 “할 일이 생겼다”고 알리는 비트 묶음입니다. 이 문서에는 0x2, 0x8, 0x10, 0x800, 0x80000000이 나옵니다.
주소 표기
코드와 표의 위치는 복호화한 펌웨어 파일의 오프셋입니다. 키, 동작, 화면 ID는 K-3 II 펌웨어 1.12의 내부 값입니다.

필터가 보는 값은 공유 상태를 복사해 둔 값입니다

메뉴 필터는 앱 객체의 1바이트 캐시를 읽습니다. 공유 상태의 키 0x1D를 바꿔도, 앱이 다시 복사하기 전에는 캐시가 따라 바뀌지 않습니다.

아홉 가지 상황에서 필터가 낸 결과

같은 앱 객체와 공유 상태를 두고 아래 순서로 상태를 바꿔 가며 필터를 불렀습니다. 필터는 요청을 통과시키면 대상 화면 ID를, 거부하면 0을 돌려줍니다.

주의

캐시 바이트를 “모든 메뉴의 허용 여부”로 읽으면 안 됩니다. 캐시가 0일 때 필터는 바로 거부하지 않고 뒤의 조건으로 넘어갑니다. 위 표의 거부는 그 뒤 조건에 쓰이는 값을 따로 준비한 상태(app+0x18C = 6, app+0x198 = 0)에서 나온 결과입니다.

실행 중에 캐시를 1로 만드는 경로

복사 구간 말고도 캐시를 1로 만드는 경로가 있습니다. 앱 객체의 가상 호출이 갱신 함수로 이어지고, 키 0x1D가 1이면서 키 0x52를 부호 있는 32비트로 읽은 값이 양수일 때만 캐시에 1을 기록했습니다.

필터를 통과한 요청은 대기 레코드에 적힙니다

알림 수신자는 요청을 app+0xB0의 대기 레코드에 적고 깨움 0x800을 요청합니다. 대기 레코드에 이미 요청이 있으면 색공간 요청은 덮어쓰지 않습니다.

메뉴 화면은 자신의 +0xC4 필드에 들어 있는 창구로 알림을 보냅니다. 화면 등록부의 연결 코드는 이 필드에 app+0x4C, 즉 앱 객체의 보조 인터페이스를 넣습니다. 보조 인터페이스의 함수는 앱 객체의 원래 주소를 되찾은 뒤 필터를 부르고, 통과하면 대기 레코드 기록 함수로 넘깁니다.

이미 요청이 있을 때 덮어쓰는 조건

기록 함수를 직접 불러, 대기 레코드가 차 있을 때 어떤 요청이 기존 요청을 바꾸는지 확인했습니다. 종류가 1이고 동작이 0x0B 또는 0x2E인 요청만 덮어썼습니다.

알림 경로와 연결 코드의 위치
  • 알림 경로: 0x4A5888(상위 화면 처리기) → 0x6D5FF0 → 0x30BE40(보조 인터페이스의 함수) → 0x2FB408(필터) → 0x30B904(대기 레코드 기록). 동작은 공통 진입점 0x6D5F38에 넣었습니다.
  • 보조 인터페이스의 가상 함수 표는 0xA63DC4이고, 0xA63DCC의 항목이 0x30BE40을 가리킵니다.
  • 화면의 +0xC4에 app+0x4C를 넣는 등록부 연결 코드는 구간 0x6DA188–0x6DA1A4입니다.
  • 상위 메뉴의 위젯 0x0140B043은 표 위치 0x9B48DC에, 분류 13의 경로 행은 0x9B5EF4에 있습니다.
  • 깨움 요청 함수 0x70C3CC는 받는 쪽(app+0x14D4)과 깨움 값을 기록하고 0을 돌려주는 코드로 대신했습니다.
  • 덮어쓰기 사례에서는 인수로 0x33, 0x11223344, 0x55667788을 넣어 1바이트 인수와 두 워드 인수가 제자리에 적히는지도 확인했습니다. 모든 사례에서 레코드의 첫 워드와 빈 자리는 그대로였습니다.

작업 구간이 레코드를 옮기고 전환 함수가 화면 할당을 요청합니다

깨움 0x800을 넣은 작업 구간은 대기 레코드의 필드를 처리 중 레코드로 복사합니다. 전환 함수는 허용 판정을 통과하면 화면 등록부를 불러, 색공간 화면에 쓸 0xE8바이트를 요청합니다.

깨움 값에 따라 달라지는 복사와 초기화

복사 함수는 레코드 24바이트를 통째로 복사하지 않습니다. 대상, 출발 화면, 종류, 동작, 1바이트 인수, 두 워드 인수만 옮기고, 첫 워드와 빈 자리는 건드리지 않습니다. “초기화”는 대상을 0, 종류를 0x17, 나머지 필드를 0으로 만드는 것입니다.

작업 구간에 넣은 깨움 값과 관찰한 결과
넣은 깨움 값관찰한 결과

전환 함수가 화면 할당을 요청하기까지

  1. 전환 함수 진입 작업 구간의 진입 부분이 처리 중 레코드의 주소를 전환 함수에 넘깁니다. app+0x98의 레코드에 대상이 들어 있으면 처리 중 레코드 대신 그 레코드를 넘겼습니다.
  2. 사전 처리와 허용 판정 전환 함수는 사전 처리 함수와 허용 판정 함수를 차례로 부릅니다. 준비한 상태에서 대상 0xB4와 출발 화면 0x42는 그대로 유지됐고 판정은 허용(1)이었습니다.
  3. 화면 등록부 조회 등록부 조회 함수가 두 번 불렸습니다. 첫 번째는 현재 화면 0x42, 두 번째는 대상 화면 0xB4입니다. 대상 화면은 아직 등록부에 없었습니다.
  4. 할당 요청에서 정지 등록부는 할당 함수를 크기 0xE8(232바이트)로 불렀습니다. 실행은 할당 함수 입구에서 멈췄습니다. 할당 함수가 돌아갈 위치 바로 다음 호출이 색공간 화면 생성자입니다.

허용 판정에는 app+0x56이 관여합니다. 깨움 0x10 구간을 실행해 이 바이트를 0으로 만든 뒤 전환 함수를 부르면, 판정이 거부(0)로 나오고 등록부 조회 없이 끝났습니다.

시험 조건

깨움 값은 작업 구간에 직접 넣었습니다. 깨움 0x8과 0x10을 실제 장치 이벤트와 연결한 것이 아닙니다. 깨움 0x8 구간은 뒤에 오는 가상 호출 전에, 깨움 0x10 구간은 알림 호출 0x309E18 전에 멈췄습니다. 사전 처리가 읽는 값도 준비해 넣었습니다. 키 0x17을 읽는 별도 상태 제공자의 13바이트와 문맥 객체의 두 바이트는 0으로, 초기화 완료 플래그는 켜진 상태로 두었습니다.

한계와 남은 과제

이 문서는 “조건이 이렇게 준비되면 원본 코드가 이렇게 움직인다”는 것까지 확인했습니다. 실제 카메라에서 그 조건이 언제 만들어지는지는 다루지 못했습니다.

  • 입력 — 상위 메뉴 동작은 함수 입구에 직접 넣었습니다. 버튼이 이 동작으로 바뀌는 과정은 확인하지 않았습니다.
  • 작업 루프 — 깨움 값을 넣은 구간만 따로 실행했습니다. RTOS가 깨움 요청을 작업에 전달하는 과정과 구간 사이의 코드는 실행하지 않았습니다.
  • 화면 생성 — 할당 함수 입구에서 멈췄습니다. 생성자를 따로 실행한 결과는 색공간 메뉴 문서에 있지만, 두 실행을 하나로 잇지는 않았습니다. 생성 뒤의 초기화와 LCD 표시도 실행하지 않았습니다.
  • 조건의 동시 성립 — 필터 캐시, 허용 바이트, 현재 화면 ID는 각각 준비한 값입니다. 실기에서 이 값들이 함께 성립하는 시점은 확인하지 않았습니다.

다른 기종과 비교할 때 쓸 수 있는 것

비교할 수 있는 것은 동작의 뜻입니다. 메뉴 항목이 무엇을 요청하는지, 요청을 대기시키는 규칙, 상태를 복사하는 시점이 여기에 해당합니다. 키 번호, 화면 ID, 객체 필드 위치는 K-3 II 펌웨어의 내부 값이므로, K-3 III와 Q7에서는 각 펌웨어에서 다시 확인해야 합니다. 이 문서는 이식한 결과가 아닙니다. 세 기종 비교는 K-3 III 저장소의 UI 이식 설계에 있습니다.

재현 방법

검증기는 복호화한 펌웨어 파일 decoded.bin을 입력으로 받습니다(펌웨어 파일 구조와 복호화). 에뮬레이터는 Unicorn 2.1.4이고 CPU 모델은 Cortex-A9입니다.

python verify_ui_dispatch.py decoded.bin --compare analysis/ui-dispatch.json
