두 실험의 경계

결과 수집 실험과 DMA 준비 실험을 분리해 재현했다. 첫 실험에서는 공급한 레지스터 스냅샷을 원본 코드가 읽는 과정을 확인한다. 둘째 실험에서는 원본 코드가 만든 기본 버퍼 주소가 DMA 설정 패킷까지 전달되는지 확인한다. 첫 DMA 레지스터 읽기 직전에 실행을 멈춘다. 두 실험을 하나의 실제 촬영 실행으로 연결한 것은 아니다.

코드 위치는 복호화 파일 오프셋이며 코드 VA는 0x02000000을 더합니다. 버퍼와 MMIO 주소는 펌웨어 VA입니다. 카메라에서 직접 관측한 주소나 수치가 아닙니다. 전체 재현 기록 · 원본 코드 실행 범위와 준비 입력

결과 레지스터 읽기

결과 수집에서 count의 마지막 입력은 채널 기준 주소 +0x24의 NRDNCNT이고, length의 마지막 입력은 +0x28/+0x2C의 64비트 NRDNSIZE다. 원본 코드는 count를 32비트로 전달하고 size는 하위 32비트만 엔진 결과에 저장했다. 스냅샷은 시험자가 공급한 값이며 하드웨어가 계산한 결과가 아니다. 결과 flag는 수치가 저장된 뒤에도 0으로 남았다.

입력 용량은 NRDNLIMIT 설정에 사용된다. 원본 코드는 하위 워드의 bit 0–2를 지우고, 상위 워드의 bit 0–1만 지운다. 상위 초기값 0xA5A50003은 0xA5A50000으로 바뀌며 나머지 비트는 보존됐다. 이 값은 비트 보존 규칙을 확인하기 위한 입력으로, 실제 장치에서 유효한 설정임을 뜻하지 않는다.

기본 버퍼와 DMA 준비

DMA 준비 실험의 기본값 사례에서는 설정 레코드 24·25의 주소와 용량을 원본 생성자 일부와 풀 계산 코드가 만들었다. 주소는 0x80019E90과 0x8001B250, 용량은 각각 0x13C0바이트였다. 버퍼 주소는 원본 getter와 실제 작업자·코어 프레임을 거쳐 엔진 +0x54/+0x58에 전달됐다. 각 DMA 패킷 +4에는 이 주소가 그대로 저장됐다. 선택 인덱스와 상위 객체 연결은 준비한 입력이다.

원본 DMA 객체 계산과 연결은 두 채널에 테이블 인덱스 7·8을 사용했다. 기준 주소는 0x20005400과 0x20005500이다. 실행을 멈춘 지점의 읽기 대상 주소는 각각 0x20005404와 0x20005504다. MMIO와 대상 버퍼를 매핑하지 않아 DMA 준비 실험에서는 이 메모리에 접근하지 않았다. 앞선 PixelDetect 설정은 생략했고 0x72077C에는 같은 엔진을 인자로 별도 진입했다.

기본 생산은 일반 배열 생성자를 생략한 74E5D4부터 시작하며, 풀 주소 계산은 74EBF0에 별도 진입해 유효성 검사 전에 멈춥니다. 이어 63542C/635488의 getter, 635528의 실제 코어 호출과 634F68/635070의 전달 코드를 실행합니다. 실제 스택 프레임은 사용하지만 중간의 두 버퍼 초기화와 나머지 코어 처리는 생략합니다. replay_dma_preparation의 실행 구간

원본 6C5914/6C5978에서 만든 패킷을 6C4DE8에 전달합니다. 패킷 필드는 byte +0=0, word +4=선택 포인터, word +8=0, byte +C=0, byte +D=1입니다. 비정렬 공급값의 하위 비트도 RAM 패킷까지 보존됩니다. 실제 장치가 비정렬 버퍼를 사용하는 사례를 관측한 것은 아닙니다.

기본 주소·용량의 산술 범위는 [80019E90,8001B250)와 [8001B250,8001C610)로 맞닿으며 겹치지 않습니다. 이 범위는 기본 배치를 설명하며 실제 DMA 전송 길이나 촬영 간 재사용을 입증하지 않습니다. dma_preparation의 source_buffers·capacity_bytes·relevant_native_writes

확인하지 않은 연결

패킷 +8의 0은 엔진 +0x70의 용량과 다른 필드다. 이 두 값을 동일시하거나 0을 실제 전송량으로 해석할 근거는 없다. 추적한 주소는 검출 결과의 인코딩 레코드용이며 처리 픽셀이나 JPEG 영상 버퍼와의 동일성을 확인한 것은 아니다. 실제 DMA 전송, 완료 시점, 촬영 작업 간 재사용과 SuperResolution 메뉴 도달 조건도 미확정이다.

두 시험 모두 코드 매핑은 읽기·실행 전용이며 끝까지 원본 해시를 유지합니다. 다만 모의 RAM의 객체와 구간별 진입 상태를 준비하므로 실기 실행 기록과는 다릅니다. 결과의 바이트 길이, 인코딩된 엔트리 수, 설정 단계의 플래그, 유효 표시와 목록 마스크를 서로 같은 의미로 취급하지 않습니다.

이 문서는 앞서 공개한 작업자 매개변수·목록 응답의 결과 출처와 버퍼 준비 경계를 보완합니다. 버퍼 재사용 분석과 SuperResolution 메뉴 분석의 미확정 항목을 해결했다고 주장하지 않습니다.

재현과 검증

공개용 검증기는 입력 이미지의 정확한 크기와 SHA-256을 검사한다. 세 의존 파일의 원본 바이트는 줄바꿈을 정규화해 모두 확인한다. 확인한 바이트를 직접 실행하므로 캐시된 바이트코드는 사용하지 않는다. 결과 수집 4사례와 DMA 준비 6사례의 전체 기록 및 코드 허용 범위 해시를 기존 검증 결과와 대조하며 필드는 생략하지 않는다. 출력은 새 경로에만 생성하고 -O 실행은 거부한다.

python -m pip install unicorn==2.1.4
python -B verify_register_dma.py decoded.bin --output register-dma-new.json
python -B -m unittest discover -s tests -p test_register_dma.py

실제 확인 환경은 Python 3.12.3과 Unicorn 2.1.4입니다. 구문은 Python 3.10 문법으로도 검사했지만 다른 Python 버전의 런타임 실행은 확인하지 않았습니다. 원본 펌웨어와 복호화 이미지는 저장소에 포함하지 않습니다. 기존 분석·복호화 도구로 만든 정확한 원본 이미지가 필요합니다.

CLI 재실행과 독립 재실행의 결과가 바이트 단위로 일치했습니다. 펌웨어와 Unicorn 없이 실행하는 보호 검사 8개는 크기·해시 오류, 기존 출력과 입력 별칭, dangling symlink, -O, 모든 전이 의존성의 변경, LF/CRLF, 캐시 바이트코드와 결과 기록 변경을 검사합니다. 이 테스트 통과는 실제 카메라 동작을 보장하지 않습니다. 보호 검사 코드
