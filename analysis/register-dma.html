검출 결과 레지스터와 DMA 준비

작업자의 결과에 담기는 개수와 길이는 주변 장치 레지스터에서 옵니다. 원본 코드가 그 레지스터를 어떻게 읽는지, 결과를 받을 버퍼의 주소를 DMA에 어떻게 넘기는지 확인했습니다.

이 문서에서

  1. 배경: 결과 레지스터와 DMA 패킷
  2. 결과 레지스터: 개수는 그대로, 크기는 하위 32비트만
  3. 기본 버퍼 주소가 DMA 패킷까지 그대로 전달됩니다
  4. 한계와 남은 과제
  5. 재현과 검증
  6. 근거 파일과 참고 자료

핵심 요약

  • 결과를 모으는 원본 코드는 두 채널에서 개수(count)는 32비트 그대로, 64비트 크기(size)는 하위 32비트만 처리 객체에 저장했습니다. 레지스터 값은 시험용으로 공급한 스냅샷입니다(4사례).
  • 입력 용량을 장치 설정 레지스터에 쓸 때는 하위 워드를 8바이트 단위로 내렸습니다. 상위 워드는 아래 두 비트만 지웠습니다.
  • 설정 객체의 기본 레코드 24·25 주소가 작업자와 처리 객체를 거쳐 DMA 설정 패킷에 그대로 실렸습니다. 공급한 주소로 바꾼 대조에서도 같았습니다(6사례).
  • DMA 실험은 첫 DMA 레지스터를 읽기 직전에 멈췄습니다. 실제 전송·완료, 촬영 사이의 버퍼 재사용, Pixel Shift 메뉴와의 관계는 확인하지 않았습니다. 카메라에서 실행한 실험은 없습니다.

확인 원본 코드 실행으로 확인

  • 레지스터 설정과 결과 읽기, 처리 객체 결과 필드 저장 (4사례)
  • 기본 레코드 24·25의 주소·용량 생산과 처리 객체까지의 전달
  • DMA 객체 7·8 선택과 RAM 패킷 작성 (6사례, 채널별 별도 VM)

정적 분석 코드를 읽어 판단

  • 크기 읽기 호출부에서 상위 워드가 버려지는 위치
  • 수집 게이트가 매개변수 +0xB의 0 여부를 보는 것

모델 시험 조건으로 정한 것

  • 레지스터 스냅샷(count·size·limit 상위 워드)과 입력 용량
  • 객체 연결, 기하 값, 검출 임계값, 수집 게이트
  • DMA 대조 사례의 버퍼 주소와 용량, 선택 인덱스

미확인 확인하지 않은 것

  • 장치가 실제로 계산하는 결과와 완료 시점
  • DMA 전송, 전송 길이, 버퍼 재사용
  • SuperResolution 메뉴에서의 도달

배경: 결과 레지스터와 DMA 패킷

카메라의 영상 처리 칩에는 CPU 말고도 전용 회로가 많습니다. 펌웨어는 이런 회로를 MMIO(메모리 주소로 장치 레지스터를 읽고 쓰는 방식)로 다룹니다. 장치가 만든 결과의 개수나 크기도 레지스터에서 읽습니다. 큰 데이터는 DMA로 옮깁니다. 이때 펌웨어는 버퍼 주소 같은 설정을 장치에 넘깁니다(Linux 커널 문서: 장치 I/O, Linux 커널 문서: DMA 매핑는 일반 개념의 예입니다).

작업자 매개변수와 목록 응답에서는 결과 구조의 개수와 길이를 준비해 넣었습니다. 이 문서는 그 값이 어떤 레지스터에서 오는지와, 결과를 받을 버퍼가 어떻게 지정되는지를 봅니다. 검증기는 이 회로의 설정 코드를 PixelDetect라고 부릅니다. 결과 레지스터는 NRDNCNT·NRDNSIZE·NRDNLIMIT라는 이름으로 적습니다.

두 실험은 하나의 촬영으로 이어지지 않습니다. 결과 읽기 실험은 DMA 준비 구간을 건너뛰었습니다. DMA 준비 실험은 결과 레지스터에 닿기 전에 멈췄습니다.

읽는 법

코드 위치는 복호화 파일의 오프셋입니다. 실행 주소는 여기에 0x02000000을 더한 값입니다. 버퍼와 레지스터 주소는 펌웨어의 실행 주소(VA)입니다. 카메라에서 관측한 주소나 수치는 하나도 없습니다.

결과 레지스터: 개수는 그대로, 크기는 하위 32비트만

원본 수집 코드는 count를 32비트 그대로 옮기고 64비트 size는 하위 워드만 저장했습니다. 숫자를 저장한 뒤에도 결과 플래그는 0이었습니다.

기본 버퍼 주소가 DMA 패킷까지 그대로 전달됩니다

원본 코드가 만든 레코드 24·25의 주소가 작업자·코어·처리 객체를 거쳐 DMA 패킷 +4에 그대로 실렸습니다. 공급한 주소로 바꾼 대조에서도 패킷에는 그 주소가 들어갔습니다.

패킷의 다섯 필드는 모든 사례에서 같은 모양이었습니다. 바이트 +0은 0, 워드 +4는 선택한 버퍼 주소, 워드 +8은 0, 바이트 +0xC는 0, 바이트 +0xD는 1입니다. 비정렬 공급값의 하위 비트도 패킷까지 그대로 남았습니다. 실제 장치가 비정렬 버퍼를 쓰는 사례는 관측하지 않았습니다.

두 채널은 DMA 테이블의 인덱스 7과 8을 썼습니다. 실행을 멈춘 곳에서 다음에 읽을 레지스터는 각 채널 기준 주소 +4였습니다. 장치 메모리와 대상 버퍼는 매핑하지 않았습니다. 이 범위에 접근하면 검증기가 멈추도록 했습니다. 실제 접근은 0건이었습니다.

그림의 배치는 정책 플래그의 생산자에 나온 용량 표로 계산한 것입니다. 데이터가 0x80010090에서 시작해 인덱스 6~17이 0x9E00바이트를 차지하면, 인덱스 24는 정확히 0x80019E90에서 시작합니다. 두 범위는 맞닿을 뿐 겹치지 않습니다. 이 일치는 기본 배치를 설명할 뿐이며 실제 DMA 전송 길이나 방향, 촬영 사이의 재사용을 보여 주지 않습니다.

건너뛴 것DMA 준비 구간 두 곳, 장치 계산·완료, 수집 뒷부분전체 기동, 버퍼 초기화, 앞의 PixelDetect 설정, 실제 전송
  • 값의 뜻 패킷 +8의 0과 처리 객체 +0x70의 용량은 다른 필드입니다. 0을 실제 전송량으로 읽을 근거는 없습니다. 결과의 바이트 길이, 엔트리 수, 설정 단계의 플래그, 유효 표시, 목록 결과도 서로 다른 값으로 다룹니다.
  • 버퍼의 정체 추적한 주소는 검출 결과를 담는 레코드 자리입니다. 처리된 픽셀이나 JPEG 영상 버퍼와 같은 것인지는 확인하지 않았습니다.
  • 실행 환경 코드 매핑은 읽기·실행 전용이고 끝까지 원본 해시를 유지했습니다. 모의 RAM의 객체와 구간별 진입 상태는 준비한 것이라 카메라의 실행 기록과는 다릅니다.
  • Pixel Shift 버퍼 재사용 분석과 SuperResolution 메뉴 분석에 남은 미확정 항목은 이 문서로 풀리지 않았습니다.

재현과 검증

복호화 이미지는 저장소에 없습니다. 분석·복호화 도구로 원본 이미지를 만들어 씁니다. 검증기는 입력의 크기와 SHA-256을 먼저 확인합니다. 세 의존 파일도 줄바꿈을 정규화한 해시로 확인한 뒤 그 바이트를 직접 실행하므로 캐시된 바이트코드는 쓰지 않습니다.

python -m pip install unicorn==2.1.4
python -B verify_register_dma.py decoded.bin --output register-dma-new.json
python -B -m unittest discover -s tests -p test_register_dma.py

결과 읽기 4사례와 DMA 준비 6사례의 전체 기록, 허용 코드 범위의 원본 해시를 저장된 값과 대조합니다. 필드는 생략하지 않습니다. 출력은 새 경로에만 만들고 -O 실행은 거부합니다.

확인 환경은 Python 3.12.3과 Unicorn 2.1.4입니다. 구문은 Python 3.10 문법으로도 검사했으나 다른 버전에서 실행해 보지는 않았습니다. CLI 재실행과 독립 재실행의 결과는 바이트 단위로 같았습니다.

보호 검사 8개는 펌웨어와 Unicorn 없이 돌아갑니다. 크기·해시 오류, 기존 출력과 입력 별칭, 끊어진 심볼릭 링크, -O, 의존 파일 변경, LF/CRLF, 캐시 바이트코드, 결과 기록 변경을 검사합니다. 이 검사를 통과해도 카메라 동작이 보장되지는 않습니다.
