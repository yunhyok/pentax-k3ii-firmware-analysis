AF와 렌즈 제어 · 2단계 요청 계산과 전달

AF 요청값이 계산되어 구동 준비로 넘어가는 과정

구동 방식이 정해진 다음에는 “얼마나 움직일지”를 담은 값이 필요합니다. 이 값이 어디서 계산되고 어떤 조건을 거쳐 구동 준비 함수에 도착하는지 원본 코드로 따라갔습니다.

이 문서에서

  1. 배경: 이 문서가 따라가는 값
  2. 능력 조회는 상태 비트와 저장된 값을 보고 결정합니다
  3. 바디 경로: 한 호출이 계산한 값을 다음 호출이 읽습니다
  4. 렌즈 경로: 요청값은 렌즈 명령 0x8211의 응답에서 나옵니다
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 렌즈 능력 조회는 항상 실행되지 않습니다. 상태 비트가 켜져 있고 저장된 능력 바이트가 0일 때만 렌즈에 묻고 그렇지 않으면 저장된 값을 그대로 씁니다.
  • AF 코드는 16비트 요청값을 계산해 객체에 적어 두고 다음 호출이 그 값을 읽어 구동 준비 함수에 넘깁니다. 바디 경로에서는 입력값에서 차감값을 빼고 보정값을 더합니다. 렌즈 경로에서는 렌즈가 돌려준 2바이트 응답을 그대로 씁니다.
  • 요청값이 0이거나 음수로 해석되면 구동 준비를 부르지 않습니다. 값의 크기에 따라 구간 번호 0·1·2가 정해집니다.
  • 원본 코드 실행 25건으로 확인했습니다. 입력은 모두 연구자가 넣었고 AF 센서가 이 입력을 만드는 과정과 실제 렌즈 움직임은 다루지 않았습니다.

확인 원본 코드 실행으로 확인

  • 능력 조회의 실행 조건과 저장(8건)
  • 바디 경로의 요청값 계산과 전달(14건)
  • 렌즈 경로의 요청값과 전달(3건)
  • 구동 준비 함수의 바디·렌즈 분기점까지 실제 호출

정적 분석 코드를 읽어 판단

  • 함수들이 서로를 부르는 관계(분기 61개)
  • 바디 계산을 허용하는 설정값 목록

모델 시험 조건으로 정한 것

  • 렌즈 응답과 전송 상태(렌즈 전송 함수 하나를 대체)
  • 입력 반워드, 방향 플래그, 보정값, 계산 플래그
  • 준비해 넣은 객체, 공유 메모리, 상태값

미확인 확인하지 않은 것

  • AF 센서 신호에서 초점 오차를 구하는 알고리즘
  • 두 호출 사이의 상태 전이와 스케줄링
  • 요청값의 물리 단위, 구간 번호의 의미
  • 분기 뒤의 구동 제어와 실제 렌즈 움직임

배경: 이 문서가 따라가는 값

앞 문서에서 렌즈가 알려 준 능력 바이트의 비트 6이 AF 구동 경로를 가른다는 것을 보았습니다. 이 문서는 그 앞뒤를 채웁니다. 능력 조회가 언제 실행되는지, 그리고 구동 준비 함수가 받는 요청값이 어디서 오는지입니다.

등장하는 객체는 셋입니다. 이름은 펌웨어에 남은 C++ 클래스 이름에서 가져왔습니다.

이전 판은 CAfMotor·CAfPulse·CAfPosition의 이름이 RTTI에 근거한다고 적었습니다. 검증기가 실제로 RTTI를 대조하는 클래스는 CAfApplication, CAfMotor, CAfPulse 세 개입니다. CAfPosition이라는 이름은 근거 파일에서 확인되지 않으므로 이 문서에서는 “position 객체”라고만 부릅니다.

주소 표기

코드 위치는 복호화한 파일의 오프셋입니다. VA를 붙인 값은 실행·데이터 주소입니다. 펌웨어는 시작할 때 일부 코드를 주소 0번지 근처로 복사해 실행하는데 원문은 이 영역을 ITCM이라고 불렀습니다. 이 문서의 VA 0x2248 같은 작은 주소가 그 영역입니다. 요청값을 물리적인 이동 거리나 초점 오차 단위로 단정하지 않았습니다.

능력 조회는 상태 비트와 저장된 값을 보고 결정합니다

렌즈에 능력을 묻는 것은 상태 비트가 켜져 있고 저장된 능력 바이트가 0일 때뿐입니다.

함수 0x94DC4는 VA 0x40006064가 가리키는 기록의 둘째 바이트에서 비트 6을 봅니다. 꺼져 있으면 아무것도 하지 않고 돌아갑니다. 켜져 있어도 CLensKaf2+6에 저장된 능력 바이트가 0이 아니면 그 값을 그대로 씁니다. 저장된 값이 0일 때만 명령 0x8205로 1바이트를 요청합니다.

전송 상태가 0일 때만 응답을 능력 바이트에 기록합니다. 응답의 비트 0은 그 뒤의 초기화 분기를 가르고 비트 6은 바디·렌즈 구동 선택을 가릅니다. 이 문서의 요청값 시험은 원본 조회 코드가 직접 기록한 능력 바이트 0x80(바디 경로)과 0x40(렌즈 경로)을 이어서 썼습니다. 능력 판정을 결과 상수로 바꿔치기하지 않았습니다.

바디 경로: 한 호출이 계산한 값을 다음 호출이 읽습니다

요청값은 한 번에 전달되지 않습니다. 먼저 계산해서 객체에 적어 두고 뒤따르는 다른 호출이 그 값을 읽어 조건을 확인한 뒤 구동 준비 함수에 넘깁니다.

두 호출은 주소 0번지 영역의 같은 루틴 안에 있습니다. 생산자 호출은 VA 0x2258(파일 0xD7674)에서, 소비자 호출은 VA 0x234C(파일 0xD7768)에서 일어납니다. 실행한 구간은 VA 0x2248부터 0x225C까지와 VA 0x2348부터입니다. 두 구간 사이에서 펌웨어가 하는 일(스케줄링)은 실행하지 않았습니다.

입력을 방향에 따라 정규화합니다

능력 비트 6이 꺼진 바디 경로에서는 함수 0x544EC가 입력 반워드를 먼저 다듬습니다. 방향 플래그(VA 0x00103116)에 따라 두 가지로 처리합니다.

실행이 끝난 뒤 방향 플래그는 두 경우 모두 0이었습니다. 예를 들어 방향 1에서 입력 65,435(0xFF9B)를 넣으면 차감값은 100이 됩니다.

요청값의 계산식

시험한 상태에서 요청값은 아래 식의 하위 16비트입니다.

요청값 = 정규화한 입력(pulse+0xC2) − 차감값[0x00103168] + 보정값[0x0010316E]
  • 0이 되는 경우: 계산 플래그(accessor+0xC5F)가 1이 아니면 요청값은 0입니다. 계산 결과를 부호 있는 16비트로 읽었을 때 음수여도 0입니다.
  • 설정값 조건: 설정 키 0x2C7의 값이 허용 목록(1, 11, 12, 13, 19)에 없으면 정규화와 계산을 하지 않습니다. 시험에서는 허용되는 값 1과 허용되지 않는 값 0을 넣어 실행했고 나머지 값은 비교 명령을 읽어 확인했습니다.
  • 고정한 조건: 전역 플래그 VA 0x001030AB는 0, 준비 상태(VA 0x001030E2)는 3으로 두었습니다. 다른 상태에서도 같은 식이 쓰인다고 일반화하지 않았습니다.

보정값이 어디서 만들어지는지는 다음 문서에서 다룹니다.

소비자는 요청값의 크기에 따라 다르게 움직입니다

전달되는 경우 요청값은 pulse+0x9E와 position+0x166에 기록되고 구간 번호는 motor+0x60에 기록됩니다. 이어서 구동 준비 함수 0x52E38이 인수 8로 실제 호출됐습니다. 능력 비트 6이 꺼진 객체에서는 이 함수 안의 바디 분기점(파일 0x52ED4)에 도달했습니다. 구간 번호 0·1·2가 속도나 토크 같은 물리량과 어떤 관계인지는 확인하지 않았습니다.

렌즈 경로: 요청값은 렌즈 명령 0x8211의 응답에서 나옵니다

능력 비트 6이 켜진 경로에서는 카메라가 계산하지 않습니다. 렌즈에 물어서 받은 2바이트 값을 요청값으로 씁니다.

  1. 렌즈에 조회함수 0x4E684가 명령 0x8211로 2바이트를 요청. 응답은 넣어 준 값
  2. 값 읽기함수 0xB995C가 첫 바이트 × 256 + 둘째 바이트로 읽음
  3. 부호와 플래그 확인부호와 계산 플래그를 확인. 음수이면 요청값 0
  4. 구동 준비0x52E38을 인수 8로 호출. 렌즈 분기점 0x52E98에 도달

주의

이 결과는 “전송 함수가 실패를 알리면서 버퍼를 그대로 둔다”는 조건을 연구자가 정했을 때의 호출자 동작입니다. 실제 통신이 실패할 때 버퍼가 항상 그대로 남는지는 확인하지 않았습니다. 또한 이 분기는 능력 비트에 따른 제어 경로일 뿐이며 SDM·DC·PLM 각각의 통신 규약을 식별한 결과가 아닙니다.

렌즈 경로의 함수와 시험 조건
  • 호출 연결: 0x54688 → 0x4E684(조회), 0x4E694 → 디스패처 0x94204, 0x4E6A0 → 0xB995C(값 읽기). 음수가 아닌 결과는 0x546CC에서 저장합니다.
  • 시험 조건: CLensKaf2+0x1A의 비트 0은 0, 계산 플래그 accessor+0xC5F는 1, 잔량 필드의 초기값은 1,024(0x400)로 두었습니다.
  • 세 사례 모두 렌즈 조회는 명령 0x8211 한 번뿐이었습니다. 호출이 없는 사례는 VA 0x2350으로 돌아갔습니다.
  • 근거는 af-control.json의 lens_control_cases와 lens_error_without_reply_write입니다.

한계와 남은 과제

  • 입력의 출처: 위상차·콘트라스트 AF가 센서 신호에서 초점 오차를 만드는 알고리즘은 분석하지 않았습니다. 입력 반워드와 보정값의 출처는 AF 카운터와 보정값에서 일부 이어집니다.
  • 호출 사이: 두 호출 사이의 상태 전이와 스케줄링은 실행하지 않았습니다.
  • 분기 이후: 구동 준비 함수의 분기점 뒤에 이어지는 제어 전체와 실제 렌즈 움직임은 확인하지 않았습니다.
  • 대체와 합성: 실행을 대체한 함수는 렌즈 전송 0x93F94 하나입니다. 나머지 객체, 공유 메모리, 상태값은 검증기에 적어 둔 합성 입력입니다.

정확한 렌즈 모델 정보가 없어도 이 기본 구조의 분석은 이어 갈 수 있습니다. 모델별 수정이나 렌즈 EEPROM 변경은 적용하지 않았습니다. 미해결 항목은 hq-status.json에 정리되어 있습니다.
