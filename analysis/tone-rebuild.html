톤 보간 함수를 C로 다시 만들어 원본 호출자와 대조하기

펌웨어의 기능을 바꾸려면 원본 함수를 직접 만든 코드로 바꿔 끼울 수 있어야 합니다. 가장 작은 함수 하나로, 새 코드가 원본 자리에서 원본 호출자와 문제없이 맞물리는지 시험했습니다.

이 문서에서

  1. 배경: 톤 곡선에서 값을 읽는 방법
  2. 다시 만든 함수: 수식과 코드 크기
  3. 검증 방법: 64바이트만 바꾸고 원본 호출자를 실행
  4. 원본 호출자는 C 호출 규약보다 많은 것을 가정합니다
  5. 결과: 호출자 출력과 수치 회귀가 모두 일치
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 톤 곡선에서 값을 읽어 오는 64바이트짜리 함수를 C로 다시 작성했습니다. 정해 둔 컴파일러와 옵션으로 빌드하니 원본과 크기가 같은 64바이트 ARM 코드가 나왔습니다. 명령 내용은 원본과 다릅니다.
  • 에뮬레이터 메모리에서 이 64바이트만 바꾼 뒤 호출 지점이 3곳씩 있는 원본 호출 구간 3곳을 실행했습니다. 2,304회 호출과 출력 2,048개가 원본과 같았습니다. 기존 수치 검증 268,288개도 같은 결과를 냈습니다.
  • 원본 호출자는 C 호출 규약이 보장하지 않는 것에 기대고 있었습니다. 보간 함수가 r3과 r12를 건드리지 않는다고 가정합니다. 이번 빌드는 이 가정을 지킵니다.
  • 조건 플래그는 원본과 달라지는 경우가 있습니다. 확인한 세 호출 루프는 스스로 비교해 플래그를 다시 정하므로 영향이 없었습니다. 재포장 파일이나 설치 파일은 만들지 않았습니다.

확인 원본 코드 실행으로 확인

  • 호출 구간 3곳의 호출 지점 9곳에서 반환값, r3–r12·SP·LR 보존, A32 상태 복귀
  • 직접 호출 33건의 결과, 읽은 위치, 메모리에 쓰지 않음
  • r3·r12를 일부러 망가뜨리면 원본 호출자가 주소 오류를 냄
  • 복귀 때마다 플래그를 뒤집어도 호출자 출력이 같음

정적 분석 코드를 읽어 판단

  • 세 호출 루프가 조건 분기 전에 자체 비교 명령을 실행함
  • 빌드한 ELF의 형식, 심벌 크기, 재배치 없음

모델 시험 조건으로 정한 것

  • 곡선과 입력은 직접 만든 합성 값. 원본 곡선 표는 쓰지 않음
  • 호출자에 넣은 객체와 스택
  • CPU는 Unicorn의 Cortex-A9 모델

미확인 확인하지 않은 것

  • 아직 찾지 못한 간접 호출이 있는지
  • 실행 시간, 동시 실행, 캐시 일관성
  • 재포장·설치·부팅, 실제 영상 품질

배경: 톤 곡선에서 값을 읽는 방법

카메라는 RAW 데이터를 JPEG로 만들 때 밝기를 톤 곡선에 통과시킵니다. 곡선은 값 256개짜리 표로 저장되어 있습니다. 입력은 그보다 촘촘하므로, 표의 이웃한 두 값 사이를 직선으로 이어 중간값을 구합니다. 이 계산을 보간이라고 합니다. K-3 II의 톤 곡선 생성 경로는 RAW 이후의 톤·WB·색 행렬에서 다룹니다.

이 함수를 고른 이유는 세 가지입니다. 크기가 작고 다른 함수를 부르지 않으며 수식을 이미 원본 실행으로 확인해 두었기 때문입니다. 원본과 새 코드를 같은 조건에서 비교하기에 알맞습니다.

주소 표기

이 문서의 주소는 복호화한 이미지의 파일 오프셋이고 실행 주소는 여기에 0x02000000을 더한 값입니다. 입력 펌웨어는 읽기만 했습니다. 바꾼 64바이트는 에뮬레이터 메모리에만 있었습니다.

다시 만든 함수: 수식과 코드 크기

새 코드는 원본과 같은 수식을 계산하고 원본이 차지하던 64바이트에 꼭 맞습니다.

대상은 파일 오프셋 0x4DD3EC부터 64바이트를 차지하는 톤 보간 함수입니다. 원본 수식과 수치 검증 결과를 바탕으로 C 소스를 작성했습니다.

index = sample >> 6
fraction = sample & 63
index >= 255: return curve[255]
otherwise: return curve[index]
  + trunc_toward_zero((curve[index + 1] - curve[index]) * fraction / 64)

검증 방법: 64바이트만 바꾸고 원본 호출자를 실행

원본 이미지와, 함수 64바이트만 새 코드로 바꾼 이미지를 같은 조건으로 실행해 결과를 비교했습니다.

컴파일러는 Clang 22.1.8을 포함한 Zig 0.17.1입니다. 대상은 Cortex-A9, 명령 집합은 A32, 최적화는 -Os입니다. 만들어진 파일은 32비트 리틀엔디언 ARM ELF(EABI 5)이고 함수 심벌 전체가 4바이트 정렬된 A32 코드입니다.

ELF에는 .ARM.exidx와 그 재배치 정보도 들어 있습니다. 그러나 시험에 쓴 것은 검사를 통과한 .text 64바이트뿐이고 ELF 전체를 펌웨어에 넣지 않았습니다. .text에는 재배치 항목과 풀리지 않은 심벌이 없었습니다.

두 가지 실행 방식

  • 호출자 실행 — 보간 함수를 부르는 원본 코드 세 구간을 실행합니다. 구간마다 호출 위치가 3곳이고 각각 256회 호출합니다. 호출과 복귀 때 레지스터를 관찰하고 호출자가 메모리에 남긴 출력을 비교합니다.
  • 직접 호출 — 보간 함수만 따로 부릅니다. 512바이트 곡선 표를 매핑한 페이지의 끝에 붙여 놓고 다음 페이지는 매핑하지 않았습니다. 함수가 표 밖을 읽으면 곧바로 오류가 납니다.

원본 호출자는 C 호출 규약보다 많은 것을 가정합니다

C 호출 규약을 지키는 것만으로는 이 자리에 새 코드를 넣을 수 없습니다. 원본 호출자가 r3과 r12가 보존된다고 가정하기 때문입니다.

Arm의 32비트 호출 규약(AAPCS32)에서 r0–r3과 r12는 함수가 마음대로 써도 되는 임시 레지스터입니다. 함수가 보존해야 하는 것은 r4–r8, r10, r11과 SP입니다(r9는 플랫폼 규정에 따릅니다). 규약대로라면 컴파일러가 r3이나 r12를 계산에 써도 잘못이 아닙니다.

그런데 확인한 원본 호출자는 보간 함수에서 돌아온 직후 r3과 r12를 그대로 써서 다음 메모리 주소를 계산합니다. 원본 보간 함수가 두 레지스터를 건드리지 않기 때문에 성립하는 코드입니다. 이번 빌드는 r0–r2만 쓰고 실행에서도 r3–r12와 SP, LR, A32 상태 복귀를 확인했습니다. 이 결과는 정해 둔 컴파일러와 옵션으로 만든 코드에만 해당합니다.

플래그가 달라지는 이유와 영향

원본은 sample >> 6을 255와 비교하고 새 코드는 입력 자체를 0x3FC0과 비교합니다. 그래서 반환값이 같아도 비교가 남기는 조건 플래그가 다릅니다. 호출 규약도 N·Z·C·V 플래그는 함수 호출 전후에 정해진 값이 없다고 규정합니다.

영향이 없다는 점은 두 가지로 확인했습니다. 첫째, 세 호출 루프에서 복귀 뒤 첫 조건 분기까지의 명령을 읽어, 그 사이에 자체 CMP가 있고 조건부 실행 명령이 없음을 확인했습니다. 둘째, 원본과 새 코드 각각에서 2,304회의 복귀마다 N·Z·C·V를 모두 뒤집어 실행했는데 호출자 출력이 같았습니다.

주의

임시값인 r1·r2나 모든 플래그가 원본과 같다고 주장하지 않습니다. 아직 찾지 못한 간접 호출이 있다면 그 호출자까지 호환된다고 볼 수도 없습니다.

대조 실험의 주소와 값
  • r3 실험: 호출 위치 0x4DD510의 복귀 직후 r3을 0x40000000으로 바꿈. 0x4DD518의 2바이트 쓰기가 매핑되지 않은 주소 0x90020600을 가리켜 중단.
  • r12 실험: 호출 위치 0x4DD790의 복귀 직후 r12를 0xDEAD0000으로 바꿈. 0x4DD798의 2바이트 읽기가 0xDEAD0008을 가리켜 중단.
  • 세 루프의 자체 CMP 위치는 위 표와 같고 뒤따르는 조건 분기는 0x4DD5A4, 0x4DD7F0, 0x4DD8A0입니다. 분기는 각각 0x4DD4FC, 0x4DD780, 0x4DD84C로 돌아갑니다.
  • 플래그 뒤집기는 복귀 때마다 CPSR에 0xF0000000을 XOR하는 방식입니다.

직접 호출에서 함수가 읽은 것은 기대한 한두 개의 반워드뿐이었고 메모리에 쓰거나 스택을 쓰지 않았습니다. 문맥 포인터 자리에는 매핑하지 않은 주소를 넣었는데 접근이 없었습니다.

기존 수치 검증기를 그대로 다시 실행

새 코드를 넣은 이미지에 기존 수치 검증기를 실행해, 공개해 둔 원본 결과와 비교했습니다. 스칼라 보간 검사는 곡선 4개에서 입력 0부터 65,535까지를 모두 비교합니다. 나머지는 원본의 SIMD·합성·적용 경로가 여전히 같은 결과를 내는지 보는 회귀 검사입니다. 그 함수들까지 C로 다시 작성했다는 뜻은 아닙니다.

한계와 남은 과제

확인한 것은 특정 C 소스·컴파일러·옵션에서 나온 64바이트 코드가 원본 호출 구간 세 곳과 오프라인에서 맞물린다는 점입니다. 함수 하나의 연결 검증이며 펌웨어 전체를 다시 빌드한 것이 아닙니다.

  • 다른 빌드 — 컴파일러나 옵션이 바뀌면 r3·r12를 쓰거나 크기·메모리 접근이 달라질 수 있습니다. 그때는 처음부터 다시 검증해야 합니다.
  • 확인하지 않은 조건 — 아직 찾지 못한 간접 호출, 동시 실행, 캐시 일관성, 실시간 처리 시간, 실제 하드웨어의 영상 품질.
  • 설치 단계 — 설치용 파일 재포장, 카메라 플래시 기록, 부팅·촬영·저장은 하지 않았습니다.

재포장 검사와 업데이트 전송·기록 분석은 별개의 근거입니다. 세 결과를 합쳐서 이 C 함수가 실제 카메라에서 받아들여진다는 증거로 삼지 않습니다. 다음 단계는 이 구분을 유지하면서 다른 호출자와 상태 의존성을 더 확인하는 것입니다. 목표별 상태는 hq-status.json에 있습니다.

재현 방법

python -m pip install unicorn==2.1.4 pyelftools
python verify_tone_rebuild.py decoded.bin --zig <Zig 0.17.1 실행 파일> \
  --compare analysis/tone-rebuild.json
python -m unittest discover -s tests -v
python verify_publication.py

둘째 명령 끝의 역슬래시는 줄을 잇는 표시입니다. 셸이 이를 지원하지 않으면 한 줄로 입력합니다. 검증기는 다음 순서로 동작합니다.

  1. 입력 확인 입력 펌웨어의 크기와 SHA-256, 원본 함수 64바이트의 해시를 확인합니다.
  2. 임시 폴더에서 컴파일 Zig와 Clang의 버전이 정해 둔 값인지 확인한 뒤 아래 옵션으로 컴파일합니다. 끝나면 임시 빌드 파일을 지웁니다.
  3. ELF 검사 형식, 심벌 크기, 재배치, 실행 모드를 검사합니다. 생성 함수의 크기나 실행 모드가 원본 자리와 다르면 여기서 중단합니다.
  4. 실행과 비교 원본 호출 관계를 확인하고 원본 이미지와 교체 이미지를 실행해 비교합니다.
zig cc -target arm-freestanding-eabi -mcpu=cortex_a9 -marm -Os \
  -ffreestanding -fno-stack-protector \
  -fno-unwind-tables -fno-asynchronous-unwind-tables \
  -c tone_interpolate.c -o tone_interpolate.o
