픽셀 보정을 켤지 정하는 정책 함수와 준비 분기

보존된 픽셀 레코드가 있어도 촬영마다 보정이 실행되는 것은 아닙니다. 촬영 객체의 활성 바이트 하나가 실행 여부를 정합니다. 이 바이트를 만드는 정책 함수를 원본 코드로 실행해 어떤 조건에서 켜지고 꺼지는지 정리했습니다.

이 문서에서

  1. 배경: 보정 플래그 네 개와 정책 함수
  2. 정책 함수는 세 입력으로 표의 한 칸을 읽고, 값이 4이면 보정을 켭니다
  3. 최종 활성값은 뒤쪽의 덮어쓰기까지 보아야 합니다
  4. 촬영 준비 함수는 일부 작업 종류에서 정책 호출을 건너뜁니다
  5. 정책 결과는 패킷을 거쳐 같은 이미지 버퍼의 보정으로 이어집니다
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 정책 함수는 세 입력 A·B·C로 표 일곱 개(364칸) 가운데 한 칸을 읽습니다. 값이 4이면 픽셀 보정 활성 바이트를 켭니다. 원본 조회 함수를 364칸 전부와 경계값 21개에서 실행해, 읽은 주소와 값을 대조했습니다.
  • 표를 보지 않고 4를 쓰는 강제 조건이 있고, 그 뒤에도 디버그 키, RAM 마커, 내부 작업 종류 6이 플래그를 다시 바꿉니다. 정책 함수 전체를 53개 사례로 실행해 이 순서를 확인했습니다.
  • 촬영 준비 함수는 내부 작업 종류 5·7·8·11에서 정책 함수를 부르는 구간을 건너뜁니다. 종류 0~11의 12개 사례로 확인했습니다.
  • 정책이 만든 값을 손대지 않고 촬영 패킷 생산 코드와 처리기에 이어 주면, 작업 종류 0에서는 같은 이미지 버퍼의 두 픽셀이 고쳐졌고 종류 6에서는 버퍼가 그대로였습니다.
  • 세 입력이 ISO, 노출 시간, 온도 같은 물리량 가운데 무엇인지는 근거가 부족해 정하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 조회표 364칸과 경계 21개의 읽기 주소·값
  • 정책 함수 53개 사례의 최종 플래그와 태그
  • 준비 분기 12개 사례
  • 정책 → 패킷 → 보정 연결 2개 사례

모델 시험 조건으로 정한 것

  • 입력 A·B·C, 작업 종류, 강제 플래그
  • 설정 슬롯, RAM 마커, 디버그 바이트
  • 연결 실험의 프레임·이벤트·16×16 이미지
  • 연결 실험에서 경과 시간 조회 함수 하나를 0 반환으로 대체

미확인 확인하지 않은 것

  • A·B·C의 물리 단위와 메뉴 대응
  • 입력을 만드는 상위 코드 전체
  • 작업 스케줄러, 실제 센서 픽셀, JPEG 출력

배경: 보정 플래그 네 개와 정책 함수

보존 픽셀 레코드 문서에서 본 것처럼, 픽셀 보정 코드는 촬영 패킷의 활성 바이트가 1일 때만 이미지 버퍼를 고칩니다. 이 바이트는 촬영 객체의 CAP+0x49에서 복사됩니다. 이 문서는 CAP+0x49를 만드는 함수를 다룹니다.

정책 함수(파일 0x65EA68)는 연달아 놓인 플래그 네 개를 정합니다.

정책 함수가 정하는 네 바이트
위치이 문서에서 확인한 역할함수가 처음 넣는 값
CAP+0x47다른 보정의 활성 바이트. 디버그 키 0x1B가 지움1
CAP+0x48또 다른 보정의 활성 바이트. 디버그 키 0x1C가 지움1
CAP+0x49픽셀 레코드 보정의 활성 바이트. 촬영 패킷 +0xA로 복사됨0
CAP+0x4A별도 플래그. 설정 객체와 RAM 마커 두 개로 초기값이 정해짐조건에 따라 0 또는 1
주의

CAP+0x49는 픽셀 레코드 보정의 활성 바이트입니다. 보조 스케일러의 활성값과 같은 것이라고 가정하지 않았습니다.

표기 규칙

함수 주소는 복호화한 펌웨어 파일 안의 위치(파일 오프셋)입니다. 실행 주소는 여기에 0x02000000을 더한 값입니다. RAM 주소는 실행 주소로 적습니다. 플래그 네 개는 [+0x47, +0x48, +0x49, +0x4A] 순서로 적습니다.

정책 함수는 세 입력으로 표의 한 칸을 읽고, 값이 4이면 보정을 켭니다

A는 표의 행, B는 열, C는 일곱 표 가운데 하나를 고릅니다. 읽은 값이 4일 때만 CAP+0x49와 CAP+0x4A가 1이 됩니다.

단위를 붙이지 않고 확인한 세 입력
입력원본 코드가 값을 얻는 곳구간 나누기구간 수

표는 파일 0x9E6242부터 104바이트씩 일곱 개가 이어집니다. 4 × 13 × 7 = 364칸입니다. 원본 조회 함수를 364칸 모두와 경계값 21개(A 3개, B 12개, C 6개)에서 실행했습니다. 돌려준 값뿐 아니라 실제로 읽은 주소도 예상과 같았습니다.

C의 나눗셈은 0 쪽으로 버립니다. 원값 −9는 0이 되어 “0~9” 표를, −10은 −1이 되어 “0 미만” 표를 골랐습니다. B를 읽는 중첩 객체는 원본 생성자 0x6EAD78로 만들었고, 생성 직후의 기본값은 0x7C였습니다.

표를 건너뛰는 강제 조건

아래 셋 중 하나라도 맞으면 정책 함수는 조회 함수 대신 상수 4를 돌려주는 0x5A1054를 부릅니다.

  • CAP+0x3C가 0이 아님
  • CAP+0x5F가 0이 아님
  • CAP+0x4F가 0이 아니고, 설정 키 0xF5가 1이며, CAP+0x20B6이 2 이상

세 번째 조건은 세 필드를 하나씩 뺀 사례 세 개에서 표 조회로 돌아갔습니다. 이 플래그들을 만드는 앞쪽 호출은 촬영 준비 함수 문서에서 원본 코드로 실행했습니다. 다만 CAP+0x20B6을 만드는 상위 코드는 아직 실행하지 않았습니다.

최종 활성값은 뒤쪽의 덮어쓰기까지 보아야 합니다

표 결과가 4여도 끝이 아닙니다. 정책 함수는 뒤에서 디버그 키, RAM 마커, 작업 종류를 차례로 검사해 플래그를 다시 씁니다.

픽셀 보정 활성 바이트 CAP+0x49에 영향을 주는 조건 (코드에 놓인 순서)
순서조건결과확인한 사례
0함수 시작+0x47 = +0x48 = 1, +0x49 = 0모든 사례에서 초기값 관측
1표 또는 강제 경로의 결과가 4+0x49 = 1, +0x4A = 1결과 1·2·3은 [1, 1, 0, 0], 결과 4는 [1, 1, 1, 1]

  • 디버그 키 — 디버그 객체의 +4 바이트가 켜져 있을 때만 키 바이트를 읽습니다. 꺼 둔 채 일곱 키를 모두 1로 넣은 사례는 기본 결과와 같았습니다. 키 0x1B와 0x1C는 각각 다른 보정 플래그 +0x47과 +0x48을 지웁니다.
  • RAM 마커 — 순서 4의 마커는 ID 3 조회 뒤에 0x72DDAC가 돌려주는 고정 RAM 0x4041F3C0의 다음 워드입니다. 이 해제에는 디버그 객체 +4가 필요하지 않았습니다. 실험에서는 ID 3 공급자를 등록하지 않았으므로, 조회가 돌려주는 객체가 이 마커를 제공한다고 주장하지 않습니다.
  • 작업 종류 6 — 내부 작업 조건입니다. 노출 모드 이름이나 메뉴의 selector = 6을 뜻하지 않습니다.
  • 기록 — 함수 마지막에 최종 +0x4A, 최종 +0x49, 선택 결과를 태그 0x3F, 0x40, 0x41에 각각 적습니다. 53개 사례 모두에서 이 세 태그만 바뀌었습니다.

CAP+0x4A의 초기값

표 조회보다 먼저, 정책 함수는 CAP+0x4A의 초기값을 정합니다. RAM 마커 두 개(실행 주소 0x80000000과 0x80010000의 첫 워드가 0xA55A5AA5)와 설정 객체의 +0xC 바이트를 봅니다. 여덟 조합 가운데 셋이 모두 켜진 경우에만 [1, 1, 0, 1]이 됐습니다. 이 두 RAM 영역을 보존 섹터에서 채우는 과정은 보존 섹터 20·21과 정책 입력에서, 설정 바이트를 만드는 코드는 정책 플래그의 생산자에서 다룹니다.

설정 쌍과 디버그 키 0x1E

정책 함수는 선택 결과에 따라 설정 객체의 슬롯 두 개를 골라, 각 슬롯의 워드 두 개(+0, +8)를 CAP+0x1C8~+0x1D4에 복사합니다. 슬롯은 설정 객체 +0x18부터 16바이트 간격입니다. 결과 1은 슬롯 0·1, 결과 2는 슬롯 2·3, 결과 3과 4는 슬롯 4·5를 골랐습니다. 이 워드들의 의미는 확인하지 않았습니다.

디버그 키 0x1E를 켜면 디버그 객체 +0x12의 값 1·2·3이 슬롯 0·1, 2·3, 4·5를 직접 고릅니다. 0x1E만 켜고 1 또는 3을 넣은 두 사례에서는 +0x4A가 1이 됐고, 0x19를 함께 켜고 2를 넣은 사례에서는 0이었습니다.

촬영 준비 함수는 일부 작업 종류에서 정책 호출을 건너뜁니다

작업 종류 5·7·8·11은 준비 함수 안에서 정책 함수를 부르는 구간에 들어가지 않습니다. 정책 함수에 종류 11을 직접 넣어 본 실험과 실제 준비 경로는 구분해야 합니다.

이 문서의 실험은 준비 함수를 세 구간으로 잘라 실행했습니다. 앞부분(0x6552B0~0x655344)에서 분기 바이트를 만들고, 분기 구간(0x655374~0x65537C)을 같은 객체로 실행한 뒤, 건너뛰지 않는 종류에서는 호출 구간(0x6553D0~0x6553DC)이 정책 함수 입구에 닿는지 따로 확인했습니다. 구간 사이의 가상 호출 세 개와 다섯 개는 실행하지 않았습니다.

그 빈 구간은 촬영 준비 함수의 연속 실행이 채웁니다. 거기서는 중간 호출을 모두 원본 코드로 실행해, 앞부분 21건과 정책 반환까지 21건에서 같은 분기와 순서를 확인했습니다.

종류 11과 Pixel Shift Resolution

다른 문서의 메뉴 분석은 Pixel Shift Resolution을 내부 작업 종류 11과 연결합니다. 이 문서에서 정책 함수에 종류 5와 11을 직접 넣은 사례는 결과 4의 활성값을 유지했습니다. 그러나 이것은 조건을 바꿔 본 대조일 뿐입니다. 실제 준비 경로는 종류 11에서 정책 호출 구간을 건너뛰므로, 이 사례만으로 Pixel Shift나 RAW 현상의 준비 경로가 정책 함수를 부른다고 결론 낼 수 없습니다. 근거는 Pixel Shift 메뉴와 버퍼 수명, 마스크 CPP와 보조 JPEG 입력(작업 종류를 만드는 코드)에 있습니다.

정책 결과는 패킷을 거쳐 같은 이미지 버퍼의 보정으로 이어집니다

정책 함수가 쓴 CAP+0x49를 다시 쓰지 않고 패킷 생산 코드와 처리기를 이어 실행하면, 그 값이 보정 실행 여부를 그대로 정합니다.

표 결과가 4가 되는 같은 입력에서 작업 종류 0과 6을 비교했습니다. 다른 두 보정(+0x47, +0x48)은 원본 디버그 키 0x1B와 0x1C로 꺼서, 픽셀 레코드 보정만 남겼습니다. 그 뒤 패킷 생산 구간(0x65D650~0x65D6B4)과 처리기 구간(0x58174C~0x581818)을 이어 실행했습니다.

  • 작업 종류 0 — 보정 함수가 실행되어, 같은 16×16 이미지 버퍼의 두 중심 픽셀이 300과 450으로 바뀌었습니다.
  • 작업 종류 6 — 정책 함수가 뒤쪽에서 CAP+0x49를 0으로 되돌렸고, 처리기는 보정 함수를 부르지 않았습니다. 이미지 전체와 앞뒤 대조값이 그대로였습니다.

두 픽셀이 300과 450이 되는 계산은 보존 픽셀 레코드와 촬영 패킷 문서의 순차 보정 실험과 같은 레코드, 같은 이미지입니다.

시험 조건

이 연결 실험에서 다른 코드로 바꿔 실행한 것은 경과 시간 조회 함수 0x785F70 하나이며, 0을 돌려주게 했습니다. 보정 객체와 픽셀 레코드는 원본 코드로 적재했습니다. 촬영 입력, 프레임, 이벤트 봉투(ID 0x01180001), 디버그 상태는 시험값으로 준비했습니다. 처리기의 기본 생성자, RTOS의 작업 전달, 전체 촬영 준비, 실제 센서 픽셀과 JPEG 출력은 실행하지 않았습니다.

한계와 남은 과제

  • 입력의 의미 — A·B·C는 객체 안의 위치와 관측한 계산으로만 이름 붙였습니다. ISO, 노출 시간, 온도 같은 물리량으로 부를 근거가 아직 부족합니다.
  • 입력의 생산 — 정책 사례 53건에서는 초기화 가드, 입력 필드, 설정 메모리를 시험값으로 준비했습니다. A와 일부 강제 플래그를 원본 코드가 만드는 과정은 촬영 준비 함수 문서에 있습니다. B, C, CAP+0x20B6의 상위 생산 코드는 실행하지 않았습니다.
  • 도달 여부 — 실제 촬영에서 어떤 메뉴 설정이 어떤 작업 종류와 입력값으로 이어지는지는 이 문서의 범위 밖입니다.
  • 실물 — 실제 센서 데이터, 작업 스케줄러, JPEG 출력은 실행하지 않았습니다.
