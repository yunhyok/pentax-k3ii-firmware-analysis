PENTAX K-3 II · firmware 1.12 · 2026-11-08

보존 섹터의 설정 복사본을
RAM 변경과 쓰기 요청까지 연결했다

일반 펌웨어 업데이트가 건너뛰는 섹터 13…22 중 13과 22에서 설정 저장 경로를 확인했다. 원본은 표식과 세대 카운터로 복사본을 선택하고, 변경이 있으면 메타데이터 선택의 반대쪽 섹터에 쓰기를 요청한다. 같은 색 공간을 다시 확정한 경우에는 RAM에 기록해도 섹터 쓰기는 요청하지 않았다.

보존 구간복사본 선택저장 요청재현·한계설치 제어색 공간 메뉴

아래 플래시·RAM 위치는 VA, 함수 번호는 해제 파일 오프셋이다. 합성 메모리에서 원본 제어 코드를 실행했다. ‘쓰기 요청’은 실제 플래시 기록 성공을 뜻하지 않는다.

1. 업데이트가 보존하는 두 섹터에 설정 복사본이 있다

앞선 0xC07C 원본 실행에서 일반 진입은 128 KiB 섹터 13…22를 건너뛰었다. 이번에는 섹터 13의 VA 0x021A0000과 섹터 22의 VA 0x022C0000을 설정 제공자와 연결했다. 배포 이미지의 두 섹터는 바이트 단위로 같다. 이것은 초기 배포 내용의 비교이며 사용 중인 카메라의 두 복사본이 같다는 뜻은 아니다. 기존 섹터 순서 검증 · 복사본 해시·주소

섹터 내 범위길이대응 RAM직접 확인한 사용
+0x00000x23B40x404A4F20색 공간 0x15C·RAW 형식 0x97을 포함한 설정
+0x40000x1000x404A4628키 0x38, 바이트 +0xE4의 32비트 세대 카운터
+0x60000x7F80x404A4728별도 제공자의 저장 블록; 개별 필드 의미는 미확정

0x700770…0x700788의 원본 연결 구간은 설정 객체 +0xC에 첫 RAM 주소를 넣는다. 0x7007A4는 그 내용을 객체 +0x14의 현재값으로 복사한다. 이어 0x700E84의 설정 쓰기가 두 위치를 함께 바꾼다. 따라서 앞선 메뉴 검증에서 관찰한 RAM 미러를 이 저장 버퍼와 연결할 수 있다. 이 실행은 상위 싱글턴 접근자가 관리자를 반환한 이후부터 시작했다. 연결·복사·쓰기 대조

2. 표식과 세대 카운터를 따로 검사한다

설정 복사본 선택은 양쪽 표식의 유효·무효와 선호값 0·1을 조합한 8건으로 대조했다. A·B의 내부 바이트를 서로 다르게 바꿔 실제로 어느 쪽을 읽는지 확인했다. 둘 다 무효인 경우 선택 함수 자체는 A를 반환하지만, 후속 읽기 함수가 무효를 확인해 기본값을 사용했다. 이 두 단계를 분리하지 않으면 잘못된 설정을 읽는다고 오해할 수 있다. main_selection_cases

세대 선택은 10건을 실행했다. 양쪽이 유효하면 큰 카운터를 고르고 같으면 A를 고른다. 예외적으로 A=0xFFFFFFFF, B=0에서는 B, 반대 조합에서는 A를 선택했다. 한쪽 메타데이터가 무효면 유효한 쪽을 고른다. 일반적인 순환 순서 알고리즘 전체를 입증한 것이 아니라 원본에 있는 이 경계 처리를 확인했다. metadata_generation_cases

3. 내용이 달라야 반대쪽 섹터 쓰기를 요청한다

색 공간 변경을 양방향 저장 위치에서 실행했고 RAW 형식 변경도 같은 경로에 도달했다. sRGB 값 0을 다시 쓰는 경우 원본 setter는 현재값과 미러에 각각 기록했지만, 섹터 비교가 같아서 쓰기 요청은 0건이었다. AdobeRGB 값 1로 바꾸면 반대쪽 섹터 요청이 1건 생겼고 카운터가 5에서 6으로 바뀌었다. connected_save_cases

쓰기 경계에 오류 1·2·3을 각각 공급하면 상위 함수는 같은 값을 반환했다. 이 경우에도 RAM의 설정과 증가한 카운터는 그대로 남았다. 카운터 0xFFFFFFFF에서 증가시키면 0이 됐다. 오류 입력은 호출자 동작을 확인하기 위한 값이며 실제 하위 계층에서 모든 오류가 그대로 올라온다는 주장은 아니다. 특히 앞선 프로그램 명령의 오류 전달과 구분해야 한다.

독립 검토 뒤 두 선택값이 다른 사례를 추가했다. 메타데이터 선택은 관리자 +0x2CB, 주 설정의 표식 보정 결과는 +0x2CC다. 메타데이터가 A를 고르고 B만 주 설정 표식 검사를 통과하면, 주 설정은 B에서 읽지만 섹터 준비의 바탕은 A이고 쓰기 요청 대상은 B였다. 블록 밖의 서로 다른 표식 바이트로 이 차이를 확인했다. 따라서 이 경로가 마지막 유효 설정 복사본을 항상 보존한다고 주장할 수 없다. metadata_a_main_b

4. 29건의 함수 재생과 물리 저장 검증을 구분한다

python verify_settings_storage.py decoded.bin --compare analysis/settings-storage.json
python verify_installation.py decoded.bin --emulate --compare analysis/installation.json
python verify_color_ui.py decoded.bin --compare analysis/color-ui.json

Unicorn 2.1.4에서 설정 선택 8건, 세대 선택 10건, 연결된 설정·저장 11건을 재현했다. 원본 객체의 가상 함수 표와 읽기·복사·설정·준비·비교 명령을 사용했다. 동기화·메일박스 시작과 종료, 실제 섹터 쓰기는 명시적으로 대체했다. 검증 중 합성 플래시 영역도 바뀌지 않았는지 검사했다. 실행 경계와 단정 검사

이 결과로 보존 섹터 13과 22의 설정 저장 역할을 좁혔다. 섹터 14…21의 모든 필드, 실제 전원 차단 시 복구, 쓰기 후 활성 복사본의 전환 시점, 재부팅 후 설정 유지와 물리 플래시 수명은 검증하지 않았다. 메뉴 이벤트에서 저장 스케줄러까지 한 번에 실행한 시험도 아니다.

다른 보존 영역의 후속 검증: 섹터 14는 등록 객체의 32바이트 레코드를 별도로 저장한다. 이 경로의 상위 저장 함수는 같은 내용이어도 백엔드를 호출했다.
