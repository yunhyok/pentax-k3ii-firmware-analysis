촬영 준비와 보존 레코드 · 섹터 13·22

설정 복사본 두 벌: 읽을 쪽을 고르고 반대쪽 섹터에 쓰기를 요청하는 과정

메뉴에서 바꾼 설정이 전원을 꺼도 남으려면 플래시에 기록되어야 합니다. K-3 II 펌웨어는 설정을 섹터 두 곳에 한 벌씩 둡니다. 부팅 때 어느 쪽을 읽고, 저장할 때 어느 쪽에 쓰기를 요청하는지 원본 코드로 확인했습니다.

이 문서에서

  1. 배경: 설정을 왜 두 벌로 두는가
  2. 섹터 13과 22에 같은 구조의 설정 복사본이 있습니다
  3. 읽을 복사본은 두 단계로 고릅니다
  4. 내용이 달라졌을 때만 반대쪽 섹터에 쓰기를 요청합니다
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 업데이트가 건너뛰는 섹터 가운데 13과 22에 같은 구조의 설정 복사본이 하나씩 있습니다. 복사본마다 주 설정 블록, 세대 카운터가 든 메타데이터 블록, 용도를 정하지 못한 블록이 있습니다.
  • 읽을 복사본은 두 단계로 고릅니다. 메타데이터 블록의 마커와 세대 카운터로 한쪽을 고르고 주 설정 블록의 마커로 한 번 더 보정합니다. 주 설정이 양쪽 다 무효이면 펌웨어 기본값을 읽습니다.
  • 저장할 때는 메타데이터가 고른 섹터에 RAM의 세 블록을 덮어 원래 내용과 비교합니다. 같으면 쓰기를 요청하지 않습니다. 다르면 세대 카운터를 1 올리고 반대쪽 섹터에 쓰기를 요청합니다.
  • 두 단계의 선택이 서로 다른 섹터를 가리킬 수 있습니다. 그 경우 유효한 주 설정이 있는 유일한 섹터가 쓰기 대상이 됐습니다. 이 경로가 마지막 유효 복사본을 항상 남겨 둔다고 말할 수 없습니다.
  • 원본 함수 실행 29건으로 확인했습니다. 실제 플래시 기록, 전원 차단 뒤 복구, 재부팅 뒤 설정 유지는 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 주 설정 복사본 선택 8건, 세대 선택 10건
  • 설정 변경에서 저장 요청까지 이어 실행한 11건(쓰기 요청 9회, 요청 없음 2건)
  • 배포 펌웨어에 든 두 섹터가 바이트 단위로 같음

모델 시험 조건으로 정한 것

  • 선택·저장에 쓴 객체는 원본 가상 함수 표를 붙인 합성 객체
  • 두 섹터에는 배포 펌웨어의 내용을 넣고 마커·카운터·설정 바이트만 변경
  • 동기화 함수와 섹터 쓰기 함수는 대체하고 쓰기 결과값을 공급

미확인 확인하지 않은 것

  • 실제 플래시 기록과 수명, 전원이 끊겼을 때의 복구
  • 쓰기 뒤에 읽는 복사본이 바뀌는 시점, 재부팅 뒤 설정 유지
  • 메뉴 조작에서 저장 스케줄러까지 한 번에 이어지는 실행
  • 세 번째 블록의 필드 의미

배경: 설정을 왜 두 벌로 두는가

플래시 메모리는 저장된 값을 고치기 전에 그 구역을 블록 단위로 먼저 지워야 합니다(Zephyr 플래시 문서). 설정 한 바이트만 바뀌어도 그 바이트가 든 구역 전체를 다시 쓰게 됩니다. 지우고 다시 쓰는 도중에 전원이 끊기면 내용을 잃을 수 있습니다.

그래서 임베디드 소프트웨어는 흔히 복사본을 두 벌 두고 새 내용은 지금 쓰고 있지 않은 쪽에 기록합니다. 부트로더 U-Boot의 이중 환경 저장이 잘 알려진 예입니다. U-Boot는 저장 도중 전원이 끊겨도 유효한 백업이 남도록 복사본을 하나 더 둡니다(env/Kconfig의 ENV_REDUNDANT). 두 복사본이 모두 유효하면 저장할 때마다 올리는 일련번호가 큰 쪽을 고릅니다(env/common.c의 env_check_redund).

참고

위 내용은 일반적인 설계 방식의 설명입니다. K-3 II가 같은 목적으로 이렇게 설계됐는지, 전원이 끊겼을 때 실제로 복구되는지는 이 연구에서 확인하지 않았습니다. 아래에서 확인한 것은 펌웨어 코드가 복사본을 고르고 쓰기를 요청하는 규칙입니다.

읽는 법

섹터 번호는 플래시를 128KiB(0x20000바이트)씩 나눠 0부터 센 번호입니다. 플래시·RAM 위치는 실행 주소(VA)로, 함수 주소는 복호화한 펌웨어 파일 안의 오프셋으로 적었습니다. “쓰기 요청”은 섹터 쓰기 함수를 호출했다는 뜻이며 플래시 기록이 성공했다는 뜻이 아닙니다.

섹터 13과 22에 같은 구조의 설정 복사본이 있습니다

두 섹터는 각각 세 블록을 담고 블록마다 대응하는 RAM 사본이 있습니다. 저장할 때 이 세 블록 밖의 바이트는 그대로 유지됩니다.

+0x00000x23B40x404A4F20색 공간(설정 0x15C)과 RAW 형식(설정 0x97)을 포함한 설정값

일반 업데이트 루틴은 128KiB 섹터 13~22를 건너뜁니다(업데이트 전송과 기록 오류). 그중 섹터 13(0x021A0000)과 섹터 22(0x022C0000)가 설정 공급자와 연결되어 있습니다. 배포 펌웨어 파일에 든 두 섹터는 바이트 단위로 같습니다. 이것은 배포 파일의 비교입니다. 사용 중인 카메라의 두 복사본이 같다는 뜻이 아닙니다.

메뉴가 고치는 RAM 사본이 곧 저장용 사본입니다

원본 연결 구간은 메뉴 설정 객체에 주 설정 블록의 RAM 주소를 넣습니다. 이어지는 함수가 그 내용을 객체 안의 현재값 영역으로 복사하고 설정 쓰기 함수는 현재값과 RAM 사본 두 곳을 함께 바꿉니다. 색공간 메뉴와 표시에서 관찰한 “현재값과 미러에 1바이트씩 기록”의 미러가 바로 이 저장용 RAM 사본입니다.

이 실행은 상위의 싱글턴 접근 함수가 관리자를 돌려준 다음 지점에서 시작했습니다.

읽을 복사본은 두 단계로 고릅니다

먼저 메타데이터 블록으로 “선호하는 쪽”을 정하고 그다음 주 설정 블록의 마커를 보아 그 선택을 유지하거나 바꿉니다. 두 단계의 결과는 관리자의 서로 다른 바이트에 저장됩니다.

  1. 세대 선택메타데이터 블록의 마커와 세대 카운터로 선호 쪽 결정
  2. 주 설정 검사주 설정 블록의 두 마커로 선호 쪽을 유지하거나 변경
  3. RAM으로 읽기유효한 쪽의 0x23B4바이트, 둘 다 무효이면 기본값

1단계: 메타데이터의 세대 선택

양쪽 메타데이터가 유효하면 세대 카운터가 큰 쪽을 고릅니다. 같으면 A입니다. 한쪽만 유효하면 그쪽을 고릅니다. 카운터가 0xFFFFFFFF와 0으로 만나는 경우에는 예외적으로 0인 쪽을 고릅니다.

카운터가 최댓값에서 0으로 넘어간 직후에도 새로 쓴 쪽을 고르기 위한 처리로 읽을 수 있습니다. U-Boot의 env_check_redund도 일련번호가 255와 0으로 만나면 0인 쪽을 고르는 같은 모양의 예외를 둡니다. 다만 여기서 확인한 것은 원본 코드에 있는 이 경계 처리까지입니다. 일반적인 순환 순서 알고리즘 전체는 입증하지 않았습니다.

둘 다 유효하면 1단계의 선호를 따르고 한쪽만 유효하면 그쪽을 고릅니다. A와 B의 블록 안 바이트를 서로 다르게 바꿔 두고 실제로 어느 쪽을 읽는지 확인했습니다.

주의할 점 두 가지

둘 다 무효일 때 선택 함수 자체는 A를 돌려줍니다. 그러나 뒤따르는 읽기 함수가 무효임을 확인하고 기본값을 씁니다. 두 단계를 나눠 보지 않으면 “무효인 설정을 읽는다”고 오해할 수 있습니다.

이 검사는 블록 양끝의 마커 두 개가 맞는지만 봅니다. 설정 블록 전체의 무결성 검사로 넓혀 해석하지 않았습니다.

내용이 달라졌을 때만 반대쪽 섹터에 쓰기를 요청합니다

저장 함수는 메타데이터가 고른 섹터를 바탕으로 새 섹터 내용을 만든 뒤 원래 내용과 비교합니다. 같으면 아무것도 요청하지 않고 다르면 세대 카운터를 올려 반대쪽 섹터에 통째로 쓰기를 요청합니다.

표에서 읽을 수 있는 것은 네 가지입니다.

  • 같은 값을 다시 확정하면 RAM에는 쓰지만 섹터 쓰기는 요청하지 않습니다. 설정 쓰기 함수는 11건 모두에서 현재값과 RAM 사본에 한 번씩 기록했습니다. 값이 같았던 두 건은 섹터 비교가 같게 나와 요청이 0건이었습니다.
  • 값이 바뀌면 반대쪽 섹터에 요청이 1건 생깁니다. 색 공간은 양방향 모두에서, RAW 형식 변경도 같은 경로에서 확인했습니다.
  • 쓰기 결과값은 그대로 올라옵니다. 섹터 쓰기 함수 자리에 1·2·3을 넣으면 저장 함수도 같은 값을 반환했습니다. 이때도 RAM의 설정과 올라간 카운터는 그대로 남았습니다.
  • 카운터는 최댓값 다음에 0이 됩니다.

넣어 준 결과값은 호출자의 동작을 보려는 값입니다. 실제 하위 계층의 모든 오류가 이 값으로 올라온다는 주장이 아닙니다. 특히 프로그램 명령의 오류가 전달되지 않는 지점과는 다른 층의 이야기입니다.

두 선택이 엇갈리면 유효한 복사본이 쓰기 대상이 됩니다

1단계(메타데이터)와 2단계(주 설정)의 선택은 따로 저장됩니다. 읽기는 2단계의 결과를 따르지만 저장 함수가 바탕 섹터와 쓰기 대상을 정할 때는 1단계의 결과만 봅니다. 메타데이터는 A를 고르고 주 설정 마커는 B만 유효한 상태를 만들어 저장을 실행했습니다.

주 설정 블록 안과 세 블록 밖에 서로 다른 표시 바이트를 넣어 두어, 준비 버퍼의 바탕이 A이고 주 설정 내용은 B에서 온 것임을 구분했습니다. 이 결과로 볼 때 이 저장 경로가 마지막 유효 설정 복사본을 항상 보존한다고 주장할 수 없습니다. 실제 카메라에서 이런 상태가 생기는지는 확인하지 않았습니다.

한계와 남은 과제

이 결과는 보존 섹터 13과 22가 설정 저장에 쓰인다는 것과, 복사본 선택·쓰기 요청의 규칙을 좁힌 것입니다. 함수 단위의 재현 29건과 물리 저장의 검증은 다른 문제입니다.

  • 물리 기록 — 섹터 쓰기 함수 안쪽, 실제 플래시 기록, 플래시 수명은 다루지 않았습니다.
  • 전원 차단과 복구 — 쓰는 도중 전원이 끊겼을 때 어떤 복사본이 남는지 시험하지 않았습니다.
  • 복사본 전환 — 쓰기가 끝난 뒤 읽는 복사본이 언제 바뀌는지, 재부팅 뒤 설정이 유지되는지 확인하지 않았습니다.
  • 연속 실행: 메뉴 이벤트에서 저장 스케줄러까지를 한 번에 실행하지는 않았습니다. 부팅 전체 대신 선택 함수와 저장 함수를 따로 실행했습니다.
  • 다른 보존 섹터: 섹터 14~21의 모든 필드를 이 문서가 설명하지는 않습니다. 섹터 14는 보존 섹터 14의 진단 레코드에서 다룹니다. 그쪽의 상위 저장 함수는 내용이 같아도 섹터 쓰기 함수를 호출합니다(저장 요청).
