JPEG 출력 버퍼와
Reversal Film 메뉴의 연결

색 처리 출력과 스케일러, JPEG 압축기, Exif 작성기가 같은 작업의 포인터와 길이를 전달하는 조건부 경로를 연결했다. selector=6은 실제 메뉴 이벤트와 문자열 리소스에서도 Reversal Film에 대응한다. 출력은 파일시스템 어댑터까지 추적했으며, SD 명령·DMA와 실기 기록은 별도 검증 범위다.

초기 분석앞선 톤·색 처리 분석버퍼 전달Exif·파일 출력메뉴 이벤트검증·재현남은 범위

후속 검증: 이 보고서에서 남았던 백엔드 A→SD 명령·ADMA2와 대체 버퍼 분기를 추가 추적했다. 아래는 앞선 분석 시점의 범위다.

코드 주소는 해제 이미지의 파일 오프셋이다. 분석용 VA는 파일 오프셋 + 0x02000000이다. 장치 주소 0x2002… / 0x200E…와 구분한다. 도식은 코드와 디스크립터의 연결이며 실제 촬영을 관측한 기록은 아니다.

1. RAW 작업이 사용하는 JPEG 모듈은 별도로 있었다

앞선 분석은 모듈 8의 명령 0x00C00003과 코덱 0x53C42C를 찾았다. 그러나 검사한 RAW 작업 명령열에는 그 모듈을 직접 호출하는 항목이 없었다. 후속 분석에서 모듈 16, 명령 0x00C00002를 확인했다. 이 모듈은 0x575EB8에서 생성되고 0x57711C → 0x576CFC로 메시지를 받으며, 하위 코덱 0x53D700을 사용한다. 두 JPEG 경로를 하나로 취급해서는 안 된다. 생성자·가상 함수표·명령·호출 근거

색 처리의 직접 주소 경로에서는 0x6597E0/7EC/7F8이 작업의 세 주소를 읽어 CPP 설정 +0x2C/+0x30/+0x34에 넣는다. 0x58BDAC/B8/C4의 장치 설정과 스케일러 입력 디스크립터 0x659AC8…0x659AE8가 이 주소들을 소비한다. 다만 CPP 반복 처리 중에는 payload +0xAC의 다른 주소로 바꾸는 분기도 있다. 이 도식은 직접 주소 분기에서 성립하는 연결이며, 모든 프레임·모드를 하나의 버퍼 배치로 일반화하지 않는다. 분기 조건과 레지스터 설정

스케일러 출력 디스크립터 두 개는 JPEG 입력 payload +0/+4에도 같은 포인터로 들어간다. 압축 출력 주소는 0x660854에서 작업의 포인터 배열을 읽어 출력 디스크립터에 넣고, StoreImage의 0x657984 → 0x65798C에서도 같은 배열을 읽는다. 길이는 장치 주소 0x200E0020의 완료 결과에서 시작해 콜백, 출력 디스크립터, 작업의 길이 배열을 거친다. 포인터뿐 아니라 압축된 유효 바이트 수가 전달되는 경로도 연결했다. 주소·길이 생산자와 소비자

주소 정렬 조건도 확인했다. B2Y 장치는 하위 3비트, JPEG 장치는 하위 4비트를 지운 주소를 사용한다. 따라서 디스크립터 주소와 장치 주소의 일치에는 각각 8바이트·16바이트 정렬이 필요하다. 일반 목적지 배치 분기 0x660808…0x660844 → 0x65420C는 두 압축 목적지 주소를 16바이트 단위로 올림한다. 이 분기는 원본 명령으로 검증했다. 별도로 넣은 비정렬 합성 주소는 장치 주소와 저장 주소가 달라졌으며, 모든 입력·대체 배치 분기의 정렬까지 검증한 것은 아니다.

원본 레시피 생성 함수 0x76E7AC도 다시 실행했다. 표는 operation 5의 모듈 호출 위치이며 0부터 센다. 레시피 ID는 톤 selector와 별개다. 첫 JPEG 결과는 길이가 0보다 크고 출력 디스크립터의 용량 이내일 때 받아들이며, 그렇지 않으면 0x576C98의 재시도 분기로 간다. 재시도 이후의 모든 경로는 이번 실행 범위에 넣지 않았다.

2. Exif 작성기는 헤더와 압축 데이터를 나눠 쓴다

StoreImage+0x420의 쓰기 요청은 0x5A7D5C에서 +0x844의 서비스로 전달된다. 서비스의 실제 구현 0x7625F8은 같은 요청을 큐 명령 0으로 보낸다. 수신부 0x7C6704 → 0x7C6658는 파일 형식에 따라 작성기를 선택하며, 확인한 JPEG 분기는 0x7CD4B4 → 0x7CD3F0이다. 여기서 0x82D8B8(index=2)가 앞 절의 주 이미지 디스크립터를 반환한다. 쓰기 서비스·작성기 선택 근거 · 요청에 주 이미지 디스크립터를 넣는 경로

일반 저장 경로의 0x74566C는 부모 객체 +0x18에 파일시스템 객체의 보조 인터페이스를 넣는다. 작성기의 seek/write는 가상 함수표 0x02A6208C를 통해 0x6F024C / 0x6F01B8로 이어진다. 어댑터는 파일 핸들의 +4로 백엔드를 선택하고, +0의 내부 핸들과 버퍼 주소·길이를 넘긴다. 이 어댑터까지 포함한 원본 명령 실행에서도 두 조각의 주소·길이가 보존됐다. 파일시스템 연결과 실행 기록

앞선 보고서의 0x5A6BE8 → 0x82B3C0 경로는 일반 슬롯에서 0x744784의 저장 준비 명령 0x20000으로 이어진다. 이를 JPEG 데이터 쓰기로 해석하면 안 된다. 실제 이미지 쓰기 서비스와 준비 명령은 서로 다른 경로다.

파일시스템 어댑터 이후에는 선택된 백엔드의 가상 함수 호출이 남는다. 이번 분석은 그 백엔드의 SD 명령·블록 DMA까지 연결하거나 카메라에서 기록 성공을 확인한 결과가 아니다.

3. selector=6의 실제 메뉴 이벤트와 문자열

앞선 결론은 selector 6 → ImageTone 7의 메타데이터 변환에 근거했다. 이제 화면 객체의 가상 함수표, 이벤트 ID, 목록 리소스, 설정 쓰기까지 별도로 연결했다. 화면 이벤트 0x01205010은 0x346848의 11개 분기 중 아홉 번째이며, 0x3469AC에서 선택값 6을 0x3466EC에 전달한다. 이벤트 분기·원본 실행 결과

화면 생성자 0x343474는 가상 함수표 VA 0x02A5DF60을 설치한다. 공통 이벤트 진입점 0x6D5ED0이 그 표의 +0xC0를 호출한다. 반대 방향인 현재 선택값→이벤트 ID도 +0xBC의 0x34617C로 검증했으며, 선택값 6에서 0x01205010을 반환했다.

화면 목록 0x01205006의 리소스는 0x981F74의 선택 키 배열 [1,0,2,3,4,8,5,7,6,10,9]를 가리킨다. 키 6의 레코드 0x981FB4는 다국어 포인터 레코드 0xE3E004로 연결되고, 첫 언어 슬롯의 문자열은 0xE4C316에 있다. 0이 아닌 글리프 코드에 0x1E를 더하면 정확히 Reversal Film이 된다. 인접한 10개 이름도 같은 규칙으로 대조했다. 따라서 메뉴 표시 순서를 EXIF 값으로 가정하지 않고 펌웨어 자체에서 이름을 확인했다. 11개 이벤트·키·문자열 대응

앞선 기본 프로필 조회에서 ID 41도 selector 6을 반환했지만, 이 메뉴의 키 6과 ID 41을 같은 화면 항목으로 간주하지 않는다. 이번에 직접 연결한 것은 메뉴 이벤트 0x01205010과 공통 선택값 6이다.

4. 검증과 재현

동일한 v1.12 해제 이미지의 SHA-256 1b87bf35b290e4b4e8910beb4055c34f97504b65e249ad65e5ccc0402bd14cfc를 확인한 뒤 분석했다. 공개 JSON에는 호출·가상 함수표·구간 해시와 실행 범위가 들어 있다. 원본 펌웨어나 전체 디스어셈블은 공개하지 않는다.

원본 명령 실행 환경은 Python 3.12와 Unicorn 2.1.4다. 원본 CPU 명령은 실행하고 장치·GUI·파일 출력 경계는 합성 메모리나 훅으로 대체했다. CI는 펌웨어 없이 실행되는 단위 테스트와 공개 문서 검사를 수행하므로, 로컬 원본 명령 실행과 검증 범위가 다르다.

5. K-3 III와 같은 방법으로 확인한 범위

K-3 III의 모드·리소스 분석과 JPEG·ISP 분석에서 사용한 방식처럼 생성자·수신부·디스크립터·완료 콜백을 연결하고 가능한 작은 함수는 원본 명령으로 실행했다. K-3 III의 enum, 모듈 번호, MMIO 주소는 가져오지 않았다.

이번에 해소한 것은 조건부 소프트웨어 버퍼 경로와 실제 메뉴 이벤트의 연결이다. 남은 항목은 전체 모드의 픽셀 형식·크로마 배치, CPP의 대체 출력 분기, 파일시스템 백엔드 이후 SD 명령·DMA, 실기 JPEG 픽셀 비교다. 정확한 SoC·보조 MCU 부품 번호도 기존 미확정 상태를 유지한다. 카메라 플래시나 실기 실행은 하지 않았다.
