영상 처리와 저장 경로 · 영상 버퍼가 파일 조각이 되기까지

JPEG 출력 버퍼가 파일시스템에 닿는 경로와 Reversal Film 메뉴

색 설정이 끝난 영상은 크기 조절과 JPEG 압축을 거쳐 파일로 저장됩니다. 그 사이에 영상 버퍼의 주소와 길이가 어떻게 넘어가는지, 그리고 메뉴에서 고른 Custom Image가 어떻게 톤 선택값이 되는지를 이었습니다.

이 문서에서

  1. 배경: 버퍼를 넘긴다는 것의 의미
  2. 색 처리 출력에서 StoreImage까지 같은 주소와 길이가 전달됩니다
  3. Exif 작성기는 헤더와 압축 데이터를 두 조각으로 나눠 씁니다
  4. 메뉴에서 Reversal Film을 고르면 설정값 6이 기록됩니다
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • RAW 작업의 레시피가 쓰는 JPEG 압축 모듈은 모듈 16입니다. 앞서 찾았던 모듈 8과는 다른 경로입니다.
  • 색 처리 출력 → 스케일러 → JPEG 모듈 16 → StoreImage가 같은 작업 객체의 주소·길이 필드를 이어서 쓰고 읽습니다. 압축 버퍼의 주소뿐 아니라 압축된 유효 바이트 수가 전달되는 경로도 이었습니다. 다만 이 연결은 색 처리의 직접 주소 분기에서 성립하는 조건부 경로입니다.
  • Exif 작성기는 헤더와 압축 데이터를 큰 버퍼 하나로 합치지 않습니다. 두 조각을 차례로 “위치 이동 → 쓰기”하며, 압축 버퍼의 원래 주소와 길이가 파일시스템 어댑터까지 그대로 전달됩니다.
  • Custom Image 메뉴의 아홉 번째 항목을 고르는 이벤트가 설정값 6을 기록하고, 펌웨어에 든 그 항목의 영어 문자열은 Reversal Film입니다. 메뉴 순서를 짐작하지 않고 펌웨어 안에서 이름을 확인했습니다.
  • 모두 PC 에뮬레이터에서 원본 코드를 구간별로 실행한 결과입니다. 실제 버튼 입력, JPEG 생성, SD 카드 기록은 관측하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 레시피 4종의 모듈 순서, 색 처리 출력 평면 3개의 주소 전달, JPEG 스트림 2개의 주소·길이 전달
  • Exif 준비 함수와 출력 루프 10건: 성공 1건과 실패 4건씩, 두 출력 경로
  • 메뉴 이벤트 11개의 선택값·설정 기록·톤 분기, 역방향 조회 11건, 범위 밖 이벤트 2개와 입력 차단 1건

정적 분석 코드를 읽어 판단

  • 버퍼 경로의 분기 대상 103개, 명령 81개, 상수 13개
  • 쓰기 서비스가 파일 형식에 따라 작성기를 고르는 구조
  • 첫 압축 결과가 조건을 벗어날 때 가는 재시도 분기의 위치

모델 시험 조건으로 정한 것

  • 버퍼 주소, 압축 길이, 헤더·데이터 내용은 합성 값
  • 장치 레지스터는 일반 메모리, 화면·위젯 객체는 시험용 객체
  • 위치 이동·쓰기 호출은 가로채서 인수만 기록

미확인 확인하지 않은 것

  • 모든 모드의 픽셀 형식과 색차 배치, 색 처리의 대체 출력 분기
  • 두 출력 번호가 어느 저장 슬롯·해상도인지
  • 물리 버튼 입력, LCD 표시, 설정의 영구 저장
  • 실제 JPEG 픽셀과 SD 카드 기록

배경: 버퍼를 넘긴다는 것의 의미

영상 한 장은 큰 메모리 덩어리입니다. 펌웨어는 처리 단계마다 이것을 복사해 옮기지 않고 주소를 적은 쪽지를 넘깁니다. 이 문서에서 디스크립터라고 부르는 구조체가 그 쪽지입니다.

쉽게 말하면

앞 단계가 “결과는 이 주소에 있다”고 적어 두면 뒤 단계가 그 주소를 읽어 일을 시작합니다. 이 문서가 “연결했다”고 말하는 것은, 앞 단계가 적는 칸과 뒤 단계가 읽는 칸이 같다는 것을 코드에서 확인하고 그 구간을 실행해 같은 값이 넘어오는지 본 것입니다.

여기서는 두 가지 빈칸을 채웁니다. 앞 문서는 RAW 작업이 톤 설정에 닿는 데까지 이었지만 다음 두 가지를 남겼습니다.

  • 처리된 영상이 JPEG 압축기로, 압축 결과가 Exif 작성기로 넘어가는 연결
  • 톤 선택값 6을 화면 메뉴에서 실제로 기록하는 경로와 그 항목의 표시 이름

읽기 전에 알아 둘 표기

  • 코드 주소는 복호화한 이미지의 파일 오프셋입니다. 분석용 가상 주소는 여기에 0x02000000을 더한 값입니다. 0x2002…, 0x200E…로 시작하는 값은 장치 레지스터 주소입니다.
  • 작업 +0x…는 작업 객체 안에서의 위치입니다. 전달 데이터(payload)는 모듈마다 작업 객체 안에 하나씩 있습니다.
  • JPEG 파일은 FF D8(SOI)로 시작하고, Exif 정보는 바로 뒤의 APP1 구획(FF E1)에 들어갑니다. 미국 의회도서관의 Exif JPEG 형식 설명에 구조가 정리되어 있습니다. K-3 II의 JPEG는 Exif 2.30을 따릅니다(리코 사양).

색 처리 출력에서 StoreImage까지 같은 주소와 길이가 전달됩니다

색 처리 모듈이 정한 출력 평면 주소를 스케일러가 입력으로 읽고, 스케일러의 출력 디스크립터를 JPEG 모듈 16이 입력으로 읽습니다. 압축 결과의 주소와 길이는 작업 객체에 남아 StoreImage의 저장 요청에 들어갑니다.

JPEG 모듈은 두 개가 있습니다

앞 문서에서 찾은 JPEG 코덱은 모듈 8이었습니다. 그런데 RAW 레시피에는 모듈 8을 직접 부르는 항목이 없었습니다. 레시피가 실제로 부르는 것은 별도의 모듈 16이며, 다른 하위 코덱과 다른 레지스터 묶음을 씁니다. 두 JPEG 경로를 하나로 다루면 안 됩니다.

조건부 경로입니다

이 그림은 색 처리 모듈이 작업의 세 주소를 직접 쓰는 분기에서 성립합니다. 색 처리를 두 번 반복하는 경우에는 전달 데이터의 다른 주소로 바꾸는 분기가 있습니다. 스케일러와 압축기의 출력 사용 플래그, StoreImage의 주 JPEG 분기도 조건입니다. 모든 프레임과 모드가 같은 버퍼 배치를 쓴다고 일반화하지 않습니다. 대체 분기는 파일시스템에서 SD·DMA까지와 백엔드 B와 두 번째 CPP 출력에서 다룹니다.

주소 정렬 조건

주소를 장치 레지스터에 기록할 때 아래 비트가 떨어져 나갑니다. 색 처리 출력 쪽은 하위 3비트, JPEG 쪽은 하위 4비트입니다. 따라서 디스크립터에 적힌 주소와 장치에 기록된 주소가 같으려면 각각 8바이트, 16바이트 단위로 정렬되어 있어야 합니다.

  • 압축 목적지를 배치하는 일반 분기는 두 목적지 주소를 16바이트 단위로 올림합니다. 이 분기를 원본 코드로 실행해 정렬된 두 주소가 나오는 것을 확인했습니다.
  • 일부러 정렬되지 않은 합성 주소를 넣은 사례에서는 장치에 기록된 주소와 저장 요청에 들어간 주소가 달라졌습니다. 코드가 정렬을 따로 강제하지 않는다는 뜻입니다.
  • 모든 입력 분기와 대체 배치 분기의 정렬까지 확인한 것은 아닙니다.

Exif 작성기는 헤더와 압축 데이터를 두 조각으로 나눠 씁니다

작성기는 헤더 버퍼와 압축 데이터 버퍼를 “파일 위치, 주소, 길이” 기록 두 개로 정리한 뒤, 조각마다 위치 이동과 쓰기를 호출합니다. 압축 데이터를 새 버퍼로 복사하지 않습니다.

작성기가 만드는 12바이트 기록 두 개 (파일 위치, 주소, 길이)
기록 위치파일 위치데이터 주소바이트 수

작성기 +0x60 (압축 데이터)작성기 +0x50의 값주 이미지 디스크립터 +0x34주 이미지 디스크립터 +0x28

둘째 기록의 주소와 길이는 앞 절에서 본 StoreImage 주 이미지 디스크립터의 두 칸입니다. JPEG 모듈 16이 남긴 압축 버퍼가 그대로 파일 쓰기의 원본이 됩니다.

쓰기 요청이 작성기에 닿는 경로

  1. StoreImage가 쓰기 요청을 보냅니다 요청 구조체를 쓰기 서비스에 전달합니다.
  2. 쓰기 서비스가 큐에 넣습니다 같은 요청을 큐 명령 0으로 보냅니다.
  3. 수신부가 작성기를 고릅니다 파일 형식에 따라 작성기가 달라집니다. 모든 요청이 Exif JPEG 작성기로 가는 것은 아니며, 여기서 확인한 것은 JPEG 분기입니다.
  4. 작성기가 주 이미지 디스크립터를 받습니다 요청의 디스크립터 묶음에서 색인 2를 꺼내면 앞 절의 주 이미지 디스크립터가 나옵니다.
  5. 출력 루프가 두 조각을 내보냅니다 일반 저장 경로에서는 출력 대상이 파일시스템 객체의 보조 인터페이스로 연결되어 있습니다.

실행해 확인한 10건

준비 함수와 출력 루프를 원본 코드로 실행하고, 위치 이동·쓰기 호출을 가로채 인수를 기록했습니다. 헤더 32바이트와 압축 데이터 47바이트짜리 합성 조각을 썼습니다. 출력 인터페이스에서 직접 가로챈 경로와 파일시스템 어댑터를 거친 경로를 각각 5건씩 돌렸습니다.

메뉴에서 Reversal Film을 고르면 설정값 6이 기록됩니다

Custom Image 화면의 이벤트 처리기는 아홉 번째 항목의 이벤트를 받아 설정값 6을 기록합니다. 같은 화면의 목록 리소스에서 키 6의 영어 문자열을 복원하면 Reversal Film입니다.

앞 문서의 결론은 “선택값 6이 메타데이터의 ImageTone 값 7로 바뀐다”는 변환에 기대고 있었습니다. 여기서는 화면 쪽 근거를 따로 이었습니다.

  • 이벤트에서 설정까지 — 화면 객체의 가상 함수표에 등록된 이벤트 처리기를 실행했습니다. 이벤트마다 선택값이 기록되고, 그 값이 활성 프로필을 거쳐 설정 레코드와 현상 설정으로 전달되며, 톤 선택 함수가 해당 분기로 들어가는 것까지 확인했습니다.
  • 반대 방향 — 현재 선택값에서 이벤트 ID를 구하는 함수도 실행했습니다. 선택값 6에서 Reversal Film의 이벤트 ID가 돌아왔습니다.
  • 이름 — 목록 리소스의 키 배열, 키별 문자열 레코드, 글자 코드를 파일에서 읽었습니다. 0이 아닌 글자 코드에 0x1E를 더하면 ASCII 문자가 됩니다. 11개 항목 모두 같은 규칙으로 복원했습니다.

시험 조건

실제 버튼을 누른 관측이 아닙니다. 이벤트 ID를 처리기의 입력으로 직접 넣었고, 화면 알림과 위젯 조회·활성화는 시험용 객체가 대신했습니다. 화면 배치를 갱신하는 함수는 건너뛰었습니다. 설정 흐름은 메모리에 초기화해 둔 기본 설정 묶음(뱅크 2)에서 실행했으며, 설정을 영구 저장하는 입출력은 범위 밖입니다. 대체한 경계는 검증 결과 파일에 적혀 있습니다.

정상 범위 밖의 입력

  • 목록 범위 바로 밖의 이벤트 두 개(0x01205007, 0x01205013)를 넣었을 때 설정이 바뀌지 않았습니다.
  • 입력이 차단된 상태에서 Reversal Film 이벤트를 넣었을 때도 설정이 그대로였습니다.

프로필 ID 41과의 관계

앞 문서의 기본 프로필 조회에서 프로필 ID 41도 선택값 6을 돌려주었습니다. 이 메뉴의 키 6과 프로필 ID 41을 같은 화면 항목으로 보지 않습니다. 여기서 직접 이은 것은 Reversal Film의 메뉴 이벤트와 공통 선택값 6입니다.

한계와 남은 과제

이 문서가 이은 것은 조건부 소프트웨어 버퍼 경로와 메뉴 이벤트입니다. 남은 것은 다음과 같습니다.

  • 픽셀 형식 — 모든 모드의 픽셀 형식과 색차 배치를 정하지 않았습니다.
  • 대체 분기 — 색 처리의 대체 출력 분기는 이 문서의 그림에 넣지 않았습니다. 뒤 문서들에서 일부를 다룹니다.
  • 저장 장치 — 파일시스템 어댑터 아래의 백엔드, SD 명령, DMA는 다음 문서의 범위입니다.
  • 실물 대조 — 실제 카메라에서 만든 JPEG의 픽셀과 비교하지 않았습니다. 펌웨어를 카메라에 설치하거나 카메라에서 실행한 적도 없습니다.
  • 부품 식별 — SoC와 보조 MCU의 정확한 부품 번호는 하드웨어 식별 절의 미확정 상태 그대로입니다.

추적 방법은 K-3 Mark III 연구의 모드·리소스 분석, JPEG·ISP 분석과 같습니다. 생성자, 수신부, 디스크립터, 완료 콜백을 잇고, 작은 함수는 원본 명령으로 실행했습니다. K-3 Mark III의 열거값, 모듈 번호, 레지스터 주소는 가져오지 않았습니다.
