PENTAX K-3 II · firmware 1.12 · 2026-11-08

섹터 14의 32바이트 레코드와
진단 출력·저장 요청

업데이트가 보존하는 섹터 중 하나를 저장 객체와 연결했다. 마커에 따른 적재, 다섯 워드의 읽기·쓰기, 애플리케이션 복사본과 진단 출력 인수, 섹터 저장 요청을 원본 ARM 코드로 확인했다.

업데이트의 보존 영역설정 섹터 13·22등록과 적재복사본과 진단 출력저장 요청검증 범위

함수 주소는 해제 파일 오프셋, VA와 RAM 주소는 실행 주소다. 섹터 번호는 128KiB 단위의 0부터 시작하는 인덱스다.

1. 등록 ID 0은 섹터 14의 첫 32바이트를 다룬다

생성자 호출과 등록 코드가 같은 전역 주소를 사용한다. 등록 함수 0x6E9494의 ID 0은 관리자 +0x14에 이 객체를 넣는다. 가상 함수 표 0xA5ECEC에서 RAM 주소, 플래시 주소와 길이를 읽었으며, 길이 함수 0x71C978의 반환값 0x10은 16비트 단위 16개, 즉 32바이트다. 등록·가상 함수 표 검증

원본 관리자 적재 0x6E7EB0는 첫 워드가 0xA55A5AA5이면 플래시를, 아니면 기본값을 복사했다. 0xFFFFFFFF·0·유효 마커를 대조했고 32바이트 뒤의 대조값은 유지됐다. 기본 이미지에 들어 있는 값과 실제 장치에 보존된 값이 같다고 가정하지 않았다. 세 적재 사례

오프셋길이확인한 역할

+4…+0x104워드원본 읽기·쓰기 존재, 개별 의미 미확정

2. 진단 출력은 다섯 번째 워드를 SerialNo(UID)로 표시한다

원본 0x71C998과 0x71C9A0은 +4부터 다섯 워드를 쓰고 읽는다. 서로 다른 합성값을 넣어 순서를 대조했으며 마커와 마지막 8바이트는 유지됐다. 애플리케이션 초기화 0x82E3E4…0x82E420는 등록 ID 0을 찾아 저장용 RAM의 32바이트를 객체 +0x1528에 복사했다. 필드·복사 검증기

메시지 처리기 0x74A9D0는 메시지의 다섯 워드를 애플리케이션 사본에 기록한다. 원본 처리기를 실행해 이 사본만 바뀌고 저장용 RAM은 그대로인 것을 확인했다. 이 호출과 별도의 저장 함수를 나란히 발견한 것만으로 메시지 입력이 플래시에 저장된다고 연결하지 않았다. 사본 변경과 저장용 RAM 유지

진단 경로 0x6362BC는 저장용 RAM을 가져오고 0x6362C0은 다섯 번째 워드를 읽는다. 이 값은 스택 +0x220을 거쳐 0x636300의 형식화 호출 첫 정수 인수 r2로 전달됐다. 합성값 12345678로 인수 전달을 재현했다. 형식 문자열의 첫 필드는 %ld다. 진단 인수 경계

같은 파일 생성 경로는 C:\DacLog.csv를 열고 헤더의 첫 열을 SerialNo(UID)로 쓴 뒤 공통 행 쓰기로 돌아간다. 따라서 이 이름은 펌웨어가 해당 워드에 붙인 출력 레이블이다. 실물 시리얼 번호와의 일치, 식별값을 만드는 하드웨어, 앞의 네 워드의 뜻은 확인하지 않았다. 파일 열기·형식화·쓰기를 실제로 실행한 검증도 아니다. 파일명·헤더·분기 근거

3. 저장 함수는 기존 섹터 위에 등록 객체의 RAM을 덮어 넣는다

원본 함수는 ID 0…0x2E, 0x56, 0x57, 0x62, 0x39…0x55를 순회한다. 이번 실험은 ID 0만 등록해 그 객체의 32바이트가 임시 섹터에 들어가는지 검사했다. 다른 등록 객체의 의미와 서로 겹치는 영역까지 검증한 것은 아니다. 원본 저장 순회와 전체 바이트 대조

백엔드 경계에 0·1·2·3을 반환시키면 상위 저장 함수도 각각 같은 값을 반환했다. 원본 섹터와 RAM 내용이 같은 대조에서도 0x599914 호출은 발생했다. 이는 이 상위 함수에 섹터 13·22 저장과 같은 사전 비교가 없다는 뜻이며, 하위 백엔드가 반드시 물리 쓰기를 수행한다는 뜻은 아니다. 앞선 설정 저장의 비교 조건 · 다섯 저장 사례
