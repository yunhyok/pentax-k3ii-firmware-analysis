촬영 준비와 보존 레코드 · 섹터 14

보존 섹터 14의 32바이트 레코드: 적재, 진단 출력, 저장 요청

펌웨어를 업데이트해도 지워지지 않는 플래시 구역에는 카메라가 계속 들고 있어야 하는 값이 들어 있습니다. 그중 섹터 14의 맨 앞 32바이트를 펌웨어의 어느 코드가 읽고 어느 코드가 쓰는지 따라갔습니다.

이 문서에서

  1. 배경: 업데이트가 남겨 두는 섹터와 공급자
  2. ID 0 공급자는 섹터 14의 첫 32바이트를 맡습니다
  3. RAM 사본을 읽는 곳은 애플리케이션 복사본과 진단 출력입니다
  4. 저장 함수는 섹터 14 전체를 다시 쓰도록 요청합니다
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 섹터 14의 첫 32바이트는 등록 ID 0인 공급자가 맡는 레코드입니다. 첫 워드가 정해진 마커와 같으면 플래시에서, 다르면 펌웨어에 든 기본값에서 RAM 사본으로 복사합니다.
  • 레코드의 다섯 번째 워드는 진단용 CSV 파일의 첫 열 SerialNo(UID) 자리에 인수로 넘어갑니다. 이 이름은 펌웨어가 붙인 출력 레이블입니다. 실물 시리얼 번호와 같은 값인지는 확인하지 않았습니다.
  • 애플리케이션은 32바이트를 자기 객체에 한 번 더 복사합니다. 메시지 처리기는 이 복사본만 고쳤고 공급자의 RAM 사본은 그대로였습니다. 복사본이 저장 경로로 되돌아가는 연결은 찾지 못했습니다.
  • 저장 함수는 섹터 14 전체를 준비 버퍼에 읽고 첫 32바이트만 RAM 사본으로 바꾼 뒤 섹터 쓰기를 요청합니다. 내용이 같아도 요청합니다. 실제 플래시 기록은 실행하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 생성자와 등록 코드가 같은 객체를 ID 0 자리에 등록
  • 마커 값 세 가지에서 플래시 또는 기본값을 고르는 적재
  • 다섯 워드 읽기·쓰기, 애플리케이션 복사, 메시지 처리기의 복사본 수정
  • 진단 출력 호출의 첫 정수 인수, 저장 요청 다섯 사례

정적 분석 코드를 읽어 판단

  • 진단 경로가 C:\DacLog.csv를 열고 헤더를 쓴 뒤 공통 행 쓰기로 돌아가는 흐름
  • 헤더 첫 열의 이름과 행 형식 문자열의 첫 필드

모델 시험 조건으로 정한 것

  • 관리자·소유자·애플리케이션·메시지 객체와 섹터 내용은 합성 값
  • 공급자는 ID 0만 등록
  • 저장 때의 동기화 함수와 섹터 쓰기 함수는 대체하고 반환값을 공급

미확인 확인하지 않은 것

  • 실물 카메라의 레코드 값, UID를 만드는 하드웨어, 앞 네 워드의 뜻
  • 메시지를 보내는 쪽, 애플리케이션 사본의 역전달
  • 섹터 14를 함께 쓰는 다른 공급자, 실제 플래시 기록

배경: 업데이트가 남겨 두는 섹터와 공급자

K-3 II의 일반 펌웨어 업데이트는 플래시의 섹터 13부터 22까지를 건너뜁니다(업데이트 전송과 기록 오류). 이 문서들에서는 이 구역을 보존 섹터라고 부릅니다. 설정, 픽셀 보정 레코드처럼 새 펌웨어를 넣어도 남아 있어야 하는 내용이 여기에 있습니다.

펌웨어는 이 구역을 공급자라는 객체 단위로 다룹니다. 공급자 하나는 플래시의 어느 주소에서 몇 바이트를 맡는지, RAM의 어디에 사본을 두는지, 내용이 유효한지를 답하는 함수 묶음입니다. 보존 관리자는 공급자를 ID로 찾아 차례로 적재하고, 저장할 때는 섹터 단위로 다시 모읍니다.

쉽게 말하면

보존 섹터는 서랍장이고 공급자는 서랍 한 칸의 담당자입니다. 부팅 때 담당자가 자기 칸의 내용을 책상(RAM)에 꺼내 놓고, 저장할 때는 관리자가 책상 위 내용을 서랍장 한 단(섹터) 전체로 다시 정리해 넣어 달라고 요청합니다.

주소와 섹터 번호 읽는 법

섹터 번호는 플래시를 128KiB(0x20000바이트)씩 나눠 0부터 센 번호입니다. 섹터 n의 실행 주소는 0x02000000 + n × 0x20000이므로 섹터 14는 0x021C0000입니다. 함수와 명령의 주소는 복호화한 펌웨어 파일 안의 오프셋으로, 플래시·RAM 주소는 실행 주소(VA)로 적었습니다.

ID 0 공급자는 섹터 14의 첫 32바이트를 맡습니다

부팅 때 관리자는 섹터 14의 첫 워드가 마커와 같으면 플래시에서, 다르면 펌웨어 기본값에서 32바이트를 RAM 사본으로 복사합니다.

시작 코드의 생성자 호출과 등록 코드는 같은 전역 객체를 씁니다. 등록 함수는 ID 0 자리에 이 객체를 넣습니다. 공급자의 가상 함수 표에서 RAM 주소, 플래시 주소, 길이를 돌려주는 함수를 확인했습니다. 길이 함수가 돌려주는 0x10은 16비트 값 16개, 곧 32바이트입니다.

관리자의 적재 함수는 공급자의 유효성 함수를 불러 섹터 14의 첫 워드가 마커 0xA55A5AA5인지 봅니다. 맞으면 플래시를, 아니면 펌웨어 안의 기본값을 복사합니다. 세 가지 첫 워드로 시험했고, 32바이트 앞뒤에 둔 대조값은 그대로였습니다.

RAM 사본을 읽는 곳은 애플리케이션 복사본과 진단 출력입니다

다섯 번째 워드는 진단 CSV의 SerialNo(UID) 열로 넘어가고, 32바이트 전체는 애플리케이션 객체로 복사됩니다. 메시지로 들어온 값은 그 복사본에만 반영됩니다.

다섯 워드 읽기와 쓰기

공급자에는 +4부터 다섯 워드를 한 번에 쓰는 함수와 읽는 함수가 있습니다. 서로 다른 합성 값 다섯 개를 써 넣고 다시 읽어 순서를 대조했습니다. 읽기 함수는 개수 5를 돌려주었고, 마커와 마지막 8바이트는 바뀌지 않았습니다.

애플리케이션 복사본

애플리케이션 초기화 코드는 관리자에서 ID 0 공급자를 찾아 RAM 사본 32바이트를 자기 객체의 +0x1528에 복사합니다. 별도의 메시지 처리기는 메시지에 실려 온 다섯 워드를 이 복사본에 기록합니다. 원본 처리기를 실행해 보니 복사본만 바뀌고 공급자의 RAM 사본은 그대로였습니다.

주의

메시지 처리기와 저장 함수가 따로 있다는 사실만으로 “메시지로 들어온 값이 플래시에 저장된다”고 연결하지 않았습니다. 복사본의 값이 공급자의 RAM 사본으로 돌아가는 코드는 확인하지 못했습니다.

진단 출력의 SerialNo(UID) 열

진단 경로는 공급자의 RAM 사본 주소를 얻은 뒤 다섯 번째 워드를 읽습니다. 이 값은 스택에 잠시 저장되었다가 형식화 함수 호출의 첫 정수 인수(r2)로 전달됩니다. 합성 값 12345678을 넣어 인수까지 그대로 도착하는 것을 확인했습니다. 형식 문자열 두 가지 모두 첫 필드는 %ld입니다.

같은 파일 생성 경로는 C:\DacLog.csv를 열고, 헤더의 첫 열을 SerialNo(UID)로 쓴 뒤 공통 행 쓰기 코드로 돌아갑니다. 그래서 이 이름은 펌웨어가 다섯 번째 워드에 붙인 출력 레이블입니다.

이 이름이 말해 주지 않는 것

실물 시리얼 번호와 같은 값인지, 식별값을 만드는 하드웨어가 무엇인지, 앞의 네 워드가 무엇인지는 확인하지 않았습니다. 파일 열기·형식화·쓰기를 실제로 실행한 것도 아닙니다. 실행은 형식화 함수를 부르기 직전에서 멈췄고, 파일 이름과 헤더, 공통 행 쓰기로 돌아가는 분기는 코드를 읽어 확인했습니다.

저장 함수는 섹터 14 전체를 다시 쓰도록 요청합니다

32바이트만 바뀌어도 요청 단위는 섹터 하나(128KiB)입니다. 기존 섹터를 준비 버퍼에 읽고, 등록된 공급자의 RAM 사본을 그 위에 덮은 뒤 섹터 쓰기 함수로 넘깁니다.

  1. 섹터 읽기섹터 14의 128KiB를 준비 버퍼로 복사
  2. 공급자 순회ID 79개를 조회해 등록된 공급자의 RAM 사본을 제자리에 덮음
  3. 쓰기 요청목적지 섹터 14, 16비트 값 0x10000개
  4. 섹터 쓰기 함수시험에서는 기록하지 않고 넣어 준 상태값만 반환

저장 함수가 섹터 14를 위해 조회하는 ID는 0…0x2E, 0x56, 0x57, 0x62, 0x39…0x55 순서로 모두 79개입니다. 시험에서는 ID 0만 등록했으므로 덮어쓰기는 한 번 일어났고, 준비 버퍼는 “첫 32바이트는 RAM 사본, 나머지는 원래 섹터 내용”과 바이트 단위로 일치했습니다. 나머지 ID의 공급자가 무엇을 맡는지, 서로 겹치는 구역이 있는지는 이 시험의 범위가 아닙니다.

참고

“호출한다”는 것이 “반드시 플래시에 기록한다”는 뜻은 아닙니다. 섹터 쓰기 함수의 내부 동작은 이 시험에서 실행하지 않았습니다. 그 함수의 비교·지우기·기록 순서는 업데이트 전송과 기록 오류에서 따로 다룹니다.

저장 함수는 섹터 14를 처리한 뒤 관리자 +0x2CA 바이트를 봅니다. 이 값이 0이면 뒤의 섹터 묶음을 건너뜁니다. 0은 원본 생성자가 넣는 초기값이고, 이 시험은 그 상태에서 실행했습니다. 이 값이 1일 때 이어지는 섹터 15~19의 저장은 보존 픽셀 레코드와 촬영 패킷에 있습니다.

한계와 남은 과제

이 결과는 원본 코드의 제한된 구간을 합성 메모리에서 실행해 얻었습니다. 실물 카메라에서 얻은 값은 없습니다.

  • 레코드의 실제 내용 — 실물 카메라의 섹터 14에 무엇이 들어 있는지, 다섯 워드가 무엇을 뜻하는지 모릅니다. SerialNo(UID)는 출력 레이블로만 확인했습니다.
  • 메시지의 출처 — 애플리케이션 복사본을 고치는 메시지를 누가 보내는지 추적하지 않았습니다.
  • 복사본의 역전달 — 복사본의 값이 공급자 RAM 사본을 거쳐 플래시로 가는 경로는 확인하지 못했습니다.
  • 섹터 14의 나머지 — 저장 함수가 조회하는 나머지 ID 78개의 공급자는 등록하지 않았습니다.
  • 진단 경로의 도달 조건 — 어떤 조작으로 진단 CSV 기록에 이르는지, 파일이 실제로 만들어지는지 확인하지 않았습니다.
  • 하위 플래시 동작 — 섹터 쓰기 함수 안쪽과 전원을 끈 뒤의 유지 여부는 범위 밖입니다.
