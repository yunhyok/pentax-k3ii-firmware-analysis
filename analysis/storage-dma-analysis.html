파일 쓰기 요청이 SD 카드 명령과 DMA 설정이 되기까지

Exif 작성기가 넘긴 “이 주소에서 이만큼 써 달라”는 요청은 파일시스템과 카드 드라이버를 거쳐 SD 명령이 됩니다. 그 과정에서 버퍼 주소가 그대로 전달되는 곳과 다른 버퍼로 바뀌는 곳을 가려냈습니다.

이 문서에서

  1. 배경: 파일 하나가 카드에 쓰이는 단계
  2. 카드 용량으로 백엔드를 고르고, 백엔드 A는 카드 객체로 이어집니다
  3. 전체 섹터는 원래 버퍼를, 부분 섹터는 캐시를 카드에 넘깁니다
  4. 두 SD 포트에서 명령과 ADMA2 설명자가 설정됩니다
  5. 색 처리의 대체 출력 평면과 JPEG 목적지의 공유·재시도 조건
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 펌웨어에는 저장 백엔드가 두 개 있고, 카드를 마운트할 때 카드 용량으로 하나를 고릅니다. 이 문서는 그중 백엔드 A를 블록 콜백, SD 카드 객체, SD 명령까지 이었습니다.
  • 섹터 경계에 맞는 쓰기는 원래 버퍼 주소 그대로 카드 쓰기에 전달됩니다. 섹터 일부만 쓰는 요청은 캐시에 복사해 두었다가 나중에 캐시 주소로 내보냅니다.
  • SD 포트 두 개에서 단일 블록 쓰기(CMD24)와 다중 블록 쓰기(CMD25)의 레지스터 설정을 확인했습니다. 버퍼는 64KiB 조각마다 ADMA2 설명자 한 줄로 등록되고, 한 명령은 16MiB까지만 싣습니다.
  • 색 처리의 대체 출력 평면이 선택되는 조건과, JPEG 압축 목적지를 공유하거나 품질을 낮춰 다시 압축하는 조건도 확인했습니다.
  • 원본 코드를 합성 조건 49건으로 실행한 결과입니다. 실제 데이터가 DMA로 옮겨지거나 카드에 기록되는 것은 관측하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 파일시스템 15건: 백엔드 선택 3, 쓰기 래퍼 6, 섹터 경로 2, 블록 분할 4
  • SD 14건: 읽기·쓰기 5, 재분할 1, 용량 계산 2, 오류 5, 인터럽트 1. 레지스터 쓰기 순서와 설명자 표 전체 대조
  • 대체 버퍼 20건: 색 처리 출력 8, JPEG 배치 4, 첫 압축 판정 4, 재시도 4

정적 분석 코드를 읽어 판단

  • 백엔드 생성·등록, 블록 콜백 등록, 카드 객체 생성·조회의 연결
  • 카드 쓰기 진입점의 범위 검사·재시도·복구 분기가 있다는 사실
  • 백엔드 A가 부르는 파일시스템 라이브러리 안쪽의 호출열

모델 시험 조건으로 정한 것

  • 버퍼 주소, LBA, 카드 응답, 인터럽트 상태, 압축 길이는 넣어 준 값
  • 볼륨 조회, 잠금, 오류 정책, RTOS 이벤트, CPU 캐시 관리는 대체
  • SD 포트 레지스터는 일반 메모리, 캐시는 미리 채운 상태

미확인 확인하지 않은 것

  • 실제 DMA 전송, 전송 타이밍, 물리 SD 기록
  • 파일 할당과 클러스터 체인, 카드 쓰기의 재시도·복구 전체
  • CPU 주소와 DMA 버스 주소의 관계, 캐시 일관성
  • 두 포트가 어느 물리 슬롯인지

배경: 파일 하나가 카드에 쓰이는 단계

프로그램은 파일에 “바이트 몇 개를 써 달라”고 요청합니다. SD 카드는 바이트가 아닌 512바이트짜리 섹터(블록) 단위로만 읽고 씁니다. 그 사이를 여러 층이 맡습니다.

  1. 파일시스템파일 위치와 바이트 수를 섹터 번호(LBA)와 섹터 개수로 바꿉니다.
  2. 카드 드라이버섹터 요청을 SD 명령으로 바꿉니다. 한 블록은 CMD24, 여러 블록은 CMD25입니다.
  3. 호스트 컨트롤러명령을 보내고, 데이터가 있는 메모리 위치를 표로 만들어 하드웨어에 알려 줍니다.
  4. SD 카드하드웨어가 표를 따라 메모리에서 데이터를 가져가 카드에 보냅니다.

이 문서에 나오는 용어

  • CMD24, CMD25 — SD 규격의 쓰기 명령입니다. CMD24는 WRITE_BLOCK(한 블록), CMD25는 WRITE_MULTIPLE_BLOCK(연속 여러 블록)입니다. 읽기는 CMD17과 CMD18이고, CMD23은 블록 개수를 미리 알리는 명령, CMD9는 카드 정보(CSD)를 읽는 명령입니다. 번호와 이름은 Linux의 MMC 명령 정의와 대조했습니다.
  • DMA와 ADMA2 — DMA는 하드웨어가 메모리에서 데이터를 직접 가져가는 방식입니다. ADMA2는 SD 호스트 컨트롤러 규격의 DMA 방식으로, “이 주소에서 이만큼”을 적은 8바이트 설명자를 표로 늘어놓습니다.
  • 백엔드 A, B — 파일시스템 객체에 등록된 두 저장 구현을 이 연구에서 구분해 부르는 이름입니다. 파일시스템의 종류를 뜻하지 않습니다.
  • 주소 표기 — 코드 주소는 복호화한 이미지의 파일 오프셋이고, 가상 주소는 여기에 0x02000000을 더한 값입니다. 0xC6000000, 0xC7000000은 SD 포트의 장치 레지스터 주소입니다.

SD 명령과 CSD의 원문 규격은 SD Association의 간이 규격 내려받기 페이지에 있습니다(Part 1 Physical Layer, Part A2 SD Host Controller). 레지스터 배치와 설명자 형식은 같은 규격을 구현한 Linux의 SDHCI 정의와 대조했습니다.

그림을 읽을 때 주의

이 문서의 그림은 코드의 연결과, 합성 조건에서 관측한 값의 전달을 나타냅니다. 카메라에서 파일을 기록하거나 DMA 전송을 관측한 결과가 아닙니다.

카드 용량으로 백엔드를 고르고, 백엔드 A는 카드 객체로 이어집니다

파일시스템 어댑터는 마운트 때 정해 둔 백엔드로 쓰기를 넘깁니다. 백엔드 A의 쓰기는 파일시스템 라이브러리의 섹터 처리와 블록 콜백을 거쳐, 포트마다 하나씩 있는 SD 카드 객체의 쓰기 함수에 닿습니다.

백엔드를 고르는 기준은 카드 용량입니다

초기화 코드는 두 구현을 만들어 파일시스템 객체에 등록합니다. 마운트 함수는 카드 객체에 저장된 용량 값을 임계값 0x04040000과 부호 없이 비교해, 작으면 A를, 같거나 크면 B를 고릅니다. 경계 바로 아래, 같은 값, 바로 위의 세 값을 원본 코드로 실행해 선택을 확인했습니다.

비교하는 용량 값은 512바이트 논리 섹터의 개수입니다. 펌웨어는 CMD9로 읽은 카드 정보(CSD)를 해석해 이 값을 만듭니다. CSD의 두 가지 형식을 넣어 실행해 단위와 저장 위치를 확인했습니다.

쓰기 래퍼의 반환값이 뜻하는 것

두 백엔드의 쓰기 래퍼는 하위 함수가 0 이상의 값을 돌려주면 참을 돌려줍니다. 하위 함수의 반환값을 47, 0, −1로 바꿔 가며 백엔드마다 3건씩 실행한 결과는 참, 참, 거짓이었습니다. 따라서 래퍼가 참을 돌려주었다는 사실만으로 요청한 바이트가 모두 기록됐다고 볼 수 없습니다.

전체 섹터는 원래 버퍼를, 부분 섹터는 캐시를 카드에 넘깁니다

섹터 경계에 딱 맞는 요청은 받은 버퍼 주소를 그대로 카드 쓰기에 전달합니다. 섹터 안쪽 일부만 바꾸는 요청은 캐시의 해당 구간만 고쳐 두고, 나중에 별도의 내보내기 함수가 캐시 주소로 한 섹터를 씁니다.

섹터 처리 함수와 블록 콜백을 함께 실행했습니다. 섹터 크기는 512바이트로 두었습니다. 부분 섹터 사례는 캐시를 유지하는 조건을 켜고 유효한 캐시를 미리 준비해 둔 상태에서 시작했습니다. 캐시를 할당하고 처음 읽어 오는 과정, 파일 전체의 클러스터 구성까지 실행한 것은 아닙니다.

큰 요청은 두 번 나뉩니다

  • 블록 콜백 단위 — 블록 콜백을 부르는 함수는 한 번에 넘기는 블록 수를 0xFFFF개 이하로 자릅니다. 65,536블록 요청은 65,535블록과 1블록으로 나뉘었고, 둘째 호출의 버퍼 주소는 65,535 × 512바이트만큼 뒤였습니다.
  • 카드 명령 단위 — 카드 쓰기 루프는 호스트 객체에 든 상한으로 다시 자릅니다. 호스트 생성자가 넣는 상한은 0x8000블록, 곧 16MiB이고 64KiB 설명자 256개와 맞습니다. 65,535블록 요청은 32,768블록과 32,767블록의 CMD25 두 번이 되었습니다. 두 설명자 표 전체, 둘째 명령의 LBA와 버퍼 주소 증가, 명령 레지스터 쓰기를 대조했습니다.
  • 실패했을 때 — 첫 호출이 실패하면 둘째 호출을 하지 않았습니다. 이 사례에서는 오류 정책 함수를 0을 돌려주도록 대체했으므로, 원래 정책에 따른 재시도 전체는 실행하지 않았습니다.

두 SD 포트에서 명령과 ADMA2 설명자가 설정됩니다

카드 쓰기 함수는 버퍼를 64KiB 이하 조각으로 나눠 설명자 표를 만들고, 표의 주소와 블록 크기·개수, 인수, 명령을 포트 레지스터에 차례로 씁니다. 이 단계에서 영상 데이터를 다른 버퍼로 복사하지 않습니다.

포트와 호스트 설정

포트 설정표에는 두 줄이 있고 각각 레지스터 기준 주소 0xC6000000과 0xC7000000을 갖습니다. 초기화 코드는 이 값을 호스트의 컨트롤러 래퍼에 넘깁니다. 호스트 초기화는 제어 레지스터 +0x28의 비트 4:3에 이진수 10을 넣는데, 이는 32비트 ADMA2를 고르는 값과 같습니다.

K-3 II에는 SD 카드 슬롯이 두 개(SD1, SD2) 있습니다(사용설명서 37쪽). 포트가 둘이라는 점은 이와 어울리지만, 두 포트 주소만으로 어느 포트가 어느 슬롯인지, 칩이 무엇인지는 정할 수 없습니다.

설명자와 주소 인수

  • 설명자 형식 — 리틀 엔디언으로 {16비트 속성, 16비트 길이, 32비트 버퍼 주소}입니다. 일반 전송의 속성은 0x21, 마지막 줄은 0x23입니다. 길이 칸 0은 65,536바이트를 나타냅니다. 형식은 SDHCI의 32비트 ADMA2 설명자와 같고, 길이 0의 뜻은 Linux 드라이버의 설명과도 맞습니다.
  • 버퍼 주소 — 설명자의 주소는 받은 버퍼 포인터에 이미 등록한 바이트 수를 더한 값입니다. 129블록 사례에서 둘째 줄의 주소는 첫 줄보다 정확히 0x10000 컸습니다.
  • 주소 인수 — 카드 객체의 주소 방식 값이 2이면 LBA를 그대로, 그 밖에는 LBA를 왼쪽으로 9비트 민 값(바이트 주소)을 인수로 보냅니다. 블록 주소를 쓰는 카드와 바이트 주소를 쓰는 카드의 구분과 맞습니다. 값 2가 속한 열거형 전체와 카드 초기화의 모든 분기를 확정한 것은 아닙니다.

완료 통지와 오류 처리

  1. 인터럽트 처리기포트의 상태 레지스터를 읽어 정상 플래그와 오류 플래그로 나눕니다.
  2. RTOS 이벤트 게시같은 이벤트 객체에 두 값을 게시하고, 처리한 비트를 상태 레지스터에 다시 씁니다. 1을 쓰면 지워지는 방식의 비트입니다.
  3. 명령 완료 대기쓰기 함수가 비트 0을 기다립니다.
  4. 전송 완료 대기비트 1을 기다립니다. 오류 비트나 카드 제거 비트가 오면 실패로 처리합니다.

인터럽트 사례에서는 상태 값 0x02008003을 넣었습니다. 처리기는 0x8003과 0x02000000을 같은 이벤트 객체에 게시하고, 같은 두 값을 상태 레지스터에 기록했습니다.

시험 조건

포트 레지스터는 일반 메모리입니다. 실제 장치의 타이밍이나, 1을 쓰면 지워지는 상태 비트의 하드웨어 동작은 재현하지 않습니다. RTOS 이벤트의 게시·대기와 CPU 캐시 관리, 다중 블록 전송 뒤의 카드 상태 확인은 대체했습니다. 실행은 카드 쓰기 진입점의 범위 검사와 복구 분기를 지난 아래쪽 명령 함수 또는 블록 분할 루프에서 시작했습니다. 용량 계산 2건만 CSD 조회 함수에서 시작해 응답 레지스터를 읽고 용량을 저장하는 데까지 실행했습니다.

색 처리의 대체 출력 평면과 JPEG 목적지의 공유·재시도 조건

색 처리 모듈은 조건에 따라 평소와 다른 출력 평면을 쓰거나 두 번 반복합니다. JPEG 쪽은 두 출력이 목적지를 나눠 쓰거나 함께 쓰며, 결과가 용량에 맞지 않으면 품질을 낮춰 같은 자리에 다시 압축합니다.

앞 문서의 버퍼 경로는 색 처리 모듈이 작업의 세 평면 주소를 직접 쓰는 경우였습니다. 여기서는 그 밖의 분기를 봅니다. 이 주제의 다른 문서에서는 색 처리 모듈을 CPP라고 부릅니다.

  • 두 조건은 서로 다른 값을 봅니다 — 첫 패스의 주소 선택은 작업의 마스크 값에서 0x44 비트를 봅니다. 별도 디스크립터를 채우는 쪽의 조건(배치 구분값이 1)은 또 다른 값입니다. 두 조건을 따로 바꾼 합성 사례를 포함해 8건을 실행했습니다.
  • 두 번째 패스의 평면 — 버퍼 슬롯 13의 배치 함수가 계산합니다. 주소를 32바이트 단위로 올리고, 가로·세로 곱과 그 절반, 여백 값을 써서 세 평면을 놓습니다.
  • 처리 허용 표시 — 일반 작업 생성자는 처리 허용 표시를 1로 둡니다. 이것을 0으로 넣은 사례는 방어 분기를 보려고 주입한 것이며, 일반 작업의 상태를 관측한 결과가 아닙니다. 이 경우 출력 주소 기록 구간에 들어가지 않았습니다.
이 문서에서 확인하지 못한 연결

일반 스케일러의 입력은 여전히 직접 평면 필드를 읽습니다. 그래서 대체 출력 평면이 JPEG 모듈 16의 입력과 같은 메모리를 가리키는지는 여기서 확인되지 않았습니다. 이어지는 추적은 백엔드 B와 두 번째 CPP 출력, 마스크 CPP와 보조 JPEG 입력에 있습니다.

한계와 남은 과제

  • 이어 실행하지 않았습니다 — Exif 출력, 파일 할당, SD 쓰기를 한 번에 이어 실행한 검증이 아닙니다. 층마다 따로 실행하고 경계의 인수를 맞춰 보았습니다.
  • 파일시스템 — 실제 파일 할당과 클러스터 체인 구성, 카드 쓰기 진입점의 범위 검사·재시도·복구 경로 전체가 남아 있습니다. 백엔드 B의 파일 쓰기 아래쪽은 백엔드 B와 두 번째 CPP 출력에서 이어집니다.
  • 하드웨어 동작 — CPU 주소와 DMA 버스 주소의 관계, 캐시 일관성, 전송 타이밍, 물리 SD 기록은 합성 실행으로는 입증할 수 없습니다.
  • 영상 쪽 — 대체 출력 평면에서 스케일러·JPEG 입력으로 넘어가는 주소 관계와 실제 촬영 모드에서의 분기 선택은 더 확인해야 합니다.
  • 부품과 실기 — SoC와 보조 MCU의 정확한 부품 번호, RAW에서 JPEG까지의 물리적 픽셀 처리, 실제 촬영과 펌웨어 설치는 검증하지 않았습니다.

추적 방법은 K-3 Mark III 연구의 저장 장치 분석과 같습니다. 설정표, 호출, 레지스터를 잇고 원본 명령에 합성 상태를 넣어 정상·오류 분기를 확인했습니다. K-3 Mark III의 주소나 칩 정보는 가져오지 않았습니다.
