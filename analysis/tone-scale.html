K-3 II · 원본 정수 생산자의 공개 재현 · 2026-11-13

recipe+0x9C의 정수 생산 경로

공개 검증기는 원본 recipe+0x9C 생산자의 계산 20건과 내장 입력의 바이트 복사 3건을 재현합니다. 각 묶음의 전체 관측을 타입을 구분하는 JSON으로 직렬화하고 기존 검증 결과의 해시와 대조한 뒤 공개 메타데이터를 붙입니다. 관측 기록은 줄이지 않았습니다. 두 묶음은 별도의 VM에서 실행되므로 같은 촬영 이력으로 해석할 수 없습니다.

입력과 계산20개 조건내장 입력남은 경계재현 자료

recipe+0x9C에 쓰이는 워드의 생산자를 원본 명령으로 재현했습니다. 65EED0의 프롤로그가 만든 0x40바이트 스택 프레임을 유지한 채 산술 구간과 저장 구간에 따로 진입했습니다. 65F024가 SP+0x18에 8192를 씁니다. 조건이 맞으면 65F04C가 같은 슬롯을 덮어씁니다. 65F188에서 같은 슬롯을 읽은 값이 7198D4를 통해 같은 job의 recipe+0x9C에 저장되었습니다.

div는 부호 없는 정수 나눗셈입니다. 도식은 분리 진입을 포함한 값 전달이며 실제 촬영의 연속 실행을 뜻하지 않습니다. 저값 분기의 R8=0은 아래 표에서 별도로 다룹니다.

확인한 입력 생산자와 정수 연산

R8의 출처도 한 단계 좁혔습니다. 원본 코드는 R8을 8192로 초기화합니다. 전역 블록 4041F420의 첫 워드가 A55A5AA5일 때 그 뒤의 부호 없는 반워드를 읽습니다. 구성 서비스 0x53의 응답이 0이 아니면 다시 8192로 설정합니다. 이번에는 전역 블록 내용과 서비스 응답을 시험값으로 공급했습니다. 그 시험값에서 R8을 만드는 메모리 읽기와 조건부 설정은 원본 코드가 실행했습니다.

산술 입력 R5는 상위 서비스 경계의 시험값입니다. 원본 코드는 이를 부호 없는 정수로 비교해 최대 0x800000으로 제한합니다. 제한한 값 p가 8192보다 작으면 나눗셈 경로로 들어갑니다. 분모가 유효하면 t=67108864/R8의 정수 몫을 구합니다. p가 t보다 작을 때만 (p<<13)/t의 정수 몫으로 SP+0x18을 덮어씁니다. p가 t 이상이거나 p가 8192 이상이면 SP+0x18은 8192를 유지합니다. 뒤쪽 계산은 다른 스택 슬롯과 레지스터를 바꾸며 SP+0x18에는 쓰지 않습니다.

높은 값의 분기는 R7을 계산할 때 곱셈 결과의 하위 32비트만 남깁니다. 따라서 무한 정밀도 곱셈 뒤에 나누는 식으로 바꾸면 결과가 달라질 수 있습니다. 원본의 논리 시프트와 절삭 순서를 보존한 독립 정수식으로 레지스터와 SP+0·SP+4의 값도 대조했습니다. 다만 R6=0x4000일 때의 별도 조건부 쓰기는 이번 시험에 포함되지 않았으며 정적 코드로만 확인했습니다.

근거: 원본 실행 구간과 정수식 · 허용 실행 구간과 정적 원본 25개 구간의 해시. 명령 주소는 16진수 파일 오프셋이며 VA = 0x02000000 + 오프셋입니다. 전역 4041F420은 RAM 주소입니다.

산술과 0 입력 경계

20개 조건 중 19개가 recipe 저장까지 완료됐습니다. SP+0x18을 덮어쓴 조건은 9개, 초기값을 유지한 조건은 10개입니다. p=8191과 R8=1에서는 정수 절삭으로 recipe+0x9C에 0이 쓰였습니다. p<8192이고 R8=0인 조건은 원본 나눗셈 보조 함수에서 Thumb 처리기 2E0486으로 넘어가는 경계에서 멈췄습니다. 처리기 본문과 그 이후 동작은 실행하지 않았습니다. p=8192와 R8=0인 높은 값 분기는 8192 저장까지 완료됐습니다.

오류 처리기 앞에서 멈춘 조건의 recipe 초기값은 최종 결과로 해석하지 않습니다. 원본 712C3C의 BLX가 Thumb 2E0486에 도달했으며 처리기 명령은 실행하지 않았습니다. 정상 저장 19건은 7198D4의 4바이트 쓰기입니다. 20개 조건의 전체 관측 기록에 입력·읽기·쓰기·스택·실행 구간 해시를 보존했습니다.

같은 job에 내장된 입력

별도 재현에서는 63106C가 owner+0x220에서 읽은 job 주소를 65606C에 전달했습니다. 원본 보조 함수는 job+0x2440에 0x80을 더해 내장 입력의 주소 job+0x24C0을 만들었습니다. 71BD0C가 그 입력의 +0x18 바이트를 읽고 656088이 같은 job+0x6D에 썼습니다. 주소가 다른 배치를 포함한 3개 조건에서 확인했습니다. owner의 job 포인터와 입력 바이트는 공급한 시험값입니다. 실제 촬영에서 이 값이 생기는 경로는 확인하지 않았습니다.

검증 범위와 다음 입력 경계

산술 시험은 원본 명령을 RX 메모리에서 실행하고 명령 바이트·허용 쓰기 범위·원본 전체 해시를 검사했습니다. 모든 분모가 0이 아니라고 가정하지 않았습니다. 저값 분기의 오류 처리기 경계와 고값 분기의 정상 산술을 나누어 기록했습니다. 이 결과는 물리적 단위, Q 형식, 감마, 현재 촬영 기본값, 전체 촬영 순서나 메뉴 도달을 뜻하지 않습니다. 다음 입력 경계는 R5를 만드는 가상 호출·표와 구성 서비스 0x42, 전역 블록의 실제 생산자, owner+0x220 포인터 및 내장 입력 바이트의 생산자입니다.

recipe+0x9C에 0이 쓰이는 조건과 저값 분기에서 오류 처리기 앞에 도달하는 조건을 구분했습니다. 처리기가 값을 반환하는지는 확인하지 않았습니다. 실제 촬영의 입력 생산자, 작업 순서, 버퍼 재사용, SuperResolution 메뉴 연결은 여전히 미확정입니다. 이번 공개 재현에는 기존의 20개 계산 조건과 3개 복사 조건만 포함하며 별도 검토 중 추가한 조건은 섞지 않았습니다.

65F0D8 이후 서비스와 다른 recipe 필드의 네 쓰기는 생략했습니다. 65F150 구간의 SP+8 읽기는 대상 저장에 쓰이지 않으며 65F188에서 R1을 SP+0x18 값으로 덮어씁니다. 같은 산술 프레임은 유지하지만 각 분리 구간의 LR은 하네스 반환점으로 설정합니다. 생성자 출력이 현재 촬영 기본값이라는 근거는 없습니다.

앞선 원본 톤 입력 생산자 분석에서는 +9C 후속 생산자를 정적으로만 추적했습니다. 이 문서는 해당 생산자의 제한된 실행을 추가합니다. 앞선 문맥 계산·톤 곡선을 이번 산술 실행과 이어 돌린 것은 아닙니다. 문맥·곡선 연결 분석과 함께 읽되 별도 시험의 경계를 유지해야 합니다.

공개 실행 코드와 수치 결과

사용자는 decoded 파일을 별도로 준비해 경로를 명시해야 합니다. 검증기는 파일 크기와 전체 SHA-256을 검사한 뒤 실행 모듈을 불러옵니다. 소스와 허용 구간은 고정한 해시로 확인합니다. 출력은 새 경로에만 만들며 기존 파일·별칭·링크를 덮어쓰지 않습니다. 공개 자료에는 펌웨어 바이트나 자산이 포함되지 않습니다.

공개 JSON은 565,847바이트이며 계산 20건과 복사 3건의 관측을 모두 포함합니다. 전체 관측 해시를 먼저 확인하므로 기록에서 빠진 필드나 타입 변경도 거부합니다. 기존 연구 스냅샷의 문구는 그대로 보존하고 새 공개 메타데이터에서 저장 동작을 정확히 표현했습니다.

실행 방법

검증 환경은 Python 3.12.3과 Unicorn 2.1.4입니다. 저장소 루트에서 별도로 준비한 원본 decoded 파일을 지정하고 출력에는 새 경로를 사용하십시오. 아래 입력 경로는 예시입니다.

python -B verify_tone_scale.py /path/to/decoded.bin --output tone-scale-new.json --compare analysis/tone-scale.json
python -B -O verify_tone_scale.py /path/to/decoded.bin --output tone-scale-opt-new.json --compare analysis/tone-scale.json
python -B -m unittest discover -s tests -p test_tone_scale.py

후보가 별도 디렉터리에 있을 때만 --repository로 기존 검증기와 보조 소스가 있는 저장소를 지정합니다. 통합한 공개 배치에서는 생략합니다. 비교 실패 시 출력 파일을 만들지 않으며 기록을 제자리에서 다시 쓰는 검증 명령은 제공하지 않습니다.

원본 명령·허용 쓰기·전체 관측을 검사한 제한 재현입니다. 카메라, 모터, 부팅 및 실제 촬영 동작은 실행하지 않았고 브라우저 렌더링도 확인하지 않았습니다.
