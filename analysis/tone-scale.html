recipe+9C 정수 생산자와 내장 입력 복사

recipe 객체의 +9C 워드는 톤 문맥 계산이 읽는 입력 가운데 하나입니다. 이 값을 만드는 원본 코드의 정수 분기와, 그 앞단에서 작업 객체의 바이트가 어디서 복사되는지를 원본 코드로 실행했습니다.

이 문서에서

  1. 배경: +9C 값과 R5·R8이라는 이름
  2. 정수 분기: 언제 8192를 덮어쓰는가
  3. 20개 조건의 결과
  4. 같은 작업 객체에 내장된 입력의 복사
  5. 한계와 다음 입력
  6. 재현 방법과 근거 파일

핵심 요약

  • recipe+9C에 저장되는 워드를 만드는 원본 코드를 20개 조건으로 실행했습니다. 19건이 저장까지 끝났습니다. 그중 9건은 초기값 8192를 계산값으로 덮어썼고 10건은 8192를 그대로 저장했습니다.
  • 값을 덮어쓰는 것은 제한한 입력이 8192보다 작고 계산한 문턱보다도 작을 때뿐입니다. 정수 절삭 때문에 0이 저장되는 조건도 있습니다. 분모 R8이 0인 낮은 값 조건은 원본 나눗셈 보조 함수가 오류 처리기로 넘어가는 지점에서 멈췄습니다. 처리기는 실행하지 않았습니다.
  • 별도 시험 3건에서는 원본 코드가 작업 객체에 내장된 입력의 바이트 하나를 같은 작업 객체의 다른 바이트로 복사했습니다. 이 바이트는 톤 입력 문서에서 recipe+BC 분기를 고르는 두 바이트 중 하나입니다.
  • 입력 R5, 전역 블록, 서비스 응답, owner 포인터, 원본 바이트는 모두 시험값입니다. 두 묶음은 별도 VM에서 실행했고 실제 촬영 순서, 물리 단위, 메뉴 연결은 확인하지 않았습니다. 카메라에서 실행한 것은 없습니다.

확인 원본 코드 실행으로 확인

  • 같은 스택 프레임에서 초기화 → 조건부 덮어쓰기 → recipe+9C 저장(19건)
  • 전역 블록과 서비스 응답에서 R8을 만드는 읽기·재설정 코드
  • R8=0 낮은 값 조건이 처리기 2E0486에 도달함
  • 내장 입력 주소 계산과 바이트 복사(3건)

정적 분석 코드를 읽어 판단

  • R6=0x4000일 때의 별도 조건부 쓰기
  • 생략한 뒤쪽 서비스와 다른 recipe 필드 쓰기의 위치
  • 정적 원본 구간 25개의 해시

모델 시험 조건으로 정한 것

  • R5, 전역 블록의 magic·halfword, 구성 서비스 0x53 응답
  • owner+0x220 포인터, 내장 입력 바이트
  • 분리 구간마다 하네스 반환점으로 둔 LR

미확인 확인하지 않은 것

  • R5·전역 블록·포인터·입력 바이트를 실제로 만드는 코드
  • 오류 처리기가 값을 반환하는지
  • 실제 촬영 순서, 버퍼 재사용, SuperResolution 메뉴, 물리 단위·Q 형식·감마

배경: +9C 값과 R5·R8이라는 이름

K-3 II는 톤 곡선을 만들기 전에 문맥 계산 함수가 정수 하나를 준비합니다(계산식). recipe+A4가 0이면 이 계산의 분모 쪽 입력 x가 recipe 객체의 +9C 워드입니다. 톤 입력의 원본 생산자에서는 +9C를 쓰는 코드를 정적으로만 찾았습니다. 이 문서는 그 코드를 실제로 실행합니다.

recipe 객체
작업 객체(job) 안 job+E0C4에 있는 톤 설정 객체입니다. 용어집의 레시피(모듈 호출 순서 목록)와는 다릅니다.
R5, R8
ARM 레지스터 이름입니다. 값의 의미가 밝혀지지 않아 원본 코드가 값을 담는 레지스터 이름으로 부릅니다. R5는 산술 입력, R8은 문턱을 정하는 나눗셈의 분모입니다.
SP+0x18
생산 함수 65EED0의 프롤로그가 만든 0x40바이트 스택 프레임 안의 4바이트 자리입니다. 여기에 담긴 값이 마지막에 recipe+0x9C로 저장됩니다.
owner
작업 객체를 가리키는 포인터를 가진 다른 객체입니다. 내장 입력 시험에서 owner+0x220이 작업 객체 주소를 담습니다.

주소는 16진수 파일 오프셋이며 실행 주소(VA)는 0x02000000을 더한 값입니다. 전역 블록 4041F420은 RAM 주소입니다. div는 부호 없는 정수 나눗셈입니다.

정수 분기: 언제 8192를 덮어쓰는가

SP+0x18은 8192로 시작합니다. 낮은 값 분기에서 p가 문턱 t보다 작을 때만 계산값으로 바뀝니다.

원본 코드는 R8을 8192로 초기화합니다. 전역 블록 4041F420의 첫 워드가 A55A5AA5이면 그 뒤의 부호 없는 halfword를 읽습니다. 구성 서비스 0x53의 응답이 0이 아니면 다시 8192로 둡니다. 전역 블록 내용과 서비스 응답은 시험값입니다. 그 값에서 R8을 만드는 메모리 읽기와 조건부 설정은 원본 코드가 실행했습니다.

산술 입력 R5는 상위 서비스 경계에서 넣은 시험값입니다. 원본 코드는 R5를 부호 없는 정수로 비교해 최대 0x800000으로 제한합니다. 뒤쪽 계산은 다른 스택 슬롯과 레지스터를 바꾸지만 SP+0x18에는 쓰지 않습니다.

높은 값 분기의 세부와 정적으로만 본 부분
  • 높은 값 분기는 R7을 계산할 때 곱셈 결과의 하위 32비트만 남깁니다. 무한 정밀도 곱셈 뒤에 나누는 식으로 바꾸면 결과가 달라질 수 있습니다.
  • 원본의 논리 시프트와 절삭 순서를 지킨 독립 정수식으로 레지스터와 SP+0·SP+4의 값도 대조했습니다.
  • R6=0x4000일 때의 별도 조건부 쓰기는 이 20개 조건에 들어 있지 않고 정적 코드로만 확인했습니다.
  • 65F0D8 이후 서비스와 다른 recipe 필드의 쓰기 4개는 생략했습니다.
  • 65F150 구간의 SP+8 읽기는 대상 저장에 쓰이지 않습니다. 65F188이 R1을 SP+0x18 값으로 덮어씁니다.
  • 같은 산술 프레임은 유지하지만 분리 구간마다 LR은 하네스 반환점으로 설정합니다.

20개 조건의 결과

덮어쓴 조건 9개, 8192를 유지한 조건 10개, 처리기 앞에서 멈춘 조건 1개였습니다.

p=8191, R8=1에서는 정수 절삭으로 recipe+9C에 0이 쓰였습니다. p<8192이고 R8=0인 조건은 원본 712C3C의 BLX가 Thumb 처리기 2E0486에 닿은 지점에서 멈췄습니다. 처리기 명령은 실행하지 않았습니다. 같은 R8=0이라도 p=8192인 높은 값 분기는 8192 저장까지 끝났습니다.

처리기 앞에서 멈춘 조건의 recipe 값(생성자가 쓴 8192)은 최종 결과로 보지 않습니다. 정상 저장 19건은 모두 7198D4의 4바이트 쓰기입니다. magic_invalid는 전역 블록의 magic이 틀린 경우, config53_*는 서비스 0x53이 1이나 255를 돌려준 경우라서 R8이 8192로 남습니다. 입력·읽기·쓰기·스택·실행 구간 해시는 20개 조건의 전체 관측 기록에 있습니다.

같은 작업 객체에 내장된 입력의 복사

원본 코드가 owner에서 작업 객체 주소를 읽어 내장 입력 job+24C0의 바이트를 같은 작업 객체의 job+6D로 옮겼습니다.

  1. owner+0x220준비한 작업 객체 포인터
  2. 63106C 읽기631070에서 원본 호출
  3. 주소 계산656078 → 73DFC0: job+0x2440+0x80 = job+0x24C0
  4. 71BD0C 읽기입력+0x18(job+0x24D8)의 1바이트, 값은 준비한 것
  5. 656088 STRB같은 작업 객체의 job+0x6D에 씀

63106C가 owner+0x220에서 읽은 job 주소를 65606C에 넘깁니다. 원본 보조 함수는 job+0x2440에 0x80을 더해 내장 입력의 주소 job+0x24C0을 만듭니다. 71BD0C가 그 입력의 +0x18 바이트를 읽으면 656088이 같은 job의 +0x6D에 씁니다. owner의 job 포인터와 입력 바이트는 시험값이므로 실제 촬영에서 이 값이 생기는 경로는 모릅니다.

한계와 다음 입력

산술 시험은 원본 명령을 RX 메모리에서 실행했고 명령 바이트, 허용 쓰기 범위, 원본 전체 해시를 검사했습니다. 분모가 0인 경우도 시험에 넣어 오류 처리기 경계와 높은 값 분기의 정상 산술을 나눠 기록했습니다.

  • 뜻하지 않는 것: 물리 단위, Q 형식, 감마, 현재 촬영 기본값, 전체 촬영 순서, 메뉴 도달. 생성자 출력이 현재 촬영 기본값이라는 근거도 없습니다.
  • 남은 입력: R5를 만드는 가상 호출·표와 구성 서비스 0x42, 전역 블록의 실제 생산자, owner+0x220 포인터와 내장 입력 바이트의 생산자.
  • 남은 동작: 오류 처리기가 값을 반환하는지, 실제 촬영의 작업 순서, 버퍼 재사용, SuperResolution 메뉴 연결.
  • 공개 범위: 기존의 20개 계산 조건과 3개 복사 조건만 넣었습니다. 별도 검토 중 추가한 조건은 섞지 않았습니다.

원본 톤 입력 생산자 분석에서 정적으로만 추적한 +9C 생산자를 이 문서가 제한된 범위에서 실행했습니다. 다만 문맥 계산과 톤 곡선은 이 산술 실행과 이어 돌리지 않았습니다. 문맥·곡선 연결 분석과 함께 읽되 시험마다 경계가 따로 있습니다. R5의 상위 입력은 R5 상위 입력과 0 소비자에서 이어집니다.

재현 방법과 근거 파일

검증 환경은 Python 3.12.3과 Unicorn 2.1.4입니다. 저장소 루트에서 따로 준비한 원본 decoded 파일을 지정하고 출력에는 새 경로를 씁니다. 아래 입력 경로는 예시입니다.

python -B verify_tone_scale.py /path/to/decoded.bin --output tone-scale-new.json \
  --compare analysis/tone-scale.json
python -B -O verify_tone_scale.py /path/to/decoded.bin --output tone-scale-opt-new.json \
  --compare analysis/tone-scale.json
python -B -m unittest discover -s tests -p test_tone_scale.py

줄 끝의 역슬래시는 줄을 잇는 표시입니다. 후보가 별도 디렉터리에 있을 때만 --repository로 기존 검증기와 보조 소스가 있는 저장소를 지정합니다. 비교에 실패하면 출력 파일을 만들지 않습니다. 기록을 제자리에서 다시 쓰는 명령은 없습니다.

검증기의 보호 조건과 해시

검증기는 decoded 파일의 크기와 전체 SHA-256을 검사한 뒤 실행 모듈을 불러옵니다. 소스와 허용 구간은 고정한 해시로 확인합니다. 출력은 새 경로에만 만들고 기존 파일·별칭·링크를 덮어쓰지 않습니다. 펌웨어 바이트나 자산은 공개 자료에 없습니다.

각 묶음의 전체 관측을 타입을 구분하는 JSON으로 직렬화해 기존 검증 결과의 해시와 대조한 뒤 공개 메타데이터를 붙입니다. 관측 기록은 줄이지 않았으므로 빠진 필드나 타입 변경도 거부됩니다. 기존 연구 스냅샷의 문구는 그대로 두었습니다. 저장 동작은 새 공개 메타데이터에서 정확히 적었습니다.
