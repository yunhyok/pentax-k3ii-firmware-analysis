작업자 매개변수와 목록 응답

원본 코드가 매개변수에서 결과 플래그를 만드는 과정과, 목록 결과가 명령 응답에 기록되는 과정을 두 실험으로 확인했습니다.

이 문서에서

  1. 작업자 상수와 빌더가 매개변수를 만드는 과정
  2. 목록 결과가 메일박스를 거쳐 명령 응답으로 전달되는 과정
  3. 실행을 건너뛴 범위
  4. 재현 방법
  5. 근거 파일

핵심 요약

  • 매개변수 생산 실험 3사례에서는 원본 작업자의 상수 저장, 엔진 바이트 복사, 빌더의 로컬 mode 기록을 거쳐 결과 플래그 1·0·1을 얻었습니다.
  • 결과 전달 실험 4사례에서는 mode와 gate, 개수·길이를 시험 입력으로 준비했습니다. 원본 코드가 만든 목록 결과는 메일박스에서 LDRH로 읽혀 응답 +8에 1·1·0·0으로 기록됐습니다.
  • 실험마다 별도 VM을 사용했습니다. 결과 전달에서만 CPU 문맥을 복원했으며 RAM의 결과는 원본 코드가 복사했습니다. 처리 서비스, RTOS 대기와 완료 신호, 실제 촬영은 미실행입니다.

작업자 상수와 빌더가 매개변수를 만드는 과정

코드 주소는 복호화 이미지의 파일 오프셋입니다. 실행 주소는 여기에 0x02000000을 더한 값입니다. 객체 주소와 vtable 포인터는 별도로 가상 주소를 표시합니다.

재현기는 [worker+0x21C]에 job 주소를 넣었습니다. 원본 0x635528이 R1에 작업자 SP를 옮기고, 0x635530의 BL과 코어 진입 코드가 그 포인터를 [core SP+0x18]에 보존했습니다. 0x634D88이 같은 job을 읽고 0x634D8C에서 0x72D364를 호출해 job+0x2440을 얻습니다. 0x635048부터는 저장된 작업자 프레임을 통해 엔진 +0x51을 채웠습니다.

빌더 호출의 인수 1과 2는 각각 0x6350F0과 0x635194의 MOV에서 나왔습니다. 실제 BL은 0x6350F4와 0x635198입니다. 빌더는 job+0x162E4의 로컬 mode 워드에 각각 0x15와 0x16을 쓰고, 별도의 +0xB 바이트에는 같은 엔진의 gate 값을 복사했습니다.

별도로 실행한 0x655284–0x655290의 원본 바인딩이 엔진 +0x10C에 매개변수 주소를 기록했습니다. 정적 분석에서 생성자가 설치하는 vtable VA 0x02A684E0의 +0x14 슬롯은 0x026552B0입니다. 해당 클래스에서는 0x634D6C에서 이 슬롯을 호출하면 0x6554F0 → 0x654EBC를 거쳐 바인딩 구간으로 이어집니다. 전체 가상 호출과 job 할당은 재현하지 않았습니다. 원본의 owner +0x68 전달도 생략하고 판정 함수 R1에 같은 엔진 주소를 넣었습니다.

빌더 인수작업자 상수 저장mode+0xB결과 +0xF8명령 콜백
1원본 실행0x1511526
1상수와 저장 호출 생략0x1500505
2원본 실행, 두 번째 호출 가드 뒤에서 시작0x1611512

0 대조는 재현기가 상수와 저장 호출을 건너뛴 경우입니다. 실제 작업자의 비활성 분기는 확인하지 않았습니다. 빌더 2는 원본 getter·비교·분기 0x635170–0x635178 뒤에서 시작했습니다. 빌더 서비스 검사 직전 0x655B24에서 멈추고, 이벤트 clear를 생략한 판정을 별도로 실행했습니다. 결과 +0xF8은 설정 단계에서 쓴 플래그이며 계산이나 촬영의 완료를 보여주지 않습니다.

목록 결과가 메일박스를 거쳐 명령 응답으로 전달되는 과정

이 실험은 별도 VM에서 시작합니다. mode·gate·엔진 포인터와 결과 버퍼의 개수 및 길이 두 개를 공급하고, 원본 판정으로 플래그를 만들었습니다. 명령 selector 4가 만든 활성 요청은 한 개이며 인덱스 24와 25를 사용합니다. 이 selector와 위 실험의 빌더 인수는 서로 다른 값입니다.

원본 STRH가 [worker+0x2CC]의 초기값 0xA55A를 16비트 목록 결과로 덮었습니다. 0x632D18 LDRH는 같은 주소에서 값을 제로 확장하고 0x632D1C의 원본 반환이 이를 명령 호출자에 넘겼습니다. 0x7B514C에서 0x6C9E28을 호출하면 0x6C9E2C의 store가 응답 +8에 32비트 워드를 기록했습니다. 응답 +4는 네 사례 모두 0x19였습니다.

준비한 길이는 각 사례에서 4 / 4였습니다. 목록 결과가 1이어도 개수가 다른 사례의 D 검사는 0이었습니다. 이 응답 워드의 출처는 목록 결과이며 RTOS 대기 함수는 실행하지 않았습니다. 앞선 호출자 시험의 0x3FF는 그 시험에서 직접 넣은 값입니다. 기존 명령 호출자 시험

실행을 건너뛴 범위

  • 작업자 프레임을 만든 뒤 입력 구성과 출력 버퍼 초기화를 건너뛰고, 원본 코어 호출을 다시 시작했습니다. 결과 전달 실험의 복사 진입 시 엔진 R8은 준비했고, 매개변수 생산 실험은 그 복사나 목록·메일박스에 진입하지 않았습니다.
  • 이벤트 clear·잠금·깨우기·대기와 완료 신호는 생략했습니다. 결과 전달은 작업자 신호 0x6366F4와 명령 정리 0x7B5150 직전에서 각각 멈췄습니다. 작업자 목록의 재시도 금지 조건도 시험 입력입니다.
  • 원본 명령 바이트를 실행할 때마다 입력과 대조했습니다. 결과 전달의 기존 설정 초기화는 합성 Flash 레코드 네 범위를 같은 이미지 매핑에 놓습니다. 그 초기화 뒤 이미지의 게스트 쓰기는 없었고 최종 내용도 일치했습니다. 매개변수 생산 실험은 16MiB 원본 매핑을 읽기·실행 전용으로 보호했습니다.
  • 계산 결과의 개수·길이 생산과 버퍼 재사용, 메뉴에서의 도달, 스케줄링과 실제 카메라 동작은 확인하지 못했습니다.

재현 방법

원본 16,838,656바이트 decoded.bin을 사용합니다. 입력 SHA-256은 1b87bf35b290e4b4e8910beb4055c34f97504b65e249ad65e5ccc0402bd14cfc입니다. 기존 설정 검증기와 그 의존 소스, 설정 JSON은 LF 기준 해시를 확인한 뒤 사용합니다.

python -m pip install unicorn==2.1.4
python verify_preserved_continuity.py decoded.bin --output preserved-continuity.json
python -m unittest discover -s tests -p test_preserved_continuity.py

새 출력 경로를 지정합니다. 기존 파일과 입력 별칭을 덮어쓰지 않으며 -O 실행을 거부합니다. JSON에는 각 사례의 원본 명령 추적 해시, 준비한 입력, 관측한 핵심 저장과 읽기, 시작·중단 주소가 있습니다. 도구는 두 실험의 전체 사례 데이터 해시를 확인한 뒤 요약 결과를 기록합니다.
