촬영 준비와 보존 레코드 · 작업자의 결과 전달

작업자가 결과 플래그를 만들고 명령 응답에 넘기는 과정

보존 레코드를 고치는 명령 경로에는 시험값으로 채워 둔 빈칸이 두 곳 있었습니다. 작업자의 결과 플래그와 명령 응답에 적히는 값입니다. 이 문서는 두 값이 원본 코드에서 어디서 오는지 두 실험으로 따로 확인합니다.

이 문서에서

  1. 배경: 명령 경로에 남아 있던 두 빈칸
  2. 작업자 상수가 결과 플래그를 정합니다
  3. 목록 결과가 메일박스를 거쳐 응답 +8에 적힙니다
  4. 실행을 건너뛴 범위
  5. 재현 방법
  6. 근거 파일과 참고 자료

핵심 요약

  • 작업자는 자기 스택에 상수 1을 써 둡니다. 이 값이 처리 객체와 매개변수 객체를 거쳐 결과 플래그 1이 됐습니다. 상수 저장을 건너뛴 대조에서는 0이었습니다(3사례).
  • 작업자가 메일박스에 쓴 목록 결과를 명령 처리기가 읽어 응답 +8에 그대로 기록했습니다. 네 사례의 값은 1·1·0·0이었습니다. 이전 문서에서 응답에 넣었던 0x3FF는 시험값이었습니다.
  • 목록 결과가 1이어도 레코드 개수가 어긋나면 설정 객체의 검사 바이트는 0이 됐습니다. 두 값은 서로 다른 판정입니다.
  • 두 실험은 서로 이어 실행하지 않았습니다. 매개변수 객체의 값, 계산 결과의 개수·길이는 준비해 넣었고 RTOS 대기·완료 신호와 실제 촬영은 실행하지 않았습니다. 카메라에서 실행한 실험은 없습니다.

확인 원본 코드 실행으로 확인

  • 작업자 상수 → 처리 객체 → 매개변수 객체 → 결과 플래그 (3사례)
  • 결과 20바이트의 작업자 프레임 복사, 메일박스 기록과 읽기, 응답 +8 기록 (4사례)
  • 설정 객체 검사 바이트 C·D의 갱신 (4사례)

정적 분석 코드를 읽어 판단

  • 바인딩 구간에 이르는 가상 호출 경로(가상 함수 표의 슬롯)
  • 빌더 인수를 정하는 MOV 명령과 판정 함수 안의 비트 추출 위치

모델 시험 조건으로 정한 것

  • 작업자와 job의 연결, 객체 주소, 판정 함수의 진입 상태
  • 결과 전달 실험의 mode·gate, 계산 결과의 개수·길이
  • 명령 입력, 재시도 금지 조건, 구간 사이의 CPU 문맥

미확인 확인하지 않은 것

  • 개수·길이를 실제로 계산하는 코드와 버퍼 재사용
  • 이벤트·잠금·대기·완료 신호와 스케줄링
  • 메뉴에서의 도달과 실제 카메라 동작

배경: 명령 경로에 남아 있던 두 빈칸

보존 레코드의 상위 명령 경로는 명령 처리기가 작업 계획을 만들어 작업자에게 넘기는 과정을 실행했습니다. 작업자의 결과에 따라 레코드 개수가 바뀌고 갱신 함수가 검사 바이트를 다시 계산합니다. 그 문서에서는 두 값을 직접 넣었습니다. 작업자 스택의 결과 구조와, 명령 응답 +8에 적히는 대기 반환값입니다.

이 문서는 두 값을 원본 코드로 채워 봅니다. 결과 구조의 첫 바이트(결과 플래그)가 어디서 오는지는 실험 A, 응답 +8의 값이 어디서 오는지는 실험 B가 다룹니다.

작업자
명령 처리기가 넘긴 요청 목록을 처리하는 객체입니다. 스택 프레임 +0xF8에 20바이트 결과 구조(결과 플래그, 개수 둘, 길이 둘)를 둡니다.
처리 객체 · 매개변수 객체
작업 하나(job) 안에 있는 두 객체입니다. 처리 객체는 job+0x2440, 매개변수 객체는 job+0x162E4에 있고 처리 객체 +0x10C가 매개변수 객체를 가리킵니다.
결과 플래그
처리 객체 +0xF8의 첫 바이트입니다. 설정 단계에서 쓰는 플래그이며 계산이나 촬영이 끝났다는 표시가 아닙니다.
메일박스 · 목록 결과
작업자 +0x2CC의 16비트 칸입니다. 작업자가 요청 목록을 처리한 결과(목록 결과)를 여기에 쓰고 명령 처리기가 읽습니다.
설정 객체 C · D
정책 플래그의 생산자가 다루는 설정 객체의 검사 바이트 +0xC·+0xD입니다. 메뉴 설정 객체와는 다른 객체입니다.
CPU 문맥 복원
구간 사이를 이을 때 레지스터만 저장해 둔 값으로 되돌립니다. RAM은 그대로 두므로 결과 바이트를 재현기가 대신 옮기지 않습니다.
읽는 법

코드 주소는 복호화 이미지의 파일 오프셋입니다. 실행 주소는 여기에 0x02000000을 더한 값입니다. 객체 주소와 가상 함수 표 포인터는 실행 주소(VA)로 따로 적었습니다.

작업자 상수가 결과 플래그를 정합니다

작업자가 프레임에 쓴 상수 1이 처리 객체와 매개변수 객체를 거쳐 결과 플래그 1이 됐습니다. 이 저장을 건너뛰면 결과 플래그는 0이었습니다.

  1. 작업자 프레임MOV 1과 저장 호출이 프레임 +0x51에 1을 씀
  2. 처리 객체저장된 프레임에서 그 바이트를 읽어 처리 객체 +0x51로 복사
  3. 빌더인수에 따라 mode 워드를 쓰고 +0xB에 gate 값을 복사
  4. 판정mode bit 2와 +0xB를 AND해 결과 플래그 저장

mode 워드 0x15와 0x16은 둘 다 bit 2가 켜져 있습니다. 그래서 세 사례의 결과 플래그는 +0xB 하나로 갈렸습니다. 빌더는 인수에 따라 mode 리터럴을 고릅니다. +0xB에는 처리 객체 +0x51의 값을 따로 복사합니다.

0 대조는 재현기가 상수와 저장 호출을 건너뛴 경우입니다. 실제 작업자에 이 값을 0으로 두는 분기가 있는지는 확인하지 않았습니다. 빌더 인수 2의 사례는 원본 getter·비교·분기를 지난 뒤에서 시작했습니다. 빌더는 서비스 검사 직전에서 멈췄습니다. 판정은 이벤트 clear를 건너뛴 채 별도로 실행했습니다.

매개변수 객체를 처리 객체에 묶는 원본 바인딩 구간도 따로 실행했습니다. 이 구간에 이르는 가상 호출은 코드를 읽어 확인했을 뿐 실행하지 않았습니다. job 할당과 소유자 +0x68의 전달도 생략했습니다. 판정 함수의 R1에는 같은 처리 객체 주소를 넣었습니다.

목록 결과가 메일박스를 거쳐 응답 +8에 적힙니다

작업자가 메일박스에 쓴 목록 결과를 명령 처리기가 읽어 응답 +8에 그대로 기록했습니다. 응답 +8은 이 목록 결과에서 나옵니다.

이 실험은 실험 A와 다른 VM에서 시작합니다. mode·gate·처리 객체 포인터와 결과의 개수·길이를 공급한 뒤 원본 판정으로 결과 플래그를 만들었습니다. 명령 selector는 4로 두었습니다. 이 selector가 만드는 활성 요청은 하나이고 인덱스 24와 25를 씁니다. 실험 A의 빌더 인수와는 다른 값입니다.

  1. 설정 판정원본 판정이 결과 플래그 생산. 그 뒤 코어 문맥 복원
  2. 프레임 복사원본 코드가 20바이트를 작업자 프레임으로 복사. 그 뒤 작업자 문맥 복원
  3. 메일박스STRH가 목록 결과를 기록. 그 뒤 명령 처리기(submit) 문맥 복원
  4. 응답LDRH로 읽어 호출자에 반환하고 응답 +8에 저장

준비한 길이는 네 사례 모두 4 / 4였습니다. 응답 +4는 모두 0x19였습니다. 결과 플래그가 1이면 작업자가 개수 setter를 불러 인덱스 24·25의 개수를 저장합니다. 그래서 개수가 2 / 1인 둘째 사례는 목록 결과가 1인데도 D가 0이 됐습니다. 결과 플래그가 0인 두 사례는 개수를 저장하지 않아 D가 1로 남았습니다.

메일박스에는 처음에 0xA55A를 넣어 두었습니다. 원본 STRH가 이 값을 목록 결과로 덮었습니다. 명령 처리기의 LDRH가 같은 주소를 16비트로 읽어 0을 채운 32비트 값으로 넘겼습니다. 상위 명령 경로 문서의 호출자 시험에서 응답 +8에 나온 0x3FF는 그 시험에서 직접 넣은 값입니다.

RTOS 대기 함수는 실행하지 않았습니다. 작업자 신호 직전과 명령 정리 직전에서 각각 멈췄습니다.

실행을 건너뛴 범위

  • 구간 사이 작업자 프레임을 만든 뒤 입력 구성과 출력 버퍼 초기화를 건너뛰고 원본 코어 호출을 다시 시작했습니다. 실험 B에서 결과를 복사하는 구간에 들어갈 때 처리 객체 포인터(R8)는 준비한 값입니다.
  • 실험 A의 범위 결과 복사, 목록, 메일박스에는 들어가지 않았습니다.
  • RTOS 이벤트 clear·잠금·깨우기·대기와 완료 신호를 생략했습니다. 작업자 목록의 재시도 금지 조건도 시험 입력입니다.
  • 명령 바이트 실행한 명령은 매번 원본 이미지와 대조했습니다. 실험 A는 16MiB 원본 매핑을 읽기·실행 전용으로 보호했습니다.
  • 남은 과제 결과의 개수·길이를 계산하는 코드, 버퍼 재사용, 메뉴에서의 도달, 스케줄링과 실제 카메라 동작은 확인하지 못했습니다. 개수·길이가 실제로 무엇을 세는지는 검출 결과 레지스터와 DMA 준비가 이어서 다룹니다.

재현 방법

복호화한 decoded.bin(16,838,656바이트)이 필요합니다. 만드는 방법은 펌웨어 추출과 재현에 있습니다. 검증기는 입력의 크기와 SHA-256을 확인합니다. 기존 설정 검증기와 그 의존 파일, 설정 JSON은 줄바꿈을 LF로 맞춘 해시로 확인한 뒤 실행합니다.

python -m pip install unicorn==2.1.4
python verify_preserved_continuity.py decoded.bin --output preserved-continuity.json
python -m unittest discover -s tests -p test_preserved_continuity.py

출력 경로에는 아직 없는 새 파일 이름을 줍니다. 기존 파일과 입력 별칭을 덮어쓰지 않으며 -O 실행은 거부합니다. 출력에는 사례마다 원본 명령 추적 해시, 준비한 입력, 관측한 저장·읽기, 시작·정지 주소가 들어 있습니다. 도구는 두 실험의 전체 사례 해시를 확인한 뒤 요약을 기록합니다.
