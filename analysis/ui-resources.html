RAW 형식 메뉴의 PEF·DNG 선택과 메뉴 글자 준비

RAW 파일을 PEF로 저장할지 DNG로 저장할지 고르는 메뉴를 추적했습니다. 고른 값이 설정에 기록되는 순서와, 메뉴에 보이는 글자가 준비되는 과정을 함께 확인했습니다.

이 문서에서

  1. 배경: RAW File Format 메뉴와 두 파일 형식
  2. 분석 대상은 제조사 대응표에 공통으로 있는 항목입니다
  3. 고르기와 적용은 서로 다른 단계입니다
  4. 메뉴 글자는 리소스에서 글리프 배열로 준비됩니다
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • RAW File Format 메뉴의 두 선택지는 설정값 하나로 저장됩니다. PEF는 0, DNG는 1입니다.
  • 항목을 고르면 화면 객체의 임시값만 바뀝니다. 적용 이벤트를 받아야 RAM의 설정(현재값과 미러)에 기록합니다. 취소 이벤트는 기록하지 않고 임시값을 원래 값으로 되돌립니다.
  • 메뉴 글자 세 개(RAW File Format, PEF, DNG)가 리소스 표에서 글자 객체로 만들어지고, 언어에 따라 16비트 글리프 배열로 준비되는 과정을 실행했습니다. 화면에 그리는 단계는 실행하지 않았습니다.
  • 이 메뉴는 K-3 III에도 같은 이름으로 있습니다. 그러나 이 문서의 번호와 객체 구조는 K-3 II의 것이고, 다른 기종과 호환된다는 근거는 없습니다. 실제 버튼, LCD 표시, 플래시 저장도 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 고르기·떠나기·적용·취소 12개 사례의 임시값과 RAM 설정
  • 설정 읽기·쓰기 함수와 뱅크 계산
  • 리소스 검색에서 글자 객체 생성까지
  • 글리프 준비 12건, 래퍼 상태 2건

모델 시험 조건으로 정한 것

  • 버튼 대신 이벤트 번호를 함수에 직접 전달
  • 활성 인덱스, 뱅크 내용, 활성 언어 인덱스는 시험용 값
  • 메모리 할당, 화면 갱신, 위젯 검색·알림은 검증용 대체 코드

미확인 확인하지 않은 것

  • 물리 버튼과 이벤트 번호의 대응
  • 글꼴 그리기와 LCD 출력
  • 플래시 저장, RAW 파일 기록에 미치는 효과
  • K-3 III·Q7과의 번호·구조 호환

배경: RAW File Format 메뉴와 두 파일 형식

K-3 II 사용 설명서에서 RAW File Format은 촬영 메뉴 1의 Image Capture Settings 안에 있습니다. 선택지는 PEF와 DNG이고 기본값은 PEF입니다(K-3 II 사용 설명서 20·37쪽).

PEF
설명서는 PEF를 “PENTAX 고유의 RAW 파일 형식”이라고 설명합니다(37쪽).
DNG
Adobe가 만들어 규격을 공개한 RAW 파일 형식입니다. TIFF 6.0을 바탕으로 합니다(미국 의회도서관의 DNG 형식 설명). 설명서에는 이 제품이 Adobe의 허락을 받아 DNG 기술을 쓴다고 적혀 있습니다(109쪽).

이 문서는 두 형식의 파일 내용을 다루지 않습니다. 다루는 것은 메뉴에서 형식을 고르는 동작과 메뉴 글자입니다. 임시값, 현재값과 미러, 뱅크, 논리 동작 같은 용어는 색공간 메뉴 문서의 배경과 같은 뜻으로 씁니다. 추가로 쓰는 말은 아래와 같습니다.

글리프 코드
글자 하나를 가리키는 펌웨어 내부 번호입니다. 글꼴 안의 그림 번호에 해당하며, 표준 문자 코드라고 확정하지 않았습니다.
언어 표
같은 문구의 언어별 글리프 데이터 주소를 모아 둔 표입니다. 언어 인덱스로 한 칸을 고릅니다.
글자 객체와 래퍼
글자 객체는 문구 하나를 준비하는 객체이고, 래퍼는 그 객체를 위젯으로 감싼 객체입니다. 원문 검증기에서는 각각 renderer, wrapper라고 부릅니다.
주소 표기
코드와 표의 위치는 복호화한 펌웨어 파일의 오프셋입니다. screen+0xF9, renderer+0x90처럼 쓴 것은 객체 안의 필드 위치입니다.

분석 대상은 제조사 대응표에 공통으로 있는 항목입니다

리코의 메뉴 대비표는 K-3 II와 K-3 III의 RAW 파일 형식 항목을 서로 대응시킵니다. 이것은 기능이 같다는 근거이고, 내부 번호나 코드가 호환된다는 근거는 아닙니다.

리코가 공개한 K-3 Mark III 메뉴 대비표(K-3 II 편) 1쪽에는 K-3 II의 촬영 메뉴 1 → 記録設定(영문 설명서의 Image Capture Settings) → RAWファイル形式이 K-3 III의 촬영 메뉴 5 → RAWファイル形式과 같은 줄에 놓여 있습니다(대비표 PDF, 대비표 안내 페이지). 두 기종에 모두 있는 메뉴라서 비교의 출발점으로 골랐습니다.

세 레코드는 위젯 표 0x993334에 있는 글자(type 4) 항목입니다. 화면을 만드는 코드가 이 위젯 번호로 표를 검색하는 것까지 확인했습니다. PEF와 DNG 위젯은 글자를 보여 주는 동시에 선택을 받는 위젯입니다. 메뉴에서 이 항목 전체를 가리키는 번호는 제목 위젯과 다른 0x0150000A입니다.

고르기와 적용은 서로 다른 단계입니다

PEF나 DNG를 고르면 화면 객체의 임시값만 바뀝니다. 적용 이벤트가 와야 임시값이 RAM의 설정 0x97에 기록됩니다. 취소 이벤트는 임시값을 기존 값으로 되돌립니다.

화면을 초기화하면 저장된 설정값이 기존 값과 임시값 두 곳에 들어갑니다. 그 뒤의 동작은 이벤트에 따라 셋으로 갈립니다.

  • 적용 이벤트는 일곱 가지입니다. 0, 1, 6, 0x10, 0x11, 0x1D, 0x20에서 임시값을 설정에 기록했습니다. 이 번호를 버튼 이름으로 해석하지 않았습니다.
  • 취소로 처리되는 이벤트는 3과 0xF입니다. 설정은 그대로 두고 임시값을 기존 값으로 되돌렸습니다.
  • 다른 항목 번호로 온 이벤트는 무시됩니다. 설정도 임시값도 바뀌지 않아, 고른 값이 임시값에 남았습니다.
  • 고른 뒤 다른 위젯으로 옮겨 가도 임시값은 남습니다. 모든 사례에서 반대쪽 위젯을 떠나는 동작을 넣었고 임시값은 그대로였습니다.
  • 기록은 고른 뱅크에만 합니다. 활성 인덱스 0~7의 뱅크는 0, 0, 2, 3, 4, 5, 6, 7입니다. 현재값과 미러의 해당 뱅크 바이트만 바뀌었고, 표식값을 넣어 둔 다른 뱅크는 그대로였습니다.

저장값을 위젯 번호로 바꿔 주는 조회 함수도 실행했습니다. 0이면 PEF 위젯, 1이면 DNG 위젯을 돌려주고, 대조로 넣은 값 2에서는 “해당 위젯 없음”을 뜻하는 0을 돌려줬습니다.

참고

색공간 메뉴와 견주면 구조는 같고 세부가 다릅니다. 색공간 화면은 취소해도 임시값이 남고 다시 열 때 저장값으로 덮어씁니다. 이 화면은 기존 값을 따로 들고 있다가 취소 이벤트에서 곧바로 되돌립니다. Pixel Shift Resolution 메뉴도 고르기와 적용이 나뉘어 있고 같은 설정 쓰기 함수를 씁니다.

메뉴 글자는 리소스에서 글리프 배열로 준비됩니다

위젯 번호로 리소스 레코드를 찾아 글자 객체를 만들고, 글자 객체는 언어에 맞는 글리프 데이터를 16비트 배열로 펼칩니다. 두 구간을 각각 실행했고, 화면에 그리는 단계는 실행하지 않았습니다.

글자 객체에 들어가는 값

리소스 레코드는 20바이트이고, 위젯 번호, 종류(4), 언어 표 주소, 3, 0 순서로 들어 있습니다. 글자 객체가 만들어지면 객체의 +0x90에 언어 표 주소가, +0x84에 16비트 스타일 값이 기록됩니다. 세 레코드의 스타일 값은 모두 4였습니다.

언어에 따라 달라지는 글리프 준비

준비 함수는 활성 언어 인덱스로 언어 표의 한 칸을 고릅니다. 언어마다 글리프 데이터가 1바이트 단위인지 2바이트 단위인지는 별도의 표가 정합니다. 어느 쪽이든 결과는 16비트 배열이고, 길이에는 끝 표시(0)가 포함됩니다. 글자 객체의 +0xAC가 0이 아니면 활성 언어와 상관없이 인덱스 0을 씁니다.

인덱스 0의 영어 문구는 글리프 코드에 0x1E를 더하면 ASCII 문자로 읽힙니다. 이렇게 읽은 결과가 RAW File Format, PEF, DNG입니다. 인덱스 9에서는 세 문구 모두 비어 있어 끝 표시 하나만 나왔습니다. 인덱스 9와 10이 어느 언어인지는 확인하지 않았습니다.

주의

글리프 코드를 Unicode나 UTF-16 문자열이라고 단정하지 않습니다. 영어 문구에서 0x1E를 더하는 규칙이 맞았을 뿐입니다. 글꼴 데이터와 LCD 비트맵은 추출하지 않았습니다.

래퍼는 상태에 따라 언어 표를 바꿉니다

위젯 래퍼는 언어 표 주소를 두 개(+0x5C, +0x60) 들고 있다가 상태에 따라 하나를 골라 글자 객체에 넣습니다. 스타일 값(+0x64)도 함께 넘깁니다. 상태 0과 1을 따로 실행해 각각 첫째와 둘째 언어 표가 선택되는 것을 확인했습니다. 화면을 만드는 코드가 제목 래퍼의 둘째 언어 표에 RAW File Format의 언어 표를 넣는 것도 확인했습니다.

그래서 다른 기종의 메뉴를 옮겨 오려면 문구만 바꿔서는 안 됩니다. 객체의 상태, 포인터가 놓이는 자리, 길이를 세는 방식까지 맞춰야 합니다.

준비된 배열의 SHA-256은 ui-resources.json의 text_cases에 있습니다. 해시에는 끝 표시가 포함됩니다.

한계와 남은 과제

  • 입력 — 이벤트 번호를 화면의 가상 함수에 직접 전달했습니다. 버튼을 누른 시험이 아니고, 이벤트 번호가 어느 버튼인지도 모릅니다.
  • 표시 — 리소스 검색에서 글자 객체 생성까지, 글자 객체에서 글리프 배열까지를 각각 실행했습니다. 두 구간을 이어 화면 전체를 그린 것이 아닙니다. 글꼴 그리기와 LCD 출력은 실행하지 않았습니다.
  • 저장과 효과 — RAM의 현재값과 미러까지만 확인했습니다. 플래시 저장은 보존 섹터의 설정 저장에서 따로 다루며, 그 검증에서 PEF를 DNG로 바꾼 설정이 섹터 쓰기 요청에 도달했습니다. 이 설정이 실제 RAW 파일 기록을 어떻게 바꾸는지는 이 문서의 범위가 아닙니다.
  • 다른 기종 — K-3 III와 Q7의 번호와 글자 준비 방식은 이 결과로 대신할 수 없습니다. 지금은 기능 대응표를 바탕으로 각 기종의 고르기·적용 규칙을 비교하는 단계입니다. 메뉴를 옮겨 실행하거나 펌웨어를 고친 적은 없습니다. 세 기종 비교는 K-3 III 저장소의 UI 이식 설계에 있습니다.

재현 방법

검증기는 복호화한 펌웨어 파일 decoded.bin을 입력으로 받습니다(펌웨어 파일 구조와 복호화). 에뮬레이터는 Unicorn 2.1.4입니다.

python verify_ui_resources.py decoded.bin --compare analysis/ui-resources.json
python -m unittest discover -s tests -v
python verify_publication.py

첫 명령은 리소스 레코드, 분기, 가상 함수 표를 파일 바이트로 확인한 뒤 원본 코드를 실행합니다. 리소스 검색, 글리프 준비, 화면의 가상 함수, 뱅크 계산, RAM 쓰기는 원본 명령으로 실행하고, 결과가 저장소의 ui-resources.json과 다르면 실패합니다. 나머지 두 명령은 펌웨어 없이 돌아가는 단위 테스트와 문서 검사입니다.
