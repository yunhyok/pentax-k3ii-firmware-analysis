selector 5·6의 직접 인자와
별도 입력 객체의 생산 경로

주소와 코드 상수는 0x 접두사를 생략한 16진수로도 표기합니다. 검사 개수와 바이트 길이는 10진수입니다. 기본값·합성 RAM 재현과 실제 메뉴 변경·촬영 도달을 구분합니다.

1. 두 직접 호출의 수신자

selector 5·6에 값을 전달하는 직접 호출 두 곳을 확인했습니다. 4EBBAC는 selector 5, 4EBBC4는 selector 6으로 6EB284를 호출합니다. 두 호출의 수신 객체는 고정 RAM 주소 4047AE1C입니다. 함수 4EBAF8의 진입 R0는 R4에 보존되며, word(R4+1C)가 가리키는 별도 입력 객체에서 값을 가져옵니다. 아래 명령 주소는 파일 offset이고, 실행 VA에는 02000000을 더합니다. RAM 주소는 이미 VA입니다.

2. descriptor와 값 수식

selector 5의 인자는 6C78D0이 읽는 입력 객체+24의 unsigned halfword입니다. selector 6은 6C78E0이 읽는 입력 객체+26의 unsigned halfword입니다. ROM descriptor 9DEAB8과 9DEAC0은 각각 offset 11·12, mask FF, shift 0을 담습니다. 6EB284는 이 인자의 하위 8비트를 수신 객체+15·+16에 씁니다. 색상·대비·밝기 같은 메뉴 명칭은 붙이지 않았습니다.

3. selector 6 기본값 생산자

selector 6에는 기본값 생산 코드도 연결됩니다. 4EBAF8→4EBA80→4EB9E4의 정적 호출 관계에서, 4EBA50은 R1을 20으로 만들고 4EBA54는 6C78D8을 호출해 입력 객체+26에 halfword 0020을 저장합니다. 이 작은 원본 구간을 실행하면 나중의 getter/setter 구간이 수신 객체+16에 20을 씁니다. 두 구간 사이의 서비스와 guard는 실행하지 않았으므로 실제 전체 함수가 항상 이 값을 전달한다고 단정할 수는 없습니다.

4. selector 5와 owner의 남은 경계

selector 5의 입력 저장 위치와 쓰기 leaf 6C78C8은 확인했지만, 현재 값이 어떤 메뉴 이벤트에서 만들어졌는지는 미확정입니다. 4E8F84→56B3BC→4E8F88의 owner+1C 설정 코드도 찾았으나 이번 호출과 동일한 런타임 인스턴스인지는 확인하지 않았습니다.

5. 작은 원본 구간 재현

5개 합성 RAM 사례에서 원본 쓰기 leaf, getter, selector setter를 실행했습니다. 기본 입력은 00·20, 상위 비트가 있는 입력 0144·0128은 44·28, 최대 halfword는 FF·FF가 됐습니다. 기본값 구간을 적용한 사례는 54·20이었고, 입력 객체 주소를 옮긴 대조도 44·28이었습니다. 실제 호출 시점의 R0·R1·R2와 메모리 이벤트를 기록했으며, 수신 객체의 나머지 50바이트는 바뀌지 않았습니다. 입력 포인터와 쓰기 leaf의 인자는 실기 관측값이 아닌 시험용 값입니다.

6. manager와 기존 tone lookup의 관계

같은 함수에는 manager의 내용을 scratch 객체로 읽는 4EBB7C와 수정한 내용을 쓰는 4EBBFC도 있습니다. 두 호출의 R2는 1입니다. manager 캐시 슬롯은 4040A5DC이고, scratch의 48바이트 payload는 4047AE20–4047AE50입니다. 이 읽기·쓰기와 후속 알림 경로는 정적으로 연결했으며 실행하지 않았습니다. 기존 II31의 job+334 객체, job+349·34A 기본값 00·20, selector 6의 ROM 029E651C lookup과는 자료형·descriptor를 대조했습니다. 이번 scratch가 실제 촬영 job으로 복사되는 연속 경로를 새로 입증한 것은 아닙니다.

7. 검증 범위와 미확정 사항

분석 입력은 SHA-256으로 고정했고, 선택한 코드와 데이터 14개 범위를 별도로 기록했습니다. 전체 이미지의 정렬된 A32 분기 패턴 84개는 후보 목록으로만 취급했습니다. 실제 인자와 실행을 확인한 6EB284 호출은 두 곳입니다. Thumb·간접 호출·전체 별칭과 모든 CFG는 조사하지 않았습니다. 서비스·MMIO·CP15·부팅 재개·카메라 촬영은 실행하지 않았으며, 실제 메뉴 연결과 촬영 도달 조건은 남은 과제입니다.

8. 공개 검증과 재현

공개 CLI는 사용자가 따로 제공한 decoded 일반 파일을 정확한 크기와 SHA-256으로 한 번 캡처합니다. helper와 source contract도 고정된 크기·해시로 캡처하며, 검증한 helper bytes만 실행합니다. 입력과 14개 희소 원본 범위가 일치한 뒤 원본 leaf 구간 5개 사례를 재현합니다.

원본 II35 전체 관측의 dict·list·str·int·bool 자료형과 모든 값·순서·출처를 정본 해시로 검사합니다. 원래 Windows CRLF 직렬화도 메모리에서 복원해 원본 파일 해시와 비교합니다. 그 검사를 통과한 전체 관측을 공개 JSON에 유지합니다. 명령 주소와 읽기·쓰기 값은 포함하지만 원본 firmware bytes, 역어셈블리 목록과 사설 경로는 포함하지 않습니다. historical35는 과거 코드·환경이고 current_execution은 현재 CLI·helper·엔진 정보입니다.

기본 CI 검사는 표준 라이브러리만으로 수행하며 펌웨어와 Capstone·Unicorn을 가져오지 않습니다. 정상·-O 모드에서 각각 11개 검사가 통과했습니다. 원본 5개 사례 재현은 별도의 입력과 Capstone 배포판 5.0.9(모듈 5.0.7), Unicorn 2.1.4가 필요합니다. -O에서도 explicit require 검사가 유지됩니다. 다른 위치로 옮긴 일반 실행과 후보 위치의 -O 실행 결과는 바이트 단위로 같았습니다.

출력은 입력을 읽기 전과 쓰기 직전에 lexists로 검사하며 xb 모드로 생성합니다. 기존 파일·hardlink·dangling symlink를 덮어쓰지 않습니다. 별도 disassembly 출력 옵션은 제공하지 않습니다. 파일이 캡처된 뒤 외부에서 바뀌더라도 이번 결과는 검증한 캡처 bytes에 대한 결과입니다.

python -B verify_tone_selectors.py /path/to/decoded.bin --output /path/to/new-result.json
python -B -O verify_tone_selectors.py /path/to/decoded.bin --output /path/to/new-opt-result.json
python -B -S -m unittest discover -s tests -p test_tone_selectors.py
python -B -O -S -m unittest discover -s tests -p test_tone_selectors.py
