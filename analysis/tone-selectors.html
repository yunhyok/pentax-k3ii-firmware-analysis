톤 selector 5·6 값을 만드는 원본 코드

톤 계산에 쓰이는 selector 5와 6의 바이트를 누가 처음 쓰는지 찾았습니다. 값을 넣는 호출 두 곳과 그 값의 입력 위치, selector 6의 기본값을 쓰는 코드를 정리하고 작은 원본 구간으로 재현했습니다.

이 문서에서

  1. 배경: selector와 입력 객체
  2. 두 호출은 입력 halfword의 하위 8비트를 임시 객체에 씁니다
  3. 작은 원본 구간 5개 사례에서 하위 8비트 저장을 확인했습니다
  4. 관리자 읽기·쓰기와 기존 톤 경로는 정적으로만 이어집니다
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • selector 5·6에 값을 넣는 직접 호출 두 곳을 찾았습니다. 둘은 같은 함수 안에 있습니다. 별도 입력 객체에서 16비트 값을 하나씩 읽어 하위 8비트만 고정 RAM의 임시 객체에 저장합니다.
  • selector 6에는 기본값 32를 입력 객체에 쓰는 원본 코드도 연결됩니다. 작업 객체 생성자가 selector 6에 쓰는 값과 같은 수입니다.
  • 합성 RAM으로 만든 5개 사례에서 원본 쓰기 함수·getter·setter를 실행해 하위 8비트 저장을 확인했습니다. 임시 객체의 나머지 바이트는 바뀌지 않았습니다.
  • 두 값의 물리적 의미, 어느 메뉴 이벤트에서 오는지, 이 임시 객체가 촬영 작업으로 복사되는지는 확인하지 못했습니다. 서비스·메뉴·촬영은 실행하지 않았습니다.

확인 원본 코드 실행으로 확인

  • getter와 setter 연속 구간이 입력 halfword의 하위 8비트를 저장함
  • 기본값 구간이 입력 객체 +0x26에 32를 씀
  • 입력 객체 주소를 옮겨도 같은 결과

정적 분석 코드를 읽어 판단

  • 두 호출의 수신 객체, 기술자, 입력 위치
  • 같은 함수 안의 관리자 읽기·쓰기(R2 = 1)
  • owner+0x1C를 설정하는 후보 코드

모델 시험 조건으로 정한 것

  • 입력 객체 포인터와 원본 쓰기 함수에 넣은 값
  • 임시 객체의 처음 내용(A5로 채움)

미확인 확인하지 않은 것

  • 두 값의 물리적 의미와 메뉴 이름
  • selector 5 입력이 어느 이벤트에서 만들어지는지
  • 임시 객체에서 촬영 job으로 가는 복사 경로
  • 서비스·MMIO·CP15·부팅·촬영

배경: selector와 입력 객체

톤 입력 R5 문서에서 selector 6 바이트가 ROM 표에서 R5를 고르는 인덱스라는 것을 보았습니다. 톤 설정 관리자 문서에서는 그 바이트가 관리자 레코드에 실려 복사된다는 것까지 보았습니다. 이 문서는 바이트를 직접 쓰는 쪽을 찾습니다.

selector
설정 항목 번호입니다. setter 6EB284는 번호로 ROM 기술자를 찾아 정해진 바이트를 씁니다.
halfword
16비트(2바이트) 값입니다. ARM의 LDRH·STRH 명령이 읽고 씁니다.
임시 객체
고정 RAM 주소 0x4047AE1C의 객체입니다. 관리자 레코드를 읽어 와 고친 뒤 되돌리는 데 씁니다.
입력 객체
호출 함수의 owner가 +0x1C에 들고 있는 포인터가 가리키는 객체입니다. selector 값의 원천입니다.
표기

주소와 코드 상수는 0x를 생략한 16진수로도 씁니다. 명령 주소는 파일 오프셋이고 실행 주소에는 02000000을 더합니다. RAM 주소는 처음부터 VA입니다. 검사 개수와 바이트 길이는 10진수입니다.

두 호출은 입력 halfword의 하위 8비트를 임시 객체에 씁니다

selector 5는 입력 객체 +0x24, selector 6은 +0x26의 16비트 값을 읽어 임시 객체 +0x15·+0x16에 하위 8비트를 저장합니다.

두 호출의 수신 객체는 고정 RAM 주소 4047AE1C입니다. 호출 함수 4EBAF8의 진입 R0는 R4에 보존됩니다. 값은 word(R4+0x1C)가 가리키는 별도 입력 객체에서 가져옵니다. setter는 받은 인자의 하위 8비트를 씁니다. 색상·대비·밝기 같은 메뉴 이름은 붙이지 않았습니다.

selector 6의 기본값 생산자

selector 6에는 기본값 코드가 연결됩니다. 정적 호출 관계는 4EBAF8 → 4EBA80 → 4EB9E4입니다. 그 안에서 4EBA50이 R1을 0x20으로 만들고 4EBA54가 6C78D8을 불러 입력 객체 +0x26에 halfword 0020을 저장합니다. 이 작은 구간을 실행하면 뒤의 getter·setter 구간이 임시 객체 +0x16에 32를 씁니다.

두 구간 사이의 서비스와 가드는 실행하지 않았습니다. 그래서 실제 전체 함수가 항상 이 값을 넘긴다고 단정하지 않습니다.

selector 5와 owner의 남은 경계

selector 5의 입력 저장 위치와 쓰기 함수 6C78C8은 확인했습니다. 지금 들어 있는 값이 어떤 메뉴 이벤트에서 만들어졌는지는 정하지 못했습니다. owner+0x1C를 설정하는 코드(4E8F84 → 56B3BC → 4E8F88)도 찾았습니다. 다만 위 호출과 같은 실행 중 객체인지는 확인하지 않았습니다.

작은 원본 구간 5개 사례에서 하위 8비트 저장을 확인했습니다

모든 사례에서 저장된 바이트는 읽은 halfword의 하위 8비트였습니다. 임시 객체의 나머지 50바이트는 그대로였습니다.

실행한 원본 구간은 쓰기 함수, getter, setter입니다. 실제 호출 시점의 R0·R1·R2와 메모리 읽기·쓰기를 기록했습니다. 입력 포인터와 쓰기 함수의 인자는 실기 관측값이 아닌 시험값입니다.

실행 허용 구간과 시험 배치
  • 실행을 허용한 원본 구간: 4EBA4C..4EBA58(기본값), 4EBB98..4EBBC8(getter·setter 연속 구간), 6C78C8..6C78E8, 6EB284..6EB2D0.
  • owner는 0x10100000, 입력 객체 포인터는 하네스가 0x10101000으로 넣었습니다. relocated_owner는 0x10104000과 0x10105000입니다.
  • setter의 바이트 쓰기는 6EB2C8에서 일어납니다. 사례마다 쓰기 4건(기본값 사례 5건), 읽기 16건(17건)을 기록했습니다.
  • 전체 기록은 tone-selectors.json의 native_cases에 있습니다.

관리자 읽기·쓰기와 기존 톤 경로는 정적으로만 이어집니다

같은 함수가 관리자 레코드를 임시 객체로 읽고 고친 뒤 되돌립니다. 그 가운데 실행한 것은 getter·setter 구간뿐입니다.

관리자 캐시 슬롯은 4040A5DC이고 임시 객체의 48바이트 payload는 4047AE20–4047AE50입니다. 이 읽기·쓰기와 이어지는 통지 경로는 정적으로 연결했으며 실행하지 않았습니다. 갱신 함수의 순서는 톤 설정 관리자 문서에 있습니다.

기존 촬영 job 경로와는 자료형과 기술자를 대조했습니다. job+0x334 객체의 selector 5·6은 job+0x349·0x34A에 있으며 생성자 기본값은 0·32입니다. selector 6은 ROM 029E651C를 조회하며 인덱스 32와 40에서 8192와 16384가 나옵니다. 이 임시 객체가 실제 촬영 job으로 복사되는 연속 경로는 입증하지 않았습니다.

한계와 남은 과제

  • 호출 범위: 분석 입력은 SHA-256으로 고정했고 코드·데이터 14개 범위를 따로 기록했습니다. 전체 이미지의 정렬된 A32 분기 패턴 84개는 후보 목록으로만 다룹니다. 인자와 실행을 확인한 6EB284 호출은 두 곳입니다.
  • 찾지 않은 것: Thumb·간접 호출, 수신 객체 별칭, 다른 진입점, 전체 제어 흐름은 조사하지 않았습니다.
  • 실행하지 않은 것: 서비스·MMIO·CP15·부팅 재개·카메라 촬영은 실행하지 않았습니다. 기본값 구간과 입력 쓰기는 따로 진입했고 그 사이의 서비스·가드 호출은 재현하지 않았습니다.
  • 값의 뜻: 입력 객체 +0x24·+0x26과 각 값의 물리적 의미, 메뉴 이벤트, 촬영 도달, 픽셀 버퍼 재사용은 미확정입니다.
  • 남은 연결: 관리자와 촬영 job 사이의 실제 복사 경로가 남아 있습니다.

재현 방법

공개 검증의 동작

  • CLI는 따로 준비한 복호화 일반 파일을 정확한 크기와 SHA-256으로 한 번 캡처합니다. 보조 코드와 소스 계약도 고정한 크기·해시로 캡처하며 검증한 보조 코드 바이트만 실행합니다.
  • 입력과 14개 원본 범위가 맞아야 원본 구간 5개 사례의 재현으로 넘어갑니다.
  • 원래 기록(II35) 전체의 자료형과 모든 값·순서·출처를 정본 해시로 검사합니다. 비교 대상에는 원래의 Windows CRLF 직렬화를 메모리에서 복원한 원본 파일 해시도 들어갑니다.
  • 공개 JSON에는 명령 주소와 읽기·쓰기 값만 있고 펌웨어 바이트, 역어셈블리 목록, 개인 경로는 없습니다. historical35는 과거 코드·환경, current_execution은 현재 CLI·보조 코드·엔진 정보입니다.
  • 기본 CI 검사는 표준 라이브러리만 쓰며 펌웨어·Capstone·Unicorn을 불러오지 않습니다. 일반·-O 모드에서 각각 11개 검사가 통과했습니다.
  • 원본 사례 재현에는 입력 파일과 Capstone 배포판 5.0.9(모듈 5.0.7), Unicorn 2.1.4가 필요합니다. -O에서도 명시적 require 검사가 유지됩니다. 다른 위치로 옮긴 일반 실행과 -O 실행의 결과는 바이트 단위로 같았습니다.
  • 출력 경로는 입력을 읽기 전과 쓰기 직전에 lexists로 검사하고 xb 모드로 만듭니다. 기존 파일·하드링크·끊어진 심볼릭 링크를 덮어쓰지 않습니다. 역어셈블리 출력 옵션은 없습니다.
python -B verify_tone_selectors.py /path/to/decoded.bin --output /path/to/new-result.json
python -B -O verify_tone_selectors.py /path/to/decoded.bin --output /path/to/new-opt-result.json
python -B -S -m unittest discover -s tests -p test_tone_selectors.py
python -B -O -S -m unittest discover -s tests -p test_tone_selectors.py
