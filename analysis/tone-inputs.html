톤 입력의 원본 생산자

톤 곡선에 들어가는 정수는 recipe 객체와 문맥의 값으로 계산됩니다. 그 값을 시험 프로그램이 넣지 않고 원본 생성자와 원본 생산 코드가 쓰게 해, 입력이 어디서 오는지 한 단계 더 거슬러 올라갔습니다.

이 문서에서

  1. 배경: 생성자 값과 나중에 쓰는 값
  2. 생성자와 생산 코드가 쓰는 값
  3. 8개 경우의 실행 결과
  4. 정적으로만 찾은 경로와 다음 입력
  5. 한계
  6. 재현 방법과 근거 파일

핵심 요약

  • 문맥 계산이 읽는 recipe 필드 4개와 문맥 필드 6개에 시험 프로그램이 값을 직접 쓰지 않았습니다. 원본 생성자와 원본 생산 코드가 쓴 값만으로 8개 경우를 실행했습니다.
  • recipe+BC는 작업 객체의 halfword 값에서 계산됩니다. recipe+A4는 작업 객체의 한 바이트를 그대로 복사한 값입니다. A4가 0이면 문맥 계산이 입력을 새로 만듭니다. 0이 아니면(255 포함) 이전 문맥 값을 그대로 씁니다.
  • 결과 정수는 생성자 값만 쓴 경우 8192, 나눗셈 분기 9117, 유지 분기 32765였습니다. 이 시험은 정수 계산과 getter에서 끝나며 곡선은 다시 만들지 않았습니다.
  • 상위 작업 필드 15개는 시험용으로 넣은 값입니다. recipe+92와 +9C를 다시 쓰는 코드는 정적으로만 찾았습니다. 실제 촬영의 실행 순서, 버퍼 재사용, 값의 물리 단위는 확인하지 않았고 카메라에서 실행한 것도 없습니다.

확인 원본 코드 실행으로 확인

  • recipe 생성자와 문맥 생성자가 쓰는 초기값
  • 작업 필드에서 recipe+BC·+A4를 만드는 분기와 저장 명령
  • 문맥 계산의 유지·갱신 분기, context+7A74 저장, getter 반환
  • 일반·최적화·독립 실행의 JSON이 바이트 단위로 같음

정적 분석 코드를 읽어 판단

  • 같은 recipe의 +92를 다시 0으로 쓰는 경로
  • +9C를 쓰는 별도 단계(65EED0 → 7198D4)
  • 정적 원본 구간 55개의 해시

모델 시험 조건으로 정한 것

  • 상위 작업 필드 15개의 값(7건)
  • 생략한 중간 분류기·서비스 호출
  • CPU는 Unicorn의 Cortex-A9 설정

미확인 확인하지 않은 것

  • 상위 작업 필드를 실제로 쓰는 코드와 그 값
  • 실제 촬영의 연속 실행, 중간 덮어쓰기, 버퍼 재사용
  • SuperResolution 메뉴 도달, 물리적 EV·Q 형식·감마

배경: 생성자 값과 나중에 쓰는 값

톤 문맥과 곡선 생산자의 연결에서는 문맥 계산 함수 4DF834가 recipe와 문맥의 값으로 정수 하나를 만들어 context+7A74에 쓰는 것을 확인했습니다. 곡선 생산자는 이 정수로 톤 곡선을 만듭니다. 다만 그 시험에서는 recipe와 문맥의 입력값을 시험 프로그램이 넣었습니다.

이 문서는 그 입력을 원본 코드에게 맡깁니다. 객체의 값은 두 단계로 정해집니다.

생성자
객체를 처음 만들 때 초기값을 쓰는 함수입니다. 여기서는 recipe 생성자 7B1D4C와 문맥 생성자 859ACC입니다.
생산 코드
객체가 만들어진 뒤 필드를 다시 쓰는 코드입니다. 작업 객체의 다른 필드를 읽어 계산하거나 복사합니다.
recipe 객체
작업 객체(job) 안 job+E0C4에 있는 톤 설정 객체입니다. 용어집의 레시피(모듈 호출 순서 목록)와는 다릅니다. 문맥은 job+E608에 있습니다.

문맥 계산에는 "이전 값을 그대로 쓰는" 분기가 있습니다. 그래서 어떤 값이 언제 쓰였는지가 결과를 바꿉니다. 주소는 16진수 파일 오프셋이며 실행 주소(VA)는 0x02000000을 더한 값입니다.

생성자와 생산 코드가 쓰는 값

recipe+BC와 +A4는 원본 생산 코드가 작업 객체의 필드로 만듭니다. 문맥 계산은 A4 하나로 새 값을 쓸지 이전 값을 쓸지 정합니다.

생성자가 쓰는 초기값

문맥 생성자 859ACC는 halfword 4개(+8, +A, +C, +E)에 420·256·256·320을 씁니다. +60DC에는 8192, +7A68에는 4096을 씁니다. recipe 생성자 7B1D4C는 +92·+A4·+BC를 0으로, +9C를 8192로 초기화합니다. 이 값들은 생성자 출력일 뿐입니다. 실제 촬영에서 기본값으로 남는지는 확인하지 못했습니다. 뒤의 분기가 이 halfword를 다시 쓸 수도 있습니다.

recipe+BC와 +A4를 만드는 코드

659048의 분기는 job+3C와 job+6D 두 바이트를 읽고 결과를 고릅니다.

  • 둘 중 하나라도 0이 아니면: job+264·266·268·26A의 최대 halfword를 10으로 나누고 100을 더합니다.
  • 둘 다 0이면: job+274~282의 halfword 8개를 네 쌍으로 더합니다. 각 합을 16비트로 자른 뒤 최대값을 고릅니다.

784CA0이 이 결과를 recipe+BC에 워드로 씁니다. 이어서 7198C4가 job+2080의 바이트를 recipe+A4에 복사합니다.

문맥 계산의 유지와 갱신

4DF834는 recipe+A4가 0이면 +BC와 +9C로 문맥의 +7A68·+60DC를 갱신합니다. 0이 아니면 두 값을 그대로 둡니다. 원본 생성자 출력에서 시작한 유지 분기의 결과는 32765였습니다. 앞 문서에서 임의로 넣었던 문맥 입력을 이번에는 원본 생성자 출력으로 바꾼 것입니다. 실제 촬영 설정값이나 물리적 단위는 여전히 모릅니다.

8개 경우의 실행 결과

8개 경우 모두 원본 코드의 결과가 독립 정수식과 같았습니다. A4가 0이 아니면 255여도 유지 분기를 탔습니다.

이 실행은 context+7A74 계산과 getter 4FA83C에서 끝납니다. 톤 곡선 생성은 실행하지 않았습니다. 초기 halfword 4개와 이전 문맥값은 모든 경우에 원본 생성자 출력입니다.

실행 범위와 검사 방법
  • 재현은 구분된 원본 코드 구간을 실행했습니다. 658EBC의 스택 프레임과 같은 job에서 유도한 포인터는 유지하되 중간 분류기·서비스 호출은 생략했습니다.
  • 준비한 입력을 기록한 곳은 상위 job 필드뿐입니다. recipe의 +92·+A4·+BC·+9C와 문맥의 +8·+A·+C·+E·+60DC·+7A68에는 호스트가 직접 쓰지 않았습니다.
  • 모든 실행 명령의 원본 바이트와 허용 쓰기 범위를 검사했습니다. 계산값은 독립 정수식으로 다시 확인했습니다.
  • 쓰기 기록: 문맥 생성자 48건(경우당 6건), recipe 생성자 32건, recipe 생산 코드의 저장 14건(생성자만 쓴 경우 제외 7건 × 2).
  • 준비한 값, 주요 쓰기 명령, 전체 쓰기 건수와 해시는 결과 JSON에 있습니다.

정적으로만 찾은 경로와 다음 입력

recipe+92와 +9C를 다시 쓰는 코드는 코드를 읽어서만 찾았습니다. 그 앞의 입력은 아직 모릅니다.

정적 분석에서 같은 job+E0C4의 +92를 다시 0으로 쓰는 경로를 찾았습니다. +9C를 쓰는 별도 작업 단계도 있습니다. +9C 생산 코드 65EED0은 같은 스택의 임시값을 초기화하거나 조건부로 덮어쓴 뒤 7198D4로 넘깁니다. 이 단계는 가상 호출 결과, ROM 표 인덱스, 전역 블록, 구성 서비스의 영향을 받습니다. 관련 서비스는 실행하지 않았습니다. 다른 객체의 같은 오프셋에 쓰는 명령은 같은 생산 코드로 치지 않았습니다.

이 경계가 남아 있으므로 실제 촬영 작업의 연속 실행, 버퍼 재사용 이력, SuperResolution 메뉴 도달은 이 결과만으로 정할 수 없습니다. +9C 생산 코드의 제한된 실행은 recipe+9C 정수 생산자와 내장 입력 복사에 있습니다. 그 문서는 같은 스택 슬롯의 산술·저장 20조건과 별도의 바이트 전달 3조건을 원본으로 대조했습니다. 실행 범위는 이 문서와 따로 읽어야 합니다.

한계

  • 분리된 실행 구간의 연결을 검증한 결과입니다. 입력 서비스, 작업 스케줄, 중간 덮어쓰기, 실제 촬영의 버퍼 재사용은 확인하지 않았습니다.
  • 생성자 초기값이 현재 촬영 기본값인지 확인하지 않았습니다. 네 halfword에는 물리 채널 대응이 확인되지 않았습니다.
  • 카메라·모터·부팅 동작과 물리적 EV·Q 형식·감마 특성은 이 검증의 범위 밖입니다.

재현 방법과 근거 파일

검증 환경은 Python 3.12.3과 Unicorn 2.1.4입니다. 원본 파일을 가진 사용자가 따로 준비한 decoded 파일을 지정합니다. 저장소 루트에서 실행하고 출력에는 새 경로를 씁니다. 아래 경로는 예시입니다.

python -B verify_tone_inputs.py /path/to/decoded.bin --output tone-inputs-new.json \
  --compare analysis/tone-inputs.json
python -B -O verify_tone_inputs.py /path/to/decoded.bin --output tone-inputs-opt-new.json \
  --compare analysis/tone-inputs.json
python -B -m unittest discover -s tests -p test_tone_inputs.py

줄 끝의 역슬래시는 줄을 잇는 표시입니다. 후보 파일을 별도 디렉터리에 둘 때만 --repository로 기존 검증기와 보조 소스가 있는 저장소를 지정합니다. 소스와 입력 검사는 최적화 실행에서도 유지됩니다. 비교에 실패하면 출력 파일을 만들지 않습니다.

공개 JSON을 만드는 방법과 해시

공개 JSON은 전체 관측이 맞는지 확인한 뒤 만듭니다. 8건의 모든 기록을 타입을 구분하는 JSON으로 직렬화해 기존 검증 결과의 해시와 먼저 대조합니다. 통과하면 반복 쓰기 기록 133,546건을 건수와 순서가 반영된 해시로 줄입니다. 문맥 생성자 쓰기 48건, recipe 생성자 쓰기, 입력 생산 코드의 저장 명령, 소비 코드의 조건부 쓰기는 그대로 둡니다.

재현 코드는 decoded 파일 경로를 명시적으로 받습니다. 파일 크기와 전체 SHA-256이 다르면 실행을 거부합니다. 기존 출력 파일이나 그 별칭은 덮어쓰지 않습니다. 원본 명령은 실행할 때마다 바이트를 대조하고 코드 구간의 해시도 검사합니다. 원본 실행 함수는 그대로이며 파일 경로와 소스 캡처만 공개 저장소 구조에 맞췄습니다.
