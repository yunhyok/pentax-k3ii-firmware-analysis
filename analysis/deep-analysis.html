시작하기 · 하드웨어와 RAW 현상의 첫 지도

하드웨어 식별 근거와 RAW 현상·톤 곡선 경로

복호화한 펌웨어를 놓고 먼저 두 가지를 물었습니다. 이 코드는 어떤 프로세서에서 돌아가는가, 그리고 RAW 사진을 현상할 때 밝기와 대비를 정하는 곡선은 어디서 만들어지는가. 이 문서는 두 질문에 답한 범위와 남은 빈칸을 정리합니다.

이 문서에서

  1. 배경: 무엇을 알아보려 했고 주소는 어떻게 읽는가
  2. CPU와 보조 MCU: 계열은 확인했고 부품 번호는 모릅니다
  3. RAW 현상 함수에서 컨트롤러 전달까지
  4. 톤 곡선 생성에서 B2Y 설정까지
  5. 실행으로 확인한 것: 곡선 출력 268,288개
  6. K-3 Mark III에서 한 분석을 K-3 II에도 할 수 있는가
  7. 한계와 남은 과제
  8. 재현 방법
  9. 근거 파일과 참고 자료

핵심 요약

  • 주 프로그램은 ARM 코드이고 시작 부분에 Cortex-A9를 가려내는 비교가 있습니다. 비교가 맞지 않을 때 가는 별도의 ARM 시작 코드와, 칩 버전을 읽어 진단 문구로 내보내는 코드도 찾았습니다. 칩(SoC)의 정확한 부품 번호는 알아내지 못했습니다.
  • 파일 끝의 보조 이미지는 Fujitsu F²MC-8L 계열과 호환되는 8비트 명령열입니다. 첫 명령 14개와 리셋·인터럽트 벡터가 제조사 매뉴얼의 명령표, 벡터 규칙과 맞습니다. 어떤 MCU이고 무슨 일을 맡는지는 모릅니다.
  • RAW 현상 함수를 진단 문구에서 찾아냈습니다. 호출 지점 네 곳과, 작업을 컨트롤러로 넘기는 코드까지 따라갔습니다.
  • 톤 곡선은 곡선 선택, 보간, 네 곡선 구성, 테이블 확장을 거쳐 만들어지고 B2Y라는 영상 처리 블록의 레지스터와 테이블 주소로 기록됩니다.
  • 보간·구성·확장 코드는 원본 기계어를 PC의 에뮬레이터에서 실행했습니다. 출력 268,288개가 따로 작성한 참조식과 모두 같았습니다. 입력은 직접 만든 합성 값이며 카메라에서 실행한 결과가 아닙니다.

확인 원본 코드 실행·바이트 대조

  • 톤 보간 262,144개, 테이블 확장 5,120개, 곡선 구성 1,024개 출력 일치
  • 톤 적용 함수의 합성 사례 2건, RAW 표본 변환 4건(출력 263개)
  • 보조 이미지 첫 명령 14개와 벡터, ARM 시작 코드의 명령 워드

정적 분석 코드를 읽어서 판단

  • RAW 현상 함수의 호출 지점과 컨트롤러 전달
  • 톤 준비·적용 함수의 호출 관계와 레지스터 이름
  • 기본 곡선을 만드는 두 생산자 함수
  • 보조 코드가 F²MC-8L 호환이라는 판단

모델 시험 조건으로 정한 것

  • 입력 곡선과 표본은 직접 만든 합성 값
  • B2Y 레지스터·테이블 주소 자리에 합성 RAM 배치
  • CPU는 Unicorn의 Cortex-A9 모델(명령 실행용 선택)

미확인 확인하지 않은 것

  • 실제 MIDR·칩 버전 값, SoC와 보조 MCU의 부품 번호
  • 보조 MCU의 역할과 보드 연결
  • 하드웨어 안에서 픽셀이 처리되는 순서와 수식
  • DMA·인터럽트·센서·실제 ISP 동작

배경: 무엇을 알아보려 했고 주소는 어떻게 읽는가

K-3 II는 리코가 2015년 4월에 발표한 DSLR입니다. 리코는 이 카메라의 영상 엔진을 PRIME III라고 소개합니다. PRIME III는 상품명이고 그 안에 든 칩의 부품 번호는 공개 자료에 없습니다. 펌웨어를 읽거나 에뮬레이터에서 실행하려면 적어도 CPU의 계열은 알아야 하므로, 펌웨어 안에서 근거를 찾았습니다.

두 번째 주제는 RAW 현상입니다. 카메라는 센서가 기록한 RAW 데이터를 JPEG로 만들 때 밝기와 대비를 톤 곡선으로 바꿉니다. 이 곡선을 만드는 코드와, 만든 곡선을 영상 처리 하드웨어에 넘기는 코드를 찾는 것이 목표였습니다. 출발점은 펌웨어 안의 진단 문자열입니다.

이 문서의 주소 표기

VA
주 이미지 코드의 분석용 주소입니다. 0x02000000 + 파일 오프셋으로 구합니다. 근거는 펌웨어 파일 구조 문서에 있습니다.
ROM
보조 이미지에만 쓰는 별도의 주소입니다. 파일 0x01000000이 ROM 0x1000에 대응합니다.
장치 주소
0x2002…, 0x20A…, 0xD000…처럼 코드가 하드웨어 레지스터나 테이블에 접근할 때 쓰는 값입니다. 코드에 적힌 값일 뿐이며 실제 물리 주소나 장치의 동작을 측정한 결과가 아닙니다.
함수 이름
진단 문자열에 나오지 않는 이름(“준비 함수”, “컨트롤러 래퍼” 등)은 설명을 위해 붙인 것입니다.
B2Y
펌웨어의 진단 문구 IO_B2Y.F_B2Y.TGCTL에 나오는 영상 처리 블록의 이름입니다. 이 문서는 코드가 이 이름으로 부르는 레지스터 묶음을 가리킬 때 씁니다.

CPU와 보조 MCU: 계열은 확인했고 부품 번호는 모릅니다

펌웨어에는 실행 코드의 근거가 세 갈래로 남아 있습니다. Cortex-A9를 가려내는 주 시작 경로, 값이 다를 때 가는 별도의 ARM 시작 코드, 그리고 F²MC-8L 호환 8비트 코드입니다.

주 CPU: Cortex-A9를 가려내는 비교

주 이미지의 시작 코드는 CPU 식별 레지스터 MIDR를 읽어 0xFFF0으로 마스킹한 값을 0xC090과 비교합니다. 부품 번호로는 0xC09이고 Arm의 문서에서 이 값은 Cortex-A9입니다. 따라서 펌웨어에 Cortex-A9를 구분하는 경로가 있다는 사실은 확인할 수 있습니다. 명령과 포인터의 세부 근거는 펌웨어 파일 구조 문서에 있습니다.

이 비교만으로는 실제로 실장된 SoC, 코어 수, 클럭을 정하지 못합니다. 리코의 제품 소개 페이지에는 PRIME III 칩 사진이 있지만 칩 위에는 PENTAX 로고만 보이고 읽을 수 있는 부품 번호는 없습니다.

값이 다를 때 가는 ARM 시작 경로

MIDR 비교가 맞지 않으면 코드는 한 주소를 반복해서 읽으며 기다립니다. 정해진 값이 읽히면 별도의 ARM 시작 코드로 분기합니다. 다른 쪽에서 값을 써 주기를 기다리는 모양이어서 공유 메모리로 보이지만 누가 쓰는지는 확인하지 않았습니다.

분기한 곳에는 CP15 제어 레지스터를 다루는 ARM 시작 코드가 있습니다. 바로 앞 파일 0x20000에는 별도의 모델·버전 헤더가 있습니다. 검증기는 이 헤더가 주 헤더와 같은 식별 문자열 HOKKTKIYHTNTMU로 시작하는지 확인합니다. 이 경로를 실행하는 코어의 종류와 역할은 알 수 없습니다.

참고

재포장과 업데이트 전송 문서가 다루는 통신 슬롯(0xC0001FD0 계열)도 같은 0xC000… 대역에 있습니다. 두 주소가 어떤 관계인지는 이 문서에서 확인하지 않았습니다.

칩 버전을 읽는 코드

VA 0x02753C6C의 함수는 장치 주소 0xD0001000을 읽어 상위 4비트만 남깁니다. VA 0x025C990C의 호출이 이 함수를 CHIP VER라는 출력 형식과 잇습니다. 칩을 식별할 때 실제로 읽어 볼 후보 주소는 얻은 셈입니다. 다만 카메라에서 읽은 값이 없고 이 값을 부품 번호로 바꾸는 표도 찾지 못했습니다.

보조 이미지: F²MC-8L 호환 코드라는 근거

F²MC-8L은 Fujitsu가 만든 8비트 마이크로컨트롤러 계열입니다. 대조에 쓴 매뉴얼에 따르면 이 계열의 CPU는 메모리의 맨 끝 0xFFFE~0xFFFF에 리셋 벡터를, 0xFFFD에 모드 데이터를 둡니다. 16비트 값은 높은 바이트를 먼저 적습니다.

보조 이미지를 ROM 0x1000~0xFFFF에 대응시키면 이 규칙과 맞아떨어집니다. 이미지의 마지막 4바이트 FF 00 10 80을 매뉴얼의 규칙대로 읽으면 다음과 같습니다.

  • 리셋 벡터 — 벡터가 가리키는 ROM 0x1080은 보조 헤더 바로 뒤, 곧 코드의 첫 바이트입니다.
  • 첫 명령: E4 02 4E는 MOVW A,#0x024E, 이어지는 E1은 MOVW SP,A로 읽힙니다. 스택을 잡고 PS(프로그램 상태)의 비트를 정리한 뒤 ROM 0x72C1을 호출하는 흐름입니다. 14개 명령이 모두 Fujitsu 명령표와 맞습니다.
  • 인터럽트 벡터: ROM 0xFFDC~0xFFFB의 2바이트 항목 16개 가운데 10개가 ROM 0x23B8을 가리킵니다. 이곳에는 레지스터를 저장하고 되돌린 뒤 RETI(인터럽트 복귀)로 끝나는 코드가 있습니다.

따라서 F²MC-8L 호환 명령어 계열이라는 판단은 근거가 탄탄합니다. 다만 호환되는 파생 제품 가운데 어느 것인지는 가려내지 못합니다. 대조에 쓴 매뉴얼은 MB89580B/BW용입니다. 이 부품이 카메라에 들어 있다고 지목하지는 않습니다.

Fujitsu Milbeaut 계열 칩으로 확정하지 않은 이유

펌웨어에는 Fujitsu의 M7용 영상 안정화 라이브러리의 이름(M7 for Fujitsu)이 남아 있습니다. 이 문자열은 관련 소프트웨어를 알려 주는 단서이지, 칩이 무엇인지 알려 주는 근거는 아닙니다.

Fujitsu(현 Socionext)의 영상 처리 칩 MB86S22는 공개 사양에 Cortex-A5를 명시합니다(Socionext MB86S22 사양). M7이라는 문자열만 보고 K-3 II의 칩을 MB86S22로 정하면, 펌웨어에 있는 Cortex-A9 비교 경로를 설명할 수 없습니다. 두 프로세서가 함께 들어 있다는 근거도 없습니다. K-3 Mark III의 SC2000A 역시 이 기종의 부품 근거로 쓰지 않았습니다.

정확한 부품 번호를 정하려면 K-3 II 기판에서 읽을 수 있는 패키지 표기, 제조사의 부품 자료, 또는 카메라에서 읽은 식별값과 공식 대응표가 필요합니다. 공개 자료에서는 이를 구하지 못했습니다.

RAW 현상 함수에서 컨트롤러 전달까지

진단 문구 DevelopmentRawImage()를 참조하는 함수가 RAW 현상의 진입점입니다. 이 함수를 부르는 곳 네 군데와, 작업을 컨트롤러로 넘기는 코드를 확인했습니다.

이 함수는 문자열을 가리키는 포인터를 검색해서는 찾을 수 없었습니다. 실제 코드는 현재 실행 위치를 기준으로 문자열 주소를 계산하는 명령(PC 상대 ADD)을 쓰기 때문입니다. VA 0x0252ADF4의 명령이 진단 문구를 참조합니다. 이 명령을 포함하는 함수의 진입점은 VA 0x02529664입니다.

  • 호출 지점 — 네 곳을 하나씩 확인했습니다(주소는 아래 세부 근거의 표). 호출 지점을 빠짐없이 찾은 목록은 아닙니다.
  • 버퍼 할당 — 할당 함수로 보이는 VA 0x0270C56C가 0을 돌려주면 오류 진단을 출력하는 쪽으로 분기합니다.
  • 작업 링크: 성공한 경로에서는 작업 객체의 +0x20C8, +0x20D0, +0x20C4에 링크를 써 넣는 작은 함수들이 호출됩니다.
  • 컨트롤러 전달: 컨트롤러 래퍼(VA 0x026DB894)는 VA 0x025A11F8을 거쳐 상태를 설정합니다. 그다음 컨트롤러 +0x340의 신호 객체에 값 1을 전달합니다.

여기까지는 CPU가 실행하는 제어 흐름입니다. 센서 픽셀이 처리되는 순서와는 구별해야 합니다.

원본 명령으로 확인한 표본 변환

VA 0x0252AE94~0x0252AEC0의 루프는 16비트 표본을 하나씩 읽어 왼쪽으로 2비트 밀고 하위 16비트를 저장합니다. 앞의 조건이 맞을 때만 이 루프를 쓰고 다른 경로는 건너뜁니다.

dst[i] = (src_u16[i] << 2) & 0xFFFF

예: 0x0001 → 0x0004
    0x3FFF → 0xFFFC
    0x4000 → 0x0000

이 루프를 에뮬레이터에서 실행해 참조식과 비교했습니다. 빈 입력, 표본 1개, 경계값 5개, 고정 시드 난수 257개의 네 사례에서 출력 263개가 모두 일치했습니다. 출력 버퍼의 경계를 넘겨 쓰지 않는지, 원본 버퍼가 그대로인지도 확인했습니다. 이 루프만 보고 입력 RAW가 항상 14비트라고 단정할 수는 없습니다.

이어지는 연결

컨트롤러에 넘긴 작업이 어떻게 처리되어 톤 준비·적용 함수까지 가는지는 이 문서에서 연결하지 못했습니다. 그림에서 이 구간을 실선 화살표로 그리지 않은 이유입니다. 작업 목록과 톤 적용까지의 연결은 RAW 이후의 톤·WB·색 행렬에서 다룹니다.

톤 곡선 생성에서 B2Y 설정까지

톤 곡선은 준비 단계에서 만들어 객체 안의 버퍼에 두고 적용 단계에서 B2Y의 제어 레지스터와 곡선 테이블 주소로 기록합니다.

레지스터 이름을 정한 근거

추적은 진단 함수가 읽는 주소와 설정 함수가 쓰는 주소를 맞춰 보는 데서 시작했습니다. 진단 함수 DumpToneGamma는 IO_B2Y.F_B2Y.TGCTL, IO_B2Y.F_B2Y.TCTBLCTL이라는 이름을 붙여 값을 출력합니다. 이때 읽는 주소와 설정 함수가 쓰는 주소가 모두 TGCTL = 0x20020800, TCTBLCTL = 0x20020804입니다. 그래서 이 이름은 근처의 문자열을 임의로 붙인 것이 아니라, 진단 출력과 접근 주소를 대조해 얻은 것입니다.

준비와 적용이 같은 객체의 함수라는 근거

객체를 만드는 생성자가 가상 함수표를 설치하고 이 표의 이웃한 두 슬롯이 준비 함수와 적용 함수를 가리킵니다. 공통 래퍼는 두 번의 호출에 같은 하위 객체를 넘기고 준비가 끝나면 플래그를 세웁니다. 서로 다른 객체의 함수를 우연히 이어 붙인 관계가 아닙니다.

곡선 선택. 선택 함수는 일반 생산자와 selector 6 생산자를 구분합니다. 두 생산자 모두 16비트 값 256개를 만들고 상한 0x4000을 씁니다. 이 문서의 근거만으로는 selector 6이 어떤 메뉴 항목인지 정할 수 없었습니다. 이후 RAW 이후의 톤·WB·색 행렬과 JPEG 출력 버퍼와 Reversal Film 메뉴에서 Reversal Film에 대응한다는 근거를 따로 확인했습니다. 준비 함수는 선택 함수와 구성 함수 사이에 세 곡선을 조정하는 함수도 부르는데 그 계산은 이 문서에서 다루지 않습니다.

보간. 입력을 x, 256개 항목의 곡선을 C라고 하면 다음과 같습니다. 차이가 음수일 때의 나눗셈은 0 쪽으로 버립니다. Python의 정수 나눗셈(//)은 음수를 아래쪽으로 내리므로 결과가 다를 수 있습니다.

q = x >> 6;  f = x & 63
q >= 255 : C[255]
그 외     : C[q] + trunc0((C[q+1] - C[q]) * f / 64)

네 곡선 구성. 세 곡선을 각각 보간한 뒤 (77·A + 150·B + 29·C) >> 8로 네 번째 곡선을 만듭니다. 계수는 밝기(휘도)를 구할 때 쓰는 가중치의 모양입니다. ITU-R BT.601의 휘도 계수 0.299, 0.587, 0.114에 256을 곱하면 76.5, 150.3, 29.2로 이 값에 가깝습니다. 그렇다고 이 사실만으로 실제 색 공간이나 채널 배치, ISP의 픽셀 계산식을 확정하지는 않습니다.

테이블 확장. 구간마다 값을 4개로 늘리고 끝값 256개를 덧붙여 16비트 값 1,280개, 곧 0xA00바이트를 만듭니다. 이 함수는 여러 값을 한꺼번에 처리하는 NEON 명령을 씁니다. 검증에 쓴 참조식은 NEON 연산의 16비트 순환, 산술 시프트, 0~0x4000 범위 제한을 그대로 따릅니다. 끝에 덧붙이는 값은 범위 제한 없이 원래의 마지막 값을 씁니다.

실행으로 확인한 것: 곡선 출력 268,288개

보간·구성·확장과 적용 함수, RAW 표본 변환은 원본 기계어를 에뮬레이터에서 실행해 참조식과 비교했습니다. 기본 곡선을 만드는 두 생산자 함수는 실행하지 않고 읽기만 했습니다.

시험 조건

코드는 Capstone 5.0.7로 읽고 수치 연산은 Unicorn 2.1.4에서 따로 떼어 실행했습니다. 에뮬레이터의 CPU를 Cortex-A9로 정한 것은 해당 명령을 실행하기 위한 선택이며 카메라에 든 칩을 확인한 증거가 아닙니다. 하드웨어 장치 대신 합성 RAM을 놓았으므로 DMA, 인터럽트, 센서, 실제 ISP의 동작은 검증하지 않았습니다.

K-3 Mark III에서 한 분석을 K-3 II에도 할 수 있는가

절차는 그대로 쓸 수 있습니다. K-3 Mark III의 명령 번호, 주소, 데이터 구조를 옮겨 오는 방식은 쓸 수 없습니다.

K-3 II의 펌웨어에도 ARM 코드(A32), 가상 함수표, 진단 문자열, 레지스터 접근 함수가 남아 있어서 같은 방법으로 추적할 수 있습니다. 아래 표는 K-3 Mark III의 공개 분석 항목을 기준으로, 이 문서를 쓴 시점에 K-3 II에서 확인한 범위를 정리한 것입니다. 그 뒤에 조사가 이어진 항목은 마지막 칸에 문서를 적었습니다.

한계와 남은 과제

  • 부품 번호를 모릅니다. 카메라에서 읽은 MIDR 값, 칩 버전 레지스터 값, 기판 표기가 없습니다. 주 이미지의 추가 ARM 시작 경로, F²MC-8L 호환 보조 코드, 패키지 부품 번호를 각각 따로 다루어 추정이 사실처럼 굳지 않게 합니다.
  • F²MC-8L 호환은 명령어 수준의 판단입니다. 호환 파생 제품이나 MCU 부품 번호를 가려내지 못합니다. MB86S22A도, MB89 계열의 어느 부품도 이 카메라의 부품으로 지목하지 않습니다.
  • 호출 지점 목록은 완전하지 않습니다. RAW 현상 함수의 직접 호출 네 곳을 확인했을 뿐입니다.
  • 픽셀 처리 순서를 그리지 못합니다. 확인한 것은 설정 코드와 테이블 전달 관계입니다. “RAW → WB → 행렬 → 감마 → 톤 → JPEG”를 확정된 순서로 볼 근거가 없습니다. 하드웨어 안의 픽셀 순서, 디모자이킹 수식, 특정 커스텀 이미지의 실제 색 재현에는 근거가 더 필요합니다.
  • 장치의 동작은 측정하지 않았습니다. 장치 메모리의 동작, 물리 주소, 픽셀 단계의 타이밍은 알 수 없습니다. 0x20A00000 테이블의 내용과 하드웨어가 픽셀마다 적용하는 변환 함수도 열려 있습니다.
  • 이름은 설명용입니다. selector와 설명자 필드의 이름은 분석하면서 붙였습니다.

이 문서를 쓸 때 다음 과제로 꼽은 것은 세 가지였습니다. 지금은 각각 다른 문서에서 다룹니다.

  • RAW 컨트롤러에 넘긴 작업이 톤 준비·적용 호출까지 이어지는 경로 → RAW 이후의 톤·WB·색 행렬

재현 방법

먼저 펌웨어 파일 구조 문서의 절차로 공식 펌웨어 1.12 파일을 복호화합니다. 원본 펌웨어는 저장소에 없습니다. 정적 검증 세 개는 Python 표준 라이브러리만 씁니다.

python verify_hardware.py .private/decoded/decoded.bin --compare analysis/hardware.json
python verify_raw_path.py .private/decoded/decoded.bin --compare analysis/raw-path.json
python verify_tone_path.py .private/decoded/decoded.bin --compare analysis/tone-path.json
python -m unittest discover -s tests -v
python verify_publication.py

원본 명령을 실행하는 수치 검증에는 Unicorn이 필요합니다. 별도의 Python 환경에 설치하기를 권합니다.

python -m pip install unicorn==2.1.4
python verify_raw_numeric.py .private/decoded/decoded.bin --compare analysis/raw-numeric.json
python verify_tone_numeric.py .private/decoded/decoded.bin --compare analysis/tone-numeric.json

각 검증기는 복호화한 이미지의 SHA-256이 맞는지 확인한 뒤, 결과를 공개된 JSON과 비교합니다.

자동 분석 도구의 결과를 어떻게 다뤘는가

공식 ZIP을 식별한 기록은 REA라는 분석 도구가 남긴 것을 그대로 썼습니다. 조사에 쓴 Windows 환경에는 REA의 펌웨어 스캐너(Binwalk)와 원시 ARM 이미지용 네이티브 분석 공급자가 준비되어 있지 않았습니다. 그래서 코드 분석은 Python, Capstone, Unicorn으로 했고 이 결과를 REA가 만든 코드 증거로 표시하지 않았습니다. 제약은 rea-summary.json에 있습니다.

자동 분석 도구 angr 10.0.5는 RAW 현상 함수의 범위에서 블록 710개를 찾았습니다. 그러나 자동으로 만든 C 유사 코드에는 함수의 앞부분만 담겼습니다. 조건부 호출과 점프 테이블을 포함한 함수 전체의 설명으로는 채택하지 않았습니다. 공개한 결론은 직접 확인한 명령열, 직접 분기, 바이트 해시, 격리 실행 결과에 한정했습니다.
