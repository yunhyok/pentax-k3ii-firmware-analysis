2. CPU 계열과 정확한 부품 번호를 구분한다

리코가 공개한 엔진명은 PRIME III다. 이는 SoC 부품 번호가 아니다. 주 시작 코드는 MIDR에서 부품 번호 0xC09를 비교하므로 Cortex-A9를 구분하는 경로가 있다는 사실은 확인할 수 있다. 하지만 이 정적 비교만으로 실장 SoC, 코어 수와 클럭을 결정할 수는 없다. 리코 제품 설명 · Arm Cortex-A9 TRM §4.3.1 · 시작 코드 검사

추가 ARM 시작 경로와 칩 버전 읽기

MIDR 비교가 맞지 않으면 공유 메모리로 보이는 주소를 대기한 뒤 0x02020100으로 이동한다. 이 위치에는 CP15 제어 레지스터를 다루는 ARM 시작 코드가 있으며, 앞쪽 파일 0x20000에는 별도의 모델·버전 헤더가 있다. 이 경로의 코어 종류와 역할은 미확정이다.

또한 VA 0x02753C6C는 0xD0001000을 읽어 상위 4비트만 남긴다. VA 0x025C990C의 호출과 CHIP VER 출력 형식이 연결된다. 칩 식별을 위한 실측 후보는 확보했지만 실제 읽기 값은 없다. 이 값을 부품 번호로 변환하는 표도 아직 찾지 못했다. 정적 검사 결과

F²MC-8L 호환 코드라는 판단 근거

보조 영역을 ROM 0x1000–0xFFFF에 대응시키면 리셋 벡터가 페이로드 첫 명령을 가리킨다. E4 02 4E는 MOVW A,#0x024E, 다음 E1은 MOVW SP,A로 해석된다. 이어지는 PS 마스크 설정과 절대 호출도 Fujitsu 명령표에 맞는다. 인터럽트 벡터 여러 개가 가리키는 ROM 0x23B8에는 레지스터 저장·복구와 RETI가 있다. Fujitsu CM25-10142-3E, CPU 벡터 표·부록 B

따라서 F²MC-8L 호환 명령어 계열이라는 판단은 강하게 뒷받침된다. 다만 호환 파생 제품까지 구분하지는 못한다. 이 설명에 사용한 매뉴얼의 MB89580B/BW를 실제 카메라 부품으로 지목하는 것은 아니다. 초기 14개 명령·벡터 검증기

Fujitsu/Milbeaut 후보를 확정하지 않은 이유

펌웨어에 Fujitsu의 M7 영상 안정화 라이브러리 명칭이 남아 있다. 이는 관련 소프트웨어의 단서다. 반면 공개 MB86S22 사양은 Cortex-A5를 명시한다. M7이라는 문자열만으로 K-3 II를 MB86S22로 확정하면 Cortex-A9 비교 경로와의 관계를 설명하지 못한다. 두 프로세서가 함께 있다는 근거도 아직 없다. K-3 III의 SC2000A 역시 이 모델의 부품 증거로 쓰지 않았다. Socionext MB86S22 사양

정확한 부품 번호를 결정하려면 K-3 II PCB의 판독 가능한 패키지 표기, 제조사 부품 자료 또는 실측 ID와 공식 대응표가 필요하다. 이번에 확인한 공개 자료에서는 이를 확보하지 못했다.

3. RAW 현상 함수에서 컨트롤러 전달까지

DevelopmentRawImage() 문자열 포인터는 단순 검색으로 참조를 찾지 못했다. 실제 코드는 PC 상대 ADD 명령으로 문자열 주소를 만든다. VA 0x0252ADF4에서 진단 문자열을 참조하는 것을 확인했고, 이를 포함하는 함수의 진입점은 0x02529664다. 네 호출 지점 0x0268F928, 0x02690554, 0x02691040, 0x02692098을 따로 검증했다. 명령어·호출 대상·구간 해시

할당 함수 후보 0x0270C56C의 반환값이 0이면 오류 진단으로 분기한다. 성공 경로에서는 작업 객체의 +0x20C8, +0x20D0, +0x20C4에 링크를 설정하는 작은 함수들이 호출된다. 컨트롤러 래퍼는 0x025A11F8을 거친 뒤 컨트롤러 +0x340의 신호 객체에 값 1을 전달한다. 이는 CPU 제어 흐름이며 센서 픽셀의 처리 순서와는 구별해야 한다. 경로 검증 코드

원본 명령으로 확인한 표본 변환

VA 0x0252AE94–0x0252AEC0의 루프는 16비트 표본을 읽고 2비트 왼쪽으로 이동시킨 뒤 하위 16비트를 저장한다. 앞선 조건이 맞을 때만 이 루프를 사용하며 다른 경로는 건너뛴다.

dst[i] = (src_u16[i] << 2) & 0xFFFF

예: 0x0001 → 0x0004
    0x3FFF → 0xFFFC
    0x4000 → 0x0000

빈 입력, 단일 표본, 경계값, 고정 시드 난수의 4개 합성 사례에서 원본 A32 명령과 참조식이 일치했다. 출력 263개와 함께 버퍼 경계, 원본 보존도 확인했다. 이 루프만으로 입력 RAW가 항상 14비트라고 단정할 수는 없다. 실행 결과 · 재현 코드

4. 곡선 생성에서 B2Y 설정까지

이번 추적은 진단 함수의 레지스터 읽기와 실제 쓰기 함수를 같은 주소로 맞추는 데서 시작했다. DumpToneGamma의 읽기와 설정 함수가 모두 TGCTL = 0x20020800, TCTBLCTL = 0x20020804를 사용한다. 따라서 해당 이름은 근처 문자열을 임의로 붙인 것이 아니라 진단 출력과 접근 주소를 대조한 결과다. ADR·레지스터·호출 근거

곡선 선택·보간·확장

선택 함수 0x024DDAB8는 일반 생산자 0x024DC980와 selector=6 생산자 0x024DD924를 구분한다. 두 생산자는 256개 halfword와 상한 0x4000을 다룬다. selector=6을 K-3 III의 리버설 모드와 곧바로 같은 이름으로 부르지는 않았다. 메뉴·리소스 연결이 더 필요하다.

보간 함수 0x024DD3EC의 입력을 x, 256개 항목의 곡선을 C라 하면 다음과 같다. 음수 차분의 나눗셈은 0 방향 절삭이며, 단순한 Python 음수 정수 나눗셈과 다를 수 있다.

q = x >> 6;  f = x & 63
q >= 255 : C[255]
그 외     : C[q] + trunc0((C[q+1] - C[q]) * f / 64)

구성 함수는 세 곡선을 각각 보간한 뒤 (77·A + 150·B + 29·C) >> 8로 네 번째 곡선을 만든다. 계수는 휘도 가중치 형태지만 이 사실만으로 실제 색 공간·채널 배치나 ISP의 픽셀 계산식을 확정하지 않는다.

확장 함수는 각 구간을 4개 값으로 늘리고 끝값 256개를 덧붙여 총 1,280개 halfword, 즉 0xA00바이트를 만든다. NEON 연산의 16비트 순환, 산술 시프트와 0–0x4000 제한을 그대로 반영해 검증했다. 끝에 덧붙이는 값은 별도 제한 없이 원래 마지막 halfword를 사용한다. 독립 참조식과 원본 명령 실행

곡선별 복사 길이는 조건에 따라 0xA00 또는 0x1000이다. 두 길이의 분기를 합성 메모리에서 모두 실행해 소스·목적지 바이트와 복사 뒤 남는 영역을 대조했다. 0x1000 분기가 언제 실제 촬영에 선택되는지는 별도 문제다.

TGCTL의 비트 0·1·16·17·24·25와 TCTBLCTL의 여러 필드를 설명자에서 읽어 수정하는 함수도 연결했다. 읽기-수정-쓰기 방식이라 관련 없는 비트는 보존한다. 다만 각 비트를 “감마 켜기”, “특정 색 공간 선택”처럼 이름 붙일 공식 레지스터 정의는 아직 없다. 필드 위치 목록 · 적용 함수 실행 대조

5. 무엇을 실행해 검증했는가

코드 판독에는 Capstone 5.0.7을 사용했고 수치 연산은 Unicorn 2.1.4로 격리 실행했다. Cortex-A9 에뮬레이터 설정은 해당 명령을 실행하기 위한 선택이며 카메라의 실장 칩을 확인한 증거는 아니다. 외부 장치 대신 합성 RAM을 배치했으므로 DMA·IRQ·센서·물리 ISP 동작은 검증하지 않았다.

기본 곡선 생산자 두 함수는 정적으로 추적했다. 아래 실행 대조는 그 뒤의 보간·구성·확장과 적용 함수에 한정하며 생산자 자체의 계산을 모두 실행한 결과는 아니다.

REA가 남긴 기존 ZIP 식별 증거를 재사용했다. 이 Windows 환경의 펌웨어 Binwalk 경로와 원시 ARM 네이티브 분석 공급자는 준비되지 않아 이번 코드 분석은 Python·Capstone·Unicorn으로 진행했다. 이를 REA 자체가 만든 코드 증거로 표시하지 않았다. REA 증거·제약

angr 10.0.5는 RAW 현상 범위에서 블록 710개를 찾았지만, 자동 생성된 C 유사 코드는 함수 앞부분만 담았다. 조건부 호출과 점프 테이블을 포함한 전체 함수 설명으로는 채택하지 않았다. 공개 결론은 확인한 명령열·직접 분기·바이트 해시와 격리 실행 결과에 한정했다.

6. 다음 분석에서 연결해야 할 지점

RAW 컨트롤러 래퍼의 후속 처리에서 톤 래퍼의 준비·적용 호출까지 연결하는 것이 다음 우선 과제다. 이 구간이 확인돼야 곡선이 어떤 현상 조건에서 적용되는지 더 정확히 설명할 수 있다. 그다음 selector와 UI 리소스를 연결하고, WB·색 행렬·클리핑과 JPEG 인코더의 설정 생산자를 같은 방식으로 추적한다.

현재 자료로는 “RAW → WB → 행렬 → 감마 → 톤 → JPEG”를 확정 순서로 그릴 수 없다. 확인한 것은 설정 코드와 테이블 전달 관계다. 하드웨어 내부의 픽셀 순서, 디모자이킹 수식, 특정 커스텀 이미지의 실제 색 재현은 추가 근거가 필요하다.

정확한 SoC·보조 MCU 부품 번호도 미확정으로 남겼다. 주 이미지의 추가 ARM 경로, F²MC-8L 호환 보조 코드와 패키지 부품 번호를 각각 관리해 추정이 사실로 굳어지지 않도록 한다.
