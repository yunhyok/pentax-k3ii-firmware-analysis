촬영 준비와 보존 레코드 · 촬영 준비 함수

촬영 준비 함수가 픽셀 보정 정책의 입력을 만드는 순서

펌웨어에는 촬영 작업 하나를 시작하기 전에 상태를 채워 넣는 준비 함수가 있습니다. 이 함수가 내부에서 부르는 함수들을 건너뛰지 않고 원본 코드로 이어 실행해, 픽셀 보정을 켤지 정하는 값이 어디서 만들어지는지 확인했습니다.

이 문서에서

  1. 배경: 준비 함수와 세 가지 실험
  2. 준비 함수는 가상 호출 25개를 순서대로 부릅니다
  3. 정책 입력은 조회 키와 고정 RAM 값에서 만들어집니다
  4. 설정 0x95가 강제 플래그 CAP+0x3C를 정하는 방식
  5. 함수가 끝날 때까지 이미지 포인터는 그대로이고 레코드 필드 두 개만 0이 됩니다
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 준비 함수는 가상 호출 25개를 정해진 순서로 실행합니다. 앞의 여덟 개가 값을 만들고 아홉 번째가 픽셀 보정 정책 함수입니다. 이 아홉 개를 원본 코드로 연속 실행한 21개 사례에서, 앞 호출이 만든 값을 정책 함수가 그대로 읽었습니다.
  • 내부 작업 종류가 5·7·8·11이면 첫 세 호출 뒤에 정책 함수가 들어 있는 구간을 건너뜁니다. 다른 21개 사례로 이 분기를 확인했습니다.
  • 별도의 세 사례는 준비 함수가 호출자에게 돌아올 때까지 실행했습니다. 이미지 포인터와 512바이트 이미지는 그대로였고 촬영 객체에 내장된 레코드 여섯 개는 16비트 필드 두 개만 0으로 바뀌었습니다.
  • 입력값은 모두 시험용으로 넣은 값입니다. 실제 촬영에서 이 값들이 어떻게 정해지는지, 값의 물리 단위나 메뉴 이름이 무엇인지는 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 아홉 호출의 순서와 대상 함수, 정책 반환까지 21개 사례
  • 작업 종류 분기 21개 사례(종류 0~11 포함)
  • 함수의 실제 반환까지 3개 사례: 호출 25개 또는 16개
  • 실행을 다른 코드로 바꾼 곳 없음

정적 분석 코드를 읽어 판단

  • 고정 RAM 주소를 돌려주는 조회 함수의 위치
  • 다섯 번째·일곱 번째 호출이 갱신하는 필드

모델 시험 조건으로 정한 것

  • 촬영 객체, 설정값, 조회 키, 디버그 바이트
  • 고정 RAM의 마커와 값, 초기화 가드
  • 512바이트 합성 이미지와 레코드 대조값

미확인 확인하지 않은 것

  • 촬영 객체 전체 생성자와 메모리 할당
  • 입력 A·B·C의 물리 단위와 메뉴 대응
  • 센서 입력, 이미지 처리, JPEG, 실물 촬영

배경: 준비 함수와 세 가지 실험

이 펌웨어는 촬영 작업 하나의 상태를 큰 구조체 하나에 모아 둡니다. 이 문서에서는 이것을 촬영 객체라고 부르고 그 안의 위치를 CAP+0x49처럼 적습니다. 준비 함수는 촬영 객체와 내부 작업 종류 번호를 받아, 객체 안의 플래그와 입력값을 채웁니다.

채우는 일은 준비 함수가 직접 하지 않고 가상 호출로 나눠 맡깁니다. 그중 하나가 픽셀 보정 정책 함수입니다. 정책 함수는 세 입력 A·B·C와 몇 개의 플래그를 보고 보정 플래그 네 개(CAP+0x47~+0x4A)를 정합니다.

정책 함수 문서의 준비 분기 실험은 중간 호출 여덟 개를 실행하지 않고 구간을 나눠 확인했습니다. 여기서는 그 중간 호출을 모두 원본 코드로 실행했습니다. 실험은 세 묶음입니다.

코드 주소는 복호화한 펌웨어 파일 안의 위치(파일 오프셋)입니다. 실행 주소는 여기에 0x02000000을 더한 값입니다. RAM 주소는 실행 주소로 적습니다. A·B·C는 정책 함수 문서에서 붙인 입력 이름이며 물리 단위는 정해지지 않았습니다.

시험 조건

모든 실행은 PC의 Unicorn 에뮬레이터(Cortex-A9 모델)에서 했습니다. 촬영 객체는 0으로 채운 메모리에 원본 가상 함수 표 주소와 시험값을 넣어 만들었습니다. 훅은 진입 주소·인수·메모리 쓰기를 기록하기만 했고 실행을 바꾸지 않았습니다.

준비 함수는 가상 호출 25개를 순서대로 부릅니다

첫 세 호출 뒤에 작업 종류 분기가 있고 통과하면 여섯 호출이 이어져 아홉 번째에서 정책 함수가 실행됩니다.

준비 함수는 촬영 객체의 가상 함수 표(파일 0xA684E0)에서 칸 번호로 함수를 고릅니다. 아래 아홉 호출은 호출 명령과 표의 내용을 파일에서 직접 확인했고 실행 중에도 같은 순서로 진입했습니다.

작업 종류에 따른 분기

준비 함수는 입구에서 작업 종류를 CAP+0x2084에 적고 종류가 5·7·8·11이면 CAP+0x2080을 1로 만듭니다. 첫 세 호출이 끝난 뒤 0x65537C의 분기가 이 바이트를 봅니다. 1이면 0x655400으로 건너뛰고 0이면 0x655380으로 이어집니다.

  • 앞부분 21건: 종류 0~11을 기본 입력으로 한 12건과 입력을 바꾼 9건입니다. 종류 5·7·8·11은 세 호출을 거친 뒤에도 0x655400에 도달했고 나머지는 0x655380에 도달했습니다.
  • 정책까지 21건: 종류 0과 6으로, 같은 촬영 객체에서 아홉 호출에 모두 진입하고 정책 함수가 반환했습니다. 정지점 0x6553E0은 실험의 경계이며 준비 함수의 반환점이 아닙니다.
주의

작업 종류는 시험 입력으로 넣었습니다. 메뉴 조작에서 준비 함수까지를 한 번에 실행한 것이 아닙니다. 종류 11을 Pixel Shift Resolution과 연결하는 근거는 Pixel Shift 메뉴와 버퍼 수명 문서에 따로 있습니다.

앞부분 21건의 입력과 출력

1~12번은 루트 키 0, 루트 키 0x2F, 자식 키 0x22, 디버그 0x66을 모두 0으로 두고 작업 종류만 0부터 11까지 바꿨습니다. 출력 네 필드는 모두 0이었고 종류 5·7·8·11만 0x655400에서, 나머지는 0x655380에서 멈췄습니다. 아래는 입력을 바꾼 13~21번입니다.

정책 입력은 조회 키와 고정 RAM 값에서 만들어집니다

정책 함수가 읽는 플래그와 입력 A는 앞쪽 호출이 조회 키의 비트, 설정값, 고정 RAM의 값을 읽어 만든 것입니다.

촬영 객체 안에는 키 리더가 두 개 있습니다. 루트 리더는 원본 생성자 0x6EBF5C로, 자식 리더는 0x6EAD78로 만들었습니다. 준비 함수의 앞쪽 호출은 이 리더와 설정 바이트에서 값을 읽어 아래 필드를 채웁니다.

A 생산 함수는 배율 0x2000으로 시작합니다. 고정 RAM의 마커가 무효이면 이 배율을 유지했고 유효 마커(0xA55A5AA5)와 값 0x4000을 넣으면 같은 인덱스의 A가 두 배가 됐습니다. 인덱스 보정은 하위 8비트에서 이루어집니다. 이 표는 감도나 노출 시간 같은 단위를 붙인 것이 아닙니다.

강제 조건에 쓰이는 두 16비트 필드는 서로 다릅니다

CAP+0x20B8은 두 번째 호출이 만들지만 정책 함수의 강제 조건이 보는 값은 그 옆의 CAP+0x20B6입니다. 루트 키 0x2F와 설정 0xF5를 1로 두었고 +0x20B8은 0x1234로 유지됐습니다. 이 상태에서 시험값으로 넣은 +0x20B6만 1에서 2로 바꾸자 정책이 표 조회 대신 강제 결과 4를 썼습니다. +0x20B6을 만드는 상위 코드는 실행하지 않았습니다.

설정 0x95가 강제 플래그 CAP+0x3C를 정하는 방식

여섯 번째 호출은 설정 0x95의 값에 따라 세 가지 경로 중 하나로 CAP+0x3C를 정합니다. 이 플래그가 1이면 정책 함수는 표를 보지 않고 결과 4를 씁니다.

설정 0x95는 이 객체 배치에서 CAP+0x15ED에 있습니다.

임계표는 파일 0x9E6202의 64바이트이며 정책 함수가 쓰는 표 일곱 개와는 다른 표입니다. 인수는 A, B, 그리고 16비트 부호 있는 C를 10으로 나눈 값입니다.

  • 경계: A = 0x2000, B = 0x24에서 C 원값 599와 600은 59와 60이 되고 CAP+0x3C는 0과 1로 갈렸습니다.
  • 값이 0인 칸 — B = 0x44의 임계값은 0이어서 C 원값이 32,767이어도 꺼진 채였습니다.
  • 우회: 루트 키 0 = 9로 CAP+0x5F가 켜지면 이 플래그가 네 번째 인수로 전달되고 C 원값이 −32,768이어도 표 검사를 거치지 않고 켜졌습니다.

같은 실행에서 A = 0x8000, B = 0, C = 0, 설정 0x95 = 1이면 정책의 표 조회 결과는 4였습니다. 작업 종류 0은 최종 플래그 [1, 1, 1, 1]을, 종류 6은 [0, 0, 0, 1]을 만들었습니다. 플래그 순서는 CAP+0x47, +0x48, +0x49, +0x4A입니다. 이 문서의 실행은 정책 함수가 반환한 곳에서 멈추며 픽셀 보정이나 JPEG 출력까지 이어 가지 않았습니다. 정책 결과가 패킷과 이미지 버퍼로 이어지는 부분은 정책 → 패킷 → 보정 연결 실험에서 따로 확인했습니다.

정책까지 실행한 21건의 전체 결과

기본값은 B = 0x7C, 키 6 = 0x20, C = 0, 나머지 0입니다. “임계 함수”는 0x739A38에 진입한 횟수입니다.

종류 11이 건너뛰는 호출

종류 0과 6은 가상 호출 25개를 모두 거쳤습니다. 종류 11은 16개만 거쳤습니다. 빠진 것은 호출 4~11 여덟 개(정책 함수 포함)와 마지막 호출 25(표의 칸 0x78)입니다.

종류 11 사례에서는 보정 플래그 네 바이트에 0xA1·0xB2·0xC3·0xD4를 미리 넣었고 반환할 때까지 그대로 남았습니다. 이 경로에서 준비 함수는 네 플래그를 0으로 초기화하지 않습니다.

내장 레코드 여섯 개와 이미지

준비 함수의 마지막 반복문(0x6554F4~0x655550)은 포인터 여섯 개가 가리키는 객체의 +0x3F0과 +0x3F2에만 0을 썼습니다. 각 레코드의 0x3FC바이트 전체와 미리 넣어 둔 인접 대조값을 비교해, 바뀐 범위가 이 4바이트뿐임을 확인했습니다. 이 포인터들은 컨테이너 CAP+0xA850 안을 가리키는 내부 주소입니다. 레코드를 여섯 번 따로 할당해 만든 것이 아닙니다.

이미지 쪽은 원본 슬롯 설정 함수 0x654218을 슬롯 1, 직접 별칭 인수 1로 불러 CAP+0x98과 CAP+0x13C에 같은 주소를 넣었습니다. 준비 함수 실행 중 CAP+0x13C와 이미지 영역에 쓴 횟수는 0회였고 512바이트 전체가 같았습니다. 시험값으로 넣은 CAP+0x160·+0x204도 유지됐지만 이 두 값을 만드는 코드는 실행하지 않았습니다.

주의

이 결과는 준비 함수 한 번의 실행 안에서 포인터와 이미지가 보존된다는 것까지입니다. 연속 촬영 중의 버퍼 할당·재사용, 이미지 처리, 스케일러·CPP 제출은 다루지 않습니다. 슬롯·메뉴·작업 수명은 Pixel Shift 메뉴와 버퍼 수명 문서를 보십시오. 같은 내장 레코드가 저장 단계에서 다시 쓰이는 과정은 JPEG 완료값과 저장 레코드에서 이어집니다.

한계와 남은 과제

고정 RAM을 읽은 것과 공급자가 등록된 것은 다릅니다

준비 함수는 ID 8·9·0x62로 등록 객체를 조회합니다. 이 실험에서는 등록표가 비어 있는 상태로 조회가 실행됐습니다. 조회 뒤에 불리는 함수는 조회 결과와 관계없이 정해진 RAM 주소를 돌려주므로, 이 실험은 해당 ID의 공급자가 실제로 등록된다는 것을 보여 주지 않습니다.
