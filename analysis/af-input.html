AF 카운터에서
보정값과 구동 요청까지

앞서 입력으로 주었던 AF 보정값의 생산자를 찾았다. 원본 드라이버 생성자와 레지스트리 연결을 실행해 두 카운터 주소를 확인했고, 같은 모터 객체의 보정값 생산·후속 계산·구동 준비 전달을 이어 검증했다. 두 시점의 카운터 값은 각각 주입했으며 실제 하드웨어가 값을 바꾸는 과정은 실행하지 않았다.

앞선 AF 계산카운터 연결보정값 생산후속 전달재현과 한계연구 상태

기본 주소 표기는 해제 파일 오프셋이다. 실행 주소에는 VA를 붙였다. CAfMotor·CAfDriver·CUdcDriver·C32bitReloadTimerDriver의 이름은 펌웨어 RTTI에서 확인했다. 내부 요청값의 물리 단위는 아직 확인하지 않았다.

1. 선택 인수 0은 타이머 0xD1을 읽는다

타이머 팩터리 0x3221C…0x322AC는 ID 0xD1과 이벤트 슬롯 0x82를 지정한다. 생성자 0x32DE0가 기술자에 담긴 VA 0x30011024를 timer+0x24에 기록한다. UDC 팩터리 0x3391C…0x339B4는 ID 0x117·슬롯 0x5F를 사용하며 생성자 0x33BF8가 VA 0x30014060을 UDC+0x1C에 연결한다. counter_binding·classes·branches

VA 0x26E4는 선택 인수 0에서 타이머 경로를, 그 외에는 UDC 경로를 호출한다. 주입한 0xAAAA1234와 0xBBBB5678에서 각각 0x1234와 0x5678이 나왔다. 레지스트리 항목과 이벤트 슬롯의 객체 포인터도 원본 생성자가 기록했다. 이벤트 슬롯 등록이 실제 인터럽트 전달을 증명하지는 않는다. 생성자 실행과 getter_cases

2. 조건을 통과하면 최초 카운터에서 보정값을 만든다

애플리케이션의 ITCM 호출 VA 0x2140은 0x54284로 이어진다. 렌즈 능력 비트 6이 꺼진 경로에서 초기 카운터를 읽고, 전역 VA 0x001030AB = 0·상태 판정 참·motor+0x4D = 0·카운터가 40보다 큰 조건을 확인한다. 이번 실행은 부모 상태 분기 이후인 VA 0x213C에서 시작한다. 전체 AF 작업의 도달 조건을 검증한 것은 아니다. additive_and_request·numeric.limits

조건을 통과한 뒤의 분기0x5234C에 전달한 원본 인수보정값
VA 0x00103120 ≠ 0, VA 0x0010311A ≠ 2(방향, 목표) = (0, 40), (1, 80)초기 카운터 − 40
VA 0x00103120 = 0 또는 VA 0x0010311A = 2(0, 0xFFFF), (1, 0)초기 카운터

0x54344는 pulse+0xBA에서 이 보정값을 빼고 하위 16비트를 저장한다. 이어 0x54358이 ITCM setter VA 0x397C를 호출한다. 실제 STRH 명령 VA 0x3980이 공유 반워드 VA 0x0010316E에 보정값을 쓴다. 초기화 호출 VA 0x19F4도 같은 setter에 0을 전달했다. native_reset_writes·native_additive_writes

경계값 40에서는 저장하지 않아 이전 보정값 12가 남았고, 41에서는 새 보정값 1을 기록했다. 상태 판정 실패·모터 플래그 설정·모드 플래그 설정·렌즈 능력 비트 6 설정 사례에서도 새 보정값을 쓰지 않았다. 호출을 생략하는 분기와 값을 지우는 동작을 구분해야 한다. 추가 대조에서는 잔량의 16비트 순환, 요청 32767 유지와 32768의 signed 해석에 따른 0 처리를 확인했다. threshold_40·threshold_41 및 나머지 조건 사례

3. 같은 객체가 보정값을 다시 읽고 요청을 전달한다

일반 사례와 상태값 2의 대체 사례는 생산자 복귀까지 실행했다. 대체 사례는 0x54414에서 방향 플래그 VA 0x00103116에 1을 쓴다. 일반 사례는 준비해 둔 0을 유지했다. 두 사례 모두 0x54424 → 0xB7130을 거쳐 상태 VA 0x001030E2 = 2를 기록했고, 이 방향·상태를 후속 계산에 그대로 사용했다. normal·alternate_state_2

후속 호출 VA 0x2258 → 0x5455C는 같은 모터 객체와 타이머 ID 0xD1을 사용한다. 0x544EC가 새 카운터를 방향에 따라 정규화하고 0x54640 → 0xB7530이 앞서 저장한 보정값을 읽는다. 계산 플래그와 모드 조건을 고정한 12건에서 요청값을 확인했다. 앞부분만 실행한 사례는 후속 방향·상태를 따로 준비했으므로 위 두 전체 꼬리 사례와 구분했다. 동일 객체 재사용과 후속 입력 조건

두 전체 꼬리 사례는 VA 0x2348부터 원본 소비자를 추가 실행해 0x52E38 입구에 도달했다. 요청 367과 40이 pulse+0x9E·position+0x166에 남았고 호출 인수는 같은 모터 객체와 8이었다. 이번 검사는 이 함수 입구에서 멈춘다. 함수 내부의 바디·렌즈 분기는 앞선 별도 검증에서 다뤘다.

4. 원본 실행 범위와 재현 방법

python verify_af_input.py decoded.bin --compare analysis/af-input.json

Unicorn 2.1.4에서 카운터 선택 3건, 보정값 분기 14건, 후속 계산 12건, 준비 함수 입구 전달 2건을 재현했다. 59개 명령·상수, 59개 분기 목적지, RTTI 6개와 코드 범위 9개의 해시를 대조한다. 해제 파일의 SHA-256도 실행 전에 확인한다. 재현 가능한 결과 전체 · 검증기

실행을 대체한 함수는 할당 0xAB71C, 바디 구동 준비 0x5234C, 대체 경로의 완료 리셋 VA 0x2A60 세 곳이다. 팩터리 진입 시의 스택·객체, 레지스트리 초기화 가드와 카운터 입력은 검증기에 명시한 합성 상태다. 광학 센서에서 초점 오차를 만드는 과정, 물리 카운터의 발생원과 단위, 호출 사이의 스케줄링 및 실제 모터 움직임은 미검증이다. execution_replacements·limits
