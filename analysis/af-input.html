AF 카운터가 보정값과 요청값이 되기까지

앞 문서에서는 요청값 계산에 들어가는 “입력”과 “보정값”을 연구자가 직접 넣었습니다. 이 문서는 두 값이 펌웨어 안에서 실제로 어디서 오는지 거슬러 올라갑니다.

이 문서에서

  1. 배경: 앞 문서에서 남은 두 가지 물음
  2. 입력의 출처: 타이머 드라이버의 카운터 레지스터
  3. 보정값의 출처: 조건을 통과하면 그 시점의 카운터로 만듭니다
  4. 이어 붙이기: 저장된 보정값이 요청값이 되어 구동 준비 입구에 도착합니다
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 요청값 계산의 입력은 타이머 드라이버가 가리키는 카운터 레지스터에서 읽습니다. 원본 드라이버 생성 코드와 등록·조회 코드를 실행해 레지스터 주소 두 개를 확인했습니다.
  • 보정값은 AF 코드가 스스로 만듭니다. 조건을 통과하면 그 시점의 카운터에서 40을 뺀 값(분기에 따라서는 카운터 그대로)을 공유 메모리에 저장합니다.
  • 같은 객체에서 “보정값 저장 → 다음 카운터로 요청값 계산 → 구동 준비 함수 입구”까지 이어서 실행했습니다. 두 사례에서 요청값 367과 40이 입구까지 전달됐습니다.
  • 카운터 값은 두 시점 모두 연구자가 넣었습니다. 실제 하드웨어가 이 값을 어떻게 바꾸는지, 값의 단위가 무엇인지는 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 드라이버 생성과 등록, 조회로 연결되는 레지스터 주소 2개
  • 카운터 선택 3건, 보정값 분기 14건
  • 뒤따르는 요청값 계산 12건
  • 구동 준비 함수 입구까지의 전달 2건

정적 분석 코드를 읽어 판단

  • 함수들이 서로를 부르는 관계(분기 59개)
  • 명령어·상수 59개와 클래스 이름 6개의 대조

모델 시험 조건으로 정한 것

  • 카운터 레지스터는 평범한 RAM. 두 시점의 값은 따로 넣음
  • 드라이버 생성 코드에 들어갈 때의 스택, 객체, 초기화 표시
  • 메모리 할당, 바디 구동 준비, 완료 리셋 함수 3개는 대체

미확인 확인하지 않은 것

  • 카운터가 세는 물리 신호와 단위
  • 호출 사이의 스케줄링과 카운터 변화
  • AF 센서가 초점 오차를 만드는 과정
  • 실제 모터의 움직임

배경: 앞 문서에서 남은 두 가지 물음

AF 요청 계산 문서에서 바디 경로의 요청값은 “정규화한 입력 − 차감값 + 보정값”이었습니다. 그 문서의 시험에서는 입력 반워드와 보정값을 연구자가 정해서 넣었습니다. 남은 물음은 둘입니다.

  • 입력은 어디서 읽는가: 모터 객체에서 포인터를 세 번 따라간 곳이라는 것만 알았습니다.
  • 보정값은 누가 쓰는가: 공유 메모리의 한 칸(VA 0x0010316E)에 들어 있다는 것만 알았습니다.

이 문서에서 “카운터”는 32비트 레지스터의 값을 가리킵니다. AF 코드는 그 하위 16비트만 씁니다. 카운터가 실제로 무엇을 세는지는 이 연구에서 알아내지 못했습니다.

주소와 이름

기본 주소 표기는 복호화한 파일의 오프셋이고 실행 주소에는 VA를 붙였습니다. VA 0x26E4처럼 작은 주소는 펌웨어가 시작할 때 주소 0번지 근처로 복사해 실행하는 코드입니다(원문 표기는 ITCM). CAfMotor, CAfDriver, CUdcDriver, C32bitReloadTimerDriver는 펌웨어의 RTTI 문자열에서 확인한 클래스 이름입니다. UDC가 무엇의 약어인지는 펌웨어에서 확인하지 못했습니다.

입력의 출처: 타이머 드라이버의 카운터 레지스터

카운터 읽기 함수는 선택 인수가 0이면 타이머 드라이버의 레지스터를, 그 밖이면 UDC 드라이버의 레지스터를 읽습니다. 이 문서의 보정값 생산과 요청값 계산은 인수 0을 씁니다.

이 연결은 연구자가 포인터를 손으로 이어 붙인 것이 아닙니다. 펌웨어의 드라이버 생성 코드와 등록 코드, 조회 코드를 실행해서 원본 명령이 직접 포인터를 채우게 했습니다.

  • 타이머: 생성 코드 0x3221C…0x322AC가 등록 ID 0xD1과 이벤트 슬롯 0x82를 지정합니다. 생성자 0x32DE0이 레지스터 주소 VA 0x30011024를 타이머 객체의 +0x24에 적습니다.
  • UDC: 생성 코드 0x3391C…0x339B4가 등록 ID 0x117과 이벤트 슬롯 0x5F를 씁니다. 생성자 0x33BF8이 VA 0x30014060을 UDC 객체의 +0x1C에 연결합니다.
  • 읽기 함수: VA 0x26E4는 선택 인수가 0이면 타이머 쪽을, 그 밖이면 UDC 쪽을 부릅니다.

생성·등록·조회 코드의 세부
  • CAfDriver는 VA 0x4000B25C의 단일 객체입니다. 상위 객체의 +0x20에 이 포인터가 들어가고(0x48EE8), 모터 객체의 +8로 복사됩니다(0x51E08…0x51E14).
  • 등록 표는 VA 0x40006944에 있고 항목 하나가 12바이트입니다. 항목에는 사용 표시 1, 등록 ID, 객체 포인터가 차례로 들어갑니다. 조회 코드 0x46BC4…0x46BD4는 ID 0xD1의 객체를 CAfDriver+4에 적습니다. 0x46C04…0x46C14는 ID 0x117의 객체를 CAfDriver+0x18에 적습니다.
  • 타이머 객체에는 레지스터 포인터가 네 개 들어갑니다: +0x18에 VA 0x30011020, +0x1C에 0x30011028, +0x20에 0x3001102C, +0x24에 0x30011024.
  • 이벤트 표는 VA 0x40007820부터이고 슬롯 하나가 4바이트입니다. 슬롯 0x82와 0x5F에는 각 드라이버 객체의 +8 주소가 들어갑니다.
  • 생성자가 요청하는 메모리 크기는 타이머 0x2C바이트, UDC 0x30바이트입니다. 할당 함수 0xAB71C는 대체했습니다.
  • 근거는 af-input.json의 counter_binding, classes, branches, getter_cases입니다.

보정값의 출처: 조건을 통과하면 그 시점의 카운터로 만듭니다

보정값을 쓰는 코드는 AF 모터 객체의 함수 0x54284입니다. 조건을 모두 통과했을 때만 새 값을 저장하고 그렇지 않으면 이전 값이 남습니다.

상위 루틴의 호출 VA 0x2140이 함수 0x54284로 이어집니다. 렌즈 능력 비트 6이 꺼진 경로에서 이 함수는 먼저 카운터를 읽고 다음 네 가지를 확인합니다.

  • 전역 모드 플래그 VA 0x001030AB가 0일 것
  • 상태 판정이 참일 것(시험에서는 상태값 1과 2가 통과, 0과 5는 통과하지 못함)
  • 모터 플래그 motor+0x4D가 0일 것
  • 카운터가 40보다 클 것
조건을 통과한 뒤의 두 분기

보정값은 두 곳에 반영됩니다. 먼저 pulse+0xBA의 값에서 보정값을 뺀 하위 16비트가 다시 저장됩니다. 이어서 저장 함수 VA 0x397C가 호출되고 그 안의 저장 명령 VA 0x3980이 공유 반워드 VA 0x0010316E에 보정값을 씁니다. 초기화 단계의 호출 VA 0x19F4도 같은 저장 함수에 0을 넘깁니다.

경계와 조건을 하나씩 바꿔 본 결과

  • 경계값: 카운터가 40이면 저장하지 않아 이전 보정값 12가 남았습니다. 41이면 새 보정값 1을 기록했습니다.
  • 조건 불충족: 상태 판정 실패, 모터 플래그가 켜진 경우, 모드 플래그가 켜진 경우, 렌즈 능력 비트 6이 켜진 경우 모두 새 보정값을 쓰지 않았습니다. 값을 지우지 않고 쓰기 호출 자체를 건너뜁니다.
  • 16비트 순환: 카운터 65,535에서 보정값은 65,495가 됩니다. 여기에 다음 카운터 42를 더하면 16비트를 넘어 요청값은 1이 됩니다.
  • 부호 경계: 요청값 32,767은 그대로 유지되고 32,768은 음수로 해석되어 0이 됩니다.

이 실행은 상위 루틴의 상태 분기를 지난 지점인 VA 0x213C에서 시작합니다. AF 작업 전체가 어떤 조건에서 이 지점에 도달하는지는 확인하지 않았습니다.

이어 붙이기: 저장된 보정값이 요청값이 되어 구동 준비 입구에 도착합니다

보정값을 만든 실행의 결과(방향 플래그, 상태, 보정값)를 그대로 둔 채 다음 단계를 실행했습니다. 그러자 같은 모터 객체에서 요청값이 계산되어 구동 준비 함수의 입구까지 전달됐습니다.

두 사례는 보정값 생산 함수가 복귀할 때까지 실행했습니다. 대체 사례에서는 원본 명령(0x54414)이 방향 플래그 VA 0x00103116에 1을 썼고 일반 사례에서는 미리 넣어 둔 0이 유지됐습니다. 두 사례 모두 0x54424에서 0xB7130을 거쳐 상태 VA 0x001030E2에 2를 기록했습니다. 뒤따르는 계산은 이 방향과 상태를 그대로 썼습니다.

요청값 계산은 VA 0x2258의 호출로 함수 0x5455C에 들어가며 같은 모터 객체와 타이머(ID 0xD1)를 씁니다. 함수 0x544EC가 새 카운터를 방향에 따라 정규화하고 0x54640의 호출이 읽기 함수 0xB7530으로 앞서 저장된 보정값을 읽습니다. 계산 플래그와 모드 조건을 고정한 12건에서 요청값을 확인했습니다. 앞부분만 실행한 사례는 방향과 상태를 따로 넣었으므로 위의 두 사례와 구분했습니다.

두 사례는 VA 0x2348부터 원본 소비자 코드를 더 실행해 구동 준비 함수 0x52E38의 입구에 도달했습니다. 요청값 367과 40이 pulse+0x9E와 position+0x166에 남았고 호출 인수는 같은 모터 객체와 8이었습니다. 이 문서의 실행은 함수 입구에서 멈춥니다. 함수 안의 바디·렌즈 분기는 AF 요청 계산 문서에서 따로 확인했습니다.

이어 붙인 실행의 세부
  • 대체 사례에서는 완료 리셋 함수(VA 0x2A60, 파일 0xD7E7C)가 인수 0으로 한 번 호출됐습니다. 이 함수는 대체했고 그 뒤 방향 플래그에 1을 쓰는 명령은 원본으로 실행했습니다.
  • 끝까지 실행한 두 사례에서는 position 객체의 +0x40에 0x400이 기록됐습니다.
  • 요청값 계산 뒤 방향 플래그는 12건 모두 0이었고 보정값은 계산 중에 바뀌지 않았습니다.
  • 소비자 쪽 호출은 VA 0x234C이고 구동 준비 호출은 파일 0x5493C에서 일어납니다.
  • 근거는 af-input.json의 normal과 alternate_state_2 사례입니다.

한계와 남은 과제

  • 카운터의 정체: 레지스터 주소와 드라이버 연결은 확인했지만 이 카운터가 어떤 물리 신호를 세는지와 값의 단위는 알지 못합니다. 요청값의 물리 단위도 마찬가지입니다.
  • 시간의 흐름: 두 시점의 카운터 값은 각각 넣어 준 것입니다. 하드웨어가 값을 바꾸는 과정, 실행 구간 사이의 스케줄링은 실행하지 않았습니다.
  • 대체한 함수: 메모리 할당 0xAB71C, 바디 구동 준비 0x5234C, 대체 분기의 완료 리셋 VA 0x2A60 세 곳입니다. 바디 구동 준비는 인수만 기록하고 돌아오게 했으므로 하드웨어 준비 동작은 실행되지 않았습니다.
  • 합성 상태: 드라이버 생성 코드에 들어갈 때의 스택과 객체, 등록 표의 초기화 표시, 카운터 입력은 검증기에 적어 둔 합성 값입니다.
  • 다루지 않은 것: 광학 센서에서 초점 오차를 만드는 과정과 실제 모터의 움직임.

미해결 항목은 hq-status.json의 af_and_lens_drive에 정리되어 있습니다.
