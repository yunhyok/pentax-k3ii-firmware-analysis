백엔드 B의 SD 쓰기와 두 번째 CPP 출력이 가는 곳

사진 한 장이 카드에 남으려면 영상 버퍼가 JPEG 압축기까지 이어지고, 파일 쓰기가 SD 카드 명령으로 바뀌어야 합니다. 이 문서는 그 길에서 비어 있던 두 구간을 다룹니다.

이 문서에서

  1. 배경: 저장 경로와 영상 버퍼 경로의 빈 구간
  2. 백엔드 B의 파일 쓰기는 A와 같은 SD 카드 함수로 내려갑니다
  3. 파일 쓰기 한 번은 섹터 경계에서 나뉩니다
  4. 두 번째 CPP 출력은 모듈 17의 합성 입력이 됩니다
  5. 마스크 분기에서는 합성 결과가 다른 버퍼로 갑니다
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • 저장 구현 두 개 가운데 백엔드 B의 파일 쓰기를 따라갔습니다. B도 백엔드 A와 같은 SD 카드 객체의 같은 쓰기 함수로 내려갑니다. 원본 코드가 SD 쓰기 명령과 DMA 설명자를 만드는 곳까지 실행했습니다.
  • 파일 쓰기 한 번은 512바이트 섹터 단위로 나뉩니다. 섹터를 꽉 채우는 부분은 원래 데이터 주소를 그대로 넘기고, 섹터 일부만 바꾸는 앞뒤 조각은 기존 섹터를 읽어 캐시에서 합친 뒤 씁니다.
  • 색 처리 모듈(CPP)이 두 번째로 내는 출력은 모듈 17의 합성 입력이 됩니다. 기본 분기에서는 합성 결과가 놓이는 버퍼가 스케일러의 입력과 같고, 스케일러의 출력은 JPEG 압축기의 입력과 같습니다.
  • 마스크 분기에서는 합성 결과가 다른 버퍼로 갑니다. 그 버퍼를 읽는 보조 스케일러는 확인한 경로에서 모두 꺼져 있었습니다.
  • 모두 PC 에뮬레이터에서 합성 메모리로 실행한 결과입니다. 실제 카드 기록, 픽셀 처리, JPEG 생성은 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • B 쓰기 래퍼에서 SD 명령 레지스터 쓰기까지 7건
  • 카드 쓰기 진입점의 블록 번호·개수·포인터·내용, ADMA 표 2,048바이트
  • 모듈 17·스케일러·JPEG 설정 구간의 디스크립터 주소 일치 4건
  • 레시피 4개에서 CPP → 모듈 17 → 스케일러 → JPEG 순서

정적 분석 코드를 읽어 확인

  • 함수표의 쓰기 칸과 호출 대상(분기 24개·79개)
  • 함수 구간 해시 9개·10개

모델 시험 조건으로 넣은 값

  • 이미 할당된 4,096바이트 파일과 드라이브 상태
  • 카드 읽기 내용(0xCC), 완료 플래그, 볼륨 조회 결과
  • 평면 주소, 합성 모드 0·2·4, 보조 스케일러 활성값 1

미확인 확인하지 않은 것

  • 마운트, 클러스터 할당, 복구 분기
  • 실제 DMA 전송, 캐시 일관성, 카드 기록
  • 픽셀 내용, JPEG 바이트, 촬영 메뉴에서 이 분기에 이르는 조건

배경: 저장 경로와 영상 버퍼 경로의 빈 구간

이 주제의 다른 문서가 이미 두 줄기를 따라갔습니다. JPEG 출력 버퍼 문서는 색 처리 출력이 스케일러와 JPEG 압축기를 거쳐 파일시스템 어댑터에 닿는 과정을 다룹니다. 파일시스템에서 SD·DMA까지 문서는 저장 구현 A가 SD 카드 명령으로 내려가는 과정을 다룹니다. 두 문서가 다루지 않는 구간이 둘 있습니다.

  • 저장 구현 B의 아래쪽 — B가 파일 쓰기를 어떤 카드 함수로 넘기는지
  • CPP의 두 번째 출력 — 색 처리가 한 번 더 돌 때 나오는 영상이 어디로 가는지

전체 흐름은 영상 처리 경로 안내에 있습니다. 아래 표는 이 문서에서 쓰는 이름입니다.

백엔드 B의 파일 쓰기는 A와 같은 SD 카드 함수로 내려갑니다

B의 쓰기 래퍼에서 출발한 요청은 파일시스템 함수표, 섹터 처리, 블록 브리지를 차례로 거쳐 A가 쓰는 것과 같은 카드 쓰기 함수에 닿습니다. 거기서 SD 쓰기 명령과 ADMA 설명자가 만들어집니다.

디스패처는 파일 핸들에서 드라이브를 찾은 뒤 파일시스템 함수표에서 쓰기 함수를 꺼내 부릅니다. 시험에서는 함수표의 첫 행을 썼습니다. 블록 브리지는 볼륨 이름으로 카드 객체를 찾고, 그 객체의 함수표에서 쓰기 칸을 부릅니다. 이 칸에 든 함수가 백엔드 A의 경로에서 확인한 것과 같은 0x7589E8입니다.

SD 명령 레지스터에 기록된 값

정상 쓰기 사례에서는 카드 쓰기 함수를 가로막지 않고 원본 카드·호스트 코드까지 실행했습니다. 합성 포트 0xC6000000에 기록된 값은 아래와 같습니다. 레지스터 배치와 설명자 형식은 SD 호스트 컨트롤러 표준(SDHCI)의 정의와 맞습니다.

클러스터 번호에서 블록 번호 계산

파일시스템은 파일 위치를 클러스터 번호로 관리합니다. 함수 0xEBD250이 클러스터 번호를 블록 번호로 바꿉니다.

LBA = (cluster − 2) × drive[+0x34] + drive[+0x30] + uint64(drive[+0x18], drive[+0x1C])

시험에서는 cluster = 2, 클러스터당 8섹터, 시작값 0x100, 데이터 오프셋 0x20을 넣어 LBA 0x120을 얻었습니다. 그다음 파일 안의 바이트 위치를 섹터 크기 512로 나눕니다.

시험 조건
  • 드라이브 상태와 파일 상태는 직접 만든 값입니다. 파일 크기 조회에는 4,096바이트를, 영역 조회에는 준비해 둔 영역 하나를 돌려주었습니다.
  • 함수표는 첫 행만 썼습니다. 다른 행, 마운트, 클러스터 할당은 실행하지 않았습니다.
  • 볼륨 조회는 합성 볼륨 이름 C:를 확인한 뒤 합성 카드 객체를 돌려주도록 대체했습니다. 이 카드 객체의 섹터 수(0x100000)는 B가 선택되는 크기보다 작습니다. 시험이 선택 과정을 거치지 않고 B의 래퍼에서 바로 시작하기 때문입니다.
  • 잠금, 캐시 관리, 완료 대기는 성공 값을 돌려주도록 대체했습니다.

파일 쓰기 한 번은 섹터 경계에서 나뉩니다

섹터를 꽉 채우는 가운데 부분은 원래 데이터 주소를 그대로 카드 쓰기에 넘깁니다. 섹터 일부만 바꾸는 앞뒤 조각은 기존 섹터를 읽어 캐시에서 합친 뒤 캐시 주소를 넘깁니다.

파일 위치 7에서 1,030바이트를 쓰는 사례로 확인했습니다. 첫 섹터에 505바이트, 가운데 섹터에 512바이트, 마지막 섹터에 13바이트가 들어갑니다.

카드 쓰기 함수에 들어온 객체, 블록 번호, 블록 수, 포인터, 512바이트 내용을 요청마다 기대값과 비교했습니다. 이어서 원본 호스트 코드가 만든 ADMA 표 전체(2,048바이트)와 레지스터 값도 비교했습니다.

B 래퍼, 위치 7, 1,030바이트읽기 2회, CMD24 3회. 캐시 → 원래 소스 → 캐시요청마다 ADMA 설명자와 레지스터 값 일치
0xEADE54에서 시작, 12바이트기존 섹터를 읽고 끝의 500바이트 보존부분 섹터의 보존 처리
0xEAE0F4에서 시작, 12바이트읽기 없이 끝의 500바이트를 0으로 채움캐시를 0xA5로 채워 두고 실행해, 원본 코드가 실제로 0을 쓰는지 확인
B 래퍼, 카드 쓰기에서 실패를 돌려줌래퍼 반환 0, 결과 −10009SD 명령을 실행하기 전의 실패 처리
B 래퍼, 길이 0래퍼 반환 0, 결과 −11. 카드 호출 없음파일 쓰기 래퍼의 길이 검사
주의

가운데 조각의 주소 0x100101F9는 정렬되지 않은 합성 주소입니다. 코드가 그 주소를 고치지 않고 넘긴다는 사실만 알 수 있습니다. 실제 장치가 이런 주소를 받아들이는지, CPU 캐시와 버스 사이의 데이터가 일치하는지는 알 수 없습니다. 카드 읽기는 0xCC로 채운 데이터로 대체했습니다.

백엔드 A와 다른 점

백엔드 A의 시험에서는 부분 섹터 쓰기가 캐시에만 반영되고, 따로 실행한 비우기(flush) 함수에서 카드로 나갔습니다. B의 시험에서는 같은 쓰기 호출 안에서 읽기와 쓰기가 일어났습니다. 두 결과 모두 각자의 시험 조건에서 관측한 것이므로, 두 구현의 일반적인 차이라고 단정하지 않습니다.

끝을 0으로 채우는 함수는 따로 확인했습니다

0xEAE0F4는 부분 섹터의 나머지를 0으로 채웁니다. 이 동작은 함수에 직접 들어가서 확인했습니다. 그런데 파일 쓰기 본체가 이 함수를 부르는 곳(0xEB23E0부터 0xEB2404까지)은 길이를 512바이트 단위로 올린 뒤 부릅니다. 그래서 이 결과만으로 “파일 끝에 덧붙여 쓰면 나머지가 항상 0으로 채워진다”고 말할 수 없습니다.

두 번째 CPP 출력은 모듈 17의 합성 입력이 됩니다

CPP가 두 번째 패스에서 내는 세 평면은 모듈 17이 둘째 입력으로 읽습니다. 기본 분기에서 모듈 17은 결과를 첫 번째 영상의 평면에 다시 쓰고, 스케일러가 그 평면을 읽습니다. 스케일러의 출력은 JPEG 모듈의 입력과 같은 디스크립터입니다.

CPP는 보통 한 번 실행됩니다. 작업의 job+0x59가 0이 아니면 한 번 더 실행되고, 그때는 출력 주소가 job+0x2194 디스크립터의 평면으로 바뀝니다. 이 값을 켜는 경로로 확인한 것은 RAW 현상의 Color Fringe Correction 메뉴입니다. 두 번째 출력을 누가 읽는지가 이 절의 질문입니다.

화살표는 디스크립터와 주소가 전달되는 관계입니다. 단계마다 필요한 합성 상태를 넣고 설정 구간을 따로 실행했습니다. 합성 장치, 스케일러, JPEG를 이어서 실행해 픽셀을 넘긴 결과가 아닙니다.

합성 요청의 수는 내부 모드에 따라 달라집니다

모듈 17은 평면마다 합성 요청을 하나씩 만듭니다. 색차 평면 둘은 항상 요청하고, 내부 모드가 1, 2, 4 가운데 하나이면 Y 평면도 요청합니다. 이 모드는 시험에서 넣어 준 내부 값이며, 메뉴 이름과 연결한 값이 아닙니다.

마스크 분기에서는 합성 결과가 다른 버퍼로 갑니다

작업의 마스크 바이트에 0x44 비트가 있으면 모듈 17은 입력과 목적지를 마스크용 디스크립터로 바꿉니다. 일반 스케일러는 여전히 기본 평면을 읽습니다. 마스크 쪽 버퍼를 읽는 보조 스케일러는 활성값이 0이면 건너뛰는데, 0이 아닌 값을 쓰는 코드는 찾지 못했습니다.

CPP가 처음 출력 주소를 고를 때 job+0x20B4 & 0x44가 0이 아니면 job+0x7F에 1을 씁니다. 모듈 17은 이 값이 1이면 첫째 입력과 목적지를 모두 job+0x2354로 바꿉니다. 일반 스케일러는 이 디스크립터를 읽지 않고 job+0x2140을 읽습니다.

보조 스케일러는 job+0x2354를 입력(payload+0x18)으로 삼고 job+0x238C에 출력합니다. 다만 스케일러의 활성 바이트 payload+0x38이 0이면 이 처리를 건너뜁니다. 설정 코드는 이 바이트를 0으로 초기화합니다. 값을 1로 바꿔 넣었을 때에만 보조 스케일러 호출이 일어났습니다. 이 실행은 읽는 쪽 코드의 동작을 확인한 것이며, 실제 작업이 그 상태에 이른다는 근거가 아닙니다.

이 분기의 현재 상태

  • 활성값 — 스케일러 설정을 처음부터 큐 호출 직전까지 실행한 64건에서도 활성 바이트는 0이었습니다. 0이 아닌 값을 쓰는 코드는 아직 찾지 못했습니다. (활성값 추적)
  • JPEG 보조 입력 — JPEG 모듈은 job+0x21E8과 job+0x2204도 읽습니다. 보조 스케일러 출력과 JPEG 보조 입력은 서로 다른 디스크립터를 씁니다. 활성값을 1로 넣고 일반 배치 뒤에 같은 기준 주소로 마스크 배치를 만든 합성 사례에서 두 쌍의 평면 주소가 일치했습니다. (조건부 주소 공유)
  • 마스크 값의 변화 — 모듈 20이 끝나면 마스크 값에서 0x44 비트가 사라지고, 그 뒤의 CPP는 기본 평면에 출력합니다. Pixel Shift 레시피에서는 모듈 20이 CPP보다 앞에 있습니다. (모듈 20, 레시피 순서)
기본 분기 결론의 범위

모듈 17 안에는 기능·설정 검사와 메모리 준비 단계가 있습니다. 합성 요청 검증은 그 뒤의 디스크립터 읽기와 요청 조립 구간에서 시작했습니다. 그래서 기본 분기의 결론은 “필요한 조건이 성립하면 같은 버퍼로 이어진다”까지입니다. 디스크립터가 다르다는 사실만으로 실제 평면 메모리가 겹칠 가능성을 배제할 수도 없습니다.

한계와 남은 과제

  • 백엔드 B — 대표적인 쓰기 경로 하나를 SD 명령과 ADMA 설정까지 이었습니다. 파일 전체의 클러스터 할당, 마운트, 복구 분기는 실행하지 않았습니다.
  • CPP 기본 분기 — 합성 목적지와 스케일러 입력, 스케일러 목적지와 JPEG 입력의 주소가 같다는 것까지 확인했습니다. 메뉴 조작에서 출발해 이 조건이 모두 성립하는 경로, 사이의 레시피 단계가 주소나 내용을 바꾸는지는 남아 있습니다.
  • 마스크 분기 — 보조 스케일러를 켜는 코드, 실제 작업에서 보조 출력과 JPEG 보조 입력이 같은 평면을 쓰는지, 모듈 17 앞단의 기능 검사가 남아 있습니다.
  • 하드웨어 — RAW 픽셀 처리, JPEG 생성, Exif에서 SD 매체까지의 연속 실행, DMA 데이터 전송과 캐시 일관성은 확인하지 않았습니다. SoC와 보조 MCU의 정확한 부품 번호도 정해지지 않았습니다.

재현 방법

분석 대상은 K-3 II 펌웨어 1.12(fwdc230b.bin)입니다. 검증기는 이 파일을 복호화한 이미지 decoded.bin을 입력으로 받습니다. 만드는 방법은 펌웨어 파일 구조와 복호화에 있습니다. 원본 코드 실행에는 Unicorn 2.1.4가 필요합니다.

python verify_backend_b.py decoded.bin --compare analysis/backend-b.json
python verify_cpp_handoff.py decoded.bin --compare analysis/cpp-handoff.json
python -m unittest discover -s tests -v
python verify_publication.py

앞의 두 명령은 결과를 공개된 JSON과 비교합니다. 뒤의 두 명령은 펌웨어 없이 실행되며 단위 테스트, HTML과 링크, 공개 파일 범위, 근거 해시의 일관성을 검사합니다. 저장소에는 펌웨어와 전체 디스어셈블리를 넣지 않았습니다.
