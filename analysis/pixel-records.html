촬영 패킷·같은 버퍼의 보정까지

업데이트가 보존하는 섹터 15~19를 원본 픽셀 보정 코드와 연결했다. 촬영 패킷의 활성 바이트에 따른 실행, 앞선 보정 결과를 다음 레코드가 읽는 순서, 적재된 설명자의 수명과 섹터 저장 요청을 검증했다.

섹터 14Pixel Shift·버퍼 수명활성값 생산자저장 영역픽셀 수정촬영 패킷저장·검증 범위

함수 주소는 해제 파일 오프셋, VA와 RAM 주소는 실행 주소다. 섹터 번호는 128KiB 단위의 0부터 시작하는 인덱스다. 이 보정 경로를 보조 스케일러 활성 경로나 SuperResolution 전용 처리로 단정하지 않았다.

1. 10개 등록 객체가 보존 섹터 5개를 나누어 관리한다

시작 코드의 생성자와 등록 구간을 그대로 실행해 ID 0x58…0x61이 같은 관리자의 전역 객체 10개를 가리키는지 확인했다. 플래시는 0x021E0000 + 0x10000×n, RAM은 0x40130000 + 0x10000×n이다. 가상 함수 표는 처음 7개와 나머지 3개가 다른 구간에 있으므로 하나의 연속 배열로 계산하지 않았다. 생성자·등록·주소 대조

첫 워드가 0xA55A5AA5인 묶음은 64KiB 전체를 복사한다. 무효 묶음은 마커 0xFFFFFFFF, 다음 워드 0x00003FFE, 나머지 0으로 초기화됐다. 배포 이미지에 들어 있는 다음 워드 0x3FFE0000과는 다르다. 설명자는 다음 워드의 하위 16비트를 레코드 수로 읽고 0x2A94로 제한한다. 전체 적재 바이트·상한 세 사례

새 객체의 설명자는 0이며 원본 처리기는 첫 무효 설명자에서 순회를 끝낸다. 0번과 2번만 유효한 상태로 둔 대조에서는 0번만 처리했다. 이미 적재된 객체는 초기화 바이트 +0x12가 1이면 재적재하지 않는다. 별도로 적재 함수를 다시 호출하면 RAM이 기본값으로 바뀌어도 기존 설명자 필드가 남았다. 이 실험만으로 실제 촬영마다 객체를 다시 만든다거나 무효 레코드를 안전하게 건너뛴다고 해석할 수 없다. 캐시·무효 간격·명시적 재적재

2. 보정은 같은 16비트 이미지 버퍼를 순서대로 수정한다

원본 0x73A5EC는 6바이트 레코드에서 좌표와 플래그를 읽어 0x739F80에 전달한다. 플래그 상위 2비트에 1을 더한 값이 객체의 임계값보다 크면 건너뛴다. 하위 바이트가 0이 아니면 그 비트를 먼저 사용하고 0이면 비트 8~13을 사용한다. 선택한 방향 중 최대 두 이웃을 읽어 평균을 같은 이미지에 쓴다. 코드의 진단 문자열도 이를 Pixel Correct Data라고 부른다. 방향 표·임계값·원본 진단 근거

전체 512바이트 이미지와 앞뒤 대조값을 검사했으며 순서 반전·한 묶음의 두 레코드·단일 이웃·상하위 마스크 우선순위·임계값 경계·중심 좌표 경계를 대조했다. 함수 반환값은 기록한 픽셀 수가 아니라 방문한 레코드 수다. 임계값이나 중심 좌표 때문에 기록을 건너뛴 사례도 반환값은 1이었다. 앞선 12회 직접 보정 대조에서 사용한 이웃 좌표는 이미지 안에 있다. 아래의 경계 대조는 별도 입력이다. 12회 직접 보정 검증

별도 대조: 중심 좌표 검사와 이웃 주소 계산은 다르다

원본 0x739F44는 중심 좌표를 검사한다. 이웃 오프셋을 더한 뒤의 0x73A028/0x73A034와 0x73A080/0x73A090은 좌표를 16비트로 자른다. 0x739F38은 계산된 주소를 추가 범위 검사 없이 읽는다. 별도 합성 대조에서 중심 (15, 8)의 오른쪽 이웃은 다음 행의 바이트 +290을, 중심 (0, 8)의 왼쪽 이웃은 논리 이미지 밖의 +131324를 읽었다. x=16 또는 y=16인 중심은 거부했다. 원본 읽기·쓰기 주소 여섯 대조

레코드 y=65535에 객체의 행 오프셋 2를 더하면 16비트 절단 뒤 행 1이 됐다. 이웃 값 65535와 65534의 평균은 65534여서 합산이 먼저 16비트로 넘치는 계산과 구분된다. 향후 C 재구현이나 이식에서는 중심 검사만으로 이웃 접근이 유효하다고 가정할 수 없다. 보정표의 좌표 제약과 버퍼 패딩을 확인하거나 이웃 접근을 별도로 검사해야 한다. 실제 카메라에 이런 레코드가 있는지와 촬영 중 도달 여부는 검증하지 않았다. 분리한 경계 재현 코드

3. 촬영 컨텍스트의 활성 바이트가 패킷을 거쳐 같은 버퍼에 적용된다

원본 설정 함수 0x597AB4로 처리기와 보정 객체를 연결한 뒤 같은 메모리 상태에서 패킷 생산 구간과 처리기 구간을 실행했다. 활성값 0에서는 이미지 전체가 유지됐고, 1에서는 같은 이미지 포인터가 보정 객체 +0xC에 들어가 중심값 300·450을 만들었다. 프레임의 크기와 패킷의 임계값도 원본 조회 함수가 가져왔다. 두 패킷 실행과 호출 순서

패킷 +8과 +9가 제어하는 별도 보정은 두 값을 0으로 두어 건너뛰었다. +0xA가 0이어도 프레임·임계값 설정은 실행된다. 촬영 컨텍스트의 플래그·프레임·이벤트 봉투는 입력으로 준비했다. 처리기의 기본 생성자와 작업 스케줄러는 실행하지 않았고 보정 실행에서는 시간 조회 함수 0x785F70만 0을 반환하도록 대체했다. 따라서 이 결과는 두 원본 구간 사이의 포인터·분기 연결을 입증하며 실제 센서 입력이나 촬영 모드 도달 이력을 입증하지 않는다. 별도로 검증한 메뉴·버퍼 수명 범위

4. 적재 후 저장은 다섯 섹터에 RAM 묶음을 둘씩 넣는다

원본 적재 함수는 관리자 +0x2CA를 1로 설정한다. 이 상태에서 0x6E8528을 실행하면 섹터 14에 이어 15~19를 준비한다. 섹터 15~19는 등록된 RAM 두 묶음의 128KiB 연결과 바이트 단위로 일치했다. 이번 실험은 픽셀 공급자 10개만 등록했으므로 섹터 14는 원본 내용이 그대로 전달됐다. 섹터 읽기·덮어쓰기 인수·요청 해시
