보존 섹터 15~19의 픽셀 레코드와 이미지 버퍼 보정

펌웨어 업데이트가 건드리지 않는 플래시 구역에는 픽셀 좌표와 보정 방향을 적은 레코드 자리가 있습니다. 이 레코드가 RAM으로 올라와 이미지 버퍼의 픽셀 값을 바꾸는 과정을 원본 코드로 따라갔습니다.

이 문서에서

  1. 배경: 결함 픽셀 보정과 보존 섹터
  2. 등록 객체 10개가 보존 섹터 다섯 개를 나누어 맡습니다
  3. 보정은 같은 16비트 이미지 버퍼를 레코드 순서대로 고칩니다
  4. 중심 좌표는 검사하지만 이웃 좌표는 검사하지 않습니다
  5. 촬영 패킷의 활성 바이트가 보정 실행을 정합니다
  6. 저장 함수는 섹터마다 RAM 묶음 두 개를 넣어 기록을 요청합니다
  7. 한계와 남은 과제
  8. 재현 방법
  9. 근거 파일과 참고 자료

핵심 요약

  • 보존 섹터 15~19(640KiB)는 64KiB 묶음 10개로 나뉘고, 등록 객체 10개가 하나씩 맡습니다. 묶음의 첫 워드가 유효 마커일 때만 내용이 RAM으로 복사됩니다.
  • 레코드 하나는 6바이트(x, y, 플래그)입니다. 보정 코드는 플래그가 가리키는 방향의 이웃 픽셀을 최대 두 개 읽어 평균을 같은 버퍼에 씁니다. 그래서 뒤의 레코드는 앞에서 고친 값을 읽고, 순서가 바뀌면 결과도 달라집니다.
  • 보정이 실행되는지는 촬영 패킷의 활성 바이트가 정합니다. 0이면 이미지가 그대로였고 1이면 같은 버퍼가 고쳐졌습니다.
  • 원본 코드는 중심 좌표만 검사하고 이웃 좌표는 검사하지 않습니다. 시험용 좌표 여섯 개로, 이웃 주소가 다음 행이나 이미지 밖으로 나갈 수 있음을 확인했습니다.
  • 모든 입력은 시험용으로 만든 값입니다. 실제 카메라에 어떤 레코드가 들어 있는지, 플래시에 실제로 기록되는지는 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 등록 객체 10개의 생성·등록과 주소 getter
  • 픽셀 보정 12회: 이미지 전체와 앞뒤 대조값 일치
  • 좌표 경계 6회: 읽기·쓰기 주소 일치
  • 패킷 활성 0/1 두 사례, 섹터 저장 요청 18개

모델 시험 조건으로 정한 것

  • 플래시 내용, 레코드, 16×16 합성 이미지
  • 촬영 객체의 플래그, 프레임, 이벤트 봉투
  • 시간 조회 함수(0 반환)와 저장 경로의 네 함수 대체

미확인 확인하지 않은 것

  • 실물 카메라의 보정표 내용과 좌표 제약
  • 작업 스케줄러, 실제 촬영에서의 도달
  • 플래시 물리 기록, 전원 차단 뒤 유지

배경: 결함 픽셀 보정과 보존 섹터

이미지 센서에는 늘 지나치게 밝거나 어둡게 읽히는 픽셀이 생길 수 있습니다. K-3 II 사용설명서는 이런 픽셀을 찾아 보정하는 기능을 설정 메뉴의 Pixel Mapping으로 안내합니다. 설명서의 문구는 “Maps out and corrects any defective pixels on the sensor”이며, 문제 해결 표에서는 밝은 점이나 어두운 점이 보일 때 이 기능을 실행하라고 적습니다.

이 문서는 펌웨어 안에서 그와 같은 종류의 일을 하는 코드를 다룹니다. 좌표가 적힌 레코드를 읽어 해당 픽셀을 이웃 값으로 바꾸는 코드이며, 펌웨어의 진단 문자열도 이 데이터를 “Pixel Correct Data”라고 부릅니다. 다만 메뉴의 Pixel Mapping 기능이 이 레코드를 만드는지는 이 연구에서 확인하지 않았습니다.

레코드가 놓이는 곳은 보존 섹터입니다. 펌웨어 업데이트 코드는 128KiB 섹터 13~22를 건너뛰며(업데이트 전송과 기록 오류), 그 가운데 15~19가 픽셀 레코드 자리입니다. 보존 섹터 전체의 지도는 촬영 준비·보존 레코드 안내에 있습니다.

표기 규칙

섹터 번호는 플래시를 128KiB 단위로 잘라 0부터 센 번호입니다. 함수 주소는 복호화한 펌웨어 파일 안의 위치(파일 오프셋)이고, 플래시·RAM 주소는 실행 주소입니다. 파일 오프셋에 0x02000000을 더하면 실행 주소가 되므로, 섹터 15의 시작은 0x021E0000입니다.

주의

이 보정 경로를 보조 스케일러의 활성 경로나 SuperResolution(Pixel Shift Resolution) 전용 처리라고 단정하지 않았습니다.

등록 객체 10개가 보존 섹터 다섯 개를 나누어 맡습니다

섹터 15~19는 64KiB 묶음 10개이며, 유효 마커가 있는 묶음만 RAM으로 복사되어 보정 객체의 설명자에 연결됩니다.

시작 코드의 생성자와 등록 구간을 그대로 실행해, ID 0x58~0x61이 같은 관리자에 등록된 전역 객체 10개를 가리키는지 확인했습니다. n번째 묶음의 플래시 주소는 0x021E0000 + 0x10000 × n, RAM 주소는 0x40130000 + 0x10000 × n입니다. 10개의 가상 함수 표는 앞의 7개와 뒤의 3개가 파일의 서로 다른 구간에 있어, 하나의 연속 배열로 계산하지 않았습니다.

  • 무효인 묶음 — RAM은 마커 0xFFFFFFFF, 다음 워드 0x00003FFE, 나머지 0으로 초기화됩니다. 배포 펌웨어 파일의 같은 위치에는 0xFFFFFFFF와 0x3FFE0000이 들어 있어 둘째 워드가 서로 다릅니다.

배포 파일과 실물은 다를 수 있습니다

배포 펌웨어 파일에서 이 열 묶음의 첫 워드는 유효 마커가 아닙니다. 그러나 업데이트는 이 구역을 건너뛰므로, 실제 카메라의 플래시에는 다른 내용이 남아 있을 수 있습니다. 이 연구는 배포 파일과 실물의 보존 데이터가 같다고 가정하지 않았습니다.

적재는 한 번만 일어나고, 첫 무효 묶음에서 순회가 끝납니다

  • 새 객체 — 보정 객체를 원본 생성자로 만들면 설명자는 모두 0입니다. 보정 함수는 처음 불릴 때 한 번 적재합니다.
  • 첫 무효에서 종료 — 0번과 2번 묶음만 유효하게 둔 사례에서, 보정 함수는 0번만 처리하고 끝났습니다. 2번의 레코드는 쓰이지 않았습니다.
  • 적재 캐시 — 객체의 초기화 바이트(+0x12)가 1이면 다시 적재하지 않습니다. 플래시 쪽을 무효로 바꾼 뒤 같은 객체로 다시 실행해도 처음 적재한 레코드로 보정했습니다.
  • 명시적 재적재 — 적재 함수를 직접 다시 부르면 RAM은 기본값으로 바뀌지만, 객체의 기존 설명자 필드는 그대로 남았습니다.

이 관측만으로 실제 촬영마다 객체를 새로 만든다거나, 무효 레코드를 안전하게 건너뛴다고 해석할 수는 없습니다.

레코드의 플래그가 이웃을 고르는 방법

순회 함수(0x73A5EC)는 6바이트 레코드에서 좌표와 플래그를 읽어 보정 핵심 함수(0x739F80)에 넘깁니다. 핵심 함수는 플래그의 비트로 이웃을 고릅니다.

  • 수준과 임계값 — 플래그의 위쪽 2비트에 1을 더한 값이 객체의 임계값보다 크면 그 레코드를 건너뜁니다. 플래그 0x4001은 임계값 1에서 건너뛰었고 임계값 2에서는 적용됐습니다.
  • 하위 묶음 우선 — 아래 8비트가 0이 아니면 그 비트만 씁니다. 0이면 비트 8~13을 씁니다. 플래그 0x0301은 비트 0의 이웃 하나만 읽어 200을 썼고, 0x0300은 4픽셀 떨어진 좌우 이웃 120과 401의 평균 260을 썼습니다.
  • 최대 두 개 — 고른 방향 가운데 앞의 두 이웃까지만 읽어 평균을 냅니다. 플래그 0x0007은 비트 0과 1의 이웃만 써서 300이 됐습니다.
  • 반환값 — 순회 함수가 돌려주는 값은 기록한 픽셀 수가 아니라 방문한 레코드 수입니다. 임계값이나 중심 좌표 때문에 기록을 건너뛴 사례에서도 1을 돌려주었습니다.
픽셀 보정 12회의 입력과 결과

레코드는 (x, y, 플래그)입니다. “적재”는 그 실행에서 적재 함수가 불린 횟수입니다. 기본 이미지는 0~255가 차례로 든 16×16 배열에 (6, 8) = 200, (10, 8) = 400, (8, 8) = 9999, (8, 12) = 600, (8, 10) = 8888을 넣은 것입니다. 9번만 (4, 8) = 120, (12, 8) = 401을 넣은 다른 이미지입니다.

중심 좌표는 검사하지만 이웃 좌표는 검사하지 않습니다

중심이 이미지 안에 있어도, 이웃 좌표를 더한 결과가 행 끝을 넘거나 음수가 되면 원본 코드는 그대로 계산한 주소를 읽습니다.

원본 0x739F44는 중심 좌표가 이미지 안에 있는지 검사합니다. x = 16 또는 y = 16인 중심은 거부했고, 읽기와 쓰기가 일어나지 않았습니다. 그러나 이웃 오프셋을 더한 뒤에는 좌표를 16비트로 자르는 명령(UXTH)만 있고, 계산된 주소는 범위 검사 없이 읽힙니다.

이 결과의 뜻과 한계

이 코드를 C로 다시 만들거나 다른 곳에 옮길 때, 중심 검사만으로 이웃 접근이 안전하다고 가정할 수 없습니다. 보정표의 좌표 제약과 버퍼의 여백을 확인하거나 이웃 접근을 따로 검사해야 합니다.

이미지 밖의 값도 같은 합성 RAM에 미리 넣어 둔 것입니다. 실제 센서 보정표의 레코드나 카메라의 메모리 배치를 재현한 실험이 아닙니다. 실제 카메라에 이런 좌표의 레코드가 있는지, 촬영 중 이 경로에 도달하는지는 확인하지 않았습니다.

촬영 패킷의 활성 바이트가 보정 실행을 정합니다

촬영 객체의 활성 바이트가 패킷으로 복사되고, 처리기는 그 바이트가 1일 때만 같은 이미지 포인터로 보정 함수를 부릅니다.

  1. 촬영 객체이미지 포인터 CAP+0x13C, 활성 바이트 CAP+0x49, 임계값 CAP+0x1646C를 시험값으로 준비
  2. 패킷 생산 구간0x65D650~0x65D6B4가 CAP+0xA3E8의 패킷에 값을 복사
  3. 이벤트 봉투ID 0x01180001, +8이 같은 패킷을 가리키도록 준비
  4. 처리기 구간0x58174C~0x581818이 프레임 크기와 임계값을 설정하고 활성 바이트를 검사
  5. 보정 호출활성 1이면 0x581814에서 순회 함수 호출, 0이면 건너뜀

원본 설정 함수 0x597AB4로 처리기와 보정 객체를 연결한 뒤, 같은 메모리 상태에서 패킷 생산 구간과 처리기 구간을 차례로 실행했습니다.

  • 활성 0 — 이미지 전체가 그대로였습니다. 그래도 원본 조회 함수가 프레임에서 크기(16×16)를, 패킷에서 임계값을 가져와 보정 객체에 넣는 부분은 실행됐습니다.
  • 활성 1 — 같은 이미지 포인터가 보정 객체의 +0xC에 들어갔고, 중심 값 두 개가 300과 450으로 바뀌었습니다.

패킷의 +8과 +9가 켜는 다른 보정은 두 값을 0으로 두어 건너뛰었습니다. 활성 바이트를 만드는 정책 함수는 픽셀 보정 활성값과 준비 분기에서 다루며, 정책 → 패킷 → 보정을 이어 실행한 결과도 그 문서에 있습니다.

시험 조건

촬영 객체의 플래그, 프레임, 이벤트 봉투는 입력으로 준비했습니다. 처리기의 기본 생성자와 작업 스케줄러는 실행하지 않았습니다. 보정 실행에서는 시간 조회 함수 0x785F70만 0을 돌려주게 바꿨습니다. 따라서 이 결과는 두 원본 구간 사이의 포인터와 분기 연결을 보여 줄 뿐, 실제 센서 입력이나 촬영 모드에서의 도달을 보여 주지 않습니다. 메뉴와 버퍼 수명은 Pixel Shift 메뉴와 버퍼 수명에서 따로 다룹니다.

저장 함수는 섹터마다 RAM 묶음 두 개를 넣어 기록을 요청합니다

적재가 한 번 일어난 뒤 저장 함수를 실행하면, 섹터 14에 이어 15~19 다섯 섹터의 기록 요청이 플래시 백엔드 입구에 도달합니다.

  1. 저장 함수 0x6E8528관리자의 +0x2CA가 1일 때 섹터 15~19 묶음을 처리. 이 바이트는 적재 함수가 1로 만듦
  2. 섹터 읽기 0x599D18대상 섹터 128KiB를 임시 영역 0x40459204로 복사
  3. 덮어 넣기 0x599E88등록 객체의 RAM 묶음 두 개(64KiB씩)를 섹터 안의 자리에 복사
  4. 백엔드 입구 0x599914목적지와 길이 0x10000(16비트 단위)를 기록하고 시험용 상태값으로 복귀

섹터 15~19의 임시 영역은 등록된 RAM 묶음 두 개를 이어 붙인 128KiB와 바이트 단위로 같았습니다. 이 실험에서는 픽셀 등록 객체 10개만 등록했으므로, 섹터 14는 원래 내용이 그대로 전달됐습니다. 섹터 14 자체의 저장은 보존 섹터 14의 진단 레코드에서 다룹니다.

한계와 남은 과제

  • 실물 데이터 — 플래시 내용과 이미지는 모두 합성 입력입니다. 배포 펌웨어 파일과 실제 카메라에 남아 있는 보존 데이터가 같다고 가정하지 않았습니다.
  • 레코드의 출처 — 누가 언제 이 레코드를 만드는지, 사용자 메뉴의 Pixel Mapping과 관계가 있는지는 확인하지 않았습니다.
  • 도달 경로 — 시작 코드 전체, 작업 스케줄러, 실제 촬영 모드에서 이 보정에 도달하는 이력은 실행하지 않았습니다. 준비한 소유자 객체와 싱글턴 가드로 전체 시작 과정을 건너뛰었습니다.
  • 이웃 경계 — 좌표 경계 사례는 원본의 주소 계산을 보여 줄 뿐입니다. 실제 보정표에 그런 좌표가 들어갈 수 있는지는 알 수 없습니다.
  • 물리 기록 — 저장은 백엔드 입구까지입니다. 플래시에 실제로 쓰이는지, 전원이 꺼진 뒤 유지되는지는 확인하지 않았습니다.
