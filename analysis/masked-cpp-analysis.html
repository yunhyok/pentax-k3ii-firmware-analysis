마스크 경로의 활성 조건은 일부 남아 있다.

보조 스케일러의 두 출력과 JPEG의 보조 입력을 연결할 수 있는 메모리 배치 조건을 확인했다. 그러나 확인한 두 초기화 경로는 보조 스케일러를 끈다. 실제 작업에서 이를 켜고 같은 메모리를 공유하게 만드는 경로는 아직 확정하지 못했다. 별도로 RAW 현상의 Color Fringe Correction 메뉴와 두 번째 CPP 패스의 조건을 연결했다.

코드 위치는 해제 이미지의 파일 오프셋이다. 코드 VA는 오프셋 + 0x02000000이며 job+…와 payload+…는 객체 내부 오프셋이다. 원본 ARM 명령을 합성 상태에서 구간별로 실행했다. 아래의 주소 일치는 픽셀 내용이나 실기 실행을 증명하지 않는다.

1. 보조 스케일러를 켜는 생산자는 아직 찾지 못했다

스케일러 payload는 job+0xA7B4에 있다. 생성자 호출 0x653B74 → 0x71B0B0은 활성 바이트 payload+0x38에 0을 쓴다. 설정 함수의 0x659FAC → 0x71B090도 0을 전달한다. 두 지점 모두 먼저 바이트를 0xA5로 채운 뒤 원본 코드를 실행해 0으로 덮어쓰는 것을 확인했다. 생산자·호출·실행 근거

주 이미지 16 MiB를 4바이트 경계로 검색했다. setter 0x71B090을 직접 분기 대상으로 삼는 곳은 0x659FAC 하나였다. setter의 VA와 같은 정렬된 워드는 없다. MOVW의 payload·gate 오프셋 후보와 STRB [Rn,#0x38] 후보 177개도 기록했다. 계산한 포인터를 통한 쓰기, 메모리 복사, 간접 실행, 다른 명령어 형식은 이 검색으로 배제할 수 없다. 따라서 “항상 비활성인 코드”라는 결론은 내리지 않는다. 검색 범위와 단언

2. JPEG 보조 입력과의 연결은 앞선 메모리 배치에 달려 있다

앞선 분석은 JPEG의 주 입력 +0x21B0/+0x21CC를 확인했다. 이번에는 모듈 16이 +0x21E8과 +0x2204도 읽는 것을 확인했다. 설정 함수는 이 디스크립터들을 JPEG payload의 +8/+0xC에 넣는다. 실제 수신 경로의 0x576FE8과 0x577044는 각각 압축 함수에 넘긴다. 첫 보조 입력의 허용값은 1이고 두 번째는 job+0x65 == 0일 때 1이다. JPEG 설정·수신 실행 사례

레이아웃 생성자 0x6609AC에서 job+0x20B2 == 1인 분기는 별도 디스크립터를 구성하고 일반 디스크립터의 평면 주소는 그대로 둔다. 일반 스케일러 설정도 job+0x178…0x18C의 기존 일반 주소를 다시 JPEG 보조 디스크립터에 쓴다. 세 가지 이력을 원본 코드로 실행한 결과는 다음과 같다. 세 레이아웃의 실제 주소

합성 레이아웃 이력세 쌍의 평면 주소JPEG가 읽은 값
새 작업에서 마스크 레이아웃만 구성모두 불일치초기 0으로 둔 일반 주소가 그대로 남음
일반 → 마스크, 같은 시작 주소·치수·패딩모두 일치보조 스케일러 출력과 같은 주소
일반 → 마스크, 앞선 시작 주소가 다름모두 불일치앞선 일반 주소 유지; job+0x65=1이면 둘째 호출 생략

보조 처리의 진행 메시지 0x020C0001은 0x6DBEE0으로 이어진다. 일반 완료 메시지 0x020C0002는 모듈 2 완료 처리로 들어가 +0x21E8/+0x2204의 치수를 바꾸지만 평면 포인터를 복사하지 않는다. 따라서 완료 메시지만으로 두 주소 집합이 연결되지는 않는다. 이 결과는 “실제 작업이 같은 배치를 재사용하는가”를 후속 검증 대상으로 좁힌다.

3. 마스크의 생산 조건과 작업 종류를 분리했다

준비 함수 0x6552B0는 내부 작업 종류를 job+0x2084에 저장한다. 종류 5는 +0x2080=1, 7·8은 +0x2080/+0x2081=1, 11은 +0x2080/+0x2082=1로 만든다. 실제 DevelopmentRawImage의 0x52A8B4는 종류 5를 전달하며, 원본 가상 함수표를 거쳐 준비 함수에 진입하는 것도 실행했다. 이 숫자들을 P·Av·M 같은 노출 모드명으로 해석하지 않는다. 작업 종류 0–11 검증

마스크 생산자 0x65FEA8의 우선순위는 아래와 같다. +0x20B2는 이 문서에서 작업의 배치 구분값으로 부른다. enum은 job+0x34가 가리키는 객체의 +0x300에서 읽으며 사용자 메뉴명은 미확정이다.

선행 조건배치 구분값마스크 +0x20B4
+0x2082 == 1무관0x40
위 조건 아님00x01
+0x2080 != 01 / 그 밖의 비영 값0x04 / 0x02
+0x2080 == 0, enum=31 / 그 밖의 비영 값0x40 / 0x20
+0x2080 == 0, enum≠31 / 그 밖의 비영 값0x04 / 0x02

이 생산자 안에서는 mask & 0x44 != 0이 되는 조건이 job+0x2082 == 1 또는 job+0x20B2 == 1이다. RAW 현상 경로의 0x52A048…0x52A080은 네 작업에 구분값 1·2·3·4를 쓴다. 앞선 코드에서 설정 태그 0x98 != 0이고 내부 억제값 stack+0x20 == 0이면 추가 작업 셋을 할당하고 확장 플래그 stack+0x28=1을 만든다. 원본 분기·할당 호출·구분값 기록·종류 5의 마스크 생산자를 이어 실행하면 첫 작업은 마스크 4, 나머지 세 작업은 마스크 2를 만든다. 할당기는 합성 작업 주소를 반환하도록 대체했다. 입력 종류 0·1·2가 억제값을 켜는 코드도 확인했지만, 이 입력 종류와 태그의 촬영 메뉴 의미는 미확정이다. 네 작업 구분값·마스크 검사

별도의 0x7B55AC 경로는 전역 설정 API에서 ID 0x98을 읽어 1이면 SuperResolution DevMode 진단 분기로 들어간다. 그 안의 0x7B5720이 작업 종류 11을 전달하며, 가상 함수표를 거친 준비 함수 진입을 원본 코드로 실행했다. 이 진단 분기에서 종류 11을 선택한다는 점은 확인됐다. 이 전역 설정과 RAW 작업의 태그 저장소는 별도 API이므로 숫자가 같다는 이유로 동일 객체나 동일 메뉴 이벤트라고 단정하지 않는다. 진단 문자열·분기·실제 종류 11 호출

4. 두 번째 CPP 패스는 RAW 현상의 Color Fringe Correction과 연결된다

위젯 ID 0x032900EB의 리소스 행 0x9D1904에서 영어 문자열 Color Fringe Correction을 복원했다. 화면 갱신 함수는 이 위젯과 screen+0x4B5의 설정값을 함께 사용한다. 같은 바이트를 다섯 번째 항목 토글 함수가 바꾼다. 적용 경로가 설정 객체의 +0x8C9에 전달한다. 문자열, 표시 값, 수정 값, 적용 값을 연결한 결과다. 리소스 포인터·토글·설정 전달 근거

두 토글 방향과 초기값 0·1의 조합 4건, 선택값과 세 가드 조건의 조합 16건을 실행했다. 설정 enum 조회·태그 쓰기·작업 종류 5의 패스 생산자는 원본 코드로 실행했다. 0x619960/0x619934 두 질의의 반환값만 주입했다. 가드의 실제 기기 상태와 사용자 의미는 아직 확인하지 않았다. RAW 현상 안에도 stack+0x20 != 0일 때 태그를 0으로 지우는 0x52A7F4 경로가 있다.

리코 공식 안내도 이 기능을 RAW 현상의 렌즈 보정 항목으로 설명하고 일반 촬영 시의 설정과 구분한다. 따라서 현재 확인한 실제 사용자 기능은 RAW 현상 보정이다. 특정 노출 모드에서 촬영 직후 마스크 경로가 실행된다는 뜻은 아니다. Ricoh K-3 II FAQ의 Color Fringe Correction 안내

5. 모듈 20 출력은 마스크 전환 뒤 CPP 입력이 된다

모듈 20의 설정은 마스크 0x04일 때 연결 작업 네 개의 +0x204를, 0x40일 때는 +0x13C를 소스로 읽는다. 목적지는 현재 작업의 +0x1F8/+0x1FC/+0x200이다. 원본 할당 함수의 슬롯 15로 이 목적지를 구성하고 슬롯 16으로 연결 작업의 +0x204도 구성해 주소 전달을 확인했다. 두 마스크의 할당·소스·목적지 실행

완료 후에는 mask & 0x44가 0이 되고 CPP가 세 평면 입력을 고르는 조건인 mask & 0x88이 참이 된다. 이 변화는 마스크 값이 고정된 촬영 모드 식별자가 아니라 처리 상태로도 쓰인다는 근거다. 이전 CPP·합성의 어느 시점에 해당 완료가 배치되는지와 실제 픽셀의 유효성은 전체 레시피에서 추가로 확인해야 한다.

6. 검증 방법과 재현 자료

7. 남은 도달 조건

남은 핵심은 보조 스케일러를 켜는 비영 값의 생산자와 실제 작업에서 일반·마스크 레이아웃이 같은 평면을 재사용하는 이력이다. JPEG 보조 입력의 소비자는 찾았지만 실제 작업에서 이 두 조건이 성립하는지는 확인하지 못했다. SuperResolution 작업 종류 11의 실제 사용자 메뉴, 태그 0x98의 촬영 측 생산자, 모듈 17의 선행 기능 검사와 비동기 작업의 전체 순서도 추가 추적 대상이다.

실제 RAW 픽셀·JPEG 생성·Exif·SD까지의 연속 실행, DMA 전송과 캐시 일관성은 확인하지 않았다. 정확한 SoC·보조 MCU 부품번호도 미확정 상태를 유지한다.
