영상 처리와 저장 경로 · 마스크 분기와 RAW 현상 조건

마스크 CPP 분기의 버퍼 연결과 그 분기에 들어가는 조건

색 처리 결과가 평소와 다른 버퍼로 가는 분기가 있습니다. 그 버퍼가 JPEG 압축기까지 이어지는지, 어떤 작업과 메뉴가 이 분기를 여는지 조사했습니다.

이 문서에서

  1. 배경: 마스크 분기란 무엇인가
  2. 보조 스케일러를 켜는 값은 확인한 경로에서 0입니다
  3. JPEG 보조 입력과 주소가 같아지는지는 버퍼 배치 이력에 달려 있습니다
  4. 작업 종류와 배치 구분값이 마스크 분기를 정합니다
  5. Color Fringe Correction 메뉴는 두 번째 CPP 패스를 켭니다
  6. 모듈 20이 끝나면 마스크 값이 바뀌고 다음 CPP 입력이 정해집니다
  7. 한계와 남은 과제
  8. 재현 방법
  9. 근거 파일과 참고 자료

핵심 요약

  • 마스크 분기의 출력을 받는 보조 스케일러와, JPEG 모듈이 읽는 보조 입력 두 개를 찾았습니다. 둘은 서로 다른 디스크립터입니다. 평면 주소는 버퍼를 같은 조건으로 연달아 배치한 시험에서만 일치했습니다.
  • 보조 스케일러는 활성 바이트가 0이면 실행되지 않습니다. 확인한 초기화 경로 두 곳은 모두 0을 씁니다. 0이 아닌 값을 쓰는 코드는 찾지 못했습니다.
  • 어떤 작업이 마스크 분기에 들어가는지는 작업 종류와 배치 구분값이 정합니다. RAW 현상에서 작업이 넷으로 늘어나면 첫 작업만 들어가고, Pixel Shift용 작업 종류는 항상 들어갑니다.
  • RAW 현상 메뉴의 Color Fringe Correction 값은 설정 태그 하나를 거쳐 CPP의 두 번째 패스를 켭니다. 마스크 분기와는 별개의 조건입니다.
  • 모듈 20이 끝나면 마스크 값이 바뀌고, 그 뒤의 CPP는 모듈 20의 출력을 입력으로 읽습니다.

확인 원본 코드 실행으로 확인

  • 생성자와 설정 함수가 활성 바이트를 0으로 덮어씀
  • 버퍼 배치 이력 3건의 평면 주소 비교
  • 작업 종류 12개, 마스크 24건, 완료 전환 7건
  • 메뉴 토글 4건, 조건부 내보내기 16건, RAW 작업 확장 3건

정적 분석 코드를 읽어 확인

  • 주 이미지 16 MiB에서 활성값 설정 함수를 부르는 곳 검색
  • 메뉴 문자열 리소스 복원
  • 작업 종류 7·8을 넘기는 호출 지점

모델 시험 조건으로 넣은 값

  • 활성 바이트 1
  • 버퍼 시작 주소, 치수, 배치 순서
  • 가드 질의 두 개의 답, 작업 할당기의 반환 주소

미확인 확인하지 않은 것

  • 0이 아닌 활성값을 쓰는 코드
  • 실제 작업에서 두 배치가 같은 평면을 쓰는지
  • 가드 조건과 입력 종류가 사용자에게 뜻하는 것

배경: 마스크 분기란 무엇인가

색 처리 모듈 CPP는 결과를 쓸 평면 주소를 고를 때 작업의 마스크 바이트(job+0x20B4)를 봅니다. 이 값에 0x44 비트가 없으면 기본 평면에 씁니다. 있으면 별도의 디스크립터 묶음에 씁니다. 이 문서에서는 뒤의 경우를 마스크 분기라고 부릅니다.

백엔드 B와 두 번째 CPP 출력 문서는 기본 분기에서 CPP → 합성 모듈 17 → 스케일러 → JPEG로 이어지는 주소 관계를 확인했습니다. 마스크 분기는 디스크립터가 달라서 같은 결론을 쓸 수 없습니다. 그래서 질문이 셋 남습니다.

  1. 마스크 쪽 버퍼는 JPEG 모듈까지 이어지는가
  2. 어떤 작업이 마스크 분기에 들어가는가
  3. 사용자가 고르는 어떤 메뉴가 관련되는가

주소 읽는 법

코드 위치는 복호화한 이미지의 파일 오프셋입니다. 실행 주소(VA)는 여기에 0x02000000을 더한 값입니다. job+…와 payload+…는 객체 안의 위치입니다. 원본 코드를 구간별로 실행해 주소를 비교했으며, 주소가 같다는 결과가 픽셀 내용이나 카메라에서의 실행을 증명하지는 않습니다.

보조 스케일러를 켜는 값은 확인한 경로에서 0입니다

보조 스케일러는 스케일러 payload의 활성 바이트가 0이면 건너뜁니다. 이 바이트를 쓰는 곳으로 확인한 생성자와 설정 함수는 모두 0을 씁니다. 1을 넣어 주었을 때에만 보조 스케일러가 두 번 호출됐습니다.

스케일러 payload는 작업의 job+0xA7B4에 있습니다. 두 쓰는 경로 모두, 먼저 활성 바이트를 0xA5로 채워 둔 뒤 원본 코드를 실행해 0으로 덮어쓰는 것을 확인했습니다. 읽는 쪽에서는 스케일러 진입점에서 호출 인수를 기록하고 장치 처리는 대체했습니다. 실제 크기 변환은 실행하지 않았습니다.

이미지 전체에서 쓰는 곳을 찾아본 범위

주 이미지 16 MiB를 4바이트 단위로 훑어 활성 바이트를 쓸 만한 곳을 찾았습니다.

JPEG 보조 입력과 주소가 같아지는지는 버퍼 배치 이력에 달려 있습니다

JPEG 모듈은 주 입력 말고 보조 입력 두 개도 읽습니다. 이 입력과 보조 스케일러의 출력은 서로 다른 디스크립터입니다. 일반 배치를 먼저 만들고 같은 시작 주소·치수로 마스크 배치를 이어 만든 시험에서만 평면 주소가 일치했습니다.

“= ?”는 주소가 같을 수 있다는 표시이며 복사 명령이 아닙니다. 디스크립터의 +4, +8, +0xC에 든 세 평면 주소를 짝마다 비교했습니다. 앞 단계의 합성 결과가 실제로 이 메모리에 기록됐는지는 확인하지 않았습니다.

JPEG 모듈이 보조 입력을 읽는 방식

JPEG의 주 입력은 job+0x21B0과 job+0x21CC입니다. 모듈 16은 여기에 더해 job+0x21E8과 job+0x2204도 읽습니다. 설정 함수가 이 두 디스크립터를 JPEG payload의 +8과 +0xC에 넣고, 수신 경로의 0x576FE8과 0x577044가 각각 압축 함수에 넘깁니다. 첫째 보조 입력은 항상 허용되고, 둘째는 job+0x65가 0일 때만 허용됩니다.

배치 이력 세 가지를 실행한 결과

평면 주소는 배치 생성 함수 0x6609AC가 정합니다. 배치 구분값 job+0x20B2가 1이면 이 함수는 마스크 측 디스크립터를 만들고 일반 측 평면 주소는 건드리지 않습니다. 일반 스케일러 설정은 job+0x178부터 job+0x18C까지의 기존 일반 주소를 JPEG 보조 디스크립터에 다시 씁니다.

완료 메시지도 두 주소 묶음을 잇지 않습니다. 보조 처리의 진행 메시지 0x020C0001은 컨트롤러의 0x6DBEE0으로 갑니다. 일반 완료 메시지 0x020C0002는 모듈 2 완료 처리로 들어가 job+0x21E8과 job+0x2204의 치수를 바꾸지만 평면 포인터는 복사하지 않습니다.

작업 종류와 배치 구분값이 마스크 분기를 정합니다

마스크 값을 만드는 함수는 작업 종류에서 나온 플래그 세 개, 배치 구분값, 촬영 쪽 enum 하나를 봅니다. 마스크 분기에 들어가는 값(0x04, 0x40)은 작업 종류가 11이거나 배치 구분값이 1일 때에만 나옵니다.

작업 종류가 플래그 세 개를 정합니다

준비 함수 0x6552B0는 넘겨받은 내부 작업 종류를 job+0x2084에 저장하고 플래그 세 개를 정합니다. 종류 0부터 11까지를 모두 실행했습니다. 이 숫자는 P·Av·M 같은 노출 모드 번호가 아닙니다.

종류 5와 11은 호출 지점에서 출발해 원본 가상 함수표를 거쳐 준비 함수에 들어가는 것까지 실행했습니다. 두 진단 문자열 분기는 같은 함수 안에 있습니다. 전역 설정 0x98이 1이면 SuperResolution 쪽으로, 아니면 Normal 쪽으로 갑니다. 이 설정은 촬영 메뉴의 Pixel Shift Resolution이 쓰는 값이며, 두 분기를 디스패처부터 실행한 결과는 메뉴 연결에 있습니다.

마스크 값을 정하는 순서

종류 0·5·7·11, 구분값 0·1·2, enum 0·3을 조합한 24건을 가로챈 함수 없이 실행해 이 순서를 확인했습니다. enum은 job+0x34가 가리키는 객체의 +0x300에서 읽습니다. 이 값이 어떤 메뉴에 해당하는지는 정해지지 않았습니다. job+0x20B2는 이 문서에서 배치 구분값이라고 부릅니다.

RAW 현상에서 네 작업에 구분값이 매겨지는 과정

배치 구분값을 쓰는 코드는 RAW 현상 경로에 있습니다. 작업의 설정 태그 0x98이 0이 아니고 내부 억제값(stack+0x20)이 0이면, 작업 세 개를 더 할당하고 확장 플래그(stack+0x28)를 1로 만듭니다. 이어서 0x52A048부터 0x52A080까지의 코드가 네 작업에 구분값 1, 2, 3, 4를 씁니다.

입력 종류가 0, 1, 2이면 억제값을 켜는 코드가 있습니다. 실행한 사례는 종류 0과 3입니다. 이 입력 종류가 무엇을 뜻하는지는 확인하지 못했습니다.

RAW 작업의 태그 0x98은 RAW 파일의 MakerNote 0x0243에서 가져옵니다. 첫 바이트가 1이면 1이 되고, ExifTool은 이 바이트를 PixelShiftResolution(0 = Off, 1 = On)으로 풉니다. 촬영 메뉴가 쓰는 전역 설정 0x98과는 번호만 같고 저장소가 다릅니다(두 저장소의 구분). 따라서 위 과정은 Pixel Shift로 기록한 RAW를 현상할 때 작업이 넷으로 늘어나는 경로로 읽을 수 있습니다. 네 작업이 네 장의 노출에 하나씩 대응하는지는 확인하지 않았습니다.

RAW 현상 코드 말고 촬영 쪽에도 구분값을 쓰는 곳이 있습니다. 버퍼 수명 문서에서 다룹니다.

Color Fringe Correction 메뉴는 두 번째 CPP 패스를 켭니다

RAW 현상 화면의 Color Fringe Correction 선택값은 설정 객체를 거쳐 태그 0x245로 나가고, 작업 종류가 5이고 이 태그가 1일 때 CPP가 한 번 더 실행됩니다. 마스크 분기나 보조 스케일러를 켜는 조건은 아닙니다.

  1. RAW 현상 메뉴Color Fringe Correction 항목. 화면의 +0x4B5가 0과 1 사이에서 바뀜
  2. 적용0x5E7CDC → 0x61A898. 설정 객체의 +0x8C9에 선택값 저장
  3. 조건부 내보내기세 조건이 모두 맞으면 태그 0x245에 선택값 기록
  4. 두 번째 패스 결정0x65FAE0. 작업 종류 5이고 태그가 1이면 job+0x59와 +0x8D에 1

job+0x59가 1이면 CPP가 한 번 더 실행됩니다. 그 출력이 모듈 17의 합성 입력이 되는 과정은 앞 문서에 있습니다.

메뉴 이름을 확인한 근거

위젯 ID 0x032900EB의 리소스 행 0x9D1904에서 영어 문자열 Color Fringe Correction을 복원했습니다. 화면을 다시 그리는 함수는 이 위젯과 화면의 +0x4B5 값을 함께 씁니다. 같은 바이트를 다섯 번째 항목의 토글 함수가 바꾸고, 적용 경로가 설정 객체의 +0x8C9로 옮깁니다. 문자열, 표시 값, 바꾸는 코드, 적용하는 코드를 이은 결과입니다.

선택값과 세 조건을 조합한 16건 가운데 태그가 1이 된 것은 “선택값 1, 세 조건 모두 성립” 한 건뿐이었습니다. 토글 방향 둘과 초깃값 0·1을 조합한 4건에서는 값이 매번 뒤집혔고, 적용 뒤 설정 객체에 같은 값이 들어갔습니다. 두 질의 함수가 기기의 어떤 상태를 묻는지는 확인하지 않았습니다. RAW 현상 코드에는 억제값(stack+0x20)이 0이 아닐 때 이 태그를 0으로 지우는 경로(0x52A7F4)도 있습니다.

작업 종류 12개와 태그 값 0·1·2를 조합한 36건에서 두 번째 패스가 켜진 것은 종류 5, 태그 1뿐이었습니다.

제조사 설명과의 대조

리코의 공식 FAQ는 Color Fringe Correction을 RAW 현상의 렌즈 보정에서 설정한다고 안내합니다. 사용 설명서도 촬영 메뉴의 렌즈 보정에는 네 항목만 싣고, RAW 현상에서는 Color Fringe Correction도 설정할 수 있다고 적습니다. 그래서 현재 확인한 사용자 기능은 RAW 현상의 보정입니다. 특정 노출 모드로 촬영한 직후에 마스크 분기가 실행된다는 뜻이 아닙니다.

모듈 20이 끝나면 마스크 값이 바뀌고 다음 CPP 입력이 정해집니다

모듈 20은 연결된 작업 네 개에서 소스 주소를 하나씩 읽고, 현재 작업의 세 주소에 출력합니다. 완료 처리는 마스크 0x04를 0x08로, 0x40을 0x80으로 바꿉니다. 그 뒤 CPP는 모듈 20의 목적지를 입력으로 읽습니다.

설정, 완료 처리, 그 뒤의 입력 선택을 순서대로 실행한 합성 사례입니다. 목적지는 원본 할당 함수의 슬롯 15로, 연결 작업의 +0x204는 슬롯 16으로 구성해 주소 전달을 확인했습니다. 모듈 20의 픽셀 연산과 비동기로 도는 레시피 전체는 실행하지 않았습니다.

모듈 20 완료 처리가 바꾸는 마스크 값 (7건)

완료 뒤에는 mask & 0x44가 0이 되고, CPP가 세 평면 입력을 고르는 조건인 mask & 0x88이 참이 됩니다. 입력 선택 코드는 0x65962C부터 0x659678 앞까지입니다. 마스크 값은 고정된 촬영 모드 번호가 아니라 처리 단계에 따라 바뀌는 상태로도 쓰인다는 뜻입니다.

두 경로를 합치지 않습니다

이 절의 경로는 “모듈 20의 출력이 다음 CPP의 입력이 된다”는 것입니다. 앞 절의 “마스크 CPP 출력이 보조 스케일러를 거쳐 JPEG로 간다”는 경로와는 다릅니다. 마스크 분기의 출력 job+0x2354를 모듈 20이 읽는지는 확인하지 못했습니다. 레시피 안에서 이 완료가 CPP·합성보다 앞에 오는지는 레시피별 순서에서 다룹니다.

한계와 남은 과제

보조 스케일러의 0이 아닌 활성값

  • 활성 바이트를 쓰는 곳으로 확인한 두 경로는 0을 씁니다. 스케일러 설정을 통째로 실행한 64건에서도 0이었습니다.
  • 정렬된 A32 명령만 검색했습니다. 계산한 포인터 쓰기, 메모리 복사, 간접 호출, 동시에 도는 다른 작업은 배제하지 못했습니다.
  • JPEG 보조 입력을 읽는 코드는 찾았습니다. 그러나 실제 작업에서 “보조 스케일러가 켜지고, 두 배치가 같은 평면을 쓴다”는 두 조건이 함께 성립하는지는 확인하지 못했습니다.

그 밖에 남은 것

  • Color Fringe Correction 내보내기의 두 질의 함수와 설정 enum 0x20이 뜻하는 기기 상태
  • 마스크 생산 함수가 읽는 enum(+0x300)의 메뉴 이름, RAW 현상의 입력 종류 0·1·2의 뜻
  • 모듈 17 앞단의 기능 검사, 비동기 작업의 전체 순서
  • RAW 픽셀 처리, JPEG 생성, Exif에서 SD까지의 연속 실행, DMA 전송과 캐시 일관성. SoC와 보조 MCU의 정확한 부품 번호

작업 종류 11을 고르는 사용자 메뉴와 태그 0x98의 출처는 Pixel Shift 메뉴와 버퍼 수명 문서에서 확인했습니다.
