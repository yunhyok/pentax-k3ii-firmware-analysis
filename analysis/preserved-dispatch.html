촬영 준비와 보존 레코드 · 상위 명령

보존 레코드를 고치는 상위 명령: 작업 계획, 개수 갱신, ID 0x63 패킷

보존 레코드의 검사 바이트를 다시 계산하게 만드는 호출과, 레코드를 블록 단위로 읽고 쓰는 호출이 어디서 시작되는지 명령 처리기에서부터 따라갔습니다. 실제로 실행한 곳과 값을 준비해 넣은 곳, 건너뛴 곳을 나눠 적었습니다.

이 문서에서

  1. 배경: 누가 레코드를 고치라고 시키는가
  2. 유형 2·하위 코드 4 명령이 작업 계획을 만듭니다
  3. 작업자의 결과가 개수를 바꾸고 갱신 함수가 검사 바이트를 다시 계산합니다
  4. 패킷 처리기는 공급자를 고른 뒤 명령 버퍼를 블록 함수로 넘깁니다
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 명령 처리기는 특정 유형의 명령을 받으면 입력 첫 워드에 따라 작업 계획을 만듭니다. 계획은 “어느 디스크립터 쌍을 다룰지”를 적은 요청 목록이고 그 포인터 목록이 작업자에게 복사됩니다. 입력 일곱 가지에서 확인했습니다.
  • 작업자가 낸 결과에 따라 개수를 바꾸는 함수가 불리고 명령 처리기는 대기에서 돌아온 뒤 갱신 함수를 불러 검사 바이트를 다시 계산합니다. 계산과 대기 자체는 실행하지 않았고 그 결과와 반환값을 준비해 넣었습니다.
  • 갱신 함수를 부르는 호출자는 둘입니다. 하나는 대기 반환값과 무관하게 부르고 다른 하나는 완료 표시 열 개가 정확히 모두 켜졌을 때만 부릅니다.
  • 별도의 패킷 처리기는 공급자를 고른 뒤 명령 버퍼를 ID 0x63의 블록 읽기·쓰기 함수로 넘깁니다. 공급자 선택이 틀리면 거부합니다. 이 시험은 처리기 안의 상태 검사 구간을 건너뛰고 실행했습니다.
  • 명령 객체는 합성 입력입니다. 명령이 실제로 통신이나 메뉴에서 오는지는 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 명령 분기와 작업 계획 7건, 다른 하위 코드의 거부 1건
  • 포인터 목록의 복사, 작업자의 플래그 검사와 요청 조회
  • 결과에 따른 개수·길이 함수 호출과 갱신 3건, 인덱스 경계 1건, 완료 마스크 3건
  • 패킷 왕복 6쌍, 잘못된 공급자 선택의 거부 4건

배경: 누가 레코드를 고치라고 시키는가

정책 플래그의 생산자는 디스크립터의 개수를 바꾸고 갱신 함수를 부르면 검사 바이트가 다시 계산된다는 것을 보였습니다. 섹터 20·21 문서는 ID 0x63 레코드를 블록 단위로 읽고 쓰는 패킷 함수를 보였습니다. 두 문서 모두 그 함수들에 인수를 직접 넣었습니다. 이 문서는 한 단계 위로 올라가, 펌웨어 안에서 그 함수들을 부르는 명령 처리기를 봅니다.

명령 객체
명령 하나를 담는 버퍼입니다. +0x858에 유형, +0x859에 하위 코드가 있고 입력 워드는 +8부터, 응답은 +4와 +8에 기록됩니다.
작업 계획 · 요청
명령 처리기가 스택에 만드는 요청 목록입니다. 요청 하나는 디스크립터 인덱스 한 쌍과 요청 종류를 담습니다.
작업자
요청 목록을 받아 처리하는 객체입니다. 명령 처리기는 목록을 넘긴 뒤 작업자의 처리를 기다리고 작업자는 계산 결과를 자기 스택의 결과 구조에 둡니다.
설정 객체 · 디스크립터
앞 문서에서 설명한, 검사 바이트 +0xC·+0xD와 인덱스 0~25의 디스크립터를 가진 객체입니다.
읽는 법

코드 주소는 복호화한 펌웨어 파일 안의 오프셋으로, RAM 주소는 실행 주소(VA)로 적었습니다. 명령 객체는 합성 입력입니다. 실제 통신으로 명령이 도착하거나 카메라 메뉴에서 이벤트가 일어나는 과정을 재현한 것이 아닙니다.

유형 2·하위 코드 4 명령이 작업 계획을 만듭니다

명령 처리기는 입력 첫 워드(0~4)에 따라 다룰 디스크립터 인덱스 쌍을 정하고 요청을 스택에 만든 뒤 그 포인터 목록을 작업자에게 복사합니다.

계획에 나오는 인덱스는 0~17과 24, 25입니다. 검사 바이트를 만드는 두 그룹의 인덱스와 같은 집합입니다. 입력 0은 그룹 1(인덱스 0~5)을, 입력 1~4는 그룹 2를 다룹니다.

명령 처리기는 명령 객체에서 유형과 하위 코드를 읽습니다. 유형 2, 하위 코드 4이면 계획 함수로 들어갑니다. 계획 함수는 촬영 서비스에서 설정 객체를 조회해 스택에 보관해 두고 입력 첫 워드로 계획을 고릅니다. 하위 코드 7을 넣은 대조에서는 0x81을 반환했고 작업 목록을 넘기지 않았습니다.

요청이 작업자에게 넘어가는 방식

요청 자체는 계획 함수의 스택에 그대로 남습니다. 작업자에게 복사되는 것은 요청을 가리키는 포인터 목록(0x40바이트)입니다. 각 포인터가 실제로 스택의 요청 주소를 가리키는지 확인했습니다.

작업자는 자기 플래그의 비트 하나가 켜져 있을 때만 목록을 처리합니다. 잠금 뒤의 원본 구간에 값 2를 주면 플래그에 그 비트가 더해졌고 비트가 없는 대조에서는 작업자가 목록 처리를 건너뛰었습니다.

작업자의 스택과, 잠금 이후 플래그 저장 구간의 레지스터는 준비한 값입니다. 실제 스케줄링·깨우기·대기는 실행하지 않았습니다.

작업자의 결과가 개수를 바꾸고 갱신 함수가 검사 바이트를 다시 계산합니다

결과의 첫 바이트가 0이면 개수는 그대로 두고 길이만 갱신합니다. 0이 아니면 개수와 길이를 모두 갱신합니다. 그 뒤 갱신 함수를 부르는 조건은 호출자마다 다릅니다.

작업자는 요청의 두 인덱스 워드를 8비트로 줄이고 촬영 서비스에서 같은 설정 객체를 조회합니다. 여기까지 원본 코드로 실행했습니다. 계산 함수는 실행하지 않고 원본이 결과를 읽는 스택 위치에 값을 직접 넣은 뒤 그다음 호출자 코드를 실행했습니다.

인덱스 범위 밖의 요청

계획 함수가 만들지 않는 요청을 따로 넣어 보았습니다. 인덱스 워드 0x101과 26을 주면 작업자는 이를 1과 26으로 줄였습니다. 개수 함수는 인덱스가 26보다 작을 때만 저장하므로 인덱스 26의 저장은 일어나지 않았고 설정 객체에서 바뀐 것은 인덱스 1의 개수뿐이었습니다. 이 요청은 앞의 계획이 만든 값이 아니라 경계 동작을 보려고 넣은 값입니다.

패킷 처리기는 공급자를 고른 뒤 명령 버퍼를 블록 함수로 넘깁니다

공급자 선택과 블록 번호는 따로 다뤄집니다. 선택이 틀리면 상태 0x83으로 거부됩니다. 블록 번호는 명령 버퍼에 실린 채 ID 0x63의 패킷 함수까지 전달됩니다.

정정

이 문서의 이전 판은 건너뛴 구간을 패킷 “잠금”이라고 적었습니다. 그 표기는 철회했습니다. 이 구간은 잠금이 아니라 상태 사본을 만들고 그 필드를 검사하는 코드입니다. 바깥 조건은 필드 2가 2 또는 3인지, 쓰기 안쪽 조건은 필드 0이 1인지를 봅니다. 시험에서는 이 구간을 실행하지 않았으므로, 그 판정이 어떻게 나오는지는 말할 수 없습니다.

쓰기 호출자는 명령 +0xC를, 읽기 호출자는 +8을 패킷 인수로 넘깁니다. 읽기 함수는 패킷 인수의 +4에서 블록 번호를 얻기 때문에 두 배치가 다릅니다.

왕복 시험과 거부 시험

직접 선택(하위 코드 6·7)과 변환 선택(10·11) 각각에서 블록 0·1·31을 써 넣고 다시 읽었습니다. 여섯 쌍 모두에서 레코드 전체와 이웃 RAM, 명령의 응답과 그 뒤에 남은 바이트를 대조했습니다. 돌려준 워드 수는 블록 0·1·31에서 513·512·508이었습니다.

잘못된 직접 선택 0x66과 변환 입력 16은 쓰기·읽기 모두 정지점에서 상태 레지스터가 0x83이었고 ID 0x63의 함수에는 닿지 않았습니다. 이것은 공급자 선택에 대한 검사입니다. 블록 번호에 대한 검사가 아닙니다.

블록 번호 32에 대해

하위 코드 10, 변환 입력 3에 블록 번호 32를 주면, 위의 생략 구간을 지난 경로에서 첫 저장 예정 주소가 0x80010010이 됐습니다. 이 주소는 ID 0x63 구역 밖입니다(블록 배치). 실행은 저장 명령 직전에 멈췄고 RAM은 바뀌지 않았습니다. 이 결과는 준비한 명령 객체와, 상태 검사를 건너뛴 조건에서의 주소 계산만 보여 줍니다. 실제 통신 입력으로 그 상태에 이를 수 있는지, 장치에 취약성이 있는지는 확인하지 않았습니다.

한계와 남은 과제

실행 중 다른 코드로 바꾼 명령은 없습니다. 다만 시험마다 시작 상태를 준비했고 건너뛴 구간이 있습니다.

  • 명령의 출처: 명령 객체를 실제로 만드는 쪽(통신 수신, 메뉴 이벤트)은 추적하지 않았습니다. 이 명령의 선택값을 SuperResolution이나 일반 촬영 메뉴의 값과 같다고 보지 않습니다.
  • 계산과 대기 — 잠금, 스케줄러, 계산의 완료는 실행하지 않았습니다. 계산 결과와 대기 반환값은 준비한 값입니다.
  • 연결의 범위: 계획과 작업자, 갱신을 이어 본 것은 계획 0의 첫 요청 하나입니다. 일곱 입력의 계획 내용은 각각 따로 확인했습니다.
  • 패킷 처리기의 상태 검사 — 건너뛴 구간의 실제 판정과, 그 판정이 블록 번호 32 같은 입력을 막는지는 모릅니다.
  • 기록 — 원격 전달과 물리 플래시 기록은 실행하지 않았습니다.

설정 객체의 검사 바이트가 만들어지는 과정은 정책 플래그의 생산자에서, RAM 적재와 저장 준비는 보존 섹터 20·21과 정책 입력에서 따로 확인했습니다.
