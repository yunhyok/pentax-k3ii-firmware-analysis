JPEG 완료값과
저장 레코드의 연결

촬영 객체에 내장된 여섯 레코드가 저장 이벤트와 StoreImage 요청에 다시 쓰이는 경로를 확인했다. 별도 연결 실험에서는 원본 완료 코드가 만든 JPEG 길이까지 같은 객체에서 추적했다. 큐 전달과 호출자 프레임은 준비했으며, 실제 압축·파일 쓰기는 실행하지 않았다.

촬영 준비레코드 재사용저장 요청JPEG 완료 연결검증 범위

코드 주소는 해제 파일 오프셋이다. CAP은 합성 촬영 객체, StoreImage는 펌웨어의 저장 작업 이름이다. 버퍼 주소는 실제 이미지가 없는 시험값이며 압축 데이터의 내용은 검증하지 않았다.

1. 같은 여섯 레코드에 주소와 길이를 다시 쓴다

원본 포인터 등록 명령으로 만든 CAP+0xC2C4…0xC2D8은 CAP+0xA860, 0xAC5C, 0xB058, 0xB454, 0xB850, 0xBC4C를 가리킨다. 준비 코드의 초기화 뒤 모듈 9를 실행하면 선택한 계열의 두 레코드에 같은 주소로 다시 진입한다. 계열 세 개를 함께 켠 조건 한 건과 각 계열의 인덱스 0·1을 따로 켠 여섯 건에서 확인했다. 7개 레코드 전달 대조

각 레코드의 하위 서술자는 +0x4, +0x50, +0x9C, +0xE8에 있다. 서술자 안의 +0x34가 주소, +0x28이 길이다. 값이 있는 서술자는 원본 0x8598E0·0x832FB0 저장 명령으로 채워지며 0으로 초기화하는 저장은 0x5AA3B0 → 0x859888에서도 실행된다. 서로 다른 주소와 길이를 넣고 여섯 레코드의 네 서술자를 모두 대조했다. 요청한 계열은 두 인덱스 모두 생성하지만 소비 가능 표시는 CAP+0x207C/0x207D와 계열 플래그의 조합에 따른다. 생산자·필드 대조 코드

2. 이벤트 payload에서 요청 슬롯까지 별칭이 유지된다

원본 0x656984는 모듈 9에서 CAP+0xA850을 반환한다. 송신 코드가 만든 이벤트의 +0x8은 이 컨테이너, +0x10은 같은 CAP을 가리킨다. 원본 수신 선택자에 같은 이벤트를 공급하면 가용한 레코드의 주소가 반환된다. 세 계열을 함께 켠 대조에서는 첫 계열의 인덱스 0이 선택됐다. 각 계열만 켠 대조에서는 준비한 인덱스 0 또는 1이 선택됐다. 이벤트 필드·선택 결과

원본 호출자 0x5A88AC, 0x5A8BE4, 0x5A91E0에서 각각 레코드를 다시 선택해 0x5A820C로 넘겼다. StoreImage+0x82에는 인덱스, +0x83에는 시험한 세 계열에 따라 0·1·3이 기록됐다. 요청 슬롯 2의 주소와 길이는 생산자가 쓴 값과 같았다. 정지점은 0x5A8340이며 이후 요청 검증과 쓰기 서비스 0x5A7D5C는 실행하지 않았다. 호출자별 요청 대조

3. JPEG 완료 길이를 생산하는 코드까지 연결했다

별도 연결 실험은 CAP+0x2EC/+0x2F0을 대조값으로 채운 뒤 원본 완료 코드가 덮어쓰게 했다. 0x660808의 주소 생산 구간과 모듈 16의 출력 서술자 구성을 먼저 실행하고 원본 장치 설정 코드가 해당 주소를 0x200E2050에 쓰는 것도 확인했다. 수신 생성자의 일부와 대기 이후 등록 명령을 실행해 콜백 포인터를 연결했다. 완료 코드는 합성 RAM의 카운터를 읽고 0x6FE97C → 가상 슬롯 +0x8 → 0x576044 → 0x576008을 연속 실행해 수신 길이를 기록했다. 깨우기 직전 0x576030에서 멈춘 뒤 별도 서술자 저장·완료 분기를 실행하고 같은 CAP으로 모듈 9와 StoreImage 요청을 만들었다. 주소 생산·완료 저장·요청 연결

4. 연결된 범위와 남은 실행 경계

이번 결과는 동일한 합성 촬영 객체에서 주소와 길이의 생산·전달을 확인한 것이다. 기존 준비 함수의 버퍼 보존과 JPEG·Exif 출력 분석 사이에 내장 레코드와 요청 별칭의 근거를 추가했다. 실제 촬영 모드에서 이 조건이 반복되는 이력, 보조 스케일러의 픽셀 출력, JPEG 비트스트림, 파일시스템·SD의 실행까지 한 번에 입증한 것은 아니다.
