촬영 준비와 보존 레코드 · 저장 레코드

JPEG 완료 길이가 저장 레코드를 거쳐 StoreImage 요청에 닿는 경로

압축이 끝난 데이터를 파일로 쓰려면, 버퍼의 주소와 길이가 저장 작업까지 정확히 전달되어야 합니다. 촬영 객체 안의 레코드 여섯 개가 이 전달에 어떻게 쓰이는지, JPEG 완료 코드가 만든 길이가 저장 요청에 같은 값으로 닿는지 확인했습니다.

이 문서에서

  1. 배경: 저장 작업에 넘겨야 하는 것
  2. 생성부터 저장 준비까지 같은 여섯 레코드를 다시 씁니다
  3. 저장 이벤트에서 요청 슬롯까지 같은 레코드 주소가 유지됩니다
  4. JPEG 완료 코드가 만든 길이가 같은 객체의 저장 요청까지 이어집니다
  5. 한계와 남은 과제
  6. 재현 방법
  7. 근거 파일과 참고 자료

핵심 요약

  • 촬영 객체에는 레코드 여섯 개가 내장되어 있습니다. 생성, 준비 함수의 초기화, 저장 준비가 모두 같은 주소의 레코드를 다시 씁니다. 일곱 조건으로 확인했습니다.
  • 저장 준비 코드가 보내는 이벤트는 이 레코드들의 묶음을 가리킵니다. 받는 쪽은 레코드 하나를 고르고, 요청 객체의 네 슬롯에 그 레코드 안의 주소 네 개를 등록합니다. 슬롯 2가 주 버퍼의 주소와 길이를 담습니다.
  • 별도의 두 사례에서, JPEG 완료 코드가 장치 카운터에서 읽은 길이가 원본 저장 명령들을 거쳐 같은 촬영 객체의 저장 요청 슬롯 2까지 같은 값으로 전달됐습니다.
  • 장치 카운터는 시험용으로 넣은 값입니다. 큐 전달과 호출자 상태는 준비했고, 실제 압축·파일 쓰기·SD 기록은 실행하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 내장 레코드 생성 앞부분, 포인터 등록, 초기화
  • 세 계열의 레코드 생산과 요청 슬롯 등록: 7개 조건
  • JPEG 출력 주소·완료 길이의 전달: 2개 사례
  • 완료 조건 3건, 길이 경계 3건, 취소 1건

모델 시험 조건으로 정한 것

  • 촬영 객체, 레시피, 가용 플래그, 버퍼 주소값
  • 장치 카운터와 상태, RAM으로 만든 장치 레지스터
  • StoreImage 이벤트 전달, 호출자 스택과 레지스터

미확인 확인하지 않은 것

  • 전체 생성자, 작업 스케줄러, 깨우기·대기
  • 실물 인코더와 압축 데이터의 내용
  • 요청 검증, 쓰기 서비스, SD 기록

배경: 저장 작업에 넘겨야 하는 것

이 펌웨어에서 파일 저장을 맡는 작업의 이름은 StoreImage입니다. StoreImage가 일을 하려면 “어느 버퍼의 몇 바이트를 쓸지”를 알아야 합니다. 이 정보는 촬영 객체 안의 레코드에 담겨 전달됩니다.

  • 내장 레코드 — 촬영 객체의 CAP+0xA850 컨테이너 안에 0x3FC(1,020)바이트짜리 레코드 여섯 개가 연달아 놓여 있습니다. 촬영 준비 함수가 끝날 때 두 필드를 0으로 초기화하는 바로 그 레코드입니다.
  • 서술자 — 레코드마다 버퍼를 가리키는 작은 구조(서술자)가 네 개 있습니다. 서술자 안의 +0x34가 주소, +0x28이 길이입니다.
  • 모듈 — 촬영 객체의 일은 번호가 붙은 모듈 단위로 불립니다. 이 문서에는 저장 레코드를 채우고 이벤트를 보내는 모듈 9와, JPEG 출력 서술자를 다루는 모듈 16이 나옵니다.

이 문서의 결과는 준비 함수의 버퍼 보존과 JPEG 출력 버퍼 분석 사이를 잇습니다.

표기 규칙

코드 주소는 복호화한 펌웨어 파일 안의 위치(파일 오프셋)입니다. 실행 주소는 여기에 0x02000000을 더한 값입니다. CAP은 합성한 촬영 객체의 시작 주소입니다. 버퍼 주소는 실제 이미지가 없는 시험값이며, 버퍼의 내용은 읽지 않았습니다.

생성부터 저장 준비까지 같은 여섯 레코드를 다시 씁니다

레코드 여섯 개는 세 계열로 나뉘고, 계열마다 다른 함수가 주 서술자에 주소와 길이를 채웁니다.

원본 포인터 등록 명령으로 만든 CAP+0xC2C4~+0xC2D8의 여섯 포인터는 CAP+0xA860, +0xAC5C, +0xB058, +0xB454, +0xB850, +0xBC4C를 가리킵니다. 준비 함수의 초기화 구간을 실행한 뒤 모듈 9(0x65C174)를 실행하면, 켜 둔 계열의 두 레코드에 같은 주소로 다시 들어갑니다. 이때 불리는 0x5AA3B0에도 같은 레코드 포인터가 전달됐습니다.

시험 조건

레코드 생성은 전체 생성자 대신 원본 호출 0x653BAC에서 0x5AA3DC 안의 배열 생성까지의 앞부분만 실행했습니다. 촬영 준비 함수의 반환 실험과 이 저장 경로 실험은 서로 다른 실행이며, 촬영 전체를 이어서 실행한 결과가 아닙니다.

저장 이벤트에서 요청 슬롯까지 같은 레코드 주소가 유지됩니다

모듈 9가 만든 이벤트는 레코드 컨테이너를 가리키고, 받는 쪽은 그 안에서 고른 레코드의 내부 주소 네 개를 요청 객체에 그대로 등록합니다.

  • 송신 — 원본 0x656984는 모듈 9에서 컨테이너 CAP+0xA850을 돌려줍니다. 송신 코드가 만든 이벤트의 +0x8은 이 컨테이너를, +0x10은 같은 촬영 객체를 가리킵니다. 큐에 넣는 0x6FEA38 진입 직전에 멈췄습니다.
  • 수신 — 같은 이벤트를 원본 수신 선택 코드에 넘기면 쓸 수 있는 레코드의 주소가 돌아옵니다. 세 계열을 함께 켠 조건에서는 첫째 계열의 인덱스 0이 선택됐고, 한 계열만 켠 조건에서는 준비한 인덱스 0 또는 1이 선택됐습니다.
  • 요청 — 원본 호출자 세 곳(0x5A88AC, 0x5A8BE4, 0x5A91E0)이 각각 레코드를 다시 골라 0x5A820C에 넘겼습니다. StoreImage 객체의 +0x82에는 인덱스가, +0x83에는 세 계열에 따라 0·1·3이 기록됐습니다. 요청 슬롯 2에서 읽은 주소와 길이는 생산 함수가 쓴 값과 같았습니다.

JPEG 완료 코드가 만든 길이가 같은 객체의 저장 요청까지 이어집니다

완료 코드가 장치 카운터에서 읽은 길이는 콜백, 출력 서술자, 촬영 객체의 길이 필드를 차례로 거쳐 저장 요청 슬롯 2에 같은 값으로 도착했습니다.

JPEG 쪽의 콜백 전달(0x6FE97C)은 호출한 자리에서 바로 수신 함수를 부르는 동기 방식입니다. StoreImage가 쓰는 큐(0x6FEA38)와는 다른 경로입니다.

실행 순서

  1. 대조값 채우기 CAP+0x2EC와 +0x2F0을 대조값으로 채워, 뒤에서 원본 코드가 덮어쓰는지 볼 수 있게 했습니다.
  2. 출력 주소 생산 주소 생산 구간(0x660808)과 모듈 16의 출력 서술자 구성을 실행했습니다. 원본 장치 설정 코드가 이 주소를 장치 레지스터 0x200E2050에 쓰는 것도 확인했습니다.
  3. 콜백 연결 수신 객체 생성자의 일부와, 대기 뒤에 실행되는 등록 명령을 실행해 콜백 포인터를 연결했습니다.
  4. 완료 코드 완료 코드가 합성 RAM의 카운터를 읽고 0x6FE97C → 가상 함수 칸 +0x8 → 0x576044 → 0x576008을 이어 실행해 수신 객체에 길이를 기록했습니다. 깨우기 직전 0x576030에서 멈췄습니다.
  5. 길이 저장과 완료 분기 출력 서술자에 길이를 저장하는 구간과 완료 분기(0x6DBA14 → 0x65DC34)를 따로 실행했습니다. 완료 명령 값 0x03000002는 레지스터에 준비해 넣었습니다.
  6. 저장 요청 같은 촬영 객체로 모듈 9와 StoreImage 요청 구성을 실행하고, 요청 슬롯 2의 주소와 길이를 원본 getter로 읽었습니다.

출력 주소를 장치에 설정하는 구간은 평면 주소 세 개와 출력 주소를 16바이트 단위로 내림해 0x200E2028, 0x200E202C, 0x200E2030, 0x200E2050에 썼습니다. 첫째 출력에서는 0x12000000, 0x13000000, 0x14000000, 0x11000010이었고, 분리 조건의 둘째 출력에서는 0x12001000, 0x13001000, 0x14001000, 0x11002010이었습니다.

콜백 인수는 차례로 (0x6FE97C, 코덱 객체 +0x14), (0x576044, 수신 객체 +4), (0x576008, 수신 객체)였고, 세 곳 모두 이벤트 0x02060001과 카운터 값을 받았습니다. 촬영 객체의 길이 필드는 0x65E178의 명령이 +0x2EC와 +0x2F0에 쓰고, 공유 조건에서는 0x65E1A0이 +0x2F0에 첫 길이를 한 번 더 썼습니다. 출력 용량은 CAP+0x2E4 = 0x2000, +0x2E8 = 0x1000으로 두었습니다.

연결한 범위와 남은 경계

이 결과는 하나의 합성 촬영 객체 안에서 주소와 길이가 생산되고 전달되는 것을 확인한 것입니다. 실제 촬영 모드에서 이 조건이 되풀이되는 이력, 보조 스케일러의 픽셀 출력, JPEG 비트스트림, 파일시스템과 SD까지를 한 번에 실행한 것이 아닙니다.

구분범위
확인 원본 실행내장 레코드 생성 앞부분·포인터 등록·초기화, 세 계열의 생산, 저장 이벤트 송수신의 일부, 요청 슬롯 등록, JPEG 출력 주소와 완료 길이의 제한된 구간
모델 준비한 상태촬영 객체·레시피·가용 플래그, 장치 카운터와 상태, RAM으로 만든 장치 레지스터, 대기 뒤 콜백 등록의 인수, StoreImage 이벤트 전달, 호출자 스택과 레지스터
실행 대체없음. 관찰 훅은 진입·인수·읽기·쓰기를 기록만 함
미확인 실행하지 않은 범위전체 생성자, 작업 스케줄러, 동기화, 실물 인코더와 센서, StoreImage의 요청 검증·쓰기 서비스, SD 기록

저장 요청 이후의 파일시스템과 SD 쪽은 파일시스템에서 SD·DMA까지에서 다룹니다.
