R5의 상위 입력과 0 분모의 소비자 경계

입력 소유권구성 서비스0 소비자검증과 한계

원본 생성자·가상 호출·ROM 표

R5의 입력을 job+0x334에 내장된 객체의 바이트까지 추적했습니다. 상위 생성자 접두 구간은 job+0x30C에서 시작해 +0x28 위치에 원본 가상 함수 표 02A77CAC를 설치합니다. 표의 +8 함수 6EB180은 ROM 기술자 표를 읽습니다. selector 5는 job+0x349, selector 6은 job+0x34A의 바이트를 반환합니다. 원본 생성자가 두 위치에 쓰는 값은 각각 0과 32입니다. 이 값이 현재 촬영 설정으로 유지되는지는 확인하지 않았습니다.

selector 6의 결과는 하위 8비트 인덱스가 되어 ROM 029E651C의 워드를 고릅니다. job+0x52가 0이 아니면 8을 뺀 뒤 다시 8비트로 자릅니다. 생성자 출력 32를 사용한 재현에서는 R5가 8192였습니다. 원본 setter로 시험값 40을 저장하면 16384가 됩니다. 같은 값에서 job+0x52 시험값을 1로 바꾸면 인덱스가 32가 되어 8192가 됩니다. 선택 분기의 selector 5는 ROM 표 029DDFB4를 거쳐 추가 정수 연산에 쓰입니다. 이 분기에는 직접 진입했으며 실제 촬영의 분기 도달 조건은 실행하지 않았습니다.

입력 바이트를 갱신하는 정적 경로도 찾았습니다. owner+0x21C의 포인터에서 +0x30C를 계산한 수신 객체가 82E490에 전달됩니다. 이 함수는 전역 객체 4047B754의 +0x14가 가리키는 관리자를 참조합니다. 관리자가 선택한 버퍼의 payload 48바이트를 job+0x338에 복사합니다. 가상 함수 표 워드는 복사 대상에 포함되지 않습니다. 선택 상태와 원본 버퍼의 실제 내용·갱신 순서는 아직 미확정입니다. 앞선 owner+0x220 경로와 같은 작업이라고 합치지 않았습니다.

실선도 분리 진입 사이의 값 관계입니다. 점선의 복사·파일 경로는 정적 추적입니다. 주소는 16진수 파일 오프셋이며 VA = 0x02000000 + 오프셋입니다. 4047B754·4045859C는 RAM 주소입니다.

근거: 원본 구간 실행 코드 · 정적 원본 43개 구간의 주소·해시. 원본 ROM 워드 조회(65EF80)에는 이 문서의 120워드 관찰 구간을 보장하는 인덱스 검사 근거가 없습니다. 재현의 index<120 조건은 하네스 범위 제한입니다.

job+0x52는 모든 조건에서 시험 입력입니다. 0은 모델 RAM의 초기값이며 1은 호스트가 쓴 바이트입니다. 내장 객체 생성자가 이 바이트를 만들지는 않습니다. 이 표의 최종 R5는 구성0x42 확인에 진입하기 직전 값입니다. 실제 구성 서비스는 실행하지 않았습니다. 생성자 접두 구간은 82DEF8에서 멈추며 전체 생성자 반환을 뜻하지 않습니다. 65EF50의 조건부 R8 쓰기는 앞선 구성 서비스 비교를 실행하지 않은 상태이고 이 R5 재현에서 쓰이지 않습니다.

관리자 선택식은 관리자+0x18 상태 워드의 bit15가 0이면 그 워드 전체를 인덱스로 쓰고, bit15가 1이면 1 & ~state를 씁니다. 모든 상태를 항상 1비트로 자른다는 뜻이 아닙니다. 관리자+0x1C가 0일 때에는 그 +0x1C에 선택 인덱스 | 0x8000을 잠시 기록하고 복사한 뒤 같은 +0x1C를 0으로 씁니다. 상태 범위와 실제 버퍼 내용은 실행으로 확인하지 않았습니다. 정적 연결은 82E4D4 → 70D180 → 78591C → 6EAEBC이며, 719AE8 → 7129D0이 payload를 복사합니다.

구성 서비스 0x42의 생산자

구성 서비스 0x42의 덮어쓰기는 별도 전역 객체 4045859C에 속합니다. 객체의 +4 바이트가 0이면 서비스는 0을 반환합니다. +4가 0이 아니면 +0x71 바이트를 읽습니다. 이 값도 0이 아니어야 +0x74 워드를 읽어 R5를 덮어씁니다. 정적 추적에서 두 필드의 생산자는 C:\SYSPARAM.TXT의 STILL_SVD_GAIN 항목을 읽는 경로였습니다. 첫 토큰은 0이 아닌 값을 1로 바꿔 +0x71에 쓰고, 두 번째 토큰은 워드로 +0x74에 씁니다. 파일 읽기·토큰 변환·서비스 성공은 실행하거나 가정하지 않았습니다.

원본 생성자의 +4=0·+71=0·+74=8192와 파일 파싱 후 상태는 구분해야 합니다. 별도 정적 초기화 가드 RAM VA 404099F0는 객체 4045859C의 +4와 다른 위치입니다. 파서가 성공했다는 사실만으로 특정 키가 존재했다고 판단할 수도 없습니다.

근거: 구성 서비스 원본 30개 구간의 주소·해시. 706B30의 ID 0x42 분기는 706EA4에서 +0x71 바이트를 읽고 707120에서 반환합니다. 705A58의 키 비교 뒤 70671C에 진입하여 70672C에서 +0x71, 706738에서 +0x74에 씁니다. 토큰 변환은 base10을 지정하지만 TLS와 오류 슬롯을 거치므로 실행하지 않았습니다. 해당 구성 파일이나 카메라에 쓰지 않았습니다.

0 저장 이후 실제 소비자 명령

별도 시험에서는 원본 생성자와 산술·setter를 실행해 같은 VM의 recipe+0x9C에 0을 쓴 뒤 원본 소비자 4DF834를 실행했습니다. 소비자는 이 워드의 하위 16비트를 문맥 +0x60DC에 쓰고 최종 나눗셈의 분모로 사용했습니다. 67108864를 0으로 나누는 호출은 Thumb 처리기 2E0486의 첫 명령 앞에 도달했습니다. 그 전에 네 보조 반워드는 저장됐지만 문맥 +0x7A74의 결과 저장은 실행되지 않았습니다. 처리기 본문과 반환 결과는 미확정입니다.

대조 조건에서는 recipe+0x9C=1일 때 원본 소비자가 문맥 정수 67108864를 저장했습니다. recipe+0xA4를 원본 setter로 1로 설정한 조건에서는 recipe+0x9C=0이어도 기존 문맥 값을 유지해 32765를 저장했습니다. 이 제어값은 시험 인자입니다. 7개 상위 입력 조건과 4개 소비자 조건은 별도 시험에서 얻은 결과입니다. 실제 촬영을 연속 실행하지 않았으며 물리 단위·Q 형식·감마·메뉴 도달·버퍼 재사용 이력을 입증하지 않습니다.

각 나눗셈의 분자·분모·LR과 원본 쓰기 순서는 전체 관측 JSON에 기록했습니다. 0 조건의 최종 호출 LR의 VA는 024DF9D4입니다. 처리기 첫 명령은 실행하지 않았으므로 예외 처리 방식이나 후속 복구를 확정하지 않습니다.

검증과 남은 경계

원본 명령은 RX 메모리에서 실행하며 매 명령 바이트와 허용 구간·쓰기 대상을 검사합니다. 입력 전체 해시와 실행 후 RX 이미지 보존도 확인합니다. 생성자 대량 쓰기는 순서를 반영한 해시와 건수로 남겼습니다. 후속 쓰기와 나눗셈 인자는 개별 기록으로 남겼습니다.

공개 JSON은 328,341바이트입니다. 상위 입력 7건과 0 소비자 4건을 보존했습니다. 기존 스키마·원본 연구 코드 해시·158개 허용 구간·제한 문구까지 II31 전체 관측에 포함했습니다. 공개용 정보를 붙이기 전에 타입을 구분하는 전체 관측 해시와 기존 JSON 직렬화 해시를 모두 검사합니다. 누락한 필드나 정수와 불리언의 교체도 허용하지 않습니다.

0 소비자 시험은 65EF08..65F008, 65F0D8..65F150, 65F160..65F188 구간을 생략하며 각 분리 진입마다 LR을 하네스 반환점으로 다시 설정합니다. 산술·수신자 계산·setter에서는 원본 프레임 SP를 유지합니다. 같은 VM에서 소비자에 별도로 진입할 때는 SP를 하네스 기준값으로 재설정합니다. 실제 촬영의 연속 실행은 아닙니다. 이 네 시험에 별도로 공급한 R5=0/1을 앞선 상위 입력 7건에서 생성한 비영 R5와 이어 붙이지 않았습니다.

관측 내부의 probe_sha256은 II31 원본 연구 코드의 해시입니다. 새 공개 보조 코드의 해시는 별도 public_source_sha256에 기록합니다. 두 코드가 같은 파일인 것처럼 표시하지 않습니다. 실행 부분의 생성자·setter·가상 호출·소비자는 원본 연구 코드와 AST가 같습니다.

정적 분석 자료는 43개 상위 입력 구간과 30개 구성 서비스 구간의 주소·길이·해시로 공개합니다. 원본 펌웨어 바이트나 역어셈블리 덤프는 포함하지 않습니다. 실행 전에 사용자가 제공한 정확한 decoded 입력으로 범위 목록의 각 해시를 확인합니다.

남은 경계는 관리자의 선택 버퍼 값과 갱신자, owner+21C 작업의 호출 순서, 구성 파일의 실제 내용·로드 성공, R5 입력의 촬영 도달성, 0 처리기 본문입니다. 기존 owner+220 및 보조 스케일러 경로와의 실행 이력은 연결하지 않았습니다. 버퍼 재사용과 SuperResolution의 실제 메뉴 도달도 이 재현으로 확정할 수 없습니다. 메뉴·버퍼 수명 분석과 이전 정수 생산자 분석의 시험 경계를 유지합니다.

재현 방법

검증 환경은 Python 3.12.3과 Unicorn 2.1.4입니다. 저장소 루트에서 별도로 준비한 decoded 파일을 지정하고 출력에는 새 경로를 사용하십시오. 출력 부모 디렉터리는 미리 존재해야 합니다. 아래 입력 경로는 예시입니다.

python -B verify_tone_upstream.py /path/to/decoded.bin --output tone-upstream-new.json --compare analysis/tone-upstream.json
python -B -O verify_tone_upstream.py /path/to/decoded.bin --output tone-upstream-opt-new.json --compare analysis/tone-upstream.json
python -B -m unittest discover -s tests -p test_tone_upstream.py

후보가 별도 디렉터리에 있을 때만 --repository로 기존 검증기와 보조 소스가 있는 저장소를 지정합니다. 통합한 공개 배치에서는 생략합니다. 출력은 새 경로에만 만들며 기존 파일·하드링크·심볼릭 링크를 덮어쓰지 않습니다. 비교가 실패하면 출력 파일을 만들지 않습니다. 비교 입력은 일반 파일만 허용하고 직렬화한 결과 크기의 네 배까지만 읽습니다. 타입을 구분하는 비교는 그대로 유지합니다.
