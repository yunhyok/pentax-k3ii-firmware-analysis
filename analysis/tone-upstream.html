톤 입력 R5의 출처와 0 분모에서 멈추는 지점

톤 곡선 계산에 들어가는 정수 하나는 R5라는 값에서 만들어집니다. R5가 어떤 원본 코드와 표에서 나오는지, 그리고 그 정수에 0이 들어가면 뒤쪽 계산이 어디까지 진행되는지 확인했습니다.

이 문서에서

  1. 배경: 톤 정수와 R5
  2. R5는 내장 객체의 바이트와 ROM 표에서 나옵니다
  3. 구성 서비스는 두 필드가 모두 0이 아닐 때만 R5를 덮어씁니다
  4. 0이 저장되면 마지막 나눗셈의 분모가 0이 됩니다
  5. 검증 방법
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • R5의 입력을 작업 객체 안에 내장된 작은 객체의 바이트 두 개(selector 5와 6)까지 따라갔습니다. 원본 생성자는 두 바이트에 0과 32를 씁니다. selector 6은 ROM 표에서 R5를 고르는 인덱스가 됩니다.
  • 생성자·setter·가상 함수·ROM 표 조회를 원본 코드로 나누어 실행한 7개 조건에서 R5는 512부터 22000까지 나왔습니다. 생성자 값 그대로는 8192입니다. 이 값이 실제 촬영 설정으로 남는지는 확인하지 않았습니다.
  • 별도의 구성 서비스가 R5를 덮어쓸 수 있습니다. 그 값은 설정 파일 C:\SYSPARAM.TXT의 STILL_SVD_GAIN 항목에서 온다는 것을 코드를 읽어 추적했습니다. 파일 읽기와 서비스는 실행하지 않았습니다.
  • R5 자리에 0을 넣으면 톤 정수에 0이 저장되고 소비자 함수의 마지막 나눗셈 분모가 0이 됩니다. 실행은 0 나눗셈 처리기의 첫 명령 앞에서 멈췄고 결과는 저장되지 않았습니다. 처리기가 무엇을 하는지, 카메라가 어떻게 동작하는지는 이 결과로 알 수 없습니다.
  • 모두 PC 에뮬레이터에서 원본 코드 구간을 따로따로 실행한 결과입니다. 촬영 전체, 서비스, 메뉴 경로는 실행하지 않았고 값의 물리적 의미도 정해지지 않았습니다.

확인 원본 코드 실행으로 확인

  • 생성자 출력, setter, selector getter, ROM 표 조회, 추가 계수로 이어지는 R5 계산 7개 조건
  • 0 저장 뒤 소비자가 하위 16비트를 문맥에 쓰고 최종 분모로 쓰는 것
  • 분모 0에서 Thumb 처리기 첫 명령 앞 도달, 결과 저장 없음
  • 분모 1과 기존값 유지 조건에서 소비자가 정상 반환

정적 분석 코드를 읽어 판단

  • 관리자가 고른 48바이트 레코드가 내장 객체로 복사되는 경로
  • 구성 서비스가 R5를 덮어쓰는 조건과 설정 파일 파서
  • 상위 입력 구간 43개, 구성 서비스 구간 30개의 주소·해시

모델 시험 조건으로 정한 것

  • setter 인자 40·68·84·256과 job+0x52 바이트
  • 소비자 시험에 넣은 R5 = 0·1과 기존값 유지 제어값 1
  • 선택 경로에는 직접 진입했고 실제 도달 조건은 정하지 않음

미확인 확인하지 않은 것

  • 생성자 값이 실제 촬영에서 유지되는지, 관리자 레코드의 실제 내용
  • 설정 파일의 실제 내용과 로드 성공 여부
  • 0 처리기 본문과 반환, 카메라 동작
  • 물리 단위, Q 형식, 감마, 메뉴 도달, 버퍼 재사용

배경: 톤 정수와 R5

K-3 II의 톤 곡선 생산자는 입력 정수 몇 개를 받아 곡선을 만듭니다. 그중 하나가 레시피(recipe)의 +0x9C 워드입니다. 이 워드를 만드는 원본 코드는 recipe+9C 정수 생산자 문서에서 재현했습니다. 그 생산자가 받는 입력 레지스터가 R5입니다.

이 문서는 그 R5의 위쪽을 봅니다. R5가 어떤 객체의 어떤 바이트에서 시작하는지, 누가 그 바이트를 쓰는지, 그리고 0이 들어가면 아래쪽 소비자가 어떻게 되는지를 다룹니다.

job
사진 한 장의 처리를 담는 작업 객체입니다. 시험에서는 0x10100000에 배치했습니다.
내장 객체
job 안의 +0x334에 들어 있는 작은 객체입니다. 첫 워드에 가상 함수 표 주소가 있습니다.
selector
설정 항목 번호입니다. 원본 setter와 getter는 번호마다 ROM의 기술자(오프셋·마스크·시프트)를 읽어 객체의 정해진 바이트를 쓰거나 읽습니다.
ROM 표
펌웨어 이미지 안에 고정된 워드 배열입니다. 인덱스로 값을 고릅니다.
주소 표기

명령 주소는 복호화한 이미지의 16진수 파일 오프셋입니다. 실행 주소(VA)는 여기에 0x02000000을 더한 값입니다. 4047B754, 4045859C 같은 RAM 주소는 처음부터 VA입니다.

R5는 내장 객체의 바이트와 ROM 표에서 나옵니다

selector 6 바이트가 ROM 표의 인덱스가 되어 R5를 고르고 selector 5 바이트는 선택 경로에서 추가 계수를 고릅니다.

그림의 실선은 따로 실행한 원본 구간 사이에서 값이 이어지는 관계입니다. 전체 촬영을 연속으로 실행했다는 뜻은 아닙니다. 파선은 코드를 읽어서만 연결한 경로입니다.

원본 생성자는 job의 +0x30C에서 시작하는 상위 객체를 만들면서 그 +0x28, 곧 job+0x334에 가상 함수 표를 설치합니다. 표의 +8 함수는 ROM 기술자 표를 읽습니다. 그래서 selector 5는 job+0x349, selector 6은 job+0x34A의 바이트를 돌려줍니다. 생성자가 두 자리에 쓰는 값은 0과 32입니다.

selector 6의 값은 하위 8비트 인덱스가 되어 ROM 표의 워드를 고릅니다. job+0x52가 0이 아니면 8을 뺀 뒤 다시 8비트로 자릅니다. 선택 경로에서는 selector 5가 다른 ROM 표를 거쳐 추가 계수가 됩니다. 이 선택 경로에는 직접 진입했으며 실제 촬영에서 그 분기에 닿는 조건은 실행하지 않았습니다.

job+0x52는 모든 조건에서 시험 입력입니다. 0은 새 RAM의 초기값이고 1은 하네스가 쓴 바이트입니다. 내장 객체 생성자가 이 바이트를 만들지는 않습니다. 표의 최종 R5는 구성 서비스 확인에 들어가기 직전 값이며 구성 서비스는 실행하지 않았습니다.

입력 바이트를 갱신하는 정적 경로

내장 객체의 바이트를 다시 쓰는 경로도 코드에서 찾았습니다. owner+0x21C의 포인터에서 +0x30C를 계산한 수신 객체가 82E490에 전달됩니다. 이 함수는 전역 객체 4047B754의 +0x14가 가리키는 관리자를 참조합니다. 관리자가 고른 버퍼의 48바이트 payload가 [job+0x338, job+0x368)에 복사됩니다. 가상 함수 표 워드는 복사 대상이 아닙니다.

관리자가 버퍼를 고르는 규칙은 상태 워드(관리자 +0x18)의 bit15로 갈립니다. bit15가 0이면 워드 전체를 인덱스로 쓰고 1이면 1 & ~state를 씁니다. 관리자와 이 레코드는 톤 설정 관리자 문서에서 자세히 다룹니다. 선택 상태, 원본 버퍼의 실제 내용, 갱신 순서는 아직 정해지지 않았습니다. 다른 문서의 owner+0x220 경로와 같은 작업이라고 합치지도 않았습니다.

구성 서비스는 두 필드가 모두 0이 아닐 때만 R5를 덮어씁니다

구성 서비스 0x42의 덮어쓰기 값은 별도 전역 객체에 있습니다. 그 필드는 설정 파일 파서가 채웁니다. 이 경로는 코드를 읽어서만 확인했습니다.

  1. +4 바이트 확인0이면 서비스가 0을 돌려줌
  2. +0x71 바이트 확인0이면 R5를 그대로 둠
  3. +0x74 워드 읽기둘 다 0이 아니면 R5를 덮어씀

파서는 C:\SYSPARAM.TXT에서 STILL_SVD_GAIN 키를 비교한 뒤 두 필드를 씁니다. 생성자 출력과 파일을 읽은 뒤의 상태는 따로 보아야 합니다. 파서가 성공했다는 사실만으로 이 키가 파일에 있었다고 판단할 수도 없습니다. 파일 읽기, 토큰 변환, 서비스 성공은 실행하거나 가정하지 않았습니다. 구성 파일이나 카메라에도 아무것도 쓰지 않았습니다.

구성 서비스와 파서의 주소
  • 서비스 ID 분기 706B30에서 ID 0x42로 가면 706EA4에서 +0x71 바이트를 읽고 707120에서 반환합니다.
  • 키 비교 705A58 뒤 70671C로 들어가 70672C에서 +0x71, 706738에서 +0x74에 씁니다.
  • 토큰 변환은 10진수를 지정하지만 TLS와 오류 슬롯을 거치므로 실행하지 않았습니다.
  • 별도의 정적 초기화 가드(RAM VA 404099F0)는 객체 4045859C의 +4와 다른 위치입니다.
  • 구성 서비스 원본 30개 구간의 주소·해시는 upstream-ranges.json의 config_static에 있습니다.

0이 저장되면 마지막 나눗셈의 분모가 0이 됩니다

0을 넣은 조건에서 소비자 함수는 0 나눗셈 처리기(Thumb 코드)의 첫 명령 앞까지 갔고 결과 저장은 실행되지 않았습니다. 그 뒤의 동작은 확인하지 않았습니다.

같은 VM에서 원본 recipe·문맥 생성자와 산술·setter를 실행해 recipe+0x9C에 0을 쓴 뒤 원본 소비자 4DF834에 따로 진입했습니다. 소비자는 이 워드의 하위 16비트를 문맥 +0x60DC에 쓰고 최종 나눗셈의 분모로 썼습니다. 67108864를 0으로 나누는 호출은 Thumb 처리기 2E0486의 첫 명령 앞에 도달했습니다.

그 전에 네 보조 반워드는 저장되었습니다. 문맥 +0x7A74의 결과 저장은 실행되지 않았습니다. 처리기 첫 명령을 실행하지 않았으므로 예외 처리 방식이나 이후 복구는 알 수 없습니다.

주의

소비자 시험에 넣은 R5 = 0·1은 위 7개 조건에서 나온 R5와 이어 붙인 값이 아닙니다. 두 묶음은 따로 실행했습니다. 실제 촬영에서 이 분모가 0이 되는 일이 생기는지도 확인하지 않았습니다.

  • 네 보조 반워드: 4F98DC, 4F9954, 4F9948, 4F98D0이 문맥 +0x6010~+0x6016에 420·256·256·320을 씁니다. 719618은 +0x7A68에 16382(0x3FFE)를 씁니다.
  • 시험 배치: recipe = job+0xE0C4(0x1010E0C4), 문맥 = job+0xE608(0x1010E608). 기존값 유지 제어는 원본 setter 7198C4에 R1 = 1을 넣었습니다.
  • 분자·분모·LR과 원본 쓰기 순서 전체는 tone-upstream.json에 있습니다.

검증 방법

원본 명령은 실행 권한이 있는 메모리에서만 돌렸고 명령마다 바이트와 허용 구간을 검사했습니다.

  • 원본 명령을 읽기·실행(RX) 메모리에서 실행하며 매 명령의 바이트, 허용 구간 158개, 쓰기 대상을 검사합니다. 입력 전체 해시와 실행 후 RX 이미지가 그대로인지도 확인합니다.
  • 생성자의 대량 쓰기는 순서를 반영한 해시와 건수로, 나머지 쓰기와 나눗셈 인자는 하나씩 기록했습니다.
  • 0 소비자 시험은 65EF08..65F008, 65F0D8..65F150, 65F160..65F188 구간을 생략합니다. 분리 진입마다 LR을 하네스 반환점으로 다시 설정합니다.
  • 산술·수신자 계산·setter에서는 원본 프레임의 SP를 유지했습니다. 소비자에 따로 진입할 때는 SP를 하네스 기준값으로 다시 맞췄습니다.
  • 공개 JSON(328,341바이트)에는 상위 입력 7건과 0 소비자 4건을 모두 남겼습니다. 공개 정보를 붙이기 전에 원래 연구 기록 전체의 해시를 타입까지 구분해 확인합니다. 빠진 필드나 정수·불리언 교체는 거부합니다.
  • 정적 자료는 상위 입력 43개, 구성 서비스 30개 구간의 주소·길이·해시만 공개합니다. 원본 펌웨어 바이트나 역어셈블리는 포함하지 않습니다.
연구 코드와 공개 코드의 구분

관측 내부의 probe_sha256은 원래 연구 코드(기록 II31)의 해시입니다. 공개 보조 코드의 해시는 별도 public_source_sha256에 적었습니다. 두 코드를 같은 파일로 표시하지 않습니다. 실행 부분의 생성자·setter·가상 호출·소비자는 원래 연구 코드와 구문 트리(AST)가 같습니다.

한계와 남은 과제

  • 값의 출처: 관리자가 고르는 버퍼의 실제 값과 갱신자, owner+0x21C 작업의 호출 순서는 정해지지 않았습니다.
  • 구성 파일: 파일의 실제 내용과 로드 성공, 토큰 변환과 TLS는 실행하지 않았습니다.
  • 0 처리기: 처리기 본문, 반환값, 카메라에서의 결과는 미확인입니다.
  • 촬영 연결: R5 입력이 실제 촬영에서 도달하는지는 모릅니다. owner+0x220·보조 스케일러 경로와의 실행 이력, 버퍼 재사용, SuperResolution 메뉴 도달도 이 재현으로 정하지 못합니다.
  • 값의 뜻: 물리 단위, Q 형식, 감마, 실제 촬영 기본값은 정하지 않았습니다.

메뉴와 버퍼 수명은 메뉴·버퍼 수명 분석, 정수 생산자의 시험 범위는 이전 정수 생산자 분석을 따릅니다. 관리자 레코드를 고쳐 쓰는 코드는 톤 설정 관리자의 두 호출점과 내부 버퍼 기록 순서에서 이어집니다.

재현 방법

검증 환경은 Python 3.12.3과 Unicorn 2.1.4입니다. 저장소 루트에서 따로 준비한 복호화 파일을 지정하고 출력에는 새 경로를 씁니다. 출력의 부모 폴더는 미리 있어야 합니다. 아래 입력 경로는 예시입니다.

python -B verify_tone_upstream.py /path/to/decoded.bin --output tone-upstream-new.json \
  --compare analysis/tone-upstream.json
python -B -O verify_tone_upstream.py /path/to/decoded.bin --output tone-upstream-opt-new.json \
  --compare analysis/tone-upstream.json
python -B -m unittest discover -s tests -p test_tone_upstream.py
  • 후보 파일이 다른 폴더에 있을 때만 --repository로 기존 검증기와 보조 소스가 있는 저장소를 지정합니다. 통합한 공개 배치에서는 생략합니다.
  • 출력은 새 경로에만 만듭니다. 기존 파일·하드링크·심볼릭 링크를 덮어쓰지 않으며 비교가 실패하면 출력 파일을 만들지 않습니다.
  • 비교 입력은 일반 파일만 받고 결과 크기의 네 배까지만 읽습니다. 타입을 구분하는 비교는 그대로 유지합니다.
