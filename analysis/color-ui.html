메뉴와 UI · 색공간 메뉴의 선택과 기록

색공간 메뉴에서 고른 값이 설정에 기록되기까지

메뉴에서 sRGB나 AdobeRGB를 고르고 확정할 때 카메라 안에서 어떤 값이 언제 바뀌는지 추적했습니다. 메뉴를 고치거나 다른 기종과 비교하려면 이 순서를 먼저 알아야 합니다.

이 문서에서

  1. 배경: 색공간 메뉴와 이 문서의 용어
  2. 상위 메뉴 항목이 색공간 화면을 요청합니다
  3. 고르기, 확정, 취소에 따라 바뀌는 값이 다릅니다
  4. RAM에 기록하는 단계와 플래시에 저장하는 단계는 따로 있습니다
  5. 글자와 선택 표시는 그리기 전 단계까지 실행했습니다
  6. 한계와 남은 과제
  7. 재현 방법
  8. 근거 파일과 참고 자료

핵심 요약

  • Color Space 메뉴의 두 선택지는 설정값 하나로 저장됩니다. sRGB는 0, AdobeRGB는 1입니다.
  • 항목을 고르는 것만으로는 설정이 바뀌지 않습니다. 화면 객체 안의 임시값만 바뀝니다. 확정 동작을 받아야 RAM의 설정 두 곳(현재값과 미러)에 1바이트씩 기록하고, 취소하면 아무것도 기록하지 않습니다.
  • 이미 저장된 값과 같은 값을 확정해도 두 곳에 다시 기록합니다. 플래시 섹터로 내보내는 저장 함수는 따로 있고, 그 함수는 내용이 같으면 쓰기 요청을 생략합니다.
  • 화면의 글자 5개와 선택 그림 2개가 준비되는 과정도 실행했습니다. 실행은 화면에 그리기 전에서 멈췄습니다.
  • 모든 결과는 PC 에뮬레이터에서 원본 코드에 동작 번호를 직접 넣어 얻었습니다. 실제 버튼, LCD 표시, 플래시 기록은 확인하지 않았습니다.

확인 원본 코드 실행으로 확인

  • 선택·확정·취소·다시 열기 8개 사례의 임시값과 RAM 쓰기 횟수
  • 상위 메뉴 항목이 색공간 화면을 요청하는 알림
  • 등록부가 색공간 화면 객체를 만들어 등록하는 구간
  • 글자 5개의 글리프 배열, 선택 그림 2개의 그림 번호

모델 시험 조건으로 정한 것

  • 버튼 대신 동작 번호를 함수에 직접 전달
  • 활성 인덱스와 뱅크 내용은 시험용 값
  • 메모리 할당, 기본 화면 생성, 위젯 검색, 알림 수신자는 검증용 대체 코드

미확인 확인하지 않은 것

  • 물리 버튼이 동작 번호로 바뀌는 경로
  • LCD에 실제로 그려지는 모양
  • 플래시 기록, 재부팅 뒤 값 유지
  • 다른 기종에서의 동작

배경: 색공간 메뉴와 이 문서의 용어

K-3 II 사용 설명서에서 Color Space는 사용자 설정 메뉴 C3의 20번 항목입니다. 선택지는 sRGB와 AdobeRGB이고 기본값은 sRGB입니다. AdobeRGB로 찍은 사진은 파일 이름이 _IMG로 시작합니다(K-3 II 사용 설명서 26·84쪽).

설명서는 메뉴 조작을 이렇게 안내합니다. 십자 버튼으로 항목을 고르고, OK 버튼으로 확정하고, MENU 버튼으로 이전 화면에 돌아갑니다(9·19쪽). 펌웨어 안에서는 이 조작이 작은 번호로 바뀌어 화면 객체에 전달됩니다. 이 문서는 그 번호를 받은 뒤의 처리를 다룹니다. 어느 버튼이 어느 번호가 되는지는 확인하지 못했습니다.

위젯
화면을 이루는 부품 하나(제목, 선택 항목, 도움말)에 붙은 32비트 번호입니다.
논리 동작
화면 객체에 전달되는 작은 번호입니다. 이 문서에는 3, 6, 0x11, 0x1D가 나옵니다. 버튼 이름이 아닙니다.
임시값
화면 객체가 들고 있는 “지금 고른 값”입니다. 확정하기 전에는 설정과 별개입니다.
현재값과 미러
설정이 들어 있는 RAM의 두 위치입니다. 현재값은 설정 객체 안에 있는 사본이고, 미러는 설정 객체가 가리키는 별도 RAM 블록입니다. 미러가 플래시 섹터와 주고받는 버퍼라는 점은 보존 섹터의 설정 저장에서 다룹니다.
뱅크
같은 설정 번호의 값을 여러 벌 담는 구획입니다. 0~7의 “활성 인덱스”가 어느 뱅크를 쓸지 정합니다. 활성 인덱스가 카메라의 어떤 상태에 대응하는지는 확인하지 않았습니다.
주소 표기
코드와 표의 위치는 복호화한 펌웨어 파일의 오프셋입니다(펌웨어 파일 구조와 복호화). screen+0xE7처럼 쓴 것은 객체 안의 필드 위치입니다.

선택을 받는 위젯(선택 그림)과 글자를 보여 주는 위젯은 번호가 다릅니다. 예를 들어 sRGB는 선택 그림이 0x0191300A, 글자가 0x0191300C입니다.

상위 메뉴 항목이 색공간 화면을 요청합니다

상위 메뉴의 색공간 항목에 동작 0x1D를 주면 화면 0xB4를 열라는 알림이 나옵니다. 화면 객체를 만들어 등록하는 구간은 따로 실행해 확인했습니다.

첫 구간에서는 상위 화면 객체에 동작 0x1D를 전달했습니다. 처리기는 메뉴 분류 13의 경로 표에서 인덱스 6의 값을 읽어, 화면 0xB4를 요청하는 알림을 보냈습니다. 알림을 받는 쪽은 검증용 코드로 대신하고 전달된 값만 기록했습니다.

둘째 구간에서는 화면 등록부에 화면 ID 0xB4를 주고 실행했습니다. 등록부는 색공간 화면 생성자를 불러 객체를 만들고, 등록부의 +0x2D0(4×0xB4) 위치에 넣었습니다. 생성자는 임시값을 0으로 초기화합니다. 이 실행에서 메모리 할당 함수와 기본 화면 생성 함수는 검증용 코드로 대신했습니다.

두 구간 사이, 즉 알림을 받아 등록부를 부르기까지의 과정은 색공간 메뉴 알림과 화면 전환에서 이었습니다.

고르기, 확정, 취소에 따라 바뀌는 값이 다릅니다

항목을 고르면 화면 객체의 임시값만 바뀝니다. 확정하면 RAM 설정 두 곳에 기록하고, 취소하면 기록하지 않습니다. 화면을 다시 열면 임시값은 저장된 값으로 돌아갑니다.

취소한 뒤에도 임시값에는 고른 값이 남아 있습니다. 다만 화면을 다시 열면 열기 함수가 저장값을 읽어 임시값을 덮어쓰므로, 취소했던 선택은 사라집니다. 저장값을 선택 위젯 번호로 바꿔 주는 조회 함수도 임시값이 아니라 저장값을 따랐습니다.

표에서 읽을 수 있는 점은 네 가지입니다.

  • 확정은 값을 비교하지 않습니다. 기존 값과 같은 값을 확정하거나 아무것도 고르지 않고 확정해도, 현재값과 미러에 각각 한 번씩 기록했습니다.
  • 취소는 RAM에 쓰지 않습니다. 열기, 고르기, 항목 떠나기, 취소, 다시 열기에서는 설정 영역 쓰기가 한 번도 없었습니다. 쓰기는 메모리 쓰기 훅으로 주소·크기·값을 직접 관찰했습니다.
  • 알림 값만으로 저장 여부를 알 수 없습니다. 확정(동작 6)은 0xC2를, 취소(동작 3)는 0xC1을 보냅니다. 그런데 설정을 기록하는 동작 0x11도 0xC1을 보냈습니다. 두 값이 무엇을 가리키는지는 확인하지 않았습니다.
  • 활성 인덱스 0과 1은 뱅크 0을 함께 씁니다. 활성 인덱스 0~7에 대응하는 뱅크는 0, 0, 2, 3, 4, 5, 6, 7입니다. 기록할 때 다른 뱅크의 바이트는 바뀌지 않았습니다.

RAM에 기록하는 단계와 플래시에 저장하는 단계는 따로 있습니다

이 메뉴는 같은 값이어도 RAM에 다시 씁니다. 플래시 섹터 쓰기를 요청하는 저장 함수는 별도이고, 그 함수는 내용이 같으면 요청을 생략합니다.

  1. 확정 동작RAM 현재값과 미러에 1바이트씩 기록. 같은 값이어도 기록
  2. 저장 함수 호출메뉴 확정 뒤 언제 불리는지 미확인
  3. 섹터 내용 비교준비한 내용이 기존 섹터와 같으면 쓰기 요청 없음
  4. 플래시 기록실제 기록과 재부팅 뒤 유지는 미확인

셋째 단계는 보존 섹터의 설정 저장에서 따로 실행한 결과입니다. 그 검증에서 sRGB를 다시 쓰면 RAM에는 두 번 기록했지만 섹터 쓰기 요청은 0건이었습니다. AdobeRGB로 바꾸면 반대쪽 섹터에 쓰기 요청이 1건 생겼습니다.

주의

“같은 값이면 쓰지 않는다”는 말은 저장 함수에만 해당합니다. 메뉴의 확정 동작에는 해당하지 않습니다. 두 결과는 서로 다른 실행에서 얻었고, 메뉴 확정에서 저장 함수까지 한 번에 이어 실행한 적은 없습니다.

글자와 선택 표시는 그리기 전 단계까지 실행했습니다

화면의 글자와 선택 그림은 리소스 표에서 객체로 만들어집니다. 항목을 고르거나 떠나면 객체 안의 상태 값이 바뀝니다. 그 값이 화면에서 어떤 모양이 되는지는 확인하지 않았습니다.

  1. 리소스 조회위젯 번호로 표 0x9A2BE4의 20바이트 레코드를 찾음
  2. 객체 준비글자 5개는 글리프 배열과 길이, 그림 2개는 그림 번호
  3. 고르기·떠나기객체의 상태 바이트와 16비트 값 두 개가 바뀜
  4. 화면에 그리기글꼴·그림 합성과 LCD 출력은 실행하지 않음

글자 리소스는 언어마다 하나씩 포인터를 가진 “언어 표”를 가리킵니다. 영어 글자는 글리프 코드가 1바이트씩 저장되어 있고, 코드에 0x1E를 더하면 ASCII 문자가 됩니다. 이렇게 읽은 영어 문구는 Color Space, sRGB, AdobeRGB, Sets color space to sRGB, Sets color space to AdobeRGB입니다. 준비 함수는 이 코드를 16비트 배열로 펼치고 끝 표시(0)를 포함한 길이를 돌려줍니다.

고르거나 떠날 때 바뀌는 값

선택 그림과 글자는 같은 함수로 선택 상태를 받습니다. 한 항목을 고르면 그 항목의 선택 그림과 글자 두 객체에서 값이 아래처럼 바뀌었습니다.

100과 150은 관찰한 숫자일 뿐입니다. 확대율인지, 색이나 모양에 관한 값인지는 LCD 출력을 확인하지 않아 이름을 붙이지 않았습니다. 도움말도 고른 항목의 값이 1이 된다는 것까지만 확인했습니다. 나머지 도움말이 반드시 숨겨진다고 단정하지 않습니다.

  • 리소스 레코드는 20바이트이고 내용은 위젯 번호, 종류, 언어 표 주소(그림은 그림 번호), 3, 0 순서입니다.
  • 선택 그림(type 2)과 글자(type 4) 래퍼는 가상 슬롯 +0x48 → 0x707A54 → 0x70ACB8을 함께 씁니다.
  • 도움말(type 3) 래퍼는 슬롯 +0xC → 0x70AA6C가 객체 +0xC를 설정합니다. 검증기는 고르는 순간 위젯 0x01913001의 같은 필드가 1에서 0으로 바뀌는 것도 확인합니다. 이 위젯의 역할은 확정하지 않았습니다.
  • 글자 객체에는 언어 표 주소(+0x90)와 16비트 스타일 값 4(+0x84)가 들어갑니다. 그림 객체에는 그림 번호(+0x60)가 들어갑니다.
  • 글리프 준비 함수는 0x873964입니다. 실행은 래스터화를 시작하기 전에 멈췄습니다.
  • 고를 때와 떠날 때 화면은 최상위 선택 목록 서비스 0x708774를 한 번씩 부릅니다. 이 서비스는 검증용 코드로 대신했습니다.
  • 글리프 원본과 준비된 배열의 SHA-256은 color-ui.json의 resources와 text_cases에 있습니다. 원본 글리프와 그림 데이터는 공개하지 않습니다.

한계와 남은 과제

이 문서의 결과는 화면 객체에 동작 번호를 직접 넣었을 때의 동작입니다. 카메라에서 버튼을 눌러 확인한 것이 아닙니다.

  • 버튼 입력 — 어느 버튼이 동작 3, 6, 0x11, 0x1D가 되는지 모릅니다. 설명서의 OK·MENU 버튼과 이 번호들을 연결하지 않았습니다.
  • 알림 이후 — 상위 메뉴의 알림을 받아 화면을 여는 과정은 색공간 메뉴 알림과 화면 전환에서 화면 할당 요청까지 이었습니다. 화면 생성부터 표시까지 한 번에 이어 실행한 적은 없습니다.
  • 표시 — 글리프 배열과 객체 상태까지만 확인했습니다. 글꼴 그리기, 그림 합성, LCD 출력은 실행하지 않았습니다.
  • 저장 — RAM의 현재값과 미러까지만 관찰했습니다. 플래시 기록과 재부팅 뒤 유지는 확인하지 않았습니다.
  • 다른 기종 — 위젯 번호, 동작 번호, 객체 필드 위치는 K-3 II 펌웨어 1.12의 내부 값입니다. 다른 기종에 그대로 적용할 근거가 없습니다. 기종 사이에 공통으로 삼을 수 있는 것은 “색공간을 고른다”는 기능입니다. 세 기종 비교는 K-3 III 저장소의 UI 이식 설계에 있습니다.
