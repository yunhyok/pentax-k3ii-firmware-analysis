sRGB·AdobeRGB 메뉴를
입력 이벤트부터 RAM 기록까지 추적했다

Color Space 메뉴의 설정 번호는 0x15C이며 sRGB는 0, AdobeRGB는 1이다. 선택은 임시값만 바꾸고, 확정은 같은 값을 다시 고른 경우에도 현재값과 미러에 각각 1바이트를 기록한다. 취소는 기록하지 않으며, 다시 열면 저장값을 읽는다.

화면 연결상태·기록텍스트·선택 표시재현·한계설정 섹터 저장연구 상태

주소는 해제 파일 오프셋이다. screen+…는 객체 필드이며 이벤트·위젯 번호는 K-3 II 내부 값이다. 논리 이벤트 재생을 물리 버튼 시험으로 표현하지 않았다. 아래의 ‘저장값’은 별도 표기가 없으면 RAM 값이다.

1. 상위 메뉴가 상세 화면 0xB4를 요청한다

상위 위젯 0x0140B043에 논리 동작 0x1D를 전달하면 원본 0x4A5888 계열이 그룹 13·행 인덱스 6을 조회하고 상세 화면 0xB4를 알린다. 별도 실행한 등록부 0x6D8F3C → 0x6D9220 → 0x6D9E7C는 0x4377A0을 통해 화면 객체를 만들고 등록 슬롯 +0x2D0에 넣었다. 두 실행 사이의 알림 소비자와 물리 입력 변환은 아직 연결하지 않았다. parent_route·screen 근거

선택 이벤트 ID와 표시 글자 ID는 서로 다르다. 원본 0x9A2BE4 표와 각 객체의 가상 함수 표를 함께 대조했다. 기종 간 공통 대상으로 삼은 것은 색 공간의 기능이며, 이 숫자나 메모리 배치를 다른 모델에 그대로 적용할 근거는 없다. 리소스·가상 슬롯 검증

2. 취소 후의 임시값과 다시 열었을 때의 값이 다르다

상태 전이 8건을 실행했다. 양방향 변경·취소, 양쪽 값의 동일값 확정, 선택 없이 확정, 동작 0x11의 적용을 포함한다. 확정 사례마다 실제 메모리 쓰기 훅으로 현재 뱅크와 미러의 1바이트 기록을 각각 한 번 관찰했다. 열기·선택·이탈·취소·재열기에는 해당 설정 영역의 쓰기가 없었다. lifecycle_cases

설정의 활성 인덱스 0과 1은 저장 뱅크 0을 공유한다. 전체 매핑은 [0, 0, 2, 3, 4, 5, 6, 7]이며 바이트 위치는 뱅크 기준 0x588 + 0x15C다. 이 메뉴는 같은 값일 때 쓰기를 생략하지 않는다. 다만 별도 섹터 저장 함수에서는 준비된 내용이 기존 섹터와 같으면 쓰기 요청을 생략했다. 서로 다른 단계의 결과다.

3. 선택 표시의 객체 필드까지 실행했다

선택 그림과 글자 래퍼는 가상 슬롯 +0x48 → 0x707A54 → 0x70ACB8을 공유한다. 실제 선택·이탈 실행에서 상태 바이트와 하위 객체의 두 16비트 값이 바뀌었다. 도움말은 슬롯 +0xC → 0x70AA6C가 해당 객체 +0xC를 설정했다. 이 관찰만으로 나머지 도움말이 반드시 숨겨진다고 단정하지 않았다. focus·text_cases
