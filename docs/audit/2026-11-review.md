# 2026년 11월 문서 검수 기록 — K-3 II

v0.2.0에서 HTML 문서를 다시 쓰면서 페이지마다 내용을 검수했습니다. 이 문서는 그 결과입니다. 무엇을 어떻게 확인했는지, 무엇을 고쳤는지, 저장소 주인의 판단이 필요한 것은 무엇인지 적었습니다.

## 검수 방법과 한계

- 개편 전 HTML의 수치·주소·해시·사례 수를 그 페이지가 근거로 삼는 JSON(`analysis/*.json`)과 검증 스크립트(`verify_*.py`)의 상수에 대조했습니다. 합계와 계산 예는 다시 계산했습니다.
- 같은 값이 여러 문서에 나오는 경우 문서끼리도 맞는지 봤습니다.
- 사용설명서의 메뉴 이름, 규격의 명령 번호, 외부 소스의 행 번호, 소프트웨어 버전 같은 외부 사실은 1차 자료로 확인했습니다.
- 개편 전 문서에 있던 16진수·해시·큰 수·식별자가 새 문서에 남아 있는지 도구로 비교했습니다. 빠진 것은 이유를 확인했습니다.
- **하지 못한 것**: 이 작업 환경에는 원본 펌웨어가 없습니다. 그래서 검증 스크립트를 원본 펌웨어에 다시 돌리지 못했습니다. "근거 JSON과 일치한다"는 말은 공개된 JSON·스크립트와 맞는다는 뜻이며, 펌웨어 바이트를 다시 확인했다는 뜻이 아닙니다. 펌웨어 없이 도는 검사(`verify_publication.py`, 단위 시험 24개)는 통과했습니다.

수치·주소·사례 수는 대부분 근거와 맞았습니다. 고친 것은 주로 외부 자료 인용, 빠진 단계, 뒤 문서가 이미 해결한 "미확인" 서술입니다.

## 판단이 필요한 항목

근거가 부족해 고치지 않았거나, 이번에 새로 넣은 해석이라 빼도 되는 것들입니다.

**주소·값이 개편 전 HTML에만 있고 근거 JSON·검증기에는 없는 것** (본문에 "정적 분석"으로 표시)

- `settings-storage.html`: "키 0x38".
- `preserved-dispatch.html`: 건너뛴 구간의 주소 `0x6EB310`, `0x6EB44C→0x50F550`, `0x6EB620`, `0x6EB60C→0x520500`, `0x63495C`.
- `preserved-sector20.html`: 함수 시작 `0x6E8C08`/`0x6E8D7C`. 검증기의 실행 시작은 `0x6E8C24`/`0x6E8D98`입니다.
- `capture-prepare.html`: getter 주소 `0x73E760`/`0x73EF20`. 검증기가 확인한 호출은 `0x65EF88→0x72D894`, `0x65E7F4→0x73EA94`입니다.
- `ui-dispatch.html`: 주소 `0x309E18`. `backend-b-cpp-analysis.html`: 슬롯 17 경로 `0x65473C`.
- `installation.html`: "`0x55591C`가 오류 4와 단계 1을 저장한다". 실행으로 확인한 것은 반환값 `0x10004`뿐입니다.
- `preserved-config.html`: "`+0xD` 소비자가 마커를 다시 확인한다"는 워드 비교만 있습니다. 실행 근거는 `+0xC`에만 있습니다.

**해석의 수위**

- `backend-b-cpp-analysis.html`: Normal DevMode `0x7B5600`을 "확인"으로 표시했지만, 그 모드에 도달한다는 근거는 워드 비교뿐입니다. "입력 종류 0·1·2에서 억제가 켜진다"는 0과 3만 실행했습니다. "Normal 분기가 8을 넘긴다 = 레시피 0x08"은 대칭으로 추정한 것입니다.
- `masked-cpp-analysis.html`: "태그 0x98 ≠ 0 → 작업 네 개 = Pixel Shift RAW 현상 경로"는 해석입니다. "모듈 20의 입력 네 개 = Pixel Shift 네 장"도 같습니다.
- `ui-resources.html`: 뱅크 간격 `0x418×8 + 0x588 = 0x2648`이 `settings-storage.html`이 말하는 주 설정 블록 길이 `0x23B4`보다 깁니다. "같은 크기의 뱅크 8개"로 일반화하지 않았습니다.
- `color-ui.html`: 알림 값 `0xC1`/`0xC2`의 의미, 경로 표의 `0xB4`가 사용설명서 C3의 20번 항목이라는 대응은 추정입니다.
- `firmware-structure.html`: 0x20000 위치에 "별도의 모델·버전 헤더"가 있다는 서술은 검증기가 식별 문자열만 확인합니다. 인터럽트 벡터 16개 가운데 제조사 문서의 표에 있는 것은 12개입니다. "Fujitsu M7 손떨림 보정 라이브러리"의 근거는 문자열 `M7 for Fujitsu`뿐입니다.
- `rebuild.html`: "ITCM"이라는 용어. 근거는 시작 코드가 주소 0번지 근처로 코드를 복사한다는 것뿐이어서 "주소 0번지 근처로 복사되는 코드(원문 표기 ITCM)"로 적었습니다.
- "CPP"의 원말, "UDC"의 뜻은 모릅니다. "스케일러", "마스크"는 역할로 붙인 이름입니다.
- 추적한 처리 경로가 촬영 직후의 것인지 재생 화면의 RAW 현상인지는 원 자료에 적혀 있지 않습니다.
- 사용설명서 쪽 번호(76쪽 또는 77쪽)가 문서 사이에 다릅니다.

**이번 개편에서 새로 넣은 비교·해석** (모두 "확정한 것이 아님"이라고 한정했습니다. 원 연구 범위만 남기려면 해당 참고 상자를 지우면 됩니다.)

- `storage-dma-analysis.html`: 백엔드 경계값 34,493,956,096바이트(32.125GiB)와 SDHC/SDXC 경계의 관계.
- `settings-storage.html`: 두 섹터를 번갈아 쓰는 방식과 U-Boot의 이중 환경 저장 방식의 비교.
- `af-drive.html`: ExifTool의 렌즈 ID 241/242가 DA★ 50-135·16-50 SDM이라는 참고.
- `firmware-structure.html`: `0xC0001FFC`가 통신 슬롯과 같은 대역에 있다는 것, 계수 77·150·29가 BT.601 × 256에 가깝다는 것.
- `preserved-sector20.html`: 작업 계획의 인덱스(0–17, 24, 25)가 두 확인 묶음과 같다는 관찰. 검증기의 `CAPACITY`에서 만든 디스크립터 용량 표(인덱스 18–23은 확인된 적이 없어 뺐습니다).

**그 밖에**

- 리코의 펌웨어 사용 조건에는 수정·리버스 엔지니어링을 제한하는 조항이 있습니다. 공개 범위에 대한 판단은 저장소 주인의 몫입니다.
- 메뉴의 "Pixel Mapping"이 섹터 15–19의 레코드를 만드는지는 근거가 없습니다. 문서에 그렇게 적었습니다.

## 외부 자료로 확인한 사실 (요약)

- 펌웨어 1.12는 2021-07-20 배포, `k3ll_v112.zip`. 변경 내용은 HD PENTAX-DA★16-50mm F2.8ED PLM AW의 초점 성능 최적화 (리코 다운로드 페이지).
- PRIME III(645Z와 같은 엔진), SAFOX 11(27점), KAF2 마운트, SD 슬롯 두 개 (리코 제품 자료).
- 사용설명서: 커스텀 설정 C3의 "20. Color Space"(sRGB/AdobeRGB), Custom Image 11개 모드, Pixel Shift Resolution이 한 픽셀씩 옮긴 네 장을 합친다는 설명, RAW 현상의 Color Fringe Correction, Pixel Mapping 메뉴.
- Cortex-A9 TRM의 MIDR 값 `0xC09`. F²MC-8L의 벡터와 명령 코드(Fujitsu CM25-10142-3E).
- SD 명령 번호, CSD 용량식, SDHCI 레지스터와 ADMA2 설명자(Linux 커널 소스). SD Association 규격 PDF는 열지 못해 Linux 구현으로 대신 확인했습니다.
- NOR 플래시의 명령 순서(Infineon S29GL-N 데이터시트, U-Boot `cfi_flash.h`). 카메라에 실제로 들어간 부품이 이것이라고 주장하지는 않습니다.
- ExifTool의 ImageTone 값, PixelShiftInfo(0x0243), 렌즈 ID 표.
- XOR 복호기의 출처 소스와 SHA-256이 `decoder-comparison.json`과 일치. GPL-2.0.
- Zig 0.17.1(2026-11-02), Unicorn 2.1.4가 실제로 있는 버전임. AAPCS32의 레지스터 규칙.
